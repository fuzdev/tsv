# tsv_svelte

> Svelte component parser + formatter — drop-in replacement for Svelte's compiler frontend, with a near-Prettier formatter tracking Prettier's `svelte` plugin.

## Architecture Position

Depends on:

- [`tsv_lang`](../tsv_lang/CLAUDE.md) — `Span`, `ParseError`, doc builder, `EmbedContext` / `LayoutMode`
- `tsv_ts` — embedded TypeScript: `<script>` bodies and template `{expr}` slots
- `tsv_css` — embedded CSS: `<style>` blocks
- `tsv_html` — element classification (block / inline / void), whitespace rules

Sources of truth: Svelte's compiler for AST shape, Prettier (`svelte` plugin) for formatting. Scope is `.svelte` files only — `.svelte.ts` rune modules are pure TypeScript and go through `tsv_ts` (this crate does not handle them).

See [../../CLAUDE.md §Project Structure](../../CLAUDE.md#project-structure) for the standard crate layout (`ast/` / `lexer/` / `parser/` / `printer/`) and project-wide conventions.

## Public API

`src/lib.rs` exports free functions matching the tsv pattern:

- `parse(source, arena: &'arena Bump) -> Result<Root<'arena>>` — internal AST, bump-arena-allocated (caller owns the `Bump`). The Svelte parser creates the one arena per document and shares it with every embedded sub-AST — `tsv_ts` (`<script>` / `{expr}`) and `tsv_css` (`<style>`) — so the whole component is one bump-allocated graph. See [docs/architecture.md §Nested AST](../../docs/architecture.md#nested-ast-bump-arena-not-flatindexed).
- `format(&Root, source) -> String` — round-trips through the doc builder; `format_in(&Root, source, &DocArena)` is the same into a caller-provided doc arena (multi-file drivers reuse one via `DocArena::reset()`; embedded `<style>` shares this host arena via `tsv_css::format_embedded_in`, not a second per-block one — the CSS still renders to its own string, only doc-node storage is shared); `format_folded_in(&Root, &FoldedSource, &DocArena)` is `format_in` for a caller that folded the source itself — identical output, the document's line verdict taken from the fold's pass (what the CLI, the bindings and `format_str` call)
- `format_str(source) -> Result<String>` — parse + `format` fused (applies the format path's `<CR>` fold ahead of the parse and formats through `format_folded_in`), the same twin every language crate has
- `convert_ast_json_bytes(...) -> Vec<u8>`, `convert_ast_json_string(...) -> String`, and `convert_ast_json(...) -> serde_json::Value` — the public JSON AST (gated on `feature = "convert"`). The bytes variant is the **sole emission path** (FFI/CLI non-pretty; the string variant adds one output UTF-8 validation for `&str` boundaries — WASM `JSON.parse`, N-API): the writer (`ast/convert/write.rs`) walks the *internal* Svelte AST once and emits the wire JSON directly, never materializing a typed public tree, fusing byte→UTF-16 offset translation into the walk (per-language pipeline shapes: [docs/architecture.md §Closed Scope, Open Convention](../../docs/architecture.md#closed-scope-open-convention)). The Svelte spine (elements, blocks, tags, directives, attributes, `name_loc`) emits fused; embedded `<script>`/`{expr}` route through `tsv_ts`'s embedded writers and `<style>` children through `tsv_css`'s `write_css_children`, which hands back the `StyleSheet`'s sibling `comments` run — `parseCss`'s flat `CSSComment[]`, rebuilt from the three places tsv keeps CSS comments by the very walk that emitted the children (see [`tsv_css/CLAUDE.md`](../tsv_css/CLAUDE.md)) — for `write_css_comments` to emit into the next key. Template-expression comments (and `<script>` comments) fuse via an island-scoped attach that runs **online**, driven by this same emit: acorn assigns a node's leading comments at node *entry* and its trailing ones after its children have been walked, which are exactly the writer's `node_header` and `close_node`, and the wire emits both lists at the close. So `tsv_ts`'s `CommentAttach` runs off those two events — no second pass, no recorded tree, no per-node map — and `leadingComments`/`trailingComments` serialize in place. Each island declares only its comment WINDOW plus what acorn's walk reads about a *root*'s surroundings (`ast/convert/comment_attachment.rs`'s `attach_*`, over its own window helpers); everything else the walk needs — child visit order, `parent.end`, and which element is last in a container's body — the emit itself supplies. ⭐ Child visit order is therefore acorn's *by construction*: it IS the emitted field order, so a walk that orders a node's children differently from the wire is unrepresentable — a class a hand-maintained visit order has to get right per shape, the generic-async arrow being the subtle one ([`typescript/expressions/arrow/async_generic/params_comment_return_type`](../../tests/fixtures/typescript/expressions/arrow/async_generic/params_comment_return_type/)). `convert_ast_json` is a thin wrapper (`serde_json::from_slice(&convert_ast_json_bytes(...))`) for the `Value` consumers (the CLI's `--pretty`, the fixture gate); not an independent conversion. Gated against the canonical Svelte parser's `expected.json`, including the multibyte and template-comment fixtures that exercise the fused offset translation and island-scoped attach.
- `convert_ast_json_bytes_no_locations(...)` / `convert_ast_json_string_no_locations(...)` — the opt-in **span-only** variant: drops *every* line/column object from the Svelte wire — the acorn `loc` on `<script>`/`{expr}` nodes (via `emit_loc` threaded into the embedded `tsv_ts` writers), the root-comment `loc`, **and the element/attribute/directive `name_loc`**. Only `start`/`end` offsets remain; because that removes all line/column emission, the LF line table is never queried. `name_loc` stays derivable from a node's own `start`/`end` + type: an element names the tag run at `start + 1`, an attribute names `[start, start + name.len]` (a shorthand `{x}` names the identifier inside its braces, so a padded `{ x }` excludes the padding), and a directive its whole head token — the run from `start` to the first name terminator (`on:click|preventDefault`, not just `click`). The shipped `reconstruct_locations` helper (`crates/tsv_wasm/npm/locations.js`) restores it on that basis; `benches/js/diagnostics/no_locations_parity.ts` gates the derivation against the loc-bearing wire. Mirrors acorn's `locations: false`; a distinct narrower product, not a change to the drop-in wire (which is byte-identical). Invariant: `../../tests/no_locations.rs`.

## Distinctives

What separates this crate from `tsv_ts` / `tsv_css`:

- **Embeds two other languages.** The printer delegates `<script>` and every template `{expr}` to `tsv_ts` doc builders (e.g. `tsv_ts::build_program_doc`) and `<style>` to `tsv_css::format_embedded_in` (sharing the host doc arena — the CSS renders to its own string but builds into the host's `DocArena`, not a fresh per-block one), passing an `EmbedContext` with the current indent state and `LayoutMode::Embedded` so a root binary expression uses continuation indent (nested expressions format as in `<script>`). See `printer/script_style.rs` and `printer/nodes/tags_doc.rs`.
- **Element classification.** Every name-derived fact is packed into a `TagFacts` bitfield (`ast/internal.rs`, beside `is_component_name`) computed **once at parse** — where the raw tag `&str` is already in hand — and stored on `Element::facts` (it rides in the tail padding beside `kind`, so it costs no extra `Element` size). The element/fragment/sibling paths re-ask the same tag-name questions many times per element, so this turns each print-time read into a single field load and makes classification a reusable AST property (linter/type-checker/LSP get it free). `printer/classification/element.rs` holds only the printer-specific element-**instance** overlay on top of the facts (a Component is inline; a non-empty `<script>`/`<style>` is block via `has_raw_content`), and `printer/nodes/element_doc.rs`'s `classify_tag` unpacks `Element::facts` into the per-tag `TagClass`. The pure per-name predicates live in `tsv_html`. The exhaustive equivalence test beside `TagFacts` grades each accessor against the pure predicate it encodes — keep it green; a mispacked bit changes layout only on rare tags at rare widths, which no fixture or corpus diff can be relied on to see.
- **One element pipeline for two AST types.** `internal::Element` and `internal::SpecialElement` are distinct types that print the same shape (a name, attributes, a fragment, an open/close tag pair), so both project onto **`ElementParts`** (`printer/nodes/element_doc.rs`) and run one `analyze_element` → `compute_element_layout` → `build_content_element_doc` pipeline. They diverge only *before* it — in how the name doc and the attribute docs are built (`svelte:*` synthesizes a `this={…}` attribute) — and the tag-name-keyed questions are answered once per element by `classify_tag` → `TagClass`. This is load-bearing, not tidiness: a `special_doc.rs` carrying its own hug predicates and its own `needs_multiline` drifts from the element path (a `<slot>` that never goes multiline for block children, or that dangles its delimiters where a regular element is block-style) — pinned by [`svelte/special/slot/block_children_prettier_divergence`](../../tests/fixtures/svelte/special/slot/block_children_prettier_divergence/), which sits a `<span>` beside the `<slot>` in the same shape so the parity is the assertion. The one layout decision the special path still makes alone, `build_special_empty_doc`'s three-state group, is the remaining drift surface: an attribute that breaks (a line comment in `this={…}`) routes through the shared `build_opening_tag`, so a `svelte:*` element expands for it exactly as a regular `<div class={// c⏎foo}>` does, and the rest is a fixtures-first pass away (the hug state is pinned). Layout carries **one** `BoundaryMode` for both tags (`ElementLayout::WithContent(BoundaryMode)`) so a render-free boundary character cannot dangle one delimiter without the other — see [conformance_prettier_svelte.md §Svelte: Inline content block-style](../../docs/conformance_prettier_svelte.md#svelte-inline-content-block-style). The deliberate exception: `<pre>`/`<textarea>` are dispatched to `element_ws_sensitive_doc.rs` **before** any of this (there boundary whitespace is literal and the dangle is mandatory), and that builder keeps its own block/inline probe on purpose — inside a whitespace-preserving subtree a nested component counts as inline flow, which `ElementKind` does not model.
- **No `escapes/` module.** String/template-literal escapes are handled inside the embedded TS/CSS — Svelte itself has no escape rules at the template level.
- ⚠️ **"Is this whitespace?" has two answers here, and the crate's own [`whitespace.rs`](src/whitespace.rs) module doc is the rule** — which class a site wants follows from the QUESTION it answers (does this end a token, vs may a formatter respell it without changing what renders), never from the fact that the code is Rust. That doc also enumerates the four reads that deliberately answer to neither, each with its own argument, and the five sites where reaching for `str::trim` / `char::is_whitespace` / a `b' ' | b'\t'` byte match was the whole bug. The workspace-wide index (every class in tsv, the other crates it has bitten) is `tsv_lang`'s `whitespace.rs`. Read one of them before adding a whitespace predicate or a whitespace test.
- **A text node's edges and words are read on BYTES.** `text_edge_ws`, `trim_start_collapsible_ws` / `trim_end_collapsible_ws` (`collapsible_ws_prefix_len` / `_suffix_len` beneath them), `split_collapsible_ws` and `text_starts_with_linebreak` walk `is_collapsible_ws` bytes: the class is four ASCII bytes, so every cut is a char boundary and a byte walk is the char walk exactly. The `str` pattern spellings they replace — `trim_matches(is_collapsible_ws_char)`, `split(pred)` — decode a char per byte through a `MultiCharEqSearcher`, and what they walk here is long: a text node's edge is a `\n` plus the indent, and the fill splits every byte of every content text it packs (~44K edge trims and 300 KB of prose a pass on a Svelte corpus, worth about 0.4% of its instructions). ⚠️ That is the whole case for a byte walk — the LENGTH of what is walked. A one-space trim costs the same ~40 instructions through a searcher or a byte loop plus its slice checks (measured neutral on `tsv_lang`'s comment trims, 135K asks a pass on TypeScript — where the byte body also came out as one outlined function taking both direction flags at runtime), so the searcher there stays until a per-direction inline form is priced. `is_collapsible_ws_char` remains for the one-decode positions (`starts_with`, `ends_with`), which build no searcher; a whitespace-only test reads the parser's precomputed `Text::is_collapsible_ws_only`, the same predicate over `raw`.
- **Lazy entity decoding on `Text`.** The internal `Text` node stores `raw` plus a parse-time `TextDecoding` context (`Fragment` / `AttributeValue` / `Raw`); the decoded form comes from `Text::data() -> Cow<str>`, which borrows `raw` when no `&` is present (decode is identity) or in `Raw` context. Contexts mirror the canonical parser: fragment text decodes with text-content rules, quoted and unquoted attribute values with attribute rules, raw-content element text not at all. The printer reads `raw` — what it EMITS is the author's bytes, so an entity is never respelled — and `data()` serves the cold paths (public-AST conversion, `lang`/`context` attribute checks, root-span whitespace trimming) plus the **separator** questions, which are about what the characters *are* rather than how they are spelled: is this node the run's prose (`is_separator_like_text`), and is this separator interchangeable with a plain space (the `is_collapsible_ws` class, asked by the boundary and separator paths). That split is load-bearing in both directions — reading `raw` for the layout questions let `&#9;` pick a different layout than the tab it decodes to, and reading `data` for the emission would rewrite the author's source. The character class those questions test is `is_collapsible_ws` (`[ \t\n\r]`, `clean_nodes`' set), which is deliberately **narrower** than Rust's `is_ascii_whitespace`: a form feed is rendered content, and the wider class deleted it.
- **The wire's `loc` is two line counts, one per acorn parse.** Svelte's own positions
  (`locate-character`) open a line at `\n` alone; everything acorn parses carries the ECMAScript
  class, seeded once per island over whatever prefix Svelte prepared for it. The parser records
  each parse's start in `Root::acorn_regions` and the writer rebuilds the seed from it
  (`tsv_ts::AcornSeed`) — including for the root `comments` array, which is emitted outside the
  tree walk that would otherwise carry it. Gated by
  `tests/fixtures/svelte/syntax/whitespace/line_terminators_acorn_regions` and
  [`tests/acorn_loc_line_terminators.rs`](../../tests/acorn_loc_line_terminators.rs) (the
  lone-`<CR>` half, which cannot be a fixture input — the format path folds it). Full model +
  the per-island seeding table:
  [docs/architecture.md §`loc` lines](../../docs/architecture.md#loc-lines-two-classes-one-per-acorn-parse).
- ⚠️ **Some wire nodes have NO `loc`, because Svelte builds them rather than parsing them** —
  the counterpart to the bullet above, and the one an editor of `ast/convert/write.rs` is most
  likely to get wrong. Where the writer emits a node the parser constructed instead of handing
  its text to acorn, the result carries the acorn `type` string but a *different field set*:
  the **shorthand** `bind:x` / `class:x` `expression` (the directive name IS the expression),
  the fused `Literal` of `<svelte:element this="div">` (whose `raw` is Svelte's re-quoting, not
  the author's bytes), and `{@const}`'s whole `VariableDeclaration` + declarator — though the
  `id` inside that one DOES carry a `loc`, from `read_identifier`, so it has `character`. The
  contrast case is `{const}` / `{let}`, which really is an ordinary acorn declaration, `loc`
  throughout, and which may hold more than one declarator where `{@const}` holds exactly one.
  Each has its own interface in the shipped types rather than reusing the acorn one; the rule
  and the table live at
  [../tsv_wasm/CLAUDE.md §TS Type Maintenance](../tsv_wasm/CLAUDE.md#ts-type-maintenance), and
  `deno task check:ast-types` is what holds them apart.
- **Typed block bindings share one attach point with `tsv_ts`.** The block-context grammar (`{#each xs as pattern: T}`, `{:then pattern: T}`, `{:catch pattern: T}`) accepts a type annotation on an identifier *or* a destructuring pattern, and both readers — `parser/block.rs::parse_context_pattern` for `{#each}` and `tsv_ts::parse_pattern_with_comments` for `{:then}`/`{:catch}` — route through `tsv_ts::attach_pattern_type_annotation`, so the per-kind span convention has one definition and the two readers cannot drift. That convention is subtle: a Svelte block pattern is **not** tail-anchored (the binding's span stays on the bare name, annotation as a sibling), and for a destructured pattern the wire `end` widens past the annotation while `loc` does not — reproducing Svelte's own `read_pattern`. See [`tsv_ts/CLAUDE.md`](../tsv_ts/CLAUDE.md) §Distinctives. The same two ends also bound the binding's **comment** window — `pattern.span().end` is the bare end, `tsv_ts::pattern_binding_end` the end past the annotation, and `ast/convert/comment_attachment.rs::pattern_comment_window` spans the pair once for both the writer's pre-check and its attach filter (an interior or annotation comment attaches on the wire exactly as canonical's sub-parse does). Both block readers reject a comment in either gap *around* the annotation, matching canonical, which crosses those gaps with `allow_whitespace` alone — `{#each}` by bounding the pattern before its own annotation parse, the `{:then}`/`{:catch}` reader by gating both edges after its single sub-parse (`parse_await_value_pattern`).
- **A block head decides whether a top-level `as` is TypeScript's or its own, and says so.** `{#each}` and `{#await}` are the two heads that read their expression with a *partial* parse, and each passes an explicit `tsv_ts::TopLevelAs` policy. `{#await}` keeps it as an **assertion**: its separators are `then` / `catch`, no part of type syntax, so an `as` there is always TypeScript's and the parse ends on its own at the clause keyword. `{#each}` gives it away as the **host separator**, because its separator *is* `as` — and having given it away it owes the assertion run a reader, which is `each_binding_separator`: it walks the chain one type at a time via `tsv_ts::parse_type_extent` and answers with an `EachHeadSplit` — the head's first `as` separates, a later one does, or the head has **no binding at all**. The walk stops at the first item that is not a type, which is the binding (a destructuring default is a pattern, so `{#each xs as A[] as { a = 1 }}` splits at the second `as`). ⚠️ The separator is the run's **LAST** keyword, and only when that keyword is `as` — not the last `as` anywhere in the run — because canonical unwinds the head by stripping its expression's *outermost* node and only when that node is a `TSAsExpression`. A `satisfies` therefore **cancels** every `as` before it: `{#each xs as A[] as item satisfies B}` is binding-less, `item` being a type, where keeping the last `as` handed `item` to the binding parser and rejected a head canonical accepts. A run that simply *ends* on `satisfies` (`{#each xs as A satisfies B}`) is the same answer, and it routes through the **same** tail as a head with no `as` at all, so the two spellings of "no binding" cannot drift — pinned by [blocks/each/type_assertion_satisfies_no_binding](../../tests/fixtures/svelte/blocks/each/type_assertion_satisfies_no_binding/). ⚠️ The policy names `as` **alone**, and the walk steps over **both** keywords: `satisfies` is an assertion no separator collides with, so it is a chain *link*. Gating the pair together in the *parse* rejected `{#each xs satisfies A[] as item}`, which canonical accepts; in the *walk*, recognizing only `as` would stop dead at the `satisfies` in `{#each xs as A satisfies B as item}` — a hazard the byte scan this replaced did not have, since a scan for the last ` as ` steps over an intervening `satisfies` without having to know it exists. ⚠️ The walk asks the **type grammar** on purpose and must not be "simplified" back into a bracket-depth byte scan: `<` / `>` are not a bracket pair, so an arrow's `>` in `A<() => string>` closes a depth nothing opened — a signed depth counter goes **negative** there and fails every later `depth == 0` test. (A mapped type's `[K in T as U]` is the same question one step subtler: a depth scan survives that inner `as` only because brackets nest it, where the type grammar knows it outright.) Because the printer strips the parens the authored form needs, each of these turned valid input into output tsv itself rejected — pinned by [blocks/each/type_assertion_function_type](../../tests/fixtures/svelte/blocks/each/type_assertion_function_type/), [blocks/each/type_assertion_satisfies](../../tests/fixtures/svelte/blocks/each/type_assertion_satisfies/) and [blocks/await/type_assertion](../../tests/fixtures/svelte/blocks/await/type_assertion/), whose `unformatted_parenthesized` variants are the round-trip half.
- **Dual schema for `<script>` conversion, chosen component-globally.** The writer picks `tsv_ts::ast::convert::Schema::Acorn` when the component parses as TypeScript and `Schema::SvelteScript` otherwise; the latter omits `importKind` / `exportKind = "value"` and always emits `attributes` on import/export declarations to match Svelte's parser output. The TS decision is **component-global** (`ast/convert/special.rs`'s `component_is_typescript`, mirroring Svelte's single `this.ts` flag): the first `<script>` in source order carrying a `lang` attribute decides it for *every* script, so a plain `<script>` beside a `lang="ts"` sibling still emits the acorn shape.
  ⚠️ The same fact governs the **expression islands**, which are not `<script>`s and so take it by a different route: `Ctx::embed` sets `vanilla_acorn: !component_is_ts` on the `EmbedWriter` every island funnels through, so a `{expr}` tag, an attribute or directive value, a `{@const}` and a `{#snippet}` body all carry vanilla acorn's expression quirks in a non-TS component (see `tsv_ts`'s `Ctx::vanilla_acorn`). Keeping the two routes fed from one field is load-bearing: an island reading a hardcoded `false` emits the acorn-typescript shape in a plain component — invisible while the `<script>` arm, the one anybody writes a wire fixture for, is right.
  ⚠️ `script_lang` reads the `lang` attribute's **raw** bytes, and is the only `lang` reader that does. Svelte's `this.ts` never builds an AST for the question — it runs a regex over the template text (`1-parse/index.js`, `lang=(["'])?([^"' >]+)`) and compares the captured bytes against `ts` — so `<script lang="&#116;s">` is not TypeScript to the wire. The *formatting* question is the other one: `internal::lang_attribute` (which body does the printer format, and as what) reads the DECODED value, like prettier's `getLangAttribute`, so it calls that same spelling `ts`. Two questions, two readers, on purpose — `tests/fixtures/svelte/attributes/lang_entity` holds both answers, so a "one definition" pass that merges them fails there instead of silently changing the wire.
  ⚠️ The flag shapes the WIRE only — it does not gate the PARSE. The parser has no document TS flag, so a plain `<script>` component's TypeScript (annotations in the script, a generic or typed `{#snippet}` head, a typed block binding, `as` / `satisfies` in an expression tag) parses in tsv where Svelte rejects at the first island. A tracked over-acceptance, one class across every TS-bearing position, pinned by `tests/fixtures/svelte/script/no_lang_typescript_svelte_prettier_divergence` and cataloged in `docs/conformance_svelte.md` §TypeScript-mode gating; closing it means the parser carrying the document flag, not a per-island check.
