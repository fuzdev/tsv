# tsv_svelte

> Svelte component parser + formatter — drop-in replacement for Svelte's compiler frontend, with a near-Prettier formatter tracking Prettier's `svelte` plugin.

## Architecture Position

Depends on:

- [`tsv_lang`](../tsv_lang/CLAUDE.md) — `Span`, `ParseError`, doc builder, `EmbedContext` / `LayoutMode`
- `tsv_ts` — embedded TypeScript: `<script>` bodies and template `{expr}` slots
- `tsv_css` — embedded CSS: `<style>` blocks
- `tsv_html` — element classification (block / inline / void), whitespace rules

Sources of truth: Svelte's compiler for AST shape, Prettier (`svelte` plugin) for formatting. Scope is `.svelte` files only — `.svelte.ts` rune modules are pure TypeScript and go through `tsv_ts`.

See [../../CLAUDE.md §Project Structure](../../CLAUDE.md#project-structure) for the standard crate layout (`ast/` / `lexer/` / `parser/` / `printer/`) and project-wide conventions.

## Public API

`src/lib.rs` exports free functions matching the tsv pattern:

- `parse(source, arena: &'arena Bump) -> Result<Root<'arena>>` — internal AST in a caller-owned `Bump`: one arena per document, shared with every embedded sub-AST (`tsv_ts` for `<script>` / `{expr}`, `tsv_css` for `<style>`), so the whole component is one bump-allocated graph. See [docs/architecture.md §Nested AST](../../docs/architecture.md#nested-ast-bump-arena-not-flatindexed).
- `format(&Root, source) -> String` — through the doc builder; `format_in(&Root, source, &DocArena)` is the same into a caller-provided doc arena (multi-file drivers reuse one via `DocArena::reset()`; embedded `<style>` builds its doc nodes into this host arena via `tsv_css::format_embedded_in`, not a per-block one, but still renders to its own string); `format_folded_in(&Root, &FoldedSource, &DocArena)` is `format_in` for a caller that folded the source itself — identical output, the line verdict taken from the fold's pass (what the CLI, the bindings and `format_str` call)
- `format_str(source) -> Result<String>` — parse + `format` fused (the format path's `<CR>` fold ahead of the parse, then `format_folded_in`), the twin every language crate has
- `parse_folded(&FoldedSource, arena) -> Result<Root<'arena>>` — the parse every Svelte format entry point runs (the CLI, `tsv_arena`'s `parse_format!` behind every binding's format export, `format_str`) over the CR-folded document, erroring in the caller's coordinates (`FoldedSource::parse_with`). It owns the fold's one refusal: Svelte's template reader ends an in-tag `//` comment at `\n` alone, so folding a lone `<CR>` inside one into a line break would end the comment early and print the rest of its line as markup. When the fold rewrote a lone `<CR>` (`FoldedSource::folded_lone_cr`), the author's bytes are parsed first — their error is the format's (the one `parse` reports) — and a template-reader `//` comment (`Comment::from_template_reader`) holding a lone `<CR>` is refused with a positionless `ParseError::refusal` naming its `line:col` (the source is valid Svelte, so every binding reports a plain error, never a syntax error). A `<CR><LF>` never refuses; a document with no lone `<CR>` pays nothing. Pinned by `../../tests/svelte_tag_comment_lone_cr.rs`
- `convert_ast_json_bytes(...) -> Vec<u8>` and `convert_ast_json_string(...) -> String` — the public JSON AST (`feature = "convert"`) on the **span-only** wire every binding emits and `tsv parse` defaults to (its line/column twin, `convert_ast_json_bytes_with_locations`, is below). Each bytes function is its wire's sole emission path (`--pretty` re-indents the bytes; the string variant adds one UTF-8 validation for `&str` boundaries): the writer (`ast/convert/write.rs`) walks the *internal* AST once and emits wire JSON directly, with no typed public tree, fusing byte→UTF-16 offset translation into the walk (per-language pipeline shapes: [docs/architecture.md §Closed Scope, Open Convention](../../docs/architecture.md#closed-scope-open-convention)). The Svelte spine (elements, blocks, tags, directives, attributes — and, on the loc wire, `name_loc`) emits fused; embedded `<script>`/`{expr}` route through `tsv_ts`'s embedded writers and `<style>` children through `tsv_css`'s `write_css_children`, which hands back the `StyleSheet`'s sibling `comments` run — `parseCss`'s flat `CSSComment[]`, rebuilt from the three places tsv keeps CSS comments by the very walk that emitted the children (see [`tsv_css/CLAUDE.md`](../tsv_css/CLAUDE.md)) — for `write_css_comments` to emit into the next key. Template-expression and `<script>` comments fuse via an island-scoped attach that runs **online**, driven by this same emit: acorn assigns a node's leading comments at node *entry* and its trailing ones after its children, exactly the writer's `node_header` and `close_node`, and the wire emits both lists at the close. So `tsv_ts`'s `CommentAttach` runs off those two events — no second pass, recorded tree or per-node map — and `leadingComments`/`trailingComments` serialize in place. Each island declares only its comment WINDOW plus what acorn's walk reads about a *root*'s surroundings (`ast/convert/comment_attachment.rs`'s `attach_*`, over its own window helpers) — including, for a `read_expression` island, the grouping pairs Svelte's `preserveParens` parse walks and `remove_parens` then discards with their comments: a JSDoc cast's pair, which the writer runs as a silent frame, and the bare pairs around the root, read back off the source; everything else the walk needs — child visit order, `parent.end`, and which element is last in a container's body — the emit itself supplies. ⭐ Child visit order is therefore acorn's *by construction*: it IS the emitted field order, so a walk that orders a node's children differently from the wire is unrepresentable — a class a hand-maintained visit order has to get right per shape, the generic-async arrow being the subtle one ([`typescript/expressions/arrow/async_generic/params_comment_return_type`](../../tests/fixtures/typescript/expressions/arrow/async_generic/params_comment_return_type/)). The crate never reads the wire back: the one `Value` consumer, the fixture pipeline, reads these bytes through `tsv_debug::json::wire_value` (an unbounded read — serde_json's default 128-level limit refuses wires the parser emits fine). The span-only wire is gated against the canonical parser's `expected.json` (`loc`/`name_loc` stripped), the multibyte and template-comment fixtures exercising the offset translation and the attach; `loc` by `check:loc`, `../../tests/loc_definition.rs` and `corpus:compare:parse`'s loc arm.
- `convert_ast_json_bytes_with_locations(...)` — the `loc`-bearing wire (`tsv parse --locations`, `tsv_debug`). The span-only wire drops *every* line/column object from it — every `loc` (the embedded `tsv_ts` and `tsv_css` writers take the same `WirePositions`) **and the element/attribute/directive `name_loc`** — so only `start`/`end` offsets remain and no line table is built. `name_loc` stays derivable from a node's own `start`/`end` + type: an element names the tag run at `start + 1`, an attribute names `[start, start + name.len]` (a shorthand `{x}` names the identifier inside its braces, so a padded `{ x }` excludes the padding), and a directive its whole head token — the run from `start` to the first name terminator (`on:click|preventDefault`, not just `click`). The shipped `reconstruct_locations` helper (`crates/tsv_wasm/npm/locations.js`) restores it on that basis; `deno task check:loc` (`scripts/check_loc.ts`) gates the derivation against the loc-bearing wire over every fixture input. The span-only wire mirrors acorn's `locations: false`. Invariant: `../../tests/loc_definition.rs`.

## Distinctives

What separates this crate from `tsv_ts` / `tsv_css`:

- **Embeds two other languages.** The printer delegates `<script>` and every template `{expr}` to `tsv_ts` doc builders (e.g. `tsv_ts::build_program_doc`) and `<style>` to `tsv_css::format_embedded_in` (into the host's `DocArena`, rendering its own string — §Public API), passing an `EmbedContext` with the current indent state and `LayoutMode::Embedded` so a root binary expression uses continuation indent (nested expressions format as in `<script>`). See `printer/script_style.rs` and `printer/nodes/tags_doc.rs`. A `<script>` / `<style>` **nested in markup** formats its body the same way, one indent level inside its own tags (`build_raw_content_element_doc` in `printer/nodes/element_doc.rs`): the body parses at host-absolute offsets, and a script's program doc (`tsv_ts::build_program_body_doc`, under the top-level script's `EmbedContext::line_owning`) is embedded in the host doc so the renderer indents only the breaks it owns. A stylesheet — which the CSS printer writes rather than builds — cannot ride the host's indentation that way, so `build_nested_style_body_doc` formats it with `format_embedded_in` **twice**: at the level it is expected to render at, `Printer::body_indent_level` (the count of fragment builds open around it — `Printer::enter_fragment`, called by every fragment builder a child list goes through, never at an indent site), and once more one level deeper. A line that moved with the level is one the CSS printer broke and indented itself, and it rides a `hardline` at its indent relative to the body; a line that did not move is verbatim text (a comment interior, an escaped-newline string) and keeps its authored column behind a `literalline`. The host's renderer therefore places the body wherever the element actually renders, whether or not the fragment count matches that depth; no spelling where the two part is known to be reachable, so that placement and its fallback (a deeper format that wraps differently keeps the counted depth) are guards — the argument is on `build_nested_style_body_doc`. Under a **whitespace-sensitive ancestor** (a `<pre>` subtree, through any special element inside it too) neither body is formatted: the element takes the whitespace-sensitive builder and its content prints verbatim. ⚠️ Re-indenting a formatted body line by line *without telling the two kinds of line apart* is wrong for either: blind to a break the printer owns vs a newline inside verbatim text (a template literal, a comment interior, a `prettier-ignore` slice), it moves the latter a level every pass, and it measures width from column 0 — the style path's second format exists to make exactly that distinction. Pinned by `tests/svelte_nested_raw_content_parity.rs` and the `svelte/{script,style}/nested_*` fixtures.
- ⚠️ **A template island's `//` may not be deferred past the island, and only this crate can say so.** `tsv_ts` emitters defer a trailing line comment through `line_suffix`, licensed by the comment reaching a line end that is still JS — which past an island's closing `}` it is not, so a deferred `//` comes out as **rendered page text** (`<a href={fn() // c⏎.bar}>t</a>` → `<a href={fn().bar}>t</a> // c`, a different page). The axis is `EmbedContext::printer_owns_line`: the template printer and every island recipe leave it at its safe `false`; only the `<script>` body claims ownership (`script_style.rs`, via `EmbedContext::line_owning`). A new braced head is therefore conservative by construction — provided nobody flips the polarity for tidiness. The deferrals `tsv_ts` does NOT decline — a stripped redundant pair's interior run (`{a || (b // c⏎)}`), a sole hugged arrow's body — are caught at the island's closer instead: each braced value's trailing run is built by one seam, `Printer::value_trailing_docs`, which leads it with an **embed end** (`DocArena::embed_end`) whenever the value's doc holds a deferred run, so the run flushes before the `}` / ` as` / `;` and the closer drops below a `//` — the form the author's own after-the-value comment takes. A new island builds its trailing run through that seam, not through `trailing_comment_docs` directly. A block binding pattern has no such run and no line end before the head's `}`, so each default value inside it takes an embed end of its own (`Printer::build_pattern_assignment`). The one head that takes no comment at its end, `{#each}` with no `as`, keeps the author's pair instead (`HeadTail::CommentlessDelimiter` → `EmbedContext::value_end_takes_no_comment`), and a `{let}` / `{const}` tag the value ends on a comment takes the `;` (keyed on the embed end where only the render knows). Model, hazards and why the default points this way: [../../docs/comments.md](../../docs/comments.md).
- **Element classification.** Every name-derived fact is packed into a `TagFacts` bitfield (`ast/internal.rs`, beside `is_component_name`) computed **once at parse** — where the raw tag `&str` is already in hand — and stored on `Element::facts` (in the tail padding beside `kind`, so `Element` grows nothing). The element/fragment/sibling paths re-ask the same tag-name questions many times per element, so each print-time read is one field load, and classification is a reusable AST property (linter/type-checker/LSP get it free). `printer/classification/element.rs` holds only the printer-specific element-**instance** overlay on top of the facts (a Component is inline; a non-empty `<script>`/`<style>` is block via `has_raw_content`) — the **node-level** answer. A block-classified node can still lay out inline in its sibling list: a global `svelte:*` element glued to content on both sides, or a nested `<script>`/`<style>` that keeps its glue (it renders no box, so a break beside it can render). The readers that hold a node by position ask the positional predicates (`is_block_element_at`, `is_inline_el_or_comp_at` in `printer/nodes/fragment_doc.rs`, over `is_glued_block_exception`) instead. `classify_tag` (`printer/nodes/element_doc.rs`) unpacks `Element::facts` into the per-tag `TagClass`. The pure per-name predicates live in `tsv_html`. The exhaustive equivalence test beside `TagFacts` grades each accessor against the pure predicate it encodes — keep it green; a mispacked bit changes layout only on rare tags at rare widths, which no fixture or corpus diff can be relied on to see.
- **One element pipeline for two AST types.** `internal::Element` and `internal::SpecialElement` are distinct types that print the same shape (a name, attributes, a fragment, an open/close tag pair), so both project onto **`ElementParts`** (`printer/nodes/element_doc.rs`) and run one `analyze_element` → `compute_element_layout` → `build_content_element_doc` pipeline. They diverge only *before* it — in how the name doc and the attribute docs are built (`svelte:*` synthesizes a `this={…}` attribute) — and the tag-name-keyed questions are answered once per element by `classify_tag` → `TagClass`. This is load-bearing, not tidiness: a `special_doc.rs` carrying its own hug predicates and its own `needs_multiline` drifts from the element path (a `<slot>` that never goes multiline for block children, or that dangles its delimiters where a regular element is block-style) — pinned by [`svelte/special/slot/block_children_prettier_divergence`](../../tests/fixtures/svelte/special/slot/block_children_prettier_divergence/), which sits a `<span>` beside the `<slot>` in the same shape so the parity is the assertion. The one layout decision the special path still makes alone, `build_special_empty_doc`'s three-state group, is the remaining drift surface: an attribute that breaks (a line comment in `this={…}`) routes through the shared `build_opening_tag`, so a `svelte:*` element expands for it exactly as a regular `<div class={// c⏎foo}>` does, and the rest is a fixtures-first pass away (the hug state is pinned). Layout carries **one** `BoundaryMode` for both tags (`ElementLayout::WithContent(BoundaryMode)`) so a render-free boundary character cannot dangle one delimiter without the other — see [conformance_prettier_svelte.md §Svelte: Inline content block-style](../../docs/conformance_prettier_svelte.md#svelte-inline-content-block-style). The deliberate exception: `<pre>`/`<textarea>` are dispatched to `element_ws_sensitive_doc.rs` **before** any of this (there boundary whitespace is literal and the dangle is mandatory), and that builder keeps its own block/inline probe on purpose — inside a whitespace-preserving subtree a nested component counts as inline flow, which `ElementKind` does not model.

  **The head `<title>` is the third member of that family, and joins it at the builder rather than beside it**: its content prints verbatim too (`SpecialElementKind::preserves_content_whitespace`), so it takes the family's one content-bearing entry, `build_verbatim_content_doc` — the `<pre>`/`<textarea>` arm's too — which hands the head to `build_ws_sensitive_head_with_content_doc`, off the same `ws_sensitive_content_edges` read the other two use. So does every special element **inside** one that has content (`build_ws_sensitive_special_element_doc`, an inline member like a component): Svelte carries the ancestor's whitespace-preserving state into its fragment, so routing it to the shared pipeline would lay rendered text out as flow content. An **empty** one keeps the shared pipeline's empty layout (`build_special_empty_doc`), which is not a component's there: a wrapped head drops its `>` to a line of its own (`⏎\t></svelte:boundary>`) where a component hugs it onto the last attribute — render-same, a layout gap.

  ⚠️ That read is a **pair**, one per boundary (`ContentEdges`), and the pair is the point: the opening `>` takes a break point of its own only when the content opens on a visible byte, and the closing `>` dangles only when it ends on one. This is the exact inverse of `BoundaryMode` above — that carries ONE value for both tags because a render-free boundary is trimmed on both sides at once, where a literal boundary is trimmed by nobody and so has no shared fact to keep in sync. Keying both delimiters on the opening edge would give the mirror-image authorings `<textarea …> text</textarea>` and `<textarea …>text </textarea>` each other's answer. One input overrides the content's closing answer: a nested `<script>` / `<style>` keeps its closing tag whole (`ContentEdges::with_whole_close`), because Svelte ends a nested raw-text body at the first literal `</script>` / `</style>` — `</script⏎>` does not parse, and beside a second element of the same name it silently merges the two. An empty body (the one empty `Text` child Svelte always gives it) is no content, read by the same `has_raw_content` the block classification uses, so it lays out as an empty element (`<strong></strong>`'s shape). Spelling the head locally there instead — via `build_opening_tag`, whose `dedent(softline)` is the *block-style* `>` placement — is exactly the drift this bullet warns about, one kind answering the family's question a third way: an own-line comment left the `>` at base indent where a `<textarea>` hugs it ([`special_elements/title_head_comment_prettier_divergence`](../../tests/fixtures/svelte/special_elements/title_head_comment_prettier_divergence/)).
- **No `escapes/` module.** String/template-literal escapes are handled inside the embedded TS/CSS — Svelte itself has no escape rules at the template level.
- ⚠️ **"Is this whitespace?" has two answers here, and the crate's own [`whitespace.rs`](src/whitespace.rs) module doc is the rule** — which class a site wants follows from the QUESTION it answers (does this end a token, vs may a formatter respell it without changing what renders), never from the fact that the code is Rust. That doc also enumerates the reads that deliberately answer to neither, each with its own argument, and the sites where reaching for `str::trim` / `char::is_whitespace` / a `b' ' | b'\t'` byte match was the whole bug. The workspace-wide index (every class in tsv, the other crates it has bitten) is `tsv_lang`'s `whitespace.rs`. Read one of them before adding a whitespace predicate or a whitespace test.
- **A text node's edges and words are read on BYTES.** `text_edge_ws`, `trim_start_collapsible_ws` / `trim_end_collapsible_ws` (`collapsible_ws_prefix_len` / `_suffix_len` beneath them), `collapsible_word_ranges` (the fill's splitter) beside `split_collapsible_ws` (the prose word count's, over the same walk) and `text_starts_with_linebreak` walk `is_collapsible_ws` bytes: the class is four ASCII bytes, so every cut is a char boundary and the byte walk is the char walk exactly. The `str` pattern spellings they replace (`trim_matches(is_collapsible_ws_char)`, `split(pred)`) decode a char per byte through a `MultiCharEqSearcher`, and what they walk here is long: a text node's edge is a `\n` plus the indent, and the fill splits every byte of every content text it packs (~44K edge trims and 300 KB of prose a pass on a Svelte corpus, worth about 0.4% of its instructions). ⚠️ That is the whole case for a byte walk — the LENGTH of what is walked. A one-space trim through a byte body that is CALLED costs what the searcher costs (`tsv_lang`'s comment trims, 135K asks a pass on TypeScript, measured neutral when their byte body came out as one outlined function over two runtime direction flags); the same asks win only in the inline per-direction form those seams take (`trim_start_js_whitespace` and siblings — core's `trim_ascii*` plus a stop-byte test, the searcher cold), about twenty instructions an ask where the searcher was fifty. A short trim wins only inline, with no call and no slice check on its common path; a long walk wins either way. `is_collapsible_ws_char` remains for the one-decode positions (`starts_with`, `ends_with`), which build no searcher; a whitespace-only test reads the parser's precomputed `Text::is_collapsible_ws_only`, the same predicate over `raw`.
- **Lazy entity decoding on `Text`.** The internal `Text` node stores `raw` plus a parse-time `TextDecoding` context (`Fragment` / `AttributeValue` / `Raw`); the decoded form comes from `Text::data() -> Cow<str>`, which borrows `raw` when no `&` is present (decode is identity) or in `Raw` context — `Text::data_is_raw` asks that without building the `Cow`, the parse-time `is_collapsible_ws_only` flag answering it for a whitespace-only text (`[ \t\n\r]` holds no `&`). The wire writer never asks it of a whitespace-only text — it writes that text's `raw` and `data` as one escape window — and asks it inline for every raw-first text with content it emits (all but a raw-content element's). Contexts mirror the canonical parser: fragment text decodes with text-content rules, quoted and unquoted attribute values with attribute rules, raw-content element text not at all. The printer reads `raw` — what it EMITS is the author's bytes, so an entity is never respelled (for the reverse case see the end of this bullet) — and `data()` serves the cold paths (public-AST conversion, `lang`/`context` attribute checks, root-span whitespace trimming) plus the **separator** questions, which are about what the characters *are* rather than how they are spelled: is this node the run's prose (`is_separator_like_text`, asked through `Printer::text_is_separator_like`, which reads `raw` and decodes only when its first non-whitespace character is a `&` — the decode rewrites only what starts at one, so everything ahead of the first `&` reaches `data` as itself), and is this separator interchangeable with a plain space (the `is_collapsible_ws` class, asked by the boundary and separator paths). That split is load-bearing in both directions — reading `raw` for the layout questions let `&#9;` pick a different layout than the tab it decodes to, and reading `data` for the emission would rewrite the author's source. The character class those questions test is `is_collapsible_ws` (`[ \t\n\r]`, `clean_nodes`' set), which is deliberately **narrower** than Rust's `is_ascii_whitespace`: a form feed is rendered content, and the wider class deleted it. The reverse case — a raw character the format path spells as a reference, where the section reorder would otherwise change how the next parse reads it — goes through one spelling, `push_char_reference`, for two characters: the last character of template text the reorder leaves at the document's end, which Svelte's `parse` would trim there (written by `format_respelled_tail` when `Printer::template_tail_respell` asks, and by the lifted-run rewrite below, whose template can end on one too); and the first character after a glued seam a lifted section leaves, when the joined text would otherwise complete a character reference left open before the seam, `x&amp` + `;y` → `x&amp&#x3B;y` (written by the lifted-run rewrite and by `Printer::build_ignore_range_doc`, through `lifted_runs::glued_seam_respell`).
- **A construct that prints as its own source bytes is emitted as ONE span.** Each of these builders answers ahead of its general path when a gate proves the output is the author's bytes: `build_attribute_doc`, through `Printer::attribute_source_span` (`name="text"`, `name={path}` and the shorthand `{name}`); `build_expression_tag_doc_at`, through `Printer::tag_is_plain_path` (an expression tag that is exactly `{name}` or `{name.prop}`); and `build_head_value_doc`, by its plain-path arm — reaching every value built through it, the `build_ts_expression_doc*` wrappers included: block heads and `{#each}` keys, the prefixed tags and braced attribute heads (`{@html x}`, `{...x}`, `{@attach x}`), directive and attribute values, `bind:` sequence operands, the `{@const}` id, and the leaves and keys of a binding pattern (`{#each … as {a, b: c}}`, `{:then [a]}`). A *plain path* (`plain_path_span`, `printer/mod.rs`) is a bare reference or a lone lookup off one, the shape `tsv_ts` prints as a single flat run; its span holds no comment, and the one comment its doc could carry from outside — a block comment it **owns** — is ruled out by the tag's `{` or asked outright (`Printer::owns_leading_comment_at`). `extra.is_none()` is load-bearing there: a typed binding keeps its span on the bare name. ⚠️ Such an answer stays invisible only while its gate and its width both hold. Each gate restates what its general builder does to the bytes, so **a rule added to a general builder is owed to the gate ahead of it** (a second attribute whose value is normalized, a new pair a host puts around a value). And the fused text must be **plain ASCII with no tab** (`Printer::plain_source_span_doc`): the parts it replaces are measured one by one, and one text measures to their sum only where a width is a byte count — a wide character or a grapheme cluster reaching across a part boundary shifts a fits verdict and nothing else. `printer/fused_spans_tests.rs` grades these answers against their general builders with the answers switched off (`fuses_source_spans`), over both fixture trees, a boundary matrix (a comment, a space, a quote, a wide character inserted at every position of a construct) and a walk across the print width; a new fused shape goes into its seeds.
- **A root section written between two template nodes is lifted out of the source before the layout reads it** (`printer/lifted_runs.rs`). The canonical reorder moves a `<script>`, `<style>` or `<svelte:options>` — with the comments that travel with it — out of the template, so the nodes on either side become neighbours, and the compiler never saw the run between them either. Every layout reader (text-edge trims, the glue tests, blank-line reads, the fill) asks positionally, off source bytes that still hold the run, so the question is answered once, ahead of the parse: `Printer::lifted_runs_source` rewrites the document in the output's own layout — each section run in canonical order, the template with each such run's neighbours joined — and `format_lifted_runs` parses and formats that. The join reads every whitespace segment of the gap: none keeps the neighbours glued, any whitespace is a space, any newline a line break, and a blank line counts only from the segment before or after the run (one inside it travels with the run). A section inside a `format-ignore` range is cut out the way the range's own verbatim slice cuts it (`range_cuts`, shared by both): sections with only whitespace between them are one seam, and the strongest run in it stands for the whole seam — a run before or after the sections kept byte for byte and winning a tie (the run after over the run before), a run between them respelled as one of its line breaks, or as a single space when it holds none (render-same), and never counted as a blank line. The edge runs are kept whole because a range's bytes are the author's. At a glued seam, in a range or not, the first character after it is spelled as a reference when the join would complete one the text before it left open (`glued_seam_respell`, asked of the text joined so far). A section's freeze verdict is taken from the original, since the rewrite changes what stands above it. A document with no run between template nodes is not rewritten.
- **The wire's `loc` is one LF-only line count for the whole document.** Every object with
  numeric `start`/`end` — template nodes, `Root`, `Script`, `StyleSheet` and its `content`,
  `<svelte:options>`, root and attached comments, and every acorn and `<style>` node — gets
  `loc` immediately after `end`, from one `\n`-only line table (`locate-character`'s rule)
  shared by every island. A superset of Svelte's wire, which gives `loc` to acorn-parsed nodes
  only, and none of Svelte's `loc` quirks reproduced (acorn's ECMAScript line count on the
  nodes it parses, the `_ as ` line swallow, the tag-position `Program.loc`). Graded by
  [`tests/loc_definition.rs`](../../tests/loc_definition.rs); the model:
  [docs/architecture.md §`loc` lines](../../docs/architecture.md#loc-lines-one-rule-per-document).
- ⚠️ **Some wire nodes are Svelte's own construction, not acorn's** — and in Svelte's wire they
  carry no `loc` (tsv's gives them one, like every positioned object); the rule an editor of
  `ast/convert/write.rs` most likely gets wrong. A node the parser constructed instead of handing
  its text to acorn carries the acorn `type` string but a *different field set*:
  the **shorthand** `bind:x` / `class:x` `expression` (the directive name IS the expression),
  the fused `Literal` of `<svelte:element this="div">` (whose `raw` is Svelte's re-quoting, not
  the author's bytes), and `{@const}`'s whole `VariableDeclaration` + declarator — though the
  `id` inside that one DOES carry a `loc`, from `read_identifier`, so it has `character`. The
  contrast case is `{const}` / `{let}`, which really is an ordinary acorn declaration, `loc`
  throughout, and which may hold more than one declarator where `{@const}` holds exactly one.
  Each has its own interface in the shipped types rather than reusing the acorn one; the rule
  and the table live at
  [../tsv_wasm/CLAUDE.md §TS Type Maintenance](../tsv_wasm/CLAUDE.md#ts-type-maintenance), and
  `deno task check:ast-types` is what holds them apart.
- **Every `read_pattern` position has one reader.** Svelte reads the `{#each}` context, the `{:then}`/`{:catch}` value and the `{@const}` id with the same `read_pattern` (`1-parse/read/context.js`), and tsv reads all three with `parser/block.rs::parse_block_pattern`, which enforces both halves of it: the **head gate** (the binding starts as a name — the shared `read_identifier`, reserved words included — or as a `{`/`[` opening a matched bracket; a paren shell `(a)` or a comment is `expected_pattern`) and the **bounded extent** (the pattern ends at the name or the bracket's close, so `a.b`, `[a][0]`, `{ a }.b` and `a = 1` are tails the caller rejects rather than an expression the TS parser takes whole). A member or paren target stays legal INSIDE a destructure, which acorn reads as an assignment target (`AssignableContext::SveltePattern`). The optional `: T` is its own sub-parse (`parse_ts_type_annotation`), and its end is the TS type parser's — never a byte scan, which cannot see a function type's `=>` or a type argument list's `,`/`>`. Each caller owns only what follows the binding: `{#each}`'s `, index` / `(key)`, the `{:then}`/`{:catch}` tag's `}` (`parse_await_value_pattern`), the `{@const}` declarator's `=` (`parse_declarator`). A comment in either gap *around* the annotation is rejected by those same reads, as canonical's `allow_whitespace` rejects it; one inside a destructure or inside the annotation is acorn's and stays.
- **Typed block bindings share one attach point with `tsv_ts`.** `parse_block_pattern` routes the annotation through `tsv_ts::attach_pattern_type_annotation`, so the per-kind span convention has one definition. That convention is subtle: a Svelte block pattern is **not** tail-anchored (the binding's span stays on the bare name, annotation as a sibling), and for a destructured pattern the wire `end` widens past the annotation — reproducing Svelte's own `read_pattern` — and `loc.end` follows the widened `end` (Svelte's own `loc.end` stays at the bracket; not reproduced). See [`tsv_ts/CLAUDE.md`](../tsv_ts/CLAUDE.md) §Distinctives. The same two ends also bound the binding's **comment** window — `pattern.span().end` is the bare end, `tsv_ts::pattern_binding_end` the end past the annotation, and `ast/convert/comment_attachment.rs::attach_binding_pattern` attaches each side over its own window, as canonical's two sub-parses do (the bare pattern, then the `: T`) — `pattern_comment_window`, the writer's pre-check, is their union and must contain both.
- **A `{#snippet}` head that holds a grouping pair is parsed twice, one tree per reader.** Svelte keeps acorn's `preserveParens` for snippet parameters (and, unlike every other template expression, skips `remove_parens`), so the wire carries a `ParenthesizedExpression` per pair. That tree is the wire writer's alone — `Root::snippet_wire_parameters`, a side table keyed by the block's start, because `SnippetBlock` sets `FragmentNode`'s width. `SnippetBlock::parameters` is the paren-free parse of the same `function f(…) {}` wrapper, the tree its `function` twin parses to, and it is what the printer, the compiler and the comment ledger read (its comments, with their ownership claims, are the ones merged). ⚠️ Do not collapse the two back into one: a `ParenthesizedExpression` answers no paren question about its position, so a printer walking the preserved tree prints `(x + y) * 2` as `x + y * 2` and `-(x ** 2)` as `-x ** 2`, which does not parse. The preserved parse is Svelte's reader and alone decides acceptance; the second parse runs only when the first reports a wrapped pair (`tsv_ts::parse_embedded_preserve_parens`'s flag). Pinned by the `svelte/blocks/snippet/*param*_paren*` fixtures and `tests/fixtures_compile/snippets/param_default_paren`.
- **`{@const}`'s init is the one head rule still riding a byte SCAN, and the scan cannot see TS type syntax.** Svelte refuses a bare second declarator (`{@const a = 1, b = 2}`) while allowing a parenthesized sequence, and only the source can say which the author wrote. The scan's depth model — `parser/mod.rs::find_top_level_delim` — is `()`/`[]`/`{}` only, since `<`/`>` is ambiguous with the relational operators, so **a hit is not evidence of a top-level anything** over a region that can hold a type: a type argument list's `,` (`Map<A, B>`) and a function type's `=>` both sit there at depth 0. `reject_multi_declarator` narrows the question until the scan is sound on it, gating the comma scan on the parsed init being a `SequenceExpression`, whose separators *are* top-level commas by construction. Anything new reading this head owes the same narrowing; the scan alone refuses valid components.
- **A block head decides whether a top-level `as` is TypeScript's or its own, and says so.** `{#each}` and `{#await}` are the two heads that read their expression with a *partial* parse, each passing an explicit `tsv_ts::TopLevelAs` policy. `{#await}` keeps it as an **assertion**: its separators are `then` / `catch`, no part of type syntax, so an `as` there is always TypeScript's and the parse ends on its own at the clause keyword. `{#each}` gives it away as the **host separator**, its separator *being* `as` — and so owes the assertion run a reader, `each_binding_separator`: it walks the chain one type at a time via `tsv_ts::parse_type_extent` and answers with an `EachHeadSplit` — the head's first `as` separates, a later one does, or the head has **no binding at all**. The walk stops at the first item that is not a type, which is the binding (a destructuring default is a pattern, so `{#each xs as A[] as { a = 1 }}` splits at the second `as`). ⚠️ The separator is the run's **LAST** keyword, and only when that keyword is `as` — not the last `as` anywhere in the run — because canonical unwinds the head by stripping its expression's *outermost* node and only when that node is a `TSAsExpression`. A `satisfies` therefore **cancels** every `as` before it: `{#each xs as A[] as item satisfies B}` is binding-less, `item` being a type, where keeping the last `as` handed `item` to the binding parser and rejected a head canonical accepts. A run that simply *ends* on `satisfies` (`{#each xs as A satisfies B}`) is the same answer, routed through the **same** tail as a head with no `as` at all, so the two spellings of "no binding" cannot drift — pinned by [blocks/each/type_assertion_satisfies_no_binding](../../tests/fixtures/svelte/blocks/each/type_assertion_satisfies_no_binding/). ⚠️ The policy names `as` **alone**, and the walk steps over **both** keywords: `satisfies` is an assertion no separator collides with, so it is a chain *link*. Gating the pair together in the *parse* rejected `{#each xs satisfies A[] as item}`, which canonical accepts; in the *walk*, recognizing only `as` would stop dead at the `satisfies` in `{#each xs as A satisfies B as item}` — a hazard a byte scan for the last ` as ` lacks, since it steps over an intervening `satisfies` without knowing it exists. ⚠️ The walk asks the **type grammar** on purpose and must not be "simplified" back into a bracket-depth byte scan: `<` / `>` are not a bracket pair, so an arrow's `>` in `A<() => string>` closes a depth nothing opened — a signed depth counter goes **negative** there and fails every later `depth == 0` test. (A mapped type's `[K in T as U]` is the same question one step subtler: a depth scan survives that inner `as` only because brackets nest it, where the type grammar knows it outright.) The printer strips the parens the authored form needs, so each of these would turn valid input into output tsv itself rejects — pinned by [blocks/each/type_assertion_function_type](../../tests/fixtures/svelte/blocks/each/type_assertion_function_type/), [blocks/each/type_assertion_satisfies](../../tests/fixtures/svelte/blocks/each/type_assertion_satisfies/) and [blocks/await/type_assertion](../../tests/fixtures/svelte/blocks/await/type_assertion/), whose `unformatted_parenthesized` variants are the round-trip half.
- **Dual schema for `<script>` conversion, chosen component-globally.** The writer emits acorn-typescript's wire when the component parses as TypeScript and vanilla acorn's otherwise (`EmbedWriter::vanilla_acorn`, set by `Ctx::embed` for each `<script>`'s `Program` and every expression island alike); the latter omits `importKind` / `exportKind = "value"` and always emits `attributes` on import/export declarations to match Svelte's parser output. The TS decision is **component-global** (`ast/convert/special.rs`'s `component_is_typescript`, mirroring Svelte's single `this.ts` flag): the first `<script>` in source order with a `lang` attribute decides it for *every* script, so a plain `<script>` beside a `lang="ts"` sibling still emits the acorn shape.
  ⚠️ The same fact governs the **expression islands**, which are not `<script>`s and so take it by a different route: `Ctx::embed` sets `vanilla_acorn: !component_is_ts` on the `EmbedWriter` every island funnels through, so a `{expr}` tag, an attribute or directive value, a `{@const}` and a `{#snippet}` body all carry vanilla acorn's expression quirks in a non-TS component (see `tsv_ts`'s `Ctx::vanilla_acorn`). Keeping the two routes fed from one field is load-bearing: an island reading a hardcoded `false` emits the acorn-typescript shape in a plain component — invisible while the `<script>` arm, the one anybody writes a wire fixture for, is right.
  ⚠️ `script_lang` reads the `lang` attribute's **raw** bytes, and is the only `lang` reader that does. Svelte's `this.ts` never builds an AST for the question — it runs a regex over the template text (`1-parse/index.js`, `lang=(["'])?([^"' >]+)`) and compares the captured bytes against `ts` — so `<script lang="&#116;s">` is not TypeScript to the wire. The *formatting* question is the other one: `internal::lang_attribute` (which body does the printer format, and as what) reads the DECODED value, like prettier's `getLangAttribute`, so it calls that same spelling `ts`. Two questions, two readers, on purpose — `tests/fixtures/svelte/attributes/lang_entity` holds both answers, so a "one definition" pass that merges them fails there instead of silently changing the wire.
  ⚠️ The flag shapes the WIRE only — it does not gate the PARSE. The parser has no document TS flag, so a plain `<script>` component's TypeScript (annotations in the script, a generic or typed `{#snippet}` head, a typed block binding, `as` / `satisfies` in an expression tag) parses in tsv where Svelte rejects at the first island. A tracked over-acceptance, one class across every TS-bearing position, pinned by `tests/fixtures/svelte/script/no_lang_typescript_svelte_prettier_divergence` and cataloged in `docs/conformance_svelte.md` §TypeScript-mode gating; closing it means the parser carrying the document flag, not a per-island check.
