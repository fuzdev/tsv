# tsv_css

> CSS parser and formatter — drop-in for Svelte's `parseCss` (AST), near-Prettier formatting

## Architecture Position

Depends on `tsv_lang` for shared primitives (spans, doc builder, comments, embedding config). Consumed by `tsv_svelte` for `<style>` block embedding, and by `tsv_cli` / `tsv_wasm` / `tsv_ffi` / `tsv_napi` for top-level CSS files.

**Sources of truth**: Svelte's `parseCss` defines the public AST shape; Prettier's `css` printer defines formatter output. Both are checked at fixture-validation time.

Standard `ast/lexer/parser/printer` crate layout — see [root CLAUDE.md §Project Structure](../../CLAUDE.md#project-structure) and [`tsv_lang/CLAUDE.md`](../tsv_lang/CLAUDE.md) for the cross-cutting types (`DocArena`, `Span`, `EmbedContext`). The internal-AST/wire-JSON split follows the workspace convention — see [root CLAUDE.md §AST Architecture](../../CLAUDE.md#ast-architecture-internal-ast-vs-wire-json).

## Public API

**Standalone** (top-level CSS files):

- `parse(source, arena: &'arena Bump) -> Result<CssStyleSheet<'arena>>` — parse a full CSS file. The internal AST is bump-arena-allocated (caller-owns-`Bump`); `CssStyleSheet<'arena>` borrows from it. Matches `tsv_ts`/`tsv_svelte`'s signature for the shared `lang_bindings!` macro + CLI/FFI/WASM callers.
- `format_str(source) -> Result<String>` — parse + `format` fused (applies the format path's `<CR>` fold ahead of the parse and formats through `format_folded_in`), the same twin every language crate has
- `format(&stylesheet, source) -> String` — format with default config; `format_in(&stylesheet, source, &DocArena)` is the same into a caller-provided doc arena (multi-file drivers reuse one via `DocArena::reset()`; `format` is the fresh-arena wrapper); `format_folded_in(&stylesheet, &FoldedSource, &DocArena)` is `format_in` for a caller that folded the source itself — identical output, the line verdict taken from the fold's pass (what the CLI, the bindings and `format_str` call)
- `convert_ast_json_bytes(&stylesheet, source) -> Vec<u8>` / `convert_ast_json_string(...) -> String` — the **sole emission path** (bytes: FFI/CLI non-pretty; string: the same bytes plus one output UTF-8 validation, for WASM `JSON.parse` / N-API): the writer (`ast/convert/write.rs`) walks the *internal* AST once and emits the wire JSON directly into a pre-sized buffer (`tsv_lang::estimated_json_capacity`), never materializing a typed public tree, fusing byte→char offset translation into the walk (each position through a `ByteToCharMap`; identity on ASCII). Matches Svelte's `parseCss()` JSON shape, reusing the raw-source reconstruction helpers in `ast/convert/mod.rs` (`strip_css_comments`, `split_declaration_svelte_compat`, `raw_selector_name`, …). Gated against the canonical `parseCss` `expected.json` and `corpus:compare:parse --multibyte-only`
- `convert_ast_json(&stylesheet, source) -> serde_json::Value` — a thin wrapper (`serde_json::from_slice(&convert_ast_json_bytes(...))`) for the `Value` consumers (the CLI's `--pretty`, the fixture gate); not an independent conversion
- `convert_ast_json_bytes_no_locations(...)` / `convert_ast_json_string_no_locations(...)` — the span-only variant, present only for parity with the TS/Svelte writers and the uniform `lang_bindings!` macro. `parseCss` emits **no** per-node `loc`, so the CSS wire is already offset-only — these are **exact aliases** of the plain functions (a documented no-op, not a distinct shape). The CLI/FFI/N-API/WASM `no-locations` surfaces therefore treat the option as inert for CSS — their generated CSS rows exist for macro uniformity and are byte-identical to the plain parse.

**Embedding** (used by `tsv_svelte` for `<style>` blocks):

- `parse_embedded(source, base_offset, arena: &'arena Bump) -> Result<CssStyleSheet<'arena>>` — same parser, but span positions are shifted by `base_offset` so they index into the parent Svelte file; `arena` is the host document's `Bump`, so the embedded CSS AST shares it
- `format_embedded_in(&stylesheet, source, line_table, EmbedContext, &DocArena)` — formats with `EmbedContext::base_indent_offset` so wrapped lines respect outer Svelte indentation, building the CSS doc nodes into the host's doc arena rather than a fresh per-block one (it still renders to an owned `String`, and the arena is not reset so the host's in-flight nodes stay valid). The Svelte host is its only caller, so there is no fresh-arena twin — an embedded stylesheet always has a host arena to lend
- `ast::convert::write_css_children` / `write_css_comments` — emit an embedded-`<style>` stylesheet's `children` and `comments` arrays (no `metadata`), the two adjacent keys `tsv_svelte`'s writer composes for the `<style>` element. The first returns the opaque `CssComments` run its walk gathered; the second spends it

**Diagnostics**: `debug_token_stream` (behind the `debug_lex` feature, off in production) — the raw-lexer dump `tsv_debug lex_diff` diffs across lexer implementations.

## Distinctives

- **No canonical CSS parser of our own** — fixture validation parses through Svelte's `parseCss`, not a standalone CSS reference parser. Practical implication: AST _shape_ questions go to Svelte, not the CSS Syntax spec directly. _Validity_ (what to accept/reject) is a different axis: the north star is CSS-spec compliance, the near-term enforced goal is parity with `parseCss`, and where Svelte over-accepts invalid CSS the spec wins (tsv rejects). The parser currently **hard-fails** on the first invalid construct; spec-style error recovery is a committed future goal. See [`../../docs/conformance_svelte.md`](../../docs/conformance_svelte.md) §CSS Parser Scope & Error Model.
- **A declaration's value is bounded by a byte scan, not a token walk — so `parser/decl_scan.rs` is a second reader of the lexer's grammar.** The value's text is re-parsed from source by `parser/value/` regardless, so driving the lexer across it merely to find the `;`/`}` terminator (and `!important`, and whether it holds a comment) produced a token stream nobody kept; the same is true of the `identifier :` lookahead that tells a declaration from a nested rule (`is_type_selector_with_pseudo`). Both now scan bytes. **The consequence a contributor must know: `decl_scan` mirrors the rules that decide a token's *extent*** — `url(…)` opacity and the identifier-token-start test that gates it (`5url(` is a `Dimension` plus a plain paren, so its interior is *not* url content), strings, comments, escapes, and what counts as whitespace. It reuses the lexer's own `IDENT_CONTINUE_LUT` and `is_ascii_css_whitespace` rather than re-spelling them. Two properties keep it honest: it **declines** (falling back to a real token walk) on anything it does not fully model — an escape, a non-ASCII byte at content position, an unterminated string/comment — so it never has to reproduce a lexer *error*; and a **debug-only assertion re-derives its every result from the token walk**, so a lexer change that outruns it fails the test suite instead of silently corrupting a parse. Change token extents in `lexer/` and read `decl_scan` in the same breath. The scan also reports *which* token terminates the value — a `;`, a `}`, or end-of-source — and `seat_at_terminator` makes that token current by constructing it, so the terminator is never lexed either; a second debug assertion re-lexes it and checks the construction.

  **One fact the scan carries is not about the value's extent at all: its top-level separator CLASS** (`value/scan.rs::is_value_separator` — a comma makes the value a comma list, an ASCII whitespace run a whitespace list, neither a single leaf). `ValueParser` would otherwise derive that in a fused pass of its own over the very same bytes, so the boundary walk records it in passing and `parse_classified` skips that pass — the third walk of one value's text becoming the second, worth ~1.9% of the instructions a CSS format retires. Three things a contributor must keep straight. **Its notion of "top level" is the value parser's, not this scan's**: parens and quotes alone, so `[]` and `{}` are ordinary content to it even though the terminator search tracks them. **It describes `[value_start, value_end)`, which the walk runs past** — the whitespace before an `!important` is neither the value's nor a separator, so both positions are filtered against `value_end`. And ⚠️ **it has a different oracle from every other fact here**: the token walk answers only for the extent, so the class is graded by a `debug_assert` against `fast_scan` itself — the function whose answer it replaces, re-proved by every CSS fixture — and is *withheld* (`None`, which means "cannot say", never "no separator") wherever the two cannot be shown to agree: a comment, or a url-token, whose interior this scan steps over whole while `fast_scan` walks it byte by byte.
- **The value span the scanner hands over is already trimmed, and `parse_value_from_source` is built around that.** Real stylesheets do not put a whitespace byte at either end of a declaration value, so `locate_value` settles the common case with two byte comparisons and never walks the text. The trim itself is `trim_start_css` / `trim_end_preserving_escape` — **CSS** whitespace only, and escape-aware (see the escape bullets below) — so the fast path's guard is exactly `u8::is_ascii_whitespace`, the same set that trim acts on, and the two arms cannot disagree. A boundary byte that is not ASCII whitespace settles it outright, **including a non-ASCII one**: no byte of a multi-byte char is ASCII whitespace, and the trim would not have touched that char anyway. ⚠️ The set is `u8::is_ascii_whitespace`, **not** `char::is_whitespace` (which would eat an NBSP that is value *content*) and **not** the lexer's `is_ascii_css_whitespace` (which adds the **vertical tab** to match `parseCss`) — the vertical tab is content to this trim, the same divergence that bites the selector combinators, in the other direction. That trim is also the gate on the separator class the bullet above describes: the class was derived over the span the boundary scan measured, so it is passed on only when the trim took nothing off either end — on the rare value where it did, the class is dropped and the fused pass runs as it always has. The trim arm is graded now (an escaped trailing space like `width: 50px\ ` reaches it), with the `value_span` unit tests beside the function standing under the rest.
- **A non-ASCII space is CSS value *content*, so every value-boundary trim is CSS-whitespace-only.** CSS whitespace is ASCII-only (CSS Syntax 3 §4.2), so a boundary NBSP (U+00A0), em space (U+2003), … is not whitespace — value content, not a separator; trimming it drops content, and for a **string** element it deletes the *whole* element — the trim narrows the leaf's text while its span still covers the space, so `build_string_doc` extracts a span no longer beginning with a quote and emits nothing (`'x',;` → `'x';`, non-idempotent). Every value-boundary trim therefore routes through the escape-aware `escapes::trim_start_css` / `trim_end_preserving_escape` (CSS whitespace only — the five ASCII chars, **excluding** U+000B): `ValueParser`'s element-boundary trims (`parse` fallback, `parse_single`, `trimmed_end`, `push_comma_segment`) and the printer's `normalize_css_whitespace` final trim. tsv keeps the glued element as one opaque token; prettier splits it into two (word + string) — a `_prettier_divergence` (`css/values/lists/comma_string_nonascii_space`). The **single** (non-list) value case (`content: <NBSP>'z'`, `quotes: 'a'<NBSP>`) is closed in two spots: `locate_value`'s declaration-value-boundary trim is CSS-whitespace-only too, and the fast-path settle keeps a non-ASCII boundary byte outright — plus the **lexer's** whitespace scan (`lexer/mod.rs`) no longer treats a non-ASCII identifier code point (U+00A0 and above — NBSP, em space, …) as whitespace, so a **leading** boundary space after the `:` opens the value's first token instead of being skipped as part of the colon→value gap (CSS whitespace is ASCII-only; tsv follows `parseCss` in treating every code point ≥ U+00A0 as an identifier code point — broader than the CSS Syntax ident set, which excludes NBSP/em space/U+3000 as look-alike whitespace). The leaf classifiers (`parse_color`/`parse_dimension`/`extract_function_parts`) were **not** the drop site — a NBSP-prefixed value routes to `Identifier`, printed verbatim from its span — so their internal trims were left as-is. Same design choice (`_prettier_divergence`, `css/values/boundary_nonascii_space`).
- **The same code point is a SEPARATOR at a selector boundary, and only position tells the two apart — so the parser owns that half, and every skip owes a matching restore.** `parseCss` resolves the disagreement by ORDER: `allow_whitespace()` is JS `\s` (so `<NBSP>`, every `Zs`, `<LS>`, `<PS>`, `<ZWNBSP>` separate tokens), while `read_identifier` takes every code point ≥ U+00A0 as content. tsv mirrors the **order**, not the class — the lexer keeps reading them as identifier content (the bullet above is why), and `CssParser::skip_boundary_whitespace` steps the run back off at each juncture an `allow_whitespace()` would have reached first; a juncture added to the parser with no matching claim in the printer is content loss, the worse of the two errors. The printer half — the two claims (`Printer::preserved_boundary_ws` backward from a name, `Printer::boundary_ws_in_gap` forward over a gap), why they partition rather than overlap, the `name_run_separator` family every gap with a NAME on its left asks (a run emitted flush against a name glues into it, `[a <NBSP>]` → the name `a<NBSP>`, its own fixed point so no gate sees it), the head/tail writers, and the one document-level precondition (`source_holds_boundary_ws`) every claim is gated on — lives in [`printer/boundary_ws.rs`](src/printer/boundary_ws.rs)'s module doc, and the conformance model in [conformance_svelte.md §Boundary whitespace](../../docs/conformance_svelte.md). Three traps worth restating: `allow_comment_or_whitespace` is a LOOP, so a site consuming a comment owes the skip on BOTH sides of it (`skip_boundary_whitespace_registering_comments`, and the boundary-aware `peek_past_boundary_whitespace` for lookaheads — a lookahead narrower than the skip it predicts is the same defect as one wider than the lexer's); the compound break and the descendant combinator land together or `&<NBSP>b` is a parse error; and a printer-facing `str::trim` agrees with this class on every member **but `<ZWNBSP>`**, so the head trims ask `is_boundary_whitespace`. Pinned by [tests/css_boundary_whitespace.rs](../../tests/css_boundary_whitespace.rs), which also carries the residue.
- **The "keep the glued run verbatim" promise has one sharp edge: a run that both *starts and ends* with a quote must not be re-quoted.** `parse_string_literal` classifies a value as a single `String` only when the opening quote's first **unescaped** matching close falls at the very end (`quoted_string_spans_all`, which asks `lexer::string_end` — the crate's one string-extent primitive, shared with the lexer and with `decl_scan`'s value boundary scan; don't spell that grammar a fourth time) — not on the naive "first char is a quote and last char is the matching quote," which is also true of a glued *run* like `'a'x'b'` (string + ident + string) whose first string closes at index 2. The naive test stripped the outer quotes and re-quoted the interior, turning the **delimiter** quotes into content (`content: 'a'x'b'` → `content: "a'x'b"`) — a content corruption invisible to `roundtrip_audit --gate` (the mangled output still reparses, just to a different AST) and to SAFETY only via a `'`↔`"` frequency shift. A run that isn't a complete single string falls through to `Identifier` and is emitted verbatim, matching the CSS tokenizer; an escaped interior quote (`'a\'b'`) still closes at the end, so a genuine single string is unaffected. `_prettier_divergence` (`css/values/glued_string_run`; prettier splits + normalizes the quote to `'a' x 'b'`).
- **A `Color::Named` prints exactly like the `Identifier` it would otherwise have been, so no corpus diff can see `is_named_color` get it wrong — the generated test is what stands under it.** `format_color_from_source` renders `Named` as a verbatim `source_span` of the value, which is byte-for-byte what `build_identifier_doc` emits for the same span; the wire writer never walks the `CssValue` tree at all (it re-slices the declaration's raw source). The classification is therefore invisible to formatted output, to the wire JSON, and to every gate built on either — a lookup that wrongly rejected `red` would sail through all of them. That is a property of *today's* consumers, not of the fact: **the classification is for the linter and LSP, which read it directly, and there a wrong answer is a wrong diagnostic.** So the vocabulary sets are declared with [`keyword_set::ascii_keyword_set!`](src/keyword_set.rs), which pairs each set with an exhaustive test grading the real lookup against a plain scan of the same list. Keep that test green; it is the only thing that can fail. The macro also puts a shape pre-filter in front of the hash (every keyword is a short run of pure lowercase ASCII letters, so length, first byte, and a first-letter→length bitmap retire `var`, `solid`, `--custom-property` and friends without touching `phf`) and derives the bitmap, the length bounds, **and** a compile-time assertion of the letters-only invariant from the keyword list itself — add a keyword that breaks it and the build fails rather than the filter silently going blind. Reach for the macro for any new CSS vocabulary; `NAMED_COLORS` and `CSS_UNITS` are the two today.
- **CSS escapes are positional Unicode** (`\XXXXXX` with an optional whitespace terminator), unlike `tsv_lang::escapes` (which handles JS-style quote swapping). They decode in two places by token kind: **string values** in `escapes.rs` (`decode_escape_sequences`, at parse time) and **identifiers** in `lexer/identifiers.rs` (`decode_unicode_escape`, at lex time). Identifier decoding is **lazy** — `read_identifier` materializes a decoded value only when a `\` escape is actually present; the no-escape common case allocates nothing and the identifier's text is recovered as a verbatim source slice (so the lexer's out-of-band decode — the reused `decode_scratch` buffer read via `decoded_str` — reports `None`, and the parser's `current_decoded` is `None` for plain identifiers). On the rare escape path the lexer decodes into `decode_scratch` (parked on the lexer, capacity reused across the file, no per-identifier `String`) and the parser copies the borrowed scratch into its AST arena at receipt (`decoded_to_arena`), mirroring `tsv_ts`'s lexer. `tsv_ts` has its own `lexer/escapes.rs` for the same reason; `tsv_svelte` has none and delegates.
- **An escape is opaque to every scanner, not just to the decoders.** Decoding (above) answers *what does this escape mean*; the separate, equally load-bearing question is *how far does it reach* — and a scanner that gets it wrong reads the escaped character as structure. `escapes.rs::escape_len` is the single definition: a **literal** escape is `\` + one code point, whose payload is content (CSS Syntax 3 §4.3.4; `\` + newline is not an escape at all); a **hex** escape is `\` + up to six hex digits + **one optional whitespace terminator that belongs to the escape** (§4.3.7 — so `\41 2px` is the single ident `A2px`, not `A` then `2px`). Every scanner that walks a value, selector, or prelude for *structure* steps over an escape whole via `escape_len` — the value cursor and its separator classifiers, the top-level and comma splitters, the whitespace-run collapser, the selector and pseudo printers, `url.rs`, and the at-rule prelude readers. Otherwise a `\` before a delimiter (space, comma, `)`, `;`) is mistaken for that delimiter, and the output either stops parsing (`50px\ ;` → `50px\;`, the `;` now escaped) or silently changes meaning (`.a\ , .b` → `.a\,`, one class named `a,` and the selector list gone). `trim_end_preserving_escape` / `trim_start_css` trim **CSS** whitespace only (§4.2 — five ASCII chars, deliberately *not* `str::trim`'s Unicode `White_Space`, since NBSP and U+3000 are value *content*) and hand back a literal escape's trailing payload rather than stranding its backslash. Prettier corrupts several of these shapes identically; tsv diverges because output that does not re-parse is never the defensible side (conformance_prettier_css.md §CSS: Values / §CSS: At-Rules).
- **A block comment is opaque to every value scanner for the same reason, and `consume comments` is why.** CSS Syntax 3 §4.3.2 runs it at the start of *consume a token* and it **returns nothing** — a comment produces no token at all, so its interior can never contribute a separator or a nesting change ("or up to an EOF code point" is also why an unterminated comment reaches end-of-input rather than erroring here). [`comments.rs`](src/comments.rs) is the single definition — the crate-root twin of `escapes.rs`, since "how far does this reach" is the same question for both constructs — and **every** reader of a comment's extent goes through it: the three value scanners that share `is_value_structural` (`ValueParser::fast_scan`, `ValueCursor::consume_until`, `classify_separators`), the printer's whitespace normalizers and splitters, the declaration tail, the wire writer's comment strip, and the `:nth-*()` An+B reader on both sides — recognition (`nth_arg_is_anb`, whose `skip_anb_ws_and_comments` runs at the terminator **and** at both gaps of the term's own tail) and respacing (`normalize_an_plus_b`). The selector side is the same lesson one construct over, and it took three sweeps to finish: the An+B term (the tell was that the *terminator* already saw through a comment while the tail did not — so a split term rejected outright, or, where it had a type-selector reading (`n`, `-n`), silently mis-parsed as a selector list), then every interior gap of an attribute selector, then the two productions whose components admit a comment but **not** a `<whitespace-token>` — a `<wq-name>`'s and an `<attr-matcher>`'s (see the gap-comment bullet below). The one position left is the column combinator, where tsv lexes `||` as a single token; docs/checklist_css.md §Not Parsed carries the argument. It had been re-spelled eight times (as `find("*/")`, as a `skip_block_comment` byte loop, and as three `in_comment` state machines), which is how the value scanners came to disagree with the printer in the first place. `comment_end` answers §4.3.2's end-of-input rule for a *structure* scanner; `comment_end_checked` returns `Option` for the two callers that must tell an unterminated comment apart (the wire writer keeps it verbatim, the property-name reconstructor bails). ⚠️ **`skip_trivia_forward` — the module's one composition with whitespace, for a scanner walking an ALREADY-TOKENIZED region to a token it has no span for (the declaration scanner's value bounds, the printer's attribute-selector rebuild) — takes the *lexer's* whitespace set, not `escapes`'s.** The two differ by the vertical tab (the lexer carries it, for `parseCss` parity), and the set a post-tokenization scan uses must be the one the parser actually skipped: narrowing it stops the scan ON a vertical tab and mislocates the token behind it, which moved a comment across the matcher (`[attr⇥/* c */='value']` → `[attr= /* c */ 'value']`, silently and idempotently). Two spellings of this scan is how that bug got in; there is one now. Getting this wrong is worse than a mis-split, because nothing downstream can recover: the element's two halves come back as ordinary re-tokenized leaves, so the comment's *interior* is rewritten — whitespace runs collapsed, the body broken at its own comma, numbers and hex normalized inside it (`/* keep   this,  #FFF  .5px */` → `/* keep this,⏎#fff 0.5px */`). Every such output was a **fixed point**, so F1, the ledger, the fuzzer, roundtrip and authoring were all structurally blind to it and the corpus was green by absence. Fixture `css/values/lists/comma_comment_interior`; the interior contract is conformance_prettier_css.md §CSS: Comments.
- ⚠️ **The leaf's function detector is a FOURTH paren reader, and it does *not* share the value scanners' model.** `value/mod.rs::extract_function_parts` decides whether a leaf value is `name(args)` by counting `(`/`)` over raw bytes — **quote-blind and escape-blind**, unlike `ValueParser::fast_scan` / `ValueCursor::consume_until` / `classify_separators`, which track quote state and step an escape whole. So a paren that is *content* still moves its counter: `f("(", …)`, `f(")", …)` and `f(a\(b, …)` never balance, the value falls through to `CssValue::Identifier`, and the printer emits it verbatim from its span — which silently switches off **every** value normalization for that declaration. `f("(",.10)` keeps `"("` double-quoted and `.10` unnormalized; `linear-gradient("(",…,#FFF)` additionally keeps `#FFF` uppercase and does not break its argument list, printing past the print width. The identical value with `"x"` in place of `"("` normalizes all of them. Two things follow. **The mangled output is its own fixed point**, so idempotence, the ledger, the fuzzer, roundtrip and authoring are all structurally blind to it, and so is the wire (a declaration value crosses it as text) — only a prettier `compare` finds it. And ⚠️ **the matching paren's offset must not be *donated* from `fast_scan`**, however redundant the second walk over the same bytes looks: the two scanners answer differently by construction, so aligning them is a **behaviour** change that owes a fixture, not a shared-walk optimization. (The caller's cheap refusal on the value's *last* byte is a different question and is not implicated — it only ever refuses, following the same cannot-match pre-filter rule as [`keyword_set`](src/keyword_set.rs).)
- ⚠️ **The lexer's escape terminator is a different rule with a different oracle.** `lexer/identifiers.rs::decode_unicode_escape` terminates a hex escape on **JS `\s`** (`tsv_lang::is_js_whitespace`), not CSS whitespace, because its oracle is `parseCss` — Svelte's `read_identifier` matches the terminator with a JS `\s` regex. Nor is it Rust's `char::is_whitespace`, which the two differ from in both directions (U+FEFF, U+0085); the wire writer's `raw_selector_name` is the second reader of the same rule and asks the same class. That is not the same question as the printer's trim (§4.2, ASCII), and unifying the two moves the **AST**: narrowing the lexer splits one ident into two selectors and truncates an at-rule name. Lexer boundaries become wire spans; keep the two rules apart.
- **`convert` feature flag** (default-on) — gates the `ast::convert` layer (the writer) plus the `serde_json` dep. Disabled in the `@fuzdev/tsv_format_wasm` build, which only needs to format. See [`tsv_wasm/CLAUDE.md`](../tsv_wasm/CLAUDE.md).
- **Comments live on `CssStyleSheet`**, not on nodes. Value comments (e.g., `color: /* x */ red;`) are detected by scanning source text directly in `printer/mod.rs::has_value_comments_in_decl`, since they're not stored as `Comment` entries.
- **A declaration's text seams answer their common case on BYTES before any char machinery runs.** Every declaration passes through four small text questions — does it hold a value comment (`has_value_comments_in_decl`), is there boundary whitespace to trim off the property part (`trim_property_part`, and `extract_property_name`'s `ends_with` beside it), does the name carry an uppercase byte (`lowercase_property_name`), and, for a string value, the quote swap (`tsv_lang::escapes::swap_quote_escaping_into`) — and on real stylesheets nearly every one of them answers "no" or "nothing to do". Each is spelled as an inline gate over an outlined body: the comment question reads the parser's `has_block_comment` flag inline and calls its scan only past it; the trim tests the part's first and last byte against the six ASCII members both whitespace classes share (`byte_may_be_boundary_whitespace` — an ASCII byte outside them is a whole char nothing trims, a non-ASCII byte is a question for the predicate) and reaches `str::trim_matches` only then; the case test is `tsv_lang::swar::has_ascii_uppercase`, a word at a time; the swap hops byte runs on `next_byte_of` and writes into the literal's own buffer. ⚠️ A `str` method taking a `char` predicate — `trim_matches`, `ends_with`, `trim` — constructs a `MultiCharEqSearcher` that decodes a char from an end before it can reject, and its construction, not its walk, is the cost a per-declaration site pays; gate it, never fold the gate back into the predicate. The `debug_assert` in `trim_property_part` holds the gate to the searcher's answer under the fixture suite.
- **Three of the writer's emitters end in a STAGED RUN, and which three is a measured boundary rather than an unfinished migration.** Every CSS wire node closes with the same burst — `,"start":` N `,"end":` M, then `}` or a constant `metadata` — and `write_rule` / `write_relative_selector` / `write_named_selector` assemble theirs in `JsonWriter`'s scratch and append it once instead of five times (two of the five being `inline(never)` integer calls that spill the buffer's pointer/length/capacity at each surrounding append). ⚠️ **The node *head* bursts have the identical shape and staging them is a LOSS** — a staged run copies its static fragments twice, once into the scratch and once through the flush, so the trade is *appends removed* against *static bytes in the run*, and a head carries ~50 static bytes to a tail's ~17. Staging all seven bursts removes 2.6× more instructions than staging the three and runs ~1.05 points slower. `convert/write.rs`'s module doc §Staged runs carries the numbers and the two refuted variants; **grade any change there on `cycles`/wall, never on instructions.**
- ⚠️ **The wire's `comments` array is a fourth reading, and the writer rebuilds it — riding the emission walk, not a second one.** `parseCss` hangs a flat `CSSComment[]` off both stylesheet roots, in source order, with a `position` offset on any comment it lifted out of a declaration `value` or an at-rule `prelude`. tsv's internal AST holds the same comments in **three disjoint places**, each shaped for a printer need — detached on `CssStyleSheet.comments`, in-block as `CssBlockChild::Comment`, and (for value/prelude comments) nowhere at all — so `convert/write.rs`'s `write_children` gathers all three as it emits and merges, handing the run back in an opaque `CssComments` the caller spends on the sibling `comments` key. **Riding the emit walk is a correctness argument first**: the positioned reading then comes from the **same** `strip_css_comments_collecting` call the emitted `value` comes from, where a separate scan would drift the offsets from the string they index. It is also the cheaper shape, but only just — a standalone second walk measures ~3.4% of the wire-write phase, while fusing recovers ~1% of it (the sort/dedupe and the at-rule prelude scan stay either way), which is barely above this path's noise floor. Don't re-separate them for clarity; don't expect a perf win from tightening them further. Two more things to keep in mind when touching either side: a prelude comment arrives twice — registered *and* stripped — so the merge dedupes on `start`, keeping the positioned one; and a `position` is a **UTF-16** index into that string, measured before its trailing trim, so it can point one past the end (`color: red /* c */`).
- ⚠️ **An at-rule's prelude region is bounded by the PARSER, never by a byte scan.** Svelte reads a prelude with `read_value` from just after the name to the `{`/`;` terminator, and that reader is quote- and `url()`-aware — so a `;`/`}` inside `@import url("a;b.css") /* c */;` is not a terminator to it. `collect_prelude_comments` therefore takes the block's `{` (`block.span.start`) or the blockless form's required `;` (`span.end - 1`) rather than reusing `scan_to_terminator`, whose flat byte walk is only sound on the **post-value tail** it is documented for (whitespace, comments, `!important`). Scanning the prelude with it silently truncated the region and dropped `position` from every comment past the string — invisible to the whole CSS fixture set, because none of them put a terminator byte inside a prelude string. Fixture [`css/at_rules/import_prelude_terminator_in_string`](../../tests/fixtures/css/at_rules/import_prelude_terminator_in_string/).
- **A comment run that *opens* a value is between-material, not value content.** postcss keeps everything between a declaration's property and its value in `raws.between`, so a comment right after the colon is outside the value entirely — which is why it neither counts toward a comma list's break decision nor indents with the first element, but stays on the colon's line (`font-family: /* c */⏎\tcolor 0.3s,⏎\tb;`). tsv keeps such a comment *inside* the value span (the wire `value` is source-sliced by the writer, so the span is a printer-internal boundary) and recovers the split at print time via `leading_value_comment_run`. `MultilinePlan` / `multiline_plan` is where the whole layout is decided **once** — its existence *is* the break decision, and it carries the run to hoist plus the element-0 members that print beneath it — because a split between the routing question and the emission is what reintroduces the glued-vs-spaced 2-cycle. The break is `comma_list_should_break`, prettier's `shouldBreakList` ("some element holds more than one node" — its `flattenGroups` collapses the single-node ones), and it is **purely structural**: a source newline after the colon does not break the list — honoring it would make the output authoring-dependent on a shape nothing else in CSS honors (`margin:⏎1px 2px`, `color:⏎red`, `translate(⏎1px,⏎2px)` all collapse). `value_node_count` is the node counter, and it counts a **comment as a node**, which is what makes the glued (`x,/* c */y`) and spaced (`x, /* c */ y`) authorings converge on one fixed point.
- ⚠️ **The hoist cuts element 0 at a MEMBER boundary, so the parser has to put one there — `content_start` is a byte offset and the drop is member-granular.** A comment glued to the token after it (`/* c */color`) is one member, and cutting a byte offset out of a member is not something a member-drop can do: dropping it loses `color`, keeping it prints the comment twice. Both were live — the drop was a **fixed point** (F1, roundtrip, fabrication and the corpus all blind, the same structural blindness as the comment-opacity bug above), and the double-print was invisible to the print-once ledger because CSS value comments are not `Comment` entries. The close is to make the AST agree with `value_node_count`: `split_top_level`'s `comment_is_element` (whitespace split only) makes **a top-level comment boundary an element boundary on both sides**, so a comment run is always its own member — `consume_until`'s `stop_at_comment` ends the element before one, and the loop claims the run after it. `classify_separators` reports that boundary as a **separator**, which is what routes such a value to the split at all: nothing else is a separator, so a value whose *only* one is a glued comment (`0.3s/* c */5px`) would otherwise classify as separator-less and fuse into a single `Dimension` leaf. Then `content_members` **verifies** the boundary and returns `None` without it, so a shape that ever arrives fused declines the hoist rather than losing content. The fixture family's `unformatted_*` variants glue after `*/` for exactly this reason — that authoring axis is what the bug hid behind.
- **A leaf printer that emits from its span is blind to a comment glued to it, so the split above is also what normalizes one.** `build_identifier_doc` runs `normalize_css_whitespace` (which spaces both sides of a `/* … */`), but `build_dimension_doc` / `build_color_doc` / `build_string_doc` emit their own reconstructed text and never do. That was invisible for all but one leaf kind — a glued `#fff/* c */` or `f(x)/* c */` fails its classifier and falls through to `Identifier`, which normalizes — while `0.3s/* c */` **parsed as a `Dimension`** (the number/unit split tolerates trailing text, so the comment rode in the unit) and printed glued, alone among the leaf kinds. Splitting at the comment boundary re-classifies each side on its own, so every leaf kind reaches its normalizer; it also recovers the quote normalization a glued `"s"/* c */` lost by falling through to `Identifier` (`'s'`, not `"s"`). Prefer fixing this class at the split, not by adding a whitespace pass to a leaf printer: dimensions are the densest construct in a stylesheet and that pass would be a per-dimension byte scan for a case that is nearly never there.
- **A condition part is normalized text, except where the grammar says the tokens are a selector.** `@supports`/`@container` preludes parse into `ConditionPart`s whose content the parser re-emits token by token with the spacing the grammar calls for — which is why the declaration rules there (the space after a value `:`, the spacing around a boolean operator) have to know exactly where they apply. They don't apply inside a function's argument: `<supports-selector-fn> = selector( <complex-selector> )` (css-conditional-4), so `parse_condition_query` hands that argument to `parse_complex_selector_list` and the part carries it as a `ConditionSegment::Selectors`, which the printer renders with `build_complex_selector_doc` — the same printer a rule's own selector uses, so one selector formats one way in both positions. Spacing it as a declaration instead does not merely look wrong: `selector(div:hover)` becomes `selector(div: hover)`, a selector that no longer parses, and the condition flips false. Two invariants hold this together. **The trial parse must rewind on failure** (`CssParser::rewind_to`, which truncates `comments` as well as seeking, since a comment registered by the abandoned attempt would print twice) — an argument that isn't a selector is a `<general-enclosed>`, opaque by grammar, and it falls back to the ordinary token loop, where `general_enclosed_selector` still suppresses the declaration rules — **and the comment's padding, on both of its sides** (`pads_comment`, read by the before-pad and the after-pad alike): the tokens are still selector-shaped, so a space this arm inserts turns `selector([a=1.5]/* c */.b)` into a descendant `[a=1.5] .b`, and a bound only one side honors inserts that space from the other. A `<general-enclosed>` function that is *not* `selector()` (`foo(a/* c */b)`) has no such grammar to lose and pads normally, matching prettier both ways. And **a boolean keyword is an operator only where the grammar can start one** (`boolean_operator_position`: at a condition's start, or against a parenthesis) — otherwise an identifier that merely spells `and` gets spaced apart, splitting a value (`(font-family: and)`) or a class (`selector(.and)`). Both predicates read the previous **significant** token, with whitespace *and comments* transparent. Every spacing rule that *pads* a token — the boolean operator's space, the comment's — asks one shared question first (`needs_separator_before`), because a rule that decides on its own whether it is glued will stack with the rule that ran before it: a comment before a connector took the comment's after-space **and** the operator's before-space, `/* c */  and`. The predicate is the buffer's `trailing_spaces` count, not the previous token kind, so it also sees the space a value `:` just emitted; the one separated position a count can't show is an opening paren, which wants no separator at all.
- **`@import`'s `supports()` argument is that same condition, not a second grammar.** `supports( <supports-condition> | <declaration> )` (css-cascade-5), so `parse_function_value` hands it to `parse_condition_part` and the value rides a `CssValue::SupportsCondition` that prints through `build_condition_query_doc` — one condition, one form, in `@supports` and `@import` alike (the colon spacing, the number/hex/quote normalization, the `selector()` routing, and the cataloged divergences all follow the position rather than being re-derived). What makes that a *reuse* instead of a port: the parser is seated on the function's `(` rather than past it, so **the function's own parentheses are the condition part's**, and the bare-`<declaration>` alternative — which `<supports-condition>` has no production for — is just a parenthesized part. Exactly one part can come of that, which is also what bounds the read to the function: the query loop never runs, so a trailing `supports(a) screen` can't be swallowed as a second part.
- **Gap comments are printable only if the parser registers them.** The printer reconstructs selector/prelude gaps from the AST and re-emits comments via `comments_to_emit_in_range` lookups (CSS sets `owned_by_node` unconditionally false, so its emit-axis gates are safe by construction), so any gap whose parse path skips with the dropping `skip_whitespace_and_comments` loses them silently (a block-comment content-loss class `swallow_audit` cannot see — it audits `//` line-comment swallows — and the print-once ledger cannot either: a never-registered comment never existed as far as it knows; the comment census — `deno task census:audit`, [docs/audits.md](../../docs/audits.md) — is the standing guard, lexing both raw sides independently of registration). Use `skip_whitespace_registering_comments` in printer-reconstructed gaps; the dropping variant is safe only where the range re-emits verbatim or another mechanism recovers the comment (the declaration property→colon gap). Selector lists, `:nth-*()`/`::slotted()`/`::part()` args, the `:dir()`/`:lang()`/`::highlight()` and unrecognized functional pseudo-class selector args, and structured at-rule preludes all register today. **Combinator-boundary comments** (a comment in a gap between compounds or glued between compound members — `div /* c */ p`, `.a/* c */.b`) also register. `build_complex_selector_doc` detects one via `complex_has_boundary_comment` and routes to `build_complex_selector_doc_with_comments`, which re-emits the selector inline with each gap comment interleaved at its authored position and the surrounding gap whitespace **normalized to a single space** — the same rule as the other selector-comment positions (`:is()`/`:nth-*()`/`::slotted()` args), and unlike prettier, which freezes the source whitespace. A glued compound-internal comment (`.a/* c */.b`) is emitted glued (no spaces) so the compound never reads as a descendant `.a .b`.

  **The attribute selector is the one gap family the printer REBUILDS rather than routes**, so nothing else can carry its comments: `build_attribute_selector_text` reconstructs `[ns|name op 'value' flags]` from the AST's parts. One probe splits the work — with no comment anywhere in the selector's span it takes a plain concatenation, and `build_commented_attribute_selector_text` (every gap scan included) never runs. The commented build locates the parts it has no span for (the `|`, the matcher, the case flag) by stepping over trivia with the shared `skip_trivia_forward` (via `skip_gap_trivia`, its `u32`-span face), which is comment-aware so no scan reads a comment's content as structure (`[svg/* | */|attr]`). Two spacings apply, and which one a gap takes is a grammar fact rather than a taste call (`AttributeGap`): selectors-4 forbids white space "between **any** of the components of a `<wq-name>`" and "between the components of an `<attr-matcher>`", so those gaps stay **glued** — the `.a/* c */.b` rule again — while every other juncture is bounded by the brackets, takes a space safely, and pads the comment off its neighbours (glued only to `[` and `]`). Only the gap holding the comment changes; every other keeps its canonical empty spelling, which is what makes the output a fixed point. The **parser** side mirrors the split: the spacing-safe gaps use `skip_whitespace_registering_comments`, the whitespace-forbidden ones `register_and_skip_comments`, so a space there still rejects — with one twist, since `[svg |attr]` (a `<wq-name>`, forbidden) and `[attr |= 'v']` (a name→`<attr-matcher>` gap, allowed) share a position and are told apart only by the token past the `|`: whitespace is skipped there and *reported*, and the `<wq-name>` reading rejects retroactively. The bare type-selector spelling of the same `<wq-name>` rule needs no interleaving at all — `SimpleSelector::Type`/`Universal` emit their span verbatim, so the comment rides out inside the slice (declared to the ledger with `record_verbatim_range`). Prettier freezes → `_prettier_divergence` (conformance_prettier_css.md §CSS: Comments); parseCss rejects these entirely (`css_expected_identifier`) → also `_svelte_divergence` (conformance_svelte.md §CSS Corrections).

  ⚠️ **Nothing locates a `<wq-name>`'s separator by scanning for `|`.** The prefix is an `<ident-token>`, so an escape can put a `|` *inside* it (`[a\|b|attr]`, `a\|b|rect`) — a scan for the first one reads the escape as the separator and the rest of the prefix as the name, and silently emits a **different selector** (from the attribute printer, one that does not parse). `SimpleSelector::Type`/`Universal`/`Attribute` therefore carry `namespace_span`, the prefix's leading token, and every reader steps *forward* from its end: the separator is the next non-trivia byte, the name the one after that (the printer via `skip_gap_trivia`, the wire via `wq_name_start`). The same step is what carries both past a separator comment, so one mechanism answers both. The printer then emits the prefix **verbatim** — the wire's `namespace` is half-decoded by `raw_selector_name` like every other selector name, and re-emitting *that* turns `a\|b` into `a|b`, a prefix whose two `|` re-parse as a namespace plus a `|=` matcher.
- **Consecutive combinators are preserved, so `RelativeSelector.selectors` can be empty.** A run of combinators with no compound between them (`+ ~ .d`, `> > .a`, glued `>>.a`) parses into one **empty-compound `RelativeSelector`** per anchorless combinator (`combinator: Some(_)`, `selectors: &[]`). tsv's internal AST deliberately diverges from `parseCss` here — `parseCss` collapses the run (its `read_selector` never emits an empty relative selector, dropping all but the last), a lossy recovery tsv declines to keep the authored combinators for the future diagnostics layer (a `_svelte_prettier_divergence`; see [`../../docs/conformance_svelte.md`](../../docs/conformance_svelte.md) §CSS Corrections). Both selector printer paths (`build_complex_selector_doc` and the comment-bearing `build_complex_selector_doc_with_comments`) special-case an empty compound — the combinator emits with no trailing space (the next relative selector's separator supplies it) — so **any code walking `RelativeSelector.selectors` must not assume it is non-empty** (a `selectors[0]` index panics on these; the trailing-combinator guard in `parse_complex_selector` keeps the run from ever ending on an empty one).
- **A blank line is a POSITIONAL question here, and the shared line-break table cannot answer it.** The two "is there whitespace between these positions" helpers on `Printer` look alike and are not: `is_same_line` is a **range count** over `line_breaks` (the shared ECMAScript terminator class), while `has_blank_line_between` is prettier's `isNextLineEmpty` transcribed — skip `,; \t`, take **one** terminator, skip `" \t"`, require a second — so it asks about *the first two things the walk meets*, over a class that stops at `<LF>`/`<CR>` (excluding `<LS>`/`<PS>`, which the printer preserves into its own output and would otherwise re-count as a fabricated blank line on the next pass). A count answers `true` where the positional walk stops early, so the table **accepts strictly more**; being a superset it can refuse nothing the walk accepts, which is why consulting it as a pre-filter is not a fast path but a `partition_point` over a whole-file table bought ahead of a walk that reads a handful of bytes. The relation is held by a `debug_assert`, so the fixture suite re-proves it rather than the argument living only in prose. ⚠️ **Do not "optimize" this by reintroducing the table**, and do not assume the two helpers are interchangeable — `is_same_line` keeps the wider class deliberately, because there the conservative reading is the safe one.
- **Printer is organized by CSS spec hierarchy** (`rules.rs` → `declarations.rs` → `values.rs`, plus `atrules.rs` and `selectors.rs`), not by node kind. `selectors.rs` is shared between rules and at-rules, and rule and at-rule block bodies iterate their children through one shared `print_css_block_children` routine in `mod.rs` (blank-line preservation, inline trailing comments, format-ignore — one place, no drift); the `value_normalization/` module normalizes value text to prettier's form (numbers, hex colors, whitespace). Its number/dimension normalizers return `Cow`, borrowing an already-canonical value (`10px`, `0.5rem`) unchanged, so `build_dimension_doc` emits it as a zero-allocation verbatim `source_span` — which is why the CSS printer renders through a source-resolved entry point (passing the document `source` so `DocText::SourceSpan` slices resolve at print time, the same seam every printer uses).
