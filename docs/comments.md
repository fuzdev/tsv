# Comment Handling: The Detached Model

> The full doctrine for tsv's comment model — the `Comment` type, ownership, the three lookup axes, the hazards, and the leading-comment emitter rules. The always-loaded summary lives in [CLAUDE.md §Comment Handling](../CLAUDE.md#comment-handling-detached-model); read **this** doc before changing comment handling in any printer. The lookup API itself is documented in [`crates/tsv_lang/CLAUDE.md` §Comment Utilities](../crates/tsv_lang/CLAUDE.md#comment-utilities).

Comments are stored **separately from AST nodes** in a flat `Comment` array at the root level (`Program.comments` — an arena slice — plus `CssStyleSheet.comments` and `Root.comments`, which are `Vec`s). The printer finds comments via O(log n) binary search on span positions.

**Core type** (`tsv_lang/src/comment.rs`):

```rust
pub struct Comment {
    pub content_span: Span,        // content WITHOUT delimiters; text via content(source)
    pub is_block: bool,
    pub multiline: bool,           // content contains '\n' (precomputed; block-only in practice)
    pub span: Span,                // full comment span, delimiters included
    pub emit_character_field: bool, // Serializer hint: include `character` in JSON loc
    pub bump_pattern_columns: bool, // Serializer hint: +1 loc columns (Svelte block-pattern parse)
    pub owned_by_node: bool,        // Printed by the node it's bound to, not by the enclosing gap
}
```

## Owned comments — the one crack in the detached model

A comment that is *bound to the token after it* can't be located positionally at print time, because a paren the printer synthesizes around an enclosing expression lands between the two and re-binds it. **Every glued block comment is owned** (`owned_by_node`, set by the parser): the position is an authoring choice that binds the comment to the operand it leads, so the operand's own doc prints it and no synthesized paren can land between them. There is no content sniff — a plain `/* c */` and a bundler annotation `/* @__PURE__ */` bind their token identically. Two shapes are worth naming:

- the **glued block comment** (the general case) — printed by the innermost node its token begins (`printer/comments/owned.rs`, via `build_expression_doc`'s `prepend_owned_leading_comment`). ⚠️ *Innermost* is shorthand for *prints first*, and hazard 1 below carries the one node where the two part. Covers an ordinary leading comment and a **bundler annotation** alike (`/* @__PURE__ */` and friends mark the call *after* them as side-effect-free; a paren between the two would leave the annotation leading a paren, so the marked call is no longer droppable). No AST node is involved.
- the **JSDoc cast** — `/** @type {T} */` plus the `(` it glues to **are** the cast, so the comment is handed to the `JsdocCast` node, which prints it. `is_jsdoc_type_cast_comment` is the **only** remaining content sniff, and it governs the cast's **paren-retention** (building the `JsdocCast`), *not* ownership — ownership flows to a cast the same as to any other glued comment.

An owned comment is always a **block** comment (`owned ⇒ is_block`), and always **glued** to its token — a comment the author left on its own line leads the *line*, not the token. The one exception is the JSDoc cast, whose comment may sit a newline above its `(` and still be the cast; that difference is load-bearing and named at the shared scan (`source_scan::CommentGlue`).

Because a cast's comment may carry that authored break, the cast's own emitter (`build_jsdoc_cast_doc`) owes the comment→`(` separator an answer, and the enclosing gap gets to override the default (hardline when own-line, space when glued, soft `line` otherwise) with a **rule**. Two gap categories do, via span-keyed printer cells the gap sets before the value is built:

- a **value gap that can hang** (`mark_jsdoc_cast_value_gap` — the declarator/assignment/object-value/binding-default/enum/arrow-body `=`/`:` family): the soft-`line` arm reflows to a space (an unforced break in value position is layout, not authoring — [conformance_prettier.md §Authored breaks in value position](./conformance_prettier.md#authored-breaks-in-value-position)); the own-line arm keeps its hardline because the gap **hangs** the value, the operator ending its line.
- a **value gap that CANNOT hang** (`mark_jsdoc_cast_cannot_hang_gap` / `with_jsdoc_cast_cannot_hang_gap` — a Svelte braced head via `EmbedContext::jsdoc_cast_cannot_hang`, and a computed key's `[`→key gap): no operator line exists to end, so the hardline would strand the `(` at the host's own column, an authoring with no fixed point. **Every** arm reflows to a space, own-line included. The entry form marks the value's *left-spine* cast once per expression root; the interior form (computed keys) must **save/restore** around its subtree build, or a `conditional_group` candidate rebuilding an earlier sibling reads the clobbered cell. See [conformance_prettier_svelte.md §Svelte: Own-line JSDoc cast at a braced head](./conformance_prettier_svelte.md#svelte-own-line-jsdoc-cast-at-a-braced-head) and the computed-key entry in [conformance_prettier_ts_comments.md §Comment relocation](./conformance_prettier_ts_comments.md#comment-relocation).

## Ownership is about who PRINTS, never whether a comment EXISTS

That one sentence is the whole rule, and every bug in this class has been a violation of it. A comment can be asked about along exactly **three** axes, and the lookup API (`tsv_lang::comment`) makes the caller name which:

| axis | question | owned comments | who asks |
| --- | --- | --- | --- |
| **to emit** | "which comments must *I* print here?" | **skipped** | gap emitters (~400 sites) |
| **on page** | "does any comment OCCUPY THE PAGE here?" | **counted** | layout gates — break / expand / hug / paren / fast-path |
| **in source** | "what comment BYTES are physically here?" | **counted** | cursors — blank-line scans, offsets, `prev_end` |

`comments_to_emit_in_range` / `has_comments_to_emit_in_range` / `comments_to_emit_after` · `comments_on_page_in_range` / `has_comments_on_page_in_range` / `has_multiline_block_comments_on_page_in_range` · `comments_in_source_range` / `comments_in_source_after`. Every name states its axis, so a miswire reads as a category error at the call site rather than as plausible code. Two facts about the shape:

- **Three questions, but only two membership sets.** *On page* and *in source* both count an owned comment (it is in the output, and its bytes are in the file); only *to emit* skips it. The two names exist because the *question* differs — and naming the wrong one is the bug.
- `has_line_comments_in_range` carries **no** axis, provably: `owned ⇒ is_block`, so no line comment is ever owned and skip ≡ count. If that ever changes, it must grow an axis.

Two corollaries worth naming, because each was a whole family of bugs:

- A **zero-comment fast gate** (`let has_comments = …` guarding a whole builder) is an **on-page** question. It short-circuits the layout gates it guards, so an emit-keyed one makes every one of them blind.
- A **blank-line scan** is an **in-source** question. `has_blank_line_between*` is a raw newline count — it cannot tell a comment's own newlines from an author's blank line, so the scan must step over every comment in the gap (`blank_scan_start` / `blank_scan_end`), not just the ones this caller emits. ⚠️ **The gap that ends at an EXPRESSION start is where this bites**, because that is exactly where an owned comment can sit: the header→body tail for a brace-less body, a binary operator→operand gap, a ternary `?`→branch gap. Each fabricated a blank from the owned comment's own interior newlines, each fabrication was its own fixed point, and the ternary's also fed the break gate and dropped the branch onto its own line. Pinned with a null control per gap by `syntax/comments/owned_comment_interior_blank`.

## The five hazards

⚠️ All five have bitten. Four are ownership hazards — ownership is a sharp tool: it takes a comment out of the positional model, so every consumer of that model has to be re-examined. Only the fourth is the positional model's own: a builder that never asks.

1. **An owned comment nothing prints is a DROPPED comment.** Ownership assumes the owning node prints it, so any builder that does **not** route the node through `build_expression_doc` must claim the comment on its own seam. Two shapes do this, for the same reason:

   - **Reassembly** — a builder that rebuilds a node from parts (`build_arrow_sig_doc`, every call-argument state; `build_arrow_chain_doc`'s inner arrows; `build_assignment_pattern_doc`'s object-pattern left; `build_test_callee_flat_doc`, the flat test-call layout's break-free callee) claims via `prepend_owned_leading_comment_at`. **Printing a node from its own SOURCE BYTES is the same shape**: `build_directive_doc` emits a directive through `format_directive` — an exact code-unit sequence the string-literal printer must not re-quote — so it never reaches `build_expression_doc` either, and `/* c */ 'use strict';` dropped the comment until it claimed one. That seam's rustdoc carries the caller list; keep the two in step. ⚠️ **A reassembled node loses more than its comment**, and the comment is only the half a comment gate can see: the test-call callee also skipped the parens, the removed-paren comments and the **type arguments** the general path wraps a callee in, so `it<T>('a', fn)` printed `it('a', fn)` — silent code loss beside the drop. When one of these builders turns up, ask what ELSE its node's normal path prints.
   - **Replacement** — a **format-ignore freeze** substitutes a verbatim source slice for the node's whole doc, and the owned comment sits *outside* that slice's span, so widening the slice is not the fix; the claim is. `tsv_ts::build_frozen_node_doc` and `tsv_svelte::build_frozen_node_doc` are slice + claim in one call precisely so a freeze site cannot forget it. ⚠️ A freeze that needs a *different slice* is still the same claim: the member-expression freeze keeps its slice **layout-opaque** (so every container around it holds its tight layout), and open-coding it as a bare slice for that reason dropped a glued block ahead of the chain base at six distinct gap positions — `tsv_ts::build_frozen_opaque_node_doc` is that variant, named rather than inlined so the next such freeze differs in the slice alone.

   ⚠️ **The left-spine walk hands the claim DOWN, and the receiving arm may be a reassembly.** `prepend_owned_leading_comment` declines to claim when the node's left-spine child starts at the same position, on the reading that the child is the innermost node and the recursion will reach it — which is only true if the parent *routes* that child through `build_expression_doc`. A destructuring default whose left is an object pattern does not (it calls `build_object_pattern_doc_with_context` for the no-expand-on-nesting rule), so adding the `AssignmentPattern` arm to `left_spine_child` turned a DOUBLE-PRINT into a DROP one node over (`[/* c */ {a} = 1]`). **Every arm of `left_spine_child` is an assertion about a builder**, and the two must be read together.

   ⚠️ **Innermost-wins holds only because the innermost node prints FIRST, and one node breaks that.** A **paren-less** arrow's span starts at its own sole parameter (`x => x`, `params_start: None`), so both nodes answer the position-keyed lookup — and both claimed, at every position an arrow reaches (`/* c */ x => x` → `/* c */ (/* c */ x) => x`; the declarator, a call argument, an array element, each head of a curried chain, and an `extends (a => b)` heritage). Neither remedy the other cases use applies. The claim cannot go DOWN — the `(` is *synthesized*, so the inner position would print the comment inside a paren the author never wrote — and declining the bind in the parser would give up `OwnedCommentEffect` for the shape, which is exactly what makes the two multi-line authorings match prettier (`Pins` keeps `= /* a⏎b */ (x) => …` on the `=` line, `Hangs` drops the indentable form to its own). So the arrow keeps the claim and the **parameter is suppressed**: `Printer::with_owned_comment_claimed_above` marks the position while the parameter list builds (`build_arrow_params_doc_ungrouped`), and `prepend_owned_leading_comment` declines against that mark. The suppression is only a de-duplication because every path reaching that builder provably claims at `arrow.span.start` first — `build_expression_doc`'s seam for a plain arrow and a chain head, `prepend_owned_leading_comment_at` for the `build_arrow_sig_doc` reassembly and a chain's inner arrows; a suppression with no such claim above it is hazard 1 again, spelled the other way round. ⚠️ The rule this refines is about the **referent**, not about byte adjacency: `/* c */ (x) => x` does put the synthesized `(` between the comment and `x`, and that is right, because the token the comment was glued to *is the arrow's own first token* — the comment led the arrow before and leads it after, where prettier's `async (/* c */ x) => x` re-binds it from the arrow to the parameter. See [conformance_prettier_ts_comments.md §Comment relocation](./conformance_prettier_ts_comments.md#comment-relocation) ("A synthesized paren never lands between a comment and the token it is glued to"). Pinned by `expressions/arrow/before_bare_param_comment`.

   **Adding a third reassembly or replacement path means adding a third claim.** The lookup behind every one of them is `tsv_lang::owned_leading_comment_at`, shared across the two printers — it lives in `tsv_lang` because a per-crate twin is exactly the drift that let this hazard recur: the Svelte printer dropped a glued owned block at *every* one of its freeze sites long after the TypeScript printer had been fixed, and no gate saw it (the print-once ledger only sees a document **as authored**, and no fixture glues a comment to a frozen value).
2. **An owned comment travels *inside* its node's doc, so the gap around it can't see it.** The assignment layout inspects the operator→value gap (`rhs_comments`), which is empty for an owned comment — yet the comment still hangs the value. The node has to be asked instead: `owned_leading_comment_effect`. It is the single seam for that question (the declarator, the class property, the object value, and the `is_poorly_breakable_chain` invariant all route through it).

   **What such a comment does to the operator's line is decided by its PRINT SHAPE, not by `multiline`.** An owned comment is glued to its value by construction (`CommentGlue::SameLine`), so the two multi-line block shapes part ways: an **indentable** one (`/**⏎ * c⏎ */`, reprinted as a `MultilineText` of hard lines) *hangs* the value, while a **preserved** one (interior emitted verbatim) *pins* it to the operator's line — `const a = /* line1⏎line2 */ x;` — matching prettier, whose non-indentable comment is one opaque string. `tsv_lang::is_indentable_block` is the shared test, and `owned_leading_comment_effect` answers both halves (`OwnedCommentEffect::Hangs` / `::Pins`) from one lookup, so they cannot drift apart or be paid for twice. ⚠️ `DocArena::will_break` cannot answer this: tsv emits a preserved interior through `literalline`s so `fits` sees the newlines, and it therefore reports `true` for **both** shapes. Keying the layout on `multiline` (or on `will_break`) hangs values prettier leaves inline.
3. **A region the parser LIFTS OUT of its container is still inside the container's gap** — so two emitters print it, where hazard 1 has none. `<svelte:element this={…}>` keeps its `this` out of `Element::attributes` (it rides in the kind), yet the braces still sit in the name→`>` gap the attribute scan probes: the tag's own doc prints the comment, then the scan prints it again. `AttrGaps::claimed` is that seam — the region whose comments the scan must skip. What makes this one nasty is that **ownership masks it**: a glued *block* comment is owned, so the gap skips it and the double-print never appears; only a **line** comment (never owned — `owned ⇒ is_block`) exposes it. A lifted region needs a claim on *both* axes, and testing with block comments alone will tell you it is fine.

4. **A builder that emits only its CHILDREN's docs prints no gap comment at all** — the positional analog of hazard 1, and the one hazard that needs no ownership to bite. An *alternate-layout* container builder (a forced-hardline twin of the real one, reached when a caller needs a specific shape for its `fits()` measurement) loops over the properties or elements and pushes each child's doc — and never runs a gap lookup, so the `{`/`[`→first-item gap, the inter-item gaps, the trailing gap before `}`/`]`, and a dangling comment in an *empty* container are all DROPPED. `build_object_doc_expanded` / `build_array_doc_expanded` did this to every one of those positions; `build_array_group_doc_forced` did it to the trailing side. The **suffix** variant needs no loop to bite: `build_array_type_doc` reaches its `[]` down four routes, and three of them — the synthesized-parens arm, the expanded-parenthesized-union arm, and the paren-interior freeze arm — returned with the suffix fused into one `text()` (`")[]"`), so the element→`[` gap and the bracket interior had no emitter *on those routes only*, while the fourth emitted both. One construct answering one question four ways is the smell; the fix is the same shape as the container one — a single suffix emitter every route calls (`build_array_suffix_doc`). The **head** variant is that one read backwards, and it bites a *leaf*: the function/constructor-type hug (`build_function_params_doc`) needs a type literal with no group of its own, so instead of routing its sole parameter through the identifier builder it respelled the head inline — name, then a bare `d.text("?")`, then `d.text(": ")` — leaving the name→`?` and marker→`:` gaps with no emitter and dropping every comment in them, while the SAME construct's signature-path hug, one function away, routed correctly all along. A layout need reaching only the *body* of a node is never a licence to respell its *head*; take a seam that keeps the head shared and lets the body vary (`build_binding_type_annotation_doc_with`). Its tell is the cruelest in the family: a repro in any sibling context reports the construct healthy, because only one of its paths is blind. The destructuring pattern's tail (`build_pattern_tail_doc`) reached the same variant down a different road — a **position-free signature**. It took the `optional` flag and the annotation and no offset at all, so it could not emit a head-gap comment even in principle, and every call site read as complete because nothing in the signature suggested a gap was there to miss. A helper that renders a node's HEAD must take the position that head starts at; one that takes only its values has silently declared the gaps behind it to be somebody else's — which is why the position now travels *with* the values it belongs to, as one `PatternTail` derived from the node rather than three arguments a call site pairs up by hand. ⚠️ **And somebody usually answers** — which is what turns the drop into a RELOCATION and hides it from every loss gate. Here the claimant was the pattern's own interior scan, whose bound (`body_end`) was named "where the `{…}` body ends" and returned the *annotation's start* — one token too far, so the three head gaps (`}`→`?`, `?`→`:`, `}`→`:`) fell inside the brackets and a comment written after the `}` printed against the last element. A bound whose NAME states a syntactic landmark and whose BODY returns a different one is the recurring shape; the empty-container emitter, whose contract reads that same bound as "one past the closer", then took `span_end - 1` into the middle of the comment and dropped it outright. The fix is to hand a commented container to the comment-aware twin wholesale — the gate must precede the **empty**-container arm, or the dangling case stays open — or to share the per-item emission seam (`push_array_element_with_inline_comments`). **Ownership masks this one too, in mirror image to hazard 3**: a glued *leading* block is owned and rides inside its item's doc, so it survives; only the trailing and own-line comments are lost, and a leading-comment repro will report the builder healthy.

   The container builders are not the only family. An **operator-chain layout builder** has the identical shape: it flattens a chain into operand docs plus raw operator *text*, so every operand→operator and operator→operand gap is unemitted — `(a /* c */ && b)`, `(a || // c⏎b)`. `tsv_ts`'s two are `build_binary_chain_parts_indented` and `build_binary_chain_for_parens`; both reach their operand list only through `prepare_binary_chain_layout`, which answers the comment question first and hands a commented chain to the comment-aware twin (`operators.rs`, which collects operands *with spans* — the structural difference that makes gap emission possible at all). Which twin depends on the caller's indent: a builder whose caller already wraps it in `group(indent([softline, …]), softline)` wants the **ungrouped** twin, not the continuation-indent one, or every operand after the first indents twice. When adding a chain-layout builder, route it through the same preparation rather than calling the span-less collector directly.

5. **An owned comment a blank scan CROSSES fabricates a blank line.** The mirror of hazard 2: there the gap could not *see* the comment, here it sees nothing but the bytes. An owned comment is skipped by the emit axis yet still occupies its source range, so any scan measuring a **distance** across it reads the comment's own interior newlines as an author blank. The gaps that can hold one are exactly the gaps that **end at an expression start** — that is where a comment can be glued and therefore owned — and all three of them did it: a header→body gap whose body is **brace-less** (`else⏎// c⏎/* owned⏎⏎*/ fn();`), a binary **operator→operand** gap (`x + // c1⏎/* owned⏎⏎*/ y`), and a ternary **`?`→branch** gap, where the fabricated blank additionally fed the break gate and dropped the branch onto its own line. The fix is the in-source ceiling (`blank_scan_end`) at the scan's far end, never a wider strict scan; where an emitter already derives its next position that way (`push_leading_comment_run`, the pre-body run) the hazard cannot reach it, which is why the `)`→non-block twin was healthy while its `else` sibling was not.

   ⚠️ **No standing gate can see this one.** Nothing is dropped, double-printed, merged or rewritten, and the fabricated line is its own fixed point — so the ledger, the census, F1, the fuzzer and the blank ratchets all pass, and even the ternary's extra branch break is stable. Only a prettier `compare` finds it. A **sanction can hide it too**: at the binary gap tsv deliberately keeps a real author blank where prettier collapses it, so the fabricated blank wore the sanctioned output and only the absence of an authored blank told them apart. Pinned, with a null control per gap, by `syntax/comments/owned_comment_interior_blank`.

The first four hazards are what the **print-once comment ledger** exists to catch — the structural guard on this model: every comment a document parses must be emitted exactly once, or the audit reports it as DROPPED or DOUBLE-PRINTED (`deno task comments:audit`, gated in `deno task check`; see [audits.md §Comment Ledger Audit](./audits.md#comment-ledger-audit-commentsaudit)). Nothing else in the detached model forces a parsed comment to reach the output. Hazard 3 was found by it, not by review — the block-comment repro looked clean. One layer below the model sits the **comment census** (`deno task census:audit`; [audits.md §Comment-Census Audit](./audits.md#comment-census-audit-censusaudit)): it lexes comment trivia off the raw input and raw output and compares interior multisets, so a comment the parser consumed without ever producing — the class the ledger cannot represent, since a never-registered comment never existed as far as it knows — still counts, along with a merge or interior rewrite of one it did.

But the ledger only sees a document **as authored**, so it cannot see a *wholly* comment-blind builder until some file happens to put a comment where that builder prints: hazard 4 stayed green on `comments:audit` across zzz / gro / fuz_app / fuz_ui, prettier's TS+JS suites, and svelte's own source, because the shape simply does not occur there. The **injection** audits are the discovery arm for that class — `gaps:audit` had it pinned as sixteen known DROPPED shapes all along. When you add or change an alternate-layout builder, the ledger passing is not evidence; put a comment in each of its gaps yourself.

Prettier, oxfmt and biome all get the paren binding wrong — see [conformance_prettier_ts_comments.md §Comment relocation](./conformance_prettier_ts_comments.md#comment-relocation) and [§JSDoc / paren semantics](./conformance_prettier_ts_comments.md#jsdoc--paren-semantics).

## Content is a source slice, never owned

The content is **not stored owned** — comment text is a pure delimiter-stripped sub-slice of source, so `Comment` holds a `content_span` and recovers the text on demand via `Comment::content(source) -> &str` (`source` must be the host document the spans were recorded against); every field is `Copy`, no `String` per comment. `multiline` is precomputed so the multi-line-block expansion checks (`has_multiline_block_comments_on_page_in_range` and the printers) read an O(1), source-free flag instead of re-scanning content. The full comment span includes its delimiters (`//` / `/* */` / a `#!` hashbang, whose content includes the `#!`); the lexer is the single owner of those widths.

## Printer strategy

Range-based lookup via `comments_to_emit_in_range(prev_end, node_start)` (and its on-page / in-source siblings above). Source string for context (same-line detection, blank line preservation). Tradeoff: simple/efficient AST matching Prettier's model, but printer must manually track `prev_end` positions; edge cases (e.g., arrow function comments) require careful span math.

**Never hand a comment-aware builder an EMPTY comment list.** Every lookup above is a search over that list, so an empty one makes each of the three axes answer "no comments here" — silently, for the whole subtree, with no gate downstream to notice. There is no legitimate use: a node whose span genuinely cannot contain a comment loses nothing by taking the real list, and a node that can contain one loses everything. The shape reads as a cheap "this key can't hold a comment" assertion and is really a subtree-wide drop, which is why it is worth naming rather than re-deriving. (`<svelte:element this={…}>` dropping every comment in its expression was this, not hazard 3's double-print.)

## Leading comments: one rule, one emitter

A comment run *before* an item (a value, member, list element, or comma-separated item) is emitted by `Printer::push_leading_comment_run` (`printer/comments/mod.rs`), which implements prettier's `printLeadingComment` and picks the separator after each comment from the source around **that comment only**, never from where the item starts: **space** when nothing but spaces follow its `*/` (so a run the author glued stays glued — `/* a */ /* b */⏎X`), a soft **`line`** when a newline follows but none precedes, and a blank-preserving **`hardline`** for an own-line block or any line comment. The glue test alone is `Printer::comment_hugs_next` — the single statement of the rule, called even by the few sites whose surrounding loop must differ. The two hand-rolled leading-run sites whose loop can't route through `push_leading_comment_run` — `build_eq_comment_break_rhs` and `append_keyword_value_line_comments` (both always-broken line-comment contexts, so a two-outcome space-or-hardline separator) — share `Printer::push_leading_run_separator`, which pairs the **physical-next** anchor (`blank_scan_end`, so an owned comment glued to the value doesn't desync the decision) with the `comment_hugs_next` hug-or-blank-hardline choice. Only those two: a site whose enclosing group can still be flat needs the emitter's soft `line`, and reaching for the two-outcome separator there forces open a run prettier keeps inline. ⚠️ Do not hand-roll `is_block && is_same_line(c.span.end, X)` at a new site, and don't re-derive the anchor+separator inline — keying the hug on the *item* rather than on *what follows the comment*, or anchoring on the emit-next *past* an owned comment, splits an author-glued run or inserts a phantom blank, and was a whole bug family (unglue / block-run merge / owned-comment blank scan). A site that also owns a comma emits the gap via `push_inter_item_line_comment_gap`, which owns the break too — that is what lets the last comment hug the next item. ⚠️ **A site that must open a SHELL around the run asks the emitter, which returns whether it pushed a hardline** — tsv has no `propagateBreaks`, so a hardline inside the run is invisible to the group that would have to break for it, and `import(…)`'s parens are exactly such a shell (`build_paren_leading_value_doc`). Re-deriving the answer caller-side is the three-way rule spelled a second time: the import gap's own attempt asked "is there a newline anywhere between the `(` and this comment", which called the second half of an author-glued run own-line, split the pair, and forced the parens open on a call prettier collapses.

A retained **paren shell**'s leading run keeps its own emitter (`Printer::push_paren_shell_leading_run`), because its separator is the *delimiter's* question rather than the item's — but it asks both of the rules above, and used to ask neither. It decided each separator from the comment's own **kind**, so a `//` the author glued to the `(` was dropped to the next line and an author **blank** below it was erased. Both made the shells disagree with every other opening delimiter: `fn( // c`, `[ // c`, `{ // c` and `Array< // c` all keep the glue (a deliberate tsv divergence — prettier un-glues at all of them). The glue half is asked one step earlier, by `Printer::split_open_delimiter_glued_run` — one of the opening-delimiter rule's two emitters, which the **statement headers** joined last (§The delimiter-line question) — since a glued comment belongs to the `(` line the *caller* owns; the blank half rides in the run. The below-blank rides with the pull everywhere — KEEP, one value, every caller, via `Printer::push_delimiter_glued_blank` (§The delimiter-line question). A blank between the `(` and the comment stays erased — that one sits against the delimiter, where every bracket in both formatters drops it. Pinned by `types/paren_shell_glued_leading_line_comment_prettier_divergence`.

One gap shape is deliberately **not** a leading run: a gap the printer routes because it holds an honored format-ignore directive (the conditional `?` / `:` branches, a function type's `)`→`=>`). What follows the run in the *output* there is the operator, not the node the comments lead, so the separator rule above would measure the wrong thing — a block comment whose `*/` merely shares a line with the node's start would hug, pulling the directive off the own line that earned the freeze. Those sites share `Printer::build_own_line_preserving_run`, which asks a different question — a **routing** one, trail the previous line vs. sit above the operator's line — and returns the two sinks for the caller to place. It is the only sanctioned alternative to `push_leading_comment_run`; a new site that needs one of the two must pick deliberately, not hand-roll a third.

## Trailing and dangling runs: the separator goes BEFORE each comment, never after

A run at the **end** of a container has two shared emitters, split by whether there is a preceding item to break away from: `Printer::build_trailing_body_comments_doc` (`printer/comments/lists.rs`) for a run after the last member or statement, and `Printer::push_dangling_comment_run` for one that is the container's *only* content. Both emit the separator **before** each comment — a `hardline`, preceded by a `literalline` where the author left a blank line — and neither emits anything after one.

The one thing that separator asks is whether the author **glued** this comment to the previous one: a pair written on one line keeps that line, and everything else takes the break. A space is not the weld the rule below exists to prevent — both comments stay distinct, and a line comment never hugs, so nothing can land behind a `//`. It is asked only by the trailing emitter: prettier keeps the glue after a last item (`class A { a = 1;⏎/* c1 */ /* c2 */ }`) and splits it in an empty body (`class A { /* c1 */ /* c2 */ }`), so the *dangling* emitter's `hardline` is unconditional.

`Printer::trailing_run_hugs_previous` is the single statement of that question — the trailing-side mirror of `comment_hugs_next` on the leading side — and `Printer::push_trailing_run_separator` the emitter that pairs it with the blank-preserving `hardline`, for the runs whose own-line arm is that unconditional break: the last-item→closer walk (`Printer::build_trailing_gap_comments_ext` — tuple, type parameters and arguments, both parameter lists, the angle-bracket cast, the union's member→`|` gap), the array literal's end-of-array scan, the call family's `PartitionedComments::emit_dangling_comments` (which despite its name is a *trailing* run — an argument precedes it), and a unary operand's stripped-grouping-paren gap (`!(⏎x⏎/* c1 */ /* c2 */)`, whose vertical layout is already committed by the time the run is emitted). A run whose non-glue separator is the caller's (`build_trailing_closer_comments_doc`, the one container that may still collapse around it) asks the predicate and keeps its own arm.

⚠️ **The run's ANCHOR advances, and a loop-invariant one is this bug spelled a step earlier.** Own-line-ness is a question about a comment's own neighbours, so a scan anchored on the node the run trails (`has_newline_between(argument_end, c.span.start)`, re-asked per comment) reads the *second* half of an author-glued pair across the *first* and calls it own-line — the same split, arrived at without ever asking the glue question. Every loop here carries a cursor that steps over each comment it emits (the binary chain's two gaps, the unary operand gap, the terminator gaps below); the `i == 0` arm is where the anchor legitimately appears, because there the thing behind the comment really is the node. The literal spelling above is not hypothetical — it was `Printer::split_terminator_gap_comments`, which held its anchor at the operand's end and so split `return a⏎/* c1 */ /* c2 */;` onto two lines, at every keyword it serves.

⚠️ **EVERY comment→comment separator asks it, not just the ones at a container's end.** The question belongs to the *separator*, not to the position, so a run in the middle of a construct answers it identically: the specifier list's trailing run, a spread's stripped-paren interior (both the parent's emitter and the array's own end-of-array group scan), a binary chain's operand→operator and operator→operand gaps, a ternary branch's `?`/`:` run, a type alias's `=` run, the leading run before a non-first parameter, and a terminator's content→`;` gap (`Printer::push_gap_comments` — one emitter serving a statement's own `;`, a class member's, a type member's, a `for` head's and a declarator's, so one bare `hardline` was five divergences). Each of those hand-rolled a bare `hardline` (or, in the array group's case, a bare `line`) and split a pair the author wrote as one; the parameter one emitted **nothing at all**, welding them (`/* c1 *//* c2 */`). The remaining `push_blank_preserving_hardline` callers are exactly those whose *next* is not a comment — a value, an item, a delimiter — and that is the invariant to keep. Pinned by `syntax/comments/separator_glued_run` and, for the terminator gap, `syntax/comments/terminator_gap_glued_run` — which covers the sibling emitter (`Printer::split_terminator_gap_comments`, the parenthesizable-operand terminators) in the same file, since the rule is the separator's and not the seam's — whose triggers can only live in an `unformatted_*` variant: at the fixed point the run has floated past the `;`, so the authoring that reaches these emitters is exactly the one the fixed point erases; the operand→operator one rides inside its own cataloged divergence (`expressions/binary/operand_operator_line_comment_prettier_divergence`), where the comment's position relative to the operator is what differs, not the run's own line.

⚠️ **Whether a gap HAS a trailing run at all is prettier's comment-ATTACHMENT question, and a decorator gap answers it three different ways.** The run after a decorator (`@fn1⏎⏎// c⏎@fn2⏎a = 1;`) is attached as that decorator's *trailing* comments — so the author's blank survives, by the adjacency rule above — but only where prettier's handlers say so, and the null control is what makes that reading necessary: with **no** comment in the gap both formatters discard a blank between two decorators byte-identically, so this is not a decorator rule at all, it is a comment run's. `handleMethodNameComments` trails the decorator when the enclosing node is `isPropertyLikeNode` (`PropertyDefinition`, `MethodDefinition`, `AccessorProperty`, and — the carve-out worth naming — **`TSParameterProperty`**, so `constructor(@fn⏎⏎// c⏎private p: T)` keeps the blank while the same decorators on a plain parameter do not). A **class-like** node takes `handleClassComments` instead, which trails the LAST decorator only when the follower is *not* itself a Decorator: `@fn1⏎⏎// c⏎class A {}` keeps the blank, `@fn1⏎⏎// c⏎@fn2⏎class A {}` drops it. Everywhere the handler does not fire the comment simply LEADS the next node, and `printLeadingComment` emits a blank *after* a comment, never before. tsv's three decorator builders each state their own half of that gate (`DecoratorHost` for the parameter path, the follower test for the class-level one) over one emitter, `push_decorator_run_blank`. Pinned by `statements/class/decorator_comment_blank`.

⚠️ **A separator emitted AFTER each comment must ask the glue question of what FOLLOWS, and only when a comment does.** One site is written that way (the type alias's `=` run, whose loop pairs each comment with the gap behind it): there the predicate takes the *next* comment's start, and past the last comment the `next` is the **value**, whose placement is the leading-side question that loop does not own — asking it there hands the value a space it never asked for.

⚠️ **The question is asked BETWEEN the two comments, never of the source right after the `*/`** — and the two are not the same question, which is why the trailing side has a predicate of its own rather than calling `comment_hugs_next`. They part on exactly the byte these runs exist for: the list's own **comma**, deleted under `trailingComma: 'none'`. A scan for "what follows the `*/`" stops at that comma, reports no newline, and WELDS a comment the author gave its own line onto the previous one (`[A /* c1 */,⏎// c2]` → `A /* c1 */ // c2` — and a `//` landing there swallows whatever is printed behind it). Asking whether the author put a newline *between* the two reads past the comma, because a deleted separator is not a line. Every other trailing-run site was blind to the difference for the same structural reason: elsewhere the comma always sits behind a comment an earlier emitter already claimed, so the predecessor is `None` there — only the walk that covers a whole gap in one pass reaches it. Pinned by `syntax/comments/trailing_gap_glued_run`'s `unformatted_trailing_comma` variant, which is the authoring that carries the comma.

⚠️ **That separator's blank question is `isPreviousLineEmpty`, asked of the COMMENT** — is the line DIRECTLY ABOVE it blank (`Printer::previous_line_is_empty`, prettier's `printTrailingComment` reading it off `locStart(comment)`) — and NOT "does this gap hold a blank line somewhere". The two part wherever re-emitted structure sits between the author's blank and the comment, and the list's own **comma** is exactly that: `import {a⏎⏎,⏎// c⏎b}` leaves a blank in the gap while the line above the comment is the comma's, so the gap-wide reading preserved a blank `printModuleSpecifiers` — a bare `join([",", line], …)` — has no way to emit. The run is emitted *against* the comment, so the comment is what the blank has to be adjacent to.

⚠️ **And WHETHER a gap preserves a blank at all is the SEPARATOR's rule, never the block-binding one.** A `;` terminator ends its line, so an author blank above a deferred own-line comment survives it — at *both* block bindings, because where a same-line block sits relative to the `;` says nothing about what a comment two lines further down is worth. The two axes read off one flag is the **comma's** rule — `Printer::split_comma_gap_comments`, which preserves neither — and it was wrong the moment a `;` caller took the block-before binding: `import a = B.C`, `export as namespace D`, and the ambient module shorthand all silently ate the blank. `Printer::push_semicolon_with_gap_comments` passes `preserve_blank` unconditionally instead, which is also what collapses it and `split_member_terminator_gap_comments` into one answer. It derives the `;`'s own position from the node's `span_end` for the same reason: every terminator here is optional under ASI, so a caller-side `span.end - 1` lands inside the content whenever the author wrote none. Pinned by `syntax/comments/semicolon_gap_own_line_blank`.

⚠️ **The scan is still an IN-SOURCE question, and `blank_scan_start` is its FLOOR** rather than the caller's cursor: a comment an earlier emitter claimed, or an OWNED one printed from inside a node's doc, still occupies its bytes, and the backward walk must not leave this run's gap. The adjacency rule already refuses a multi-line block's own newlines — in `[1 /* x⏎⏎y */⏎// c]` and `fn(a /* x⏎⏎y */⏎// c)` the line above the `//` ends in `y */`, so it is not blank — where the gap-wide reading grew a blank line the author never wrote. The fabricated form is a fixed point both formatters then agree on, so F1, the ledger, the census and `blanks:audit` are all blind to it — only `fabrication:audit` on the pristine seed, or a prettier `compare`, shows it.

⚠️ The mirror-image formulation is the trap, and it has bitten every site that tried it. Emitting the separator *after* each non-last comment forces the emitter to ask what **kind** the comment was, and the answer it reaches for — "a block comment needs no break, the closing `}` follows immediately" — is false the moment another comment follows. Whatever comes next is then welded onto the block's line: `/* c1 *//* c2 */`, `/* c1 *///  c2`. Asking it before instead needs no kind test at all, because a run is a list of own-line comments and the closer supplies its own break.

**No gate can find this class.** Nothing is dropped, merged, or rewritten — the welded text reparses as the same two comments, byte for byte — so the print-once ledger and the census both balance, and the output is *stably* wrong, which leaves F1, the fuzzer, the round-trip and SAFETY blind too. Only a prettier `compare` shows it. That is the whole argument for one emitter per question here rather than a rule each container restates: a drifted copy is invisible until someone diffs it against prettier.

**A trailing GAP is the third emitter, and its separator is deferred.** `Printer::push_trailing_comments_in_range` covers the runs that trail a node *inside* a construct — a paren shell's `)`, an indexed access's `]`, a mapped-type member's value. It asks the same question before each comment, but from the source (*did the author give this one its own line?*) rather than from the run's shape, because unlike a container-end run these comments may be legitimately glued (`/* c1 */ /* c2 */` written on one line stays on one line). Two consequences are load-bearing. The break travels **inside** the `line_suffix` (`build_trailing_comment_doc_own_line`, prettier's `printTrailingComment` `hasNewline`-backwards branch): a real break emitted between two deferred comments lands in the enclosing construct and splits the very brackets the run sits in, while a buffered one replays once the line is ending. And only a **line** comment defers by construction — a block defers solely to stay behind a line comment already in the run, and a block that could sit inline must. Emitting the run back to back welds it (`// c1 // c2`) exactly as above, and mixing an inline block into a deferred run **reorders** it; both are as gate-blind as the container case, which is why open-coding this loop is the recurring bug (the mapped-type member did both). The caller supplies the layout the run sits in — the shell's `align(2)`, the expanded brackets' `indent` — because the break inherits whatever wraps the doc, not whatever wraps the closer.

**The stripped-operand gap is that emitter with one policy flipped, and the flip is what makes the reorder reachable.** `Printer::append_trailing_paren_comments` covers the region a stripped grouping paren orphans (`await (x /* c */)`, and the same gap at `yield`, a binary operand, a sequence, `export =`, and the retained parens of return/throw's hanging layout). It deliberately **defers an own-line block** where the emitter above keeps it inline — prettier floats these past the `;` and tsv follows — and everything else is the same walk: the source question per comment, the cursor over what physically precedes it, the break inside the `line_suffix`. Two things follow from the flip. A blank the author left above such a comment survives the float (prettier's `isPreviousLineEmpty`, a **second `hardline` inside the suffix** — `build_trailing_comment_doc_own_line_blank`; the `literalline` + `hardline` pair every non-deferred site uses would leave the run's own leading break's indent on the blank line). And a comment **glued behind** a deferred one must ride in the suffix too: above, only a `//` can open the run and nothing can follow one on its line, so an inline arm is unreachable — here an own-line *block* opens it, and emitting the next comment inline renders it **ahead** of the run it was written after.

`Printer::split_terminator_gap_comments` is the same walk once more, for the terminators whose operand may be parenthesized (`return` / `throw`, `export default`, `export =`) — everything in that gap floats past the `;`, except the comment a grouping paren the caller PRINTS still encloses. Its three arms are the three sentences above, and it had all three wrong at once: a fixed anchor split an author-glued pair, an own-line arm keyed on the comment's KIND sent a `//` to the statement's line as if it trailed there, and a bare `hardline` instead of the blank-preserving suffix ate the author's blank *and* rendered ahead of anything already buffered. Pinned by `syntax/comments/terminator_gap_glued_run` (the glue, stated across both terminator emitters) and `syntax/comments/terminator_gap_own_line_run`.

**⚠️ A deferred run must not leave the construct it was written in.** Deferring is *end of line*, not *escape*: the run flushes wherever the enclosing line happens to end, so a construct that closes without breaking carries the comment past its own closer — re-binding it from the node it trails to whatever statement it lands on, and landing it on a line that may already hold a deferred comment, where the two weld irreversibly. So a **line** comment in one of these gaps forces its construct **open**: the closer drops to its own line and the comment flushes inside. Every bracketed type region does this — a type literal's `}`, a type-argument list's `>`, a tuple's `]`, a function type's `)`, an indexed access's `]`, and a paren shell, which is *retained* rather than stripped for exactly this reason (`tsv_ts`'s `build_parenthesized_type_unwrap_doc`). **A shell reaches that emitter only if nothing strips it first**, and one thing did: the keyword→value paren-strip hang (`Printer::keyword_value_stripped_paren_hang`) fires on a **leading** `//` in the shell, so a shell carrying both a leading and a trailing one satisfied the retain rule while already being gone — its `//` lifted out onto the enclosing construct's closing line, where a comment authored in that construct's own trailing gap was waiting to weld with it. The seam now declines exactly the shells `Printer::paren_retains_for_trailing_run` retains, at all seven hang positions and at the cast's second, own strip path; the rule is read once, where the shell is decided, rather than at each construct's trailing emitter (which would have to learn that a deferred run is pending). The one sanctioned exception is a union / intersection member a `|`/`&` separator still **follows** in source: the next separator's per-member break ends the output line exactly where the shell ends, so the strip is lossless and the comment still trails its member. The carve-out is asked structurally — `Printer::type_member_separator_follows`, scanning past trivia and the `)` closers of enclosing redundant layers — rather than as builder context, so it stops precisely where its argument stops: the **last** member has no separator, its line ends only at the statement's tail, and a stripped shell there carried the comment past the `;` while forcing a break the reparse could not reproduce (non-idempotent, and prettier's own form there still is — pinned by `type_suffix_trailing_comment_union_member`'s `audit_signature.txt`). So the last member retains like every other position. And the break the sanctioned strip *does* force is **flush-scoped** (`DocArena::flush_break`, not `break_parent`): stripping changes the reparse geometry — the comment ends up in the composite's member gap, outside the parens it was written in — so only the group the deferred run actually flushes in re-breaks on the next pass. The unscoped node forced every intermediate group too (a shell one composite deep, `B & (A // c) | C`, broke the intersection the reparse then reprinted flat — a 2-pass convergence). `FlushBreak` is invisible to `will_break` and armed in the `arena_fits` walk: while pending in flat mode, a breakable `line` or a plain `if_break` whose break arm can break does not fit — the group owning the next line opportunity breaks, and a group with no line after the suffix stays flat. A construct that is **retained** keeps plain `break_parent` (`with_stripped_paren_trailing`'s hang seams, the retained-paren union's trailing arm): its doc regenerates identically each pass, so the unscoped force is reproducible — the scoped node is for the strips. See [conformance_prettier_ts_comments.md §Comment relocation](./conformance_prettier_ts_comments.md#comment-relocation).

The two differ only in what supplies the outer breaks. The trailing emitter owns the break away from the previous item, and reads `prev_end == 0` as "there is no previous item at all" — a comments-only file, which is how the program's `}`-less end-of-body reaches the same code. The dangling emitter leaves both outer breaks to the delimiter pair, so the caller's `sep` decides whether a lone fitting block comment stays inline (`{/* c */}`) or the body always explodes; "always breaks" is that same emitter with a `hardline` separator, not a second builder.

**Where a deferred run lands is the renderer's question, and the flush must END THE LINE.** The `line_suffix` buffer is drained by whichever comes first: a `line` the renderer takes in break mode, or a `lineSuffixBoundary` — the marker a construct plants where its own text must not follow a pending `//` (an assignment's `fluid_after_operator`, a template-literal `${…}` closer, a member lookup). Both flush, and both then end the line; prettier spells the boundary's half as a pushed `hardlineWithoutBreakParent` (`printer.js` `DOC_TYPE_LINE_SUFFIX_BOUNDARY`). A flush that ends inline instead lets the deferred `//` swallow the code the boundary exists to protect — `const x: T[K // c⏎] = y` printing as `const x: T[K] = // c` with the initializer *inside* the comment, output that does not even reparse. The obligation runs both ways: because the boundary supplies that break itself, a doc that plants one directly in front of its **own** forced break renders a blank line, so a boundary belongs only where nothing else ends the line — a chain gap, whose `build_chain_line_break` always breaks, takes `build_deferred_line_comments_doc` instead. `arena_fits` carries the other half of the rule: a boundary reached with a suffix pending does **not** fit (prettier's `hasLineSuffix`), so a group spanning one breaks rather than measuring flat across a line the flush is about to end.

**⚠️ A deferred `//` must be the ONLY thing reaching its line end — two deferred comments flushing at one break WELD.** Whatever flushes second lands inside the first `//` (`fn().bar; // c // c1`, the second becoming text of the first; a block trailer is reordered behind it instead, `.bar; /* c1 */ // c`), and the fixture, census and ledger are all blind to it because every comment is still printed once — only a prettier `compare` or the gap audit's SWALLOW class sees it. So the sanctioned deferral of a member chain's trailing-member gap `//` (`fn() // c⏎.bar;` → `fn().bar; // c`, `trailing_member_after_call_comment`) is licensed only while nothing else reaches that line end, and its askers state that: `trailing_member_gap_line_comment` refuses the deferral (the chain expands, each comment in place) when the `//` is own-line, when **any** comment follows it inside the same gap — asked on the **on-page** axis, since a follower glued to the property is owned by it and lands ahead of the deferred `//` all the same — or when a trailer follows the chain's end through closing punctuation (`Printer::trailer_follows_through_closers` — read through `)` `]` `}` `;` `,` because the expanded reprint puts `);` on a later line than the member); and the chain grouping (`group_chain_nodes`) never lets a member with a `//` in its gap sit *inside* a group at all — prettier's own rule, a node with a trailing comment closes its group and the factory merge is refused for one — since a member printed mid-group can only defer, and two such gaps weld (`fn().bar // c2 // c3`). A trailer behind a further token — an operator's right side (`fn()// c⏎.bar as T; // c1`) or a following sibling in a list (`foo(fn()// c⏎.bar, z); // c1`) — is out of that read's reach, and is caught by the flush's own separator below instead. Pinned by `chained/trailing_member_gap_comment_statement_trailer`, `chained/trailing_member_gap_comment_run` and `chained/group_interior_member_line_comment`.

**The flush is itself a RUN, and it owes the same separator — this one at render time.** `doc::arena_render_suffix` drains the buffer onto one physical line, so everything the separator rule says about a run applies to it verbatim: a suffix landing behind a `//` takes a break first (`push_run_separator`), and one that already opens its own line does not (`build_trailing_comment_doc_own_line` carries its break inside the suffix, and a second would fabricate a blank). This is the FLOOR under the build-time askers above, not a substitute for them — they keep the comment where the author wrote it, while the flush only guarantees the two never merge — and it is the only one of the two that can see the layout, which is why it closes the shapes no source read reaches. Three properties are load-bearing:

- **The line-comment test is the node's identity, never the emitted bytes.** A suffix payload is comment text, and a block comment may legitimately *contain* `//` (a URL), so the walk asks whether the LAST text node the suffix emits is a whole line comment — the same one-node spelling [`doc::swallow`](../crates/tsv_lang/src/doc/swallow.rs) keys its diagnostic on (`DocArena::line_comment_source_span` / `line_comment_text_pooled`). A printer that spelled a comment as `text("//") + <content>` would be invisible here exactly as it is there.
- **The break takes the FLUSH's indent, not the suffix's.** A suffix carries the indent it was *queued* at, deep inside a construct that has since closed; the indent of the break the flush is happening at is the document's own answer for what starts the next line, and is what a reformat then agrees with. The one shape where it does not is a switch's **last** case, where the next break is the switch's `}` — a level out from where a dangling comment in a case settles — so that one reaches its fixed point on the second pass. Cataloged with the fixture (`syntax/comments/deferred_comment_run_separator`).
- **The renderer's own newline hook is what keeps the diagnostic honest.** `render_line_break` is the single seam every break passes through, so `swallow::note_line_end` lives there rather than on a render policy: a break emitted outside a policy's reach — this separator is one — would otherwise leave the tracker's pending `//` armed and report the comment behind it as a swallow that no longer happens.

**The Svelte braced heads invert the ownership, and that is where the same class recurs.** In `{…}` / `{#if …}` / `{@const …}` a run-final `//` runs to end of line, so the closer cannot follow it — the comment's own `hardline` *is* the break the `}` takes, and a second one would render as a blank line above it. `Printer::trailing_comment_docs`' `closer_owns_break` is the one place that decides where that break is emitted from, because the renderer indents a line from the line command that produced it: a break emitted inside an `indent(…)` puts the `}` at the *content's* column, not the head's. ⚠️ **The question is what indents the content, not which builder is asking** — a freeze, an always-block value, a leading line comment hanging a braced head's continuation (at *every* braced head, via the shared `leading_line_comment_hangs_value`), and a `{@const}` init's break-after-operator layout all do, and the last two decide it *after* the run is built, so the verdict has to be hoisted above the call rather than read off the shape assembled below it. This class is as gate-blind as the weld above and for the same reason: nothing is dropped or rewritten and the wrong column is stable, so only a fixture pins it.

## Own-line-ness is a SOURCE question, at every gap

Whether a comment OWNS its line — what every expansion / break gate is really asking — is decided by two physical facts and nothing else: a newline before its `/*` (`Printer::comment_follows_content_on_its_line`) and a newline after its `*/` (`Printer::comment_hugs_next`). `Printer::comment_isolated_on_its_line` is the two-sided conjunction, prettier's `printLeadingComment` hardline condition transcribed; `Printer::is_own_line_comment` is the one-sided form, for the gates that ask only about the leading side (the union's member gate — prettier's union printer expands a block adjacent to its member where its intersection printer collapses it, so the two families genuinely differ here and must not be unified). A **type literal** differs from the object literal the same way and for a reason worth naming, since one predicate serves both (`StandaloneGlue`): a TS member's range swallows its own `;`/`,` terminator, so a comment before it is *inside* the member and never reaches prettier's container gate — which is why `type T = { a: A⏎/* c */,⏎b: B }` expands where the object literal written the same way collapses.

⚠️ **Anchoring that question on the neighboring ITEMS is the recurring bug, and "this gap holds no comma" is not the escape.** `is_same_line(prev_end, c.span.start)` is blind to every byte no item span covers, and the list does not stop at the comma: a stripped paren shell's `)`, an `&` operator, a `:` — and, on either side, **another comment**. That last one is why no gap is safe. The import-attribute `:`→value gap anchors on the exact `:`, holds no re-emitted structure whatever, and still mis-read a glued run the author gave a line of its own (`type:⏎/* c1 */ /* c2 */⏎'json'`), hanging a value both prettier and the fits-inline reading keep on the `:` line. One reading was wrong at three families at once: the intersection's two member gates (`A⏎& /* c */⏎B` broke an intersection that fits — and since the break moved the comment onto the previous member's line, tsv's own **second pass collapsed it**, so the output was not a fixed point), the `with { … }` attribute clause's comma gate (the fifth spelling of the seam question below — where a blank injected before the comma flipped the layout, which `blanks:audit` grades as NON-IDEMPOTENT), and that clause's value gap.

⚠️ **The list-EXPANSION gates carried that blindness on their TRAILING half long after the leading one was fixed, and it is the same bug.** `is_same_line(c.span.end, next_item.start)` asks where the next ELEMENT begins, so the comma the author wrote right after the `*/` is invisible to it — and the four gates that spell this question per family (`has_own_line_block_comments_in_bracket_list` for the bracketed lists, `has_standalone_block_comment` for the object family, `should_force_expansion_for_comments` for call arguments, `has_own_line_comment_between` for parameter lists, plus the params' own last-comment separator in `build_leading_param_comments`) all read it that way. `[a⏎/* c */,⏎b]` therefore expanded on pass 1 and collapsed on pass 2, when the re-emitted `/* c */ b` finally put an item on the comment's line: **non-idempotent**, one authoring reaching two fixed points depending only on where the author broke the line, across the array literal and pattern, the object pattern, tuples, type parameters and arguments, the specifier list and call arguments — with the object literal and the parameter list landing instead on a *stable* third form neither prettier nor the bare authoring produces. Prettier collapses every one of them.

⚠️ **A glued RUN given its own line does not OWN it, and a gate that says otherwise is answering the emitter's question badly.** In `<A,⏎/* c1 */ /* c2 */⏎B>` only `c1` has a newline before it and only `c2` has one after, so neither is isolated: `c1` glues to `c2`, and `c2` takes prettier's **soft `line`** — the third separator, which collapses when the list fits and breaks when it doesn't. Reading the run as one object ("does the thing the author glued end the line?") looks like the careful answer and is not: it forces open a list prettier keeps flat, at every family measured (params, type params, type args, function-type params, call args, tuples, intersections). The gate asks `Printer::comment_hugs_next` per comment; the *rendering* difference between "own line" and "pulled up" is the emitter's `line`, and only the enclosing group can decide it. A gate that pre-empts that decision replaces a width answer with a comment answer.

⚠️ **The pre-empt is not confined to the expansion GATES — a layout ARM and a hand-rolled break are the same mistake wearing different clothes**, and the tell is the same: the shell renders one way whatever the width is. The unary comment-holder parens picked a hard-broken arm outright (`(` + `indent(hardline …)` + `hardline` + `)`) whenever the one-sided `Printer::comment_cannot_glue_to_operator` held of any leading comment, so `!(⏎/* c1 */ /* c2 */⏎x)` stayed vertical where prettier collapses it — and, in the other direction, a glued run at 101 columns stayed flat, since a shell that is never a group cannot break for width either. Its fix is not a predicate swap but prettier's own `UnaryExpression` shell (an inline case in `print/estree.js`: `group(["(", indent([softline, arg]), softline, ")"])`), which asks nothing about comments at all. The `for` header, already a group, spelled the pre-empt twice more: a `hardline` before a clause's leading run keyed on `is_own_line_comment` of its **first** comment, and a break gate (`has_isolated_comment_between`) that asked each comment's trailing side against the *clause* rather than against the next comment. Every construct that genuinely must break still does, and reaches the group as a real break rather than as a decided layout — through the emitter's own `hardline` and `DocArena::will_break`. The **condition parens** (`if` / `while` / do-while / `switch`) and the **binary chain** are the same pre-empt in its last two homes, and each shows one half of the cost: the condition gap hand-rolled its own leading run — a `hardline` per comment off `is_same_line(open_paren, c.start)` — and then opened the parens off `has_own_line_leading`, a *range* reading of the same one-sided question, so `if (⏎/* c1 */ /* c2 */⏎x)` came out split across three lines where prettier writes `if (/* c1 */ /* c2 */ x)`; the binary operator→operand gap kept the run intact (it already asked `comment_hugs_next`) and pre-empted only the BREAK, gating on the newline-*after* half alone (`Printer::comment_hangs_binary_operand`, prettier's `hasLeadingOwnLineComment` — which prettier asks at the assignment seam, of the node the comments lead, not here), so the chain **and its enclosing `=`** opened on `x +⏎/* c1 */ /* c2 */⏎y`. Both fixes are the same sentence twice: the run is `push_leading_comment_run`'s to emit and the shell's break is the run's REPORT. The tell that one is left is tsv disagreeing with itself between symmetric positions — the C-style `for` head collapsed that authoring for as long as the `if` head split it. Pinned by `statements/if/condition_glued_comment_run` and `expressions/binary/operator_glued_comment_run`.

⚠️ **A run's own-line-ness and the run's INTERNAL shape are two questions, and a gap emitter that bucketed comments by line answered only the first.** The control-flow gap builder (`Printer::build_comments_between_parts`, serving `if` / `while` / do-while / `for` / for-in / for-of / `switch` / `try` / `catch` / `finally`) partitions its comments into *trailing the anchor* vs *off the anchor's line* against fixed anchors, which is exact for **that** question — a glued pair shares one physical line, so both halves answer `is_same_line(anchor_end, …)` alike. Reading how the run's comments sit relative to **each other** off those buckets is the same fixed-anchor error one step in: `is_same_line(c.span.end, body_start)` measures across every later comment in the gap, so `if (a)⏎/* c1 */ /* c2 */⏎{}` reported both comments own-line and the emitter gave each a `hardline`, **splitting a pair the author wrote as one line** — at the condition→`)` gap too, and in the `while` / do-while / `for` / for-in / for-of / `switch` / `try` / `catch` / `finally` spellings of both. The glue question is per comment, asked of its own neighbour (`comment_hugs_next` of the previous comment in the run), and the buckets say nothing about it.

⚠️ **Whether a glued pair survives is a property of WHICH RUN the gap is, not of the emitter** — which is why that fix is a per-gap policy rather than one unconditional space. The same three gaps are three different things in prettier's attach phase (`handle-if-statement-comments.js` and its `while`-like / `try` / for-x siblings), and each printer answers differently: a condition→`)` comment is a **trailing** comment of the test, and `printTrailingComment` gives the second of a glued pair a `lineSuffix([" ", …])` — glued; a header→body comment is a **leading** comment of the body, and `printLeadingComment`'s glue test reads the source right after each `*/` — glued; a `}`→continuation-keyword comment is **dangling** in the statement, and `printDanglingComments` is a `join(hardline, …)` — **split**, which tsv matches, so `}⏎/* c1 */ /* c2 */⏎else` is two lines in both formatters and is the null control any fix here must leave alone. `GapCommentRun` names the run rather than the policies because the two policies are not correlated: a leading run glues and drops an author blank above its first comment, a trailing run glues and keeps it, a dangling run does neither — three of the four states a bool pair would offer. Prettier's own inconsistency at the relocating gaps is the same rule read forward: it keeps the glued pair when it lands the run in a `catch (e)`'s parens (trailing) or in front of a `case` (leading), and splits it when it lands in an empty block (dangling). Pinned by `statements/{if,while,for}/head_body_glued_comment_run`, `statements/if/condition_comment`, and the two relocation divergences `statements/{switch,try}/head_body_glued_comment_run_prettier_divergence`. ⚠️ **And WHICH SPELLING of the glue test is the run's, not the emitter's** — the same fact one step down. Prettier's two printers are each internally consistent about which end of the region between two comments they read: `printTrailingComment` anchors on the COMMENT and reads backwards (`hasNewline(…, locStart(comment), { backwards: true })`, `isPreviousLineEmpty(locStart(comment))`), `printLeadingComment` anchors on the `*/` and reads forward (`hasNewline(locEnd(comment))`). tsv has both spellings — `Printer::trailing_run_hugs_previous` and `Printer::comment_hugs_next` — and its own docs already say they are not equivalent, parting on re-emitted structure between the two comments. At a control-flow gap that byte is a **stripped grouping paren**, so asking the forward spelling of the trailing run WELDED a comment the author gave its own line onto the previous one (`if (⏎(⏎x⏎/* c1 */)⏎/* c2 */⏎)` → `x⏎/* c1 */ /* c2 */`, and with a `//` second the weld lands a line comment mid-run). One method answers it and the blank question together (`GapCommentRun::reads_backward_from_comment`), because they are the same fact; keyed on the run, since the forward reading is CORRECT for a leading gap — prettier welds across a `(` glued to a comment there too.

⚠️ **Whether an author blank ABOVE a run's first comment survives is a property of WHICH RUN the gap is, and it is prettier's mechanics rather than a stance.** A **trailing** run's blank sits between the value and the comment, where `printTrailingComment` emits it (`isPreviousLineEmpty`) — kept, at a unary operand's stripped-paren gap, a condition's `)` gap, a retained operand shell's operand→`)` gap (a non-null's, an angle-bracket assertion's), a binary operand→operator gap. A **leading** run's sits between the introducer (an operator, a keyword, a delimiter) and the comment, and `printLeadingComment` has no emitter for it at all — its only blank check is the FORWARD one, after each comment — so it is dropped, at a value's `=`, an object `:`, a call argument, an array element, a `return` operand, and every control-flow header→body gap. A blank *between* two comments is never this question: it separates two distinct remarks and survives in both kinds of run. ⚠️ **The two questions TOUCH at one seam, and there the gap's own bucketing decides which one is being asked**: where the anchor's line already carried a comment, the blank below it is the between-two-comments kind even though it is still the blank above the run's first OWN-LINE comment. `Printer::build_comments_between_parts` emits the anchor-line bucket in one loop and the own-line bucket in another, and seeding the second loop's blank scan from the RUN's policy (rather than from the last comment the first loop printed) collapses the two — dropping `while (a) // c1⏎⏎// c2⏎{` at every control-flow header→body anchor, where prettier keeps it. The scan floors on whatever the emitter last put on the page; only an empty anchor-line bucket falls through to the run's seed. **That floor is also what stops the scan FABRICATING one**, and the two gaps that seed from a position rather than from `None` are where it did: measured from the `}`, a `}`→`else` gap's scan crosses the comment trailing it and reads that comment's own interior newlines as an author blank (`} /* c1⏎⏎*/⏎/* c2 */⏎else`, a blank neither the author nor prettier wrote), pinned with its no-interior-blank null control by `syntax/comments/keyword_gap_multiline_block_interior_blank`. The **glue** anchor is deliberately not shared with it (a comment glued to one trailing the anchor is a third question), so the two part company in that one function — one question, one predicate. Two emitters name the split — `GapCommentRun::blank_seed` (`Some`/`None`) for the control-flow gaps, `RunLeadingBlank` for `Printer::push_anchored_trailing_run`, which three trailing gaps and one leading gap share. That shared emitter is where the rule bit: the binary **operator→operand** gap is a leading run that borrows it for its anchor rule (a comment on the operator's line trails the operator) and inherited the trailing blank rule with it, keeping a blank prettier cannot emit — the lone leading gap in tsv that did. Pinned by `expressions/binary/operand_own_line_block_comment`.

⚠️ **A gap emitter that re-derives the BLANK rule fabricates one, and the fabricated line is its own fixed point.** The blank a control-flow gap keeps between two own-line comments (and above the first, where the gap seeds one) goes through a shared emitter, never a hand-rolled `literalline` off the table-only `has_blank_line_between`: either endpoint of these gaps is a node span that EXCLUDES a delimiter the printer still emits — a grouping paren the condition's span starts inside (`if (⏎(⏎x⏎)⏎/* c */⏎)`, `while (⏎/* c1 */⏎(⏎/* c2 */⏎x⏎)⏎)`) — whose two newlines a counting scan reads as an author blank, so tsv wrote a blank line the author never did, at the condition→`)` gap and at both spellings of the `(`→condition one. **Which** shared emitter is the RUN's rule, not the gap's (`GapCommentRun::reads_backward_from_comment`), and it is prettier's own split: a trailing run asks `isPreviousLineEmpty` of the comment (`Printer::push_adjacent_blank_hardline` — `printTrailingComment`), a leading one measures forward from the previous comment (`printLeadingComment`'s `skipNewline` + `hasNewline`, which tsv answers with the gap-wide strict scan, `Printer::push_blank_preserving_hardline`). The two readings part only where re-emitted structure sits between the blank and the comment, which is exactly the erased shell: keyed on the run, tsv erases a blank in the shell's TAIL with it (`if (⏎(⏎x⏎⏎)⏎/* c */⏎)`, a trailing run — prettier agrees) and keeps one written directly ahead of a comment in its HEAD (a leading run — a cataloged divergence, the same authorship claim the element-comma seam makes). Nothing standing sees any of this — every one of these forms is stable under both formatters, so F1, the ledger, the census and the blank ratchets pass, and `fabrication:audit` injects blanks rather than erasing shells; only a prettier `compare` finds them. Pinned by `statements/if/condition_comment` and `statements/do_while/condition_own_line_comment_run`'s `unformatted_stripped_paren` variants, each carrying the author-blank null control beside it, and by `statements/if/condition_shell_blank_before_comment_prettier_divergence`.

⚠️ **The same rule reaches every VALUE gap, and there a BREAK GATE asks it too — in which case the gate must take the emitter's spelling.** A ternary branch gap (`?`/`:` → the branch) is a leading run like the header→body ones, so its blank goes through the strict scan; `value_start` is the branch's own span start, which for a **parenthesized branch lies inside the stripped shell**, putting the erased `(` between the comment and it. Counting newlines there read that `(`'s two line breaks as an author blank — and because a blank in this gap is *also* what drops the value onto its own line and forces the whole ternary open, one bad reading moved the layout, not just a line: `a ? /* c */⏎(⏎b⏎) : c` came out broken across five lines where prettier writes `a ? /* c */ b : c`. Both readings had to move together, since the emitter (`emit_ternary_branch_comments`'s `blank_before_value`) and the gate (`Printer::comment_followed_by_blank`, the ternary's `has_blank_separated_comment`) are one question asked twice — a gate left on the table-only count fabricates the break on its own, with the emitter then agreeing about a blank it no longer wants. Reverse-patching either half alone fails the fixture, which is what says both are load-bearing. The author-blank null control sits in the same file and is untouched: a real blank through the same shell still keeps the blank and the break, in both formatters. Pinned by `expressions/conditional/branch_comment_blank_line`'s `unformatted_stripped_paren` variant.

⚠️ **The GLUE question at a value gap is the same defect in its other half, and it has one spelling: the comment's own neighbours.** "Did the author break after this comment?" is `Printer::comment_hugs_next` — prettier's `hasNewline(text, locEnd(comment))`, which skips spaces and tabs and asks about the very next byte. Spelled instead as a distance to the value (`is_same_line(comment_end, value_start)`, `has_newline_between(c.span.end, next)` where `next` falls through to the gap's end), it reads whatever stands between them, and at a value gap what stands there is a **grouping paren**: the author's break sits INSIDE the shell (`= /* c */ (⏎v)`), the printer never reproduces it, and the gate reports a break after a comment the author glued — hanging a value prettier hugs. The paren need not even be stripped: an object arrow body keeps its required parens and the body's span still starts past the `(`. **Six sites shared that one defect** — `Printer::broke_after_value_leading_run`, the arrow's `Printer::has_own_line_post_arrow_comment`, the `=`→value partition's hang gate, `Printer::comment_run_glued_through`, the object property's `:` gate, and the `AdjacentGlued` arm of the leading-run emitter — which is why the operator→value rule is now stated once (`Printer::comment_hangs_value_after_operator`) with the glue half delegating to `comment_hugs_next`, and why `Printer::any_comment_on_page` exists beside the `_with_next` form: a gate that binds the anchor only to ignore it is an invitation to re-derive glue from the wrong thing. The tell that a site is left is tsv disagreeing with itself between sibling seams — here the arrow was the only one of its four that un-glued a multiline block the author glued, and the assignment expression the only one of its siblings that hung a line comment the declarator and the class field trail. Pinned by `syntax/comments/value_leading_run_glued_across_paren` (the whole family, one authoring per seam, with the trigger on `unformatted_paren_break` since prettier's fixed point normalizes it away), `expressions/arrow/body_glued_multiline_block_comment` and `expressions/assignment/rhs_line_comment`.

⚠️ **The one break `will_break` cannot see is a DEFERRED one**, so a shell whose gap can hold a `//` still needs an explicit gate: a line comment rides a `line_suffix`, which reports no break and would let a flat shell carry the comment out past its own closer. That is the deferral hazard below, not a layout choice — the unary's shell asks `has_line_comments_between` over its trailing gap for exactly this and nothing else.

**A dangling comment is the one position that does not ask it.** With no item left to lead, the container's closer pulled onto the comment's line is not glue (`{ a: 1⏎/* c */ }`, `[a,⏎/* c */ ]`), and prettier expands there. Both the bracket-list and object-family gates carve it out on "does any item start at or after this comment", never on what shares its line.

⚠️ **The last-item→closer gap holds the list's own comma, so it is an ITEM gap, not a delimiter one.** Under `trailingComma: 'none'` that comma is deleted, so a block comment the author wrote after a comma pushed onto its own line (`f(a⏎, /* c */)`) has no line of its own to keep: it trails the item, prettier trails it too, and an `is_same_line(item_end, …)` reading calls it own-line and — through the hardline that placement carries — force-opens a list that fits. `Printer::closer_trailing_comment_run` is that position's claim, `Printer::has_own_line_block_comment_before_closer` (`block_comment_owns_its_line` with `item_follows: false`) the gate over it, and the two must agree: a gate that breaks a list around a comment the emitter puts back on the item's line opens it around nothing. Everything the seam's own §The element-comma seam rules say holds here too — the claim is a PREFIX, it ends at the first `//`, and it is the same walk the object literal and array literal already took, which is why those families were never wrong about it. The families that were: value parameter lists, call and `new` arguments, dynamic `import()`'s options, and the type-side parameter lists (function and constructor types, call / construct / method signatures).

**A LINE comment in that gap keeps the item anchor, and that is a sanctioned divergence rather than an oversight.** The after-comma anchor's argument is that the printer pulls the comma back onto the item's line — which reaches a *block* through the source it is glued to, and stops at a `//` written against a comma that is not in the output at all. Prettier hoists such a `//` onto the last item; tsv keeps the line the author gave it, the same form both formatters already agree on when the author writes no trailing comma. See [conformance_prettier_ts_comments.md §Comment relocation](./conformance_prettier_ts_comments.md#comment-relocation) ("**Last**-item trailing-comma line comment"). It is the one place `closer_trailing_comment_run` and the inter-item `trailing_comment_run` part ways, and the whole reason there are two walks.

⚠️ **That anchor is the last CLAIMED comment, not the item — the licence stops where its argument stops.** The argument is about the **comma**, so it reaches only a `//` with nothing but that comma ahead of it on its line. A comment the run has *already claimed* is content the printer itself pulls onto the item's line, so a `//` the author glued behind its `*/` has to travel with it: anchoring on the item strands it, splitting a pair written as one while the block it was written against moves up without it (`f(a⏎, /* b */ // c)` → `a /* b */` with `// c` alone below, where prettier and the author both have `a /* b */ // c`). The same advance is what keeps a `//` claimed past a *multi-line* block's `*/` — a line the item's own never touched — which is the shape that reached every argument list (`fn(…)`, `new`, `import()`, member chains) and the intersection's member gap while the families served by `build_trailing_gap_comments_ext` were rescued by the glue rule above. Pinned by `calls/trailing_arg_glued_run` and `types/intersection_trailing_glued_run`.

⚠️ **A comma-less closer gap is no exception.** `require('x')` and a `import(…)` with no options were held on the delimiter reading (`PartitionedComments::new`) on the argument that their gap holds nothing the two readings disagree about. It holds one thing: another comment's `*/`. The comma is not what makes the source reading necessary — only the loudest byte that needs it — so **every** gap past a `(` takes an item constructor and `new` is purely the delimiter reading its name describes.

⚠️ **A separator that CROSSES an operator carries no author blank.** The intersection emits a before-`&` own-line comment *after* the `&`, so a blank the author left ahead of that comment was written in a gap the printer does not reproduce — the operator is pulled back onto the previous member's line. Re-emitting it fabricates a blank prettier never writes, and one that does not survive: it lands after the `&`, where the next pass reads it as the after-operator gap and drops it, so the form has no fixed point (F1). Only the FIRST such comment crosses; a blank *between* two own-line comments never crosses anything and is the author's, kept by both formatters. Pinned by `types/intersection_trailing_glued_run`'s `unformatted_blank_before_amp` variant.

⚠️ **A construct that only *mirrors* a comment-aware one inherits none of this, and reads as finished while dropping everything.** The rule reaches a gap through the emitter that claims it, so a printer with no emitter there answers nothing — it is not wrong about the gap, it cannot see it. Both TypeScript **type**-level twins of a comment-aware value printer sat that way: an import type (`import('./a' /* c */)`, `import('./a', {…} /* c */)`) took the delimiter reading, never emitted the dangling half, and scanned neither options gap, while a template-literal type (`` `a${B /* c */}` ``) claimed its `${`→type gap and left the type→`}` one to nobody. Every comment in them was DROPPED, and no gate could say so: the ledger and the census see a document only as authored, both shapes are rare enough that the corpus carries none, and the output is idempotent without them. The fix in both cases was to stop mirroring — the import type now shares the dynamic-import expression's whole argument layout (`calls::build_import_args_comment_layout`), the template-literal type takes the shared closer-gap walk below — because a copy that has to be *told* about each new gap is the shape this whole file exists to prevent.

**The source reading is sound at every gap that FOLLOWS a printed item, not only the ones holding a comma** — which is why `Printer::build_trailing_gap_comments` serves three gap shapes with one walk. Its `start` is never an opening delimiter: it is a last item's end (the **closer** gap — a list's `]`/`>`/`)`, and a template-literal type interpolation's `}`), an angle-bracket cast's `>` (a **delimiter** gap), or a union member's end (an **operator** gap), and at each of those "does content precede this comment on its line" is the same question the anchor is only a lossy proxy for. ⚠️ Only the closer gap can **observe** the difference, and knowing why is what licenses the shared walk: the two readings part exactly where text no item span covers sits on the comment's line, the closer gap is the one holding the list's own comma, and the other two hold nothing but trivia. The one byte that reaches them is another comment's `*/` — but a comment claimed for *that* reason is glued to its predecessor, so the trailing arm and the glue rule above emit the same space. The two arms agree on exactly the set the two readings disagree about, and either one alone already prints `| A /* a⏎b */ /* c */⏎// d⏎| B` the way prettier does — it is the delimiter reading with *no* glue rule, the state before this seam was unified, that split the pair the author wrote on one line. Pinned by `syntax/comments/trailing_gap_glued_run`. A gap whose anchor genuinely IS the delimiter keeps the delimiter reading — `PartitionedComments::new`, `Printer::delimiter_line_comment_prefix` — and does not belong in that walk. ⚠️ **But the delimiter reading is a claim about a comment ON the delimiter's line, never a break gate**: a `(`-anchored predicate that force-opened a type-side parameter list for any block written *below* the `(` was the delimiter reading escaping its position, and it expanded `(⏎/* c */ a: string)` — a comment glued to its param — where both formatters otherwise collapse. The gate that gap actually wants is the two-sided `Printer::block_comment_owns_its_line`, which sees the param on the comment's line.

**Refusing to FORCE a break is not the same as refusing to take one.** A comment sharing the `&`'s line still keeps the line the author gave it once the intersection breaks for width — the separator behind it is the source-keyed `line` of the leading-run rule above (`build_member_leading_block_comments`), left to the enclosing group. Answer the two questions in one place and something has to give: hardcoding a space there glued a member onto the run's `*/` line, and a `line` with no group to decide it breaks unconditionally (`{ a: 1 }⏎& /* c */⏎{ b: 2 }` — an object-adjacent boundary contributes no `line` of its own, so the builder has to ask for the group itself).

## The element-comma seam: the two runs must PARTITION the gap

A comma-separated list asks about one gap twice — the previous element's **trailing** run and the next element's **leading** run — and the two answers have to cover it exactly once. Both failure modes are live bugs: a comment neither side claims is DROPPED, one both sides claim is DOUBLE-PRINTED. `Printer::collect_trailing_comments` / `push_element_comma_trailing` (`printer/comments/element_comma.rs`) are the one statement of that split, shared by the object literal, both destructuring patterns, the import/export specifier list and the enum-member loop; the array literal reaches the same rule through its own printer — its holes and fill path don't fit the shared collector. The **comma arm** — before the comma a block trails, and on the LAST element (whose comma is never emitted under `trailingComma: 'none'`) the whole run trails, since there is no next element to lead — is `block_is_before_comma`, one pure statement shared by both. The `is_last` half is load-bearing: a hand copy that only asked "before the comma?" classified a block past the last element's *source* trailing comma as leading a next element that doesn't exist, and nothing printed it. It is now derived from the slot index in one place (`Printer::element_gap_split`) rather than restated per emitter.

**The array states its split as a POSITION, not as two filters.** `Printer::element_gap_split` walks the gap once and returns where the trailing claim ends; every emitter then takes a *range* — the trailing side `[elem_end, split)`, the next element's leading side `[split, elem_start)`, the end-of-array scan what neither covers (`Printer::end_scan_emits_comment`). A filter each side re-asks is the shape that drifts, and it drifted three ways at once here: the two sides read different gates, and the end scan read a third. Two properties only the walk can carry:

- **The claim is a PREFIX of the gap's comments** — the walk stops at the first comment that does not trail, so a later one is never claimed over an earlier one left to lead. `[a⏎/* c1 */ /* c2 */, b]` is the falsifier: c1 leads its line so it leads `b`, while c2 — with c1 before it on that line — reads as trailing `a`, and a per-comment filter returns the authored pair REVERSED. Same rule and same reason as the collector's `break`.
- **The gate is the SOURCE reading** (`Printer::comment_follows_content_on_its_line`), not `is_same_line(prev_end, …)`. Two kinds of text sit in the gap outside every item span — a stripped paren shell's `)` and the comma itself — and a same-line gate is blind to both. That blindness dropped `[a⏎/* c */, b]` outright (before the comma, so the leading scan starting past the comma never saw it; not on the element's line, so the trailing side did not claim it) and mis-bound `[(⏎a⏎)/* c */, b]`. It is the same question the expansion gate asks (`Printer::has_own_line_block_comments_in_bracket_list`), which is why the two had to move together: on an item-boundary reading the expansion gate's blindness *cancelled* the seam's, so tightening either one alone lost a comment. Every comma list now reads the source there; an item-boundary reading additionally *expanded* the list on both spellings, a third fixed point neither the bare authoring nor prettier produces. **Five gates ask it**, one per family shape, and each was blind in its own spelling: `has_own_line_block_comments_in_bracket_list` (the bracketed lists), `Printer::has_standalone_block_comment` (object and type literal, whose blind half also read the opening `{`), `should_force_expansion_for_comments` (call / `new` / `import()` arguments), `Printer::has_own_line_comment_between` (parameter lists, value- and type-level) and `has_own_line_attribute_comments` (an import/export clause's `with { … }` attributes, found last because its comma is the only one inside a *brace* list that is not the object literal's). The enum needs none: its body always breaks, so both authorings already reach one fixed point.

⚠️ **The gate's "which element follows this comment?" scan must accept a ZERO-WIDTH gap.** A comment GLUED to the next item ends exactly where that item starts (`[a,⏎/* c */b]`), so a strict `start > comment.end` skips the very element the comment leads, and the comment falls through to the dangling arm — expanding the list as though nothing followed it. That was **non-idempotent**, not merely a divergence: the expanded print re-emits the run spaced (`/* c */ b`), which un-glues the comment, and the second pass collapses. All seven families carried it, and the only thing that ever distinguished the two spellings was the space — authorship no reader could see. An item *containing* the comment is excluded a step earlier, so `>=` can only ever match the element the comment is glued to.

**Both ARMS ask it, and `is_own_line_comment` can only answer for one.** A `//` glued to that same stripped `)` trails its element exactly as a block does (`[(⏎a⏎)// c⏎, b]` → `a, // c`), but `Printer::is_own_line_comment` short-circuits `!is_block → true` and calls every line comment own-line — a *layout* answer, correct where it is asked (does this comment hang the value?) and wrong at a position seam. The line arm therefore takes the bare `comment_follows_content_on_its_line`, which is also what `is_own_line_comment` is now written in terms of, so the kind short-circuit exists in one place. ⚠️ **And the run then has to END at the first line comment**, which the anchored gate used to guarantee for free: nothing can share the element's line behind a `//`, so at most one could ever be claimed. Per-comment, every comment after a `//` starts a fresh line and passes the gate — and a second deferred `//` WELDS onto the first's output line, its delimiter becoming text inside the first comment and swallowing the code behind it (`[A// c⏎,// c2⏎B]`). Both `Printer::collect_trailing_comments` and the array's `element_gap_split` break there. The ledger is blind to the weld (each comment is printed once); `gaps:audit`'s swallow arm is what catches it.

**The seam is asked by the WIDTH emitters too, and they answer it with a range.** A list that lays out by width claims `[item_end, comma_pos)` wholesale and then resumes the next item's leading scan past the comma — two decisions, both wrong in the same way. `Printer::inline_trailing_run_end` bounds the run at the separator and hands back where it stopped: the claim shrinks to the seam's prefix, and the resume anchor moves back to that end (past the comma, an unclaimed comment has no other emitter and is DROPPED). Without it, an own-line block whose comma the author glued after it (`import {a⏎/* c */, b}`) was trailed onto the *previous* item — sliding BACKWARD across that item's own comma, the one direction this section says tsv refuses, and putting five families (specifiers, type-parameter declarations, type arguments, tuples, type-level parameter lists) at odds with every other list and with prettier. Lossless and stable, so only a `compare` finds it.

⚠️ **A deferred run LEADS the next item, so its last comment takes the LEADING separator, not the element one.** `Printer::emit_multiline_comma_with_comments` defers an own-line run past the comma and then emits the list's own hardline — which is right for a comment the author gave a line of its own, and wrong for one they glued to the comma (`<T⏎/* c */, U // x>`), where the author's line ends after the comma and prettier's `printLeadingComment` emits a space. Asking `Printer::comment_hugs_next` there is the whole fix; the array literal reached the same output by collapsing a soft `line` in its per-element group, so the two families disagreed about one authoring for exactly as long as this emitter answered with the element separator. An author BLANK then belongs **ahead** of a hugging run, where it was written — the element separator can only put it after, which splits the comment from the item it leads. And a blank forces the break wherever it is preserved: a soft `line` cannot carry one, so a list whose separator is a `line` must ask before choosing (`Printer::item_gap_has_blank_line`) — the object literal's comment-aware path routed a blank gap through `line()` and DROPPED the blank its own comment-free path preserves.

⚠️ **The same emitter's after-comma CLAIM arm asks the HUG question, not a trailing one.** Deciding which gap comments trail the comma instead of leading the next item is the other half of `emit_multiline_comma_with_comments`, and an anchor-line test (`is_same_line(elem_end, …)`) answers it wrong for a **block**: in a forced-multiline layout the next item always sits on a later line, so a block the author GLUED to that item (`A, /* c */ B`) reads as trailing and is torn off the item it was written against. That put the type-side lists — tuples, type-parameter declarations, type arguments, and the parameter lists of function/constructor types and call/construct/method signatures — at odds with the object / array / parameter families *and* with prettier, all of which lead the next item. `Printer::is_stranded_after_comma_block` is the one spelling of the split, shared with the declarator / for-init / heritage sites: **stranded** (a newline before the next item) trails the comma, **hugging** leads the item. A **line** comment has no hug question to ask — nothing can follow a `//` on its line — so it is claimed outright; a block ahead of one is *stranded by that same predicate*, which is what keeps the source-ORDER rule below satisfied without a second test.

⚠️ **Past the comma the anchor is the COMMA, and it is only asked where a comma is EMITTED.** The comma is re-emitted structure — the printer pulls it back onto the previous item's line whatever the author did with it — so a `//` written after a comma the author pushed onto a line of its own (`a⏎, // c⏎ b`) belongs to that comma, and an item-anchored reading (`is_same_line(item_end, …)`) hands it to the next item's leading run, re-binding it to an item it was never written against. Both the type-side emitter and the value-level parameter list carried that reading (`Printer::comment_on_comma_line`, `Printer::param_trailing_line_comment` are the two spellings now). The scope limit is the other half of the same argument: under `trailingComma: 'none'` a **last** item's source comma is deleted, so "the comma's line" is not a position in the output at all — the parameter list's last-item region belongs to its own-line loop, and claiming into it printed the comment TWICE. That limit is also where tsv parts from prettier, which hoists such a comment onto the last item (§Comment relocation, `last_item_line_after_comma`); everywhere the comma IS emitted the two agree, so only the anchor's scope is visible from outside.

⚠️ **The comma anchor is a COMMENT-classification read, so it takes the comment line-break table.** It decides whether a `//` leaves as a trailing `line_suffix` or falls to the next item's leading run, and `Printer::set_canonical` empties the *layout* table — against which every comment in the gap reads as on the comma's line, so the canonical reprint pulls an own-line comment the author wrote against the NEXT item up onto the comma (and, through `is_stranded_after_comma_block`, lets a block jump ahead of a `//` that preceded it). Outside canonical mode the two tables are the same slice, so the normal path cannot see which one a predicate picked — and neither can the guards: the output stays lossless, idempotent and reparseable, so `canonicalize:audit` grades it clean, and `compile_compare`'s parity bar tolerates a comment POSITION difference by construction. The rule is the field's own (`layout_line_breaks`: *never read this for comment classification*); the one place it can be caught is a canonical reprint diffed against the authoring.

⚠️ **A claimed after-comma run ENDS at the first `//` the gap has already emitted** — including one from *before* the comma, which the widened anchor newly makes reachable (`a // c1⏎, // c2⏎ b` folds two source lines onto one output line). A `//` ends its output line whichever way it was emitted, so a second welds onto it (`// c1 // c2`, the second delimiter becoming text — the comment stops existing and the code behind it is swallowed) and an inline block after one comes out REORDERED ahead of it. The question asks the comment's **kind only, never its anchor line**: an anchor-line `//` leaves as a `line_suffix` and an own-line one as a deferred hardline run, and both end the line the claim would land on — asking it with the anchor reading missed the second (`a /* x⏎y */ // c1⏎, // c2⏎ b`, where the block's `*/` pushes `// c1` off the anchor's line) and welded the pair. One spelling for both emitters (`Printer::gap_emitted_line_comment_before`), since a drift between them is a weld at whichever one drifted. `gaps:audit` is what catches this; a `compare` on the plain authoring does not.

⚠️ **WHICH blank is the FAMILY's rule, not the arm's.** A hugging run moves where the `literalline` goes; it does not change which region is measured, and `BlankRule` is the only thing that answers that (`Printer::separator_gap_has_blank`, asked identically by both arms). Answering the hugging arm with `isNextLineEmpty` for every family gave the **tuple** — whose rule measures past the comma — a blank prettier collapses (`[aaaa⏎⏎/* c */, bbbb]`), and dropped the one it does keep in the mirror authoring (`[aaaa⏎/* c */,⏎⏎bbbb]`). Both forms are stable once printed, so F1, the print-once ledger and `blanks:audit` are all blind to the pair; only a `compare` finds them.

⚠️ **The seam's ANCHOR must be the element's PRINTED end, not its span end.** The two differ by exactly the text the printer erases, so an anchor that swallows a stripped shell's `)` starts the trailing scan *past* the shell's interior — and no other emitter covers it, because the element's own doc stops at the value. The families whose anchor is the inner end (`Printer::element_gap_split` on the element's own span, the object literal's `ObjectProperty::value_end`, the enum on its initializer) preserve that interior; the ones whose element node swallows the closer do not. A destructuring **`Property`** and an **`AssignmentPattern`** both do — their spans end past the `)` — so `const {a = (1 /* i */), b} = x`, `({a: (b /* i */)} = x)`, `const [a = (1 /* i */)] = x` and the parameter form `f(a = (1 /* i */))` dropped the comment outright, block and line alike, where every inner-anchored family keeps it and matches prettier. `Expression::printed_end` is that anchor, and `ObjectPatternProperty::value_end` the pattern counterpart of the object literal's: both peel exactly the two node kinds whose span was extended over an erased closer (`AssignmentPattern` → its `right`, `TSParameterProperty` → its parameter), so the region they skip provably holds nothing but `)`, whitespace and comments. Anchoring inner is not the same move as the anchor SHIFT warned about below: that one hands the parent a region the node's own doc already prints, and here the node prints none of it.

⚠️ **The EXPANSION gates over that seam take the same anchor, and moving the claim alone is a content bug of its own.** They read the gaps *between* item spans, so a shell-interior comment is not in any gap they see — and a `//` the widened claim now emits from a list the gate still calls comment-free defers out of a construct that never breaks, past the `]`/`)` and even the function body (`const {a5 = (1 // c⏎), b5} = x` came back as `const { a5 = 1, b5 } = // c⏎x;`). Three gates ask it per family (`collection_formatting_hints`, `has_own_line_block_comments_in_bracket_list`'s "inside an element" test, and the params' `has_trailing_line_comment_in_params`), and each takes the element's PRINTED span. Their **blank-line** halves deliberately keep the span end, per the distance rule below — the same split, one function apart.

⚠️ **A frozen element is the exception, in both directions, and the anchor is the FROZEN SLICE's end.** A `prettier-ignore`d element prints its span RAW, shell and comment included, so anchoring inside prints the comment the frozen slice already carries a second time — and once more on every later pass, since the emitted form still carries the directive and re-freezes (unbounded growth, not a one-off duplicate). Each family resolves its own `Option<Span>` and hands it to `Printer::element_claim_anchor`; the span, not a `bool`, because **a construct may have more than one freeze position** and the question is *how far did we print*, not *did something freeze*. A parameter has two — the list gap (`Printer::param_frozen_span`, which also covers the decorators) and the decorators→binding gap (`Printer::param_binding_frozen_span`) — and an outer-only reading reports "not frozen" for a binding the inner one emitted verbatim (`@dec⏎// prettier-ignore⏎a = (1 /* c */)`). The **expansion** gates above do not need the exception: their range is a superset either way, so a frozen element's interior comment can only over-report a break the frozen slice's own newlines already force.

**A scan that measures a DISTANCE wants the other end of that same difference.** Claiming a comment and measuring a blank line are opposite questions about one shell: the claim must start inside it (above), while a blank scan anchored inside counts the shell's own line breaks as an author blank and FABRICATES one — `[a, (⏎b⏎)⏎/* c */] = x` grew a blank above `/* c */` that the bare authoring does not, and the fabricated form is stable once printed, so no ratchet sees it (`fabrication:audit` grades pristine seeds only). `Printer::element_shell_end` is that anchor: it steps over `)` and whitespace only, **stops at the first comment**, and returns the position just after the last closer — never past the whitespace behind it, since a blank the author wrote below the `)` is authorship. The two coexist precisely because it can never advance over comment text.

⚠️ **Every trailing dangling run needs it, and a container that HAND-ROLLS that run gets to be wrong about it separately.** Three families carried the fabrication — the array pattern (`Printer::build_pattern_trailing_dangling_comments`), the enum body and the object literal (`{ a: (⏎1⏎)⏎/* c */ }`) — and the last two are one bug only in hindsight: the enum reaches the shared end-of-body emitter (`Printer::build_trailing_body_comments_doc`), while the object literal kept its own copy of that walk and so had to be fixed a second time. The copy is gone; a container whose run may still COLLAPSE passes its separator instead (`Printer::build_trailing_closer_comments_doc`, the object literal's soft `line`). ⚠️ **The `anchor` stays unshifted** — "did the last item's emitter already trail this?" is asked of the *item's* line (`Printer::comment_already_trailed`), and advancing it past the `)` would call a comment on the closer's line already-trailed and DROP it, this run being the last emitter left.

**An ELISION is a slot, not an element, and it does not open a gap of its own.** The array's hole seams used to be answered by *counting commas*: the next real element's leading scan started past the last hole's comma, on the reading that the region before it was the hole seams' business. No hole seam prints anything, so it was nobody's, and every comment in that region was DROPPED — `[x⏎/* c */, , y]`, `[/* c */, y]`, `[x, /* c */ , y]`, and a two-comment run came back with only its tail. The rule is instead the same one as everywhere else, with the holes simply not moving the anchor: the LAST REAL element's split opens the next element's leading scan, however many elisions lie in between (`Printer::leading_comment_search_start_for`, keyed on `Printer::prev_real_slot`), and where no real element follows, the region slides to the array's own trailing position (`build_array_group_doc`'s `has_trailing_elision` arm, and the array pattern's). A hole prints nothing and its comma is re-emitted structure outside every element span, so a comment slides *forward* past it, losslessly; sliding *backward* across the previous element's own comma is the move tsv refuses, and is what prettier does here. Direction, not distance, is the rule. Two corollaries the same fact carries: a spread's stripped-paren share slides with it (emitting it against the spread's own comma made tsv's output disagree with tsv's reprint of it), and no BLANK line is measured across a hole — the elision's own line break is structure, not authorship (`Printer::has_blank_line_after_slot`, prettier's `node &&`), and reading it as a blank fabricated one the next pass removed.

⚠️ **The gap's FAR end is the same fact read forwards, and it is a second bound, not the same one.** If a hole does not open a gap, it does not CLOSE one either: the region after a real element runs to the next REAL element however many elisions intervene (`next_real_element_start`, with each container naming its own fallback — `array_gap_end`, `array_pattern_gap_end`). A one-slot lookup that gives up at a hole hands the earlier element the whole rest of the container, and it then claims a comment the later element claims too — `[a, , b // c] = x` printed the `//` on BOTH. The array literal walked past the holes from the start; the array PATTERN asked only slot `i + 1`, which is the twin-lag shape this file's hazards keep producing. Where that walk finds nothing, the fallback is the container's own trailing position, exactly as above. **But the blank-line scan takes a different far end in this one case** — the HOLE's own comma (`Printer::hole_slot_comma`, the second comma past the element), because a hole's printed content *is* that comma and nothing a caller emits in the gap prints before it; a scan run to the next real element instead reads the hole's own line break as an author blank. Both bounds are live at once, and asking either question with the other's answer is a bug in a different direction: the wide one DOUBLE-PRINTS, the narrow one DROPS the blank the author wrote against the element (`[a,⏎⏎,⏎b // c] = x`).

**The leading scan resumes at the trailing run's END, never past the separator.** A scan that starts at `comma + 1` cannot see what the author wrote on the *other* side of a comma they pushed onto its own line — `a: 1⏎// c⏎, b: 2` — and the trailing collector, which takes same-line comments only, does not claim it either. That comment had no emitter at all. Three sites had this exact drop — the object literal, the import/export specifier list and the enum-member loop — each with its own spelling of "start past the comma". The two destructuring patterns never did: they already resumed at `end_pos`, which is why the drop they *did* carry was the other one, below.

**That only works because the claimed run is a PREFIX of the gap.** The moment the collector *skips* something and claims a comment after it, a caller resuming at `end_pos` steps over the skipped one and drops it — which is what happened to a non-last element's after-comma block when a line comment followed it (`a, /* c1 */ // c2`). Keeping the claim a prefix is therefore a property of the collector, not advice to callers: whenever a same-line line comment defers the run, every same-line block ahead of it is claimed too.

**And that block is claimed for a second, independent reason: source ORDER.** The line comment defers through `line_suffix`, so a block left to lead the next element renders *after* it and the authored pair `/* c1 */ // c2` comes back reversed across two lines. It is emitted between the comma and the suffix — where it was written. Same rule and same reason as the deferred-run block in `push_trailing_comments_in_range` above; a reorder is as gate-blind as the weld there (nothing dropped, nothing duplicated, the output stable), so only a prettier `compare` or a payload-order census sees it.

**The interior gaps are not the whole list: both EDGE gaps need their own emitter.** A loop that opens a gap only when `i < len - 1` has answered every gap *between* items and neither at the ends — the `(`→first-item gap and the last-item→`)` gap have no emitter at all, so a comment in either is DROPPED. This is hazard 4 reaching a builder that is **not** comment-blind: it runs a real gap lookup every iteration, and that is exactly what makes the omission read as complete. Three call-argument builders carried it. Two are loops — `build_args_joined_with_comments` and `build_call_args_with_blank_lines`, between them reached by the multiline-content, function-composition, expand-first-fallback and blank-line triggers — every one of which *preempts* its caller's own comment-aware path, so nothing downstream covered for them and the loss was total (block, own-line, after-comma, and in the joined builder the trailing `//` as well). The third is the **expand-first inline tail**, and it shows the rule does not need a loop to be broken: it hand-rolled the interior gap as "the after-comma blocks that hug the next argument" and had no last-argument emitter at all, so a block trailing the tail (`}, /* c */ b /* t */)`) was dropped in all three spellings while a hugging one survived — the partial-payload signature of a **filtered** emitter (hazard 4, variant 2) sitting where the omission reads as deliberate. Each edge has a named counterpart to `Printer::open_inter_arg_gap`: `PartitionedComments::emit_last_arg_comments` closes the list, `emit_first_arg_leading_comments` opens it. A per-argument loop calls all three, or it loses comments at the ends — and a builder with **no** loop still owes both edges. All three now take the shared seam (`build_arg_gap_docs` for the interior, `emit_last_arg_trailing_comments` for the closer).

**A single-argument HUG arm loses the same edge gap with no loop at all.** The reassembling expand-last arrow layouts (`(sig =>⏎  call(…)⏎)`, `(sig =>⏎  cond ? a : b⏎)`) build the argument from its signature and body docs rather than printing the argument's own doc, so the argument→`)` gap has no emitter on that route — `chain_args.rs` had three such arms, and a forced expansion is still one of them: expansion picks which layout an arm renders, never whether a comment is legal in it. The fix is the refusal, not a fourth emitter — a comment anywhere on the last argument defeats the hug (prettier's `shouldExpandLastArg` returns false for a commented argument), so the arm declines and the standard broken-out form, which does run the last-argument emitter, prints it. The reassembling arms ask one named pair, `arrow_hug_refused_by_comments` = `arrow_signature_has_breaking_comments || arrow_body_tail_has_comments` (`arg_wrapping.rs`), stated once rather than re-derived per builder — three identical re-derivations is how the arms drifted apart in the first place — while `last_arg_has_comments` survives as the whole-call gate (`expand_last.rs`). An arm that renders the argument's own `expandLastArg` printing (the object/array terminal) asks the **signature half alone**, because its layout does print the argument's own doc and the oracle keeps it hugged for a leading comment; a narrower spelling needs that kind of argument behind it, not just a suite that passes.

**The expand-FIRST hug has the same refusal, and its question is asked of the ROUTED gap.** Prettier's `shouldExpandFirstArg` opens with `!hasComment(firstArg)`, and prettier binds a comment with nothing after it on its line as the *preceding* node's trailing comment — so a block the author STRANDED after the first argument's comma (`() => {…}, /* c */⏎b`) is the first argument's comment and refuses the hug, while one that HUGS the next argument (`}, /* c */ b`) leads that argument and does not. tsv's `first_arg_has_any_comments` asked only `[first_end, comma)`, took the hug, and — the inline tail emitting only what leads the next argument — dropped the comment outright, in all three spellings. The two answers are exactly the routed partition's two buckets (`PartitionedComments::for_routed_arg_gap`: `trailing_*` refuses, `leading` does not), so the gate asks it as the gap's own emitter asks it rather than re-deriving a comma-relative reading. ⚠️ **The routing step is not optional anywhere it appears** — partitioning without it reclassifies every hugging comment as stranded, moving it with nothing dropped and no gate firing, which is why the pair is one named constructor rather than two calls.

That first-argument emitter carries a second obligation, because the `(` gap is the one place a comment can land on a line the builder does not own. Its same-line run splits by KIND: a block-only run goes inline ahead of the first argument (so a call that fits stays on one line), but a run containing a line comment stays whole on the `(` line — tsv's sanctioned divergence — and is handed back to the caller to inject via `wrap_call_with_hard_breaks_paren_line`. Splitting a mixed run would reverse it, and letting a `//` ride the argument's line would swallow the argument.

⚠️ **The seam's BLANK question searches the gap for the comma, and bounding that search at the next item's CONTENT silently swaps in the other family's rule.** The array family alone measures its blank from *past* the separator (prettier's `isLineAfterElementEmpty`, which walks forward over comments to the `,` and only then asks `isNextLineEmptyAfterIndex`); every other list measures from the element's own end (`isNextLineEmpty`). `Printer::has_blank_line_after_comma` therefore reads **two different upper bounds, and that is the rule rather than a redundancy**: `upper` is where the next slot's printed content begins — pulled back to a leading comment when the slot has one — and it bounds the *blank scan*, which is what keeps a comment run out of the measured range (`'a', // x⏎⏎/* c */ 'b'` measures the blank *between* them); `comma_bound` is the next element's own start and bounds the *comma search*, because an author who pushes the comma below a comment (`[a⏎// c⏎, b]`) leaves the separator **past** that content. Bounding the search at `upper` made that comma invisible, and the no-comma fallback then measured from the element's end — answering an array with the **object family's** rule, the one thing prettier's two helpers say it must not do. It cost two bugs at once, in opposite directions: a blank the author wrote *ahead* of such a comment was KEPT where prettier drops it, and — the fallback range opening at a raw span end, inside a stripped paren shell — the shell's own `)` line was read as an author blank and one was FABRICATED (`[(⏎x⏎)⏎// c⏎, y]`). Both forms are stable under both formatters, so F1, the ledger, the census and the blank ratchets all pass; only a prettier `compare` finds them. Once the separator is found the count needs no strict reading: the range opens at `comma + 1`, where the only re-emitted delimiter that can follow is the next element's stripped `(`, which `skip_stripped_open_paren` already caps the range at — a `)` cannot follow a separator comma. Pinned by `expressions/arrays/element_own_line_comma_blank` and `expressions/destructuring/array_pattern_own_line_comma_blank` (the comma search) and `expressions/arrays/element_stripped_paren_trailing_line_comment` (the fabrication), each carrying the blank-after-the-comma null control beside it.

## The statement-gap seam: the claim stops where the next statement's line begins

A statement list asks about one gap twice as well — the previous statement's same-line
trailing run and the next statement's leading run — and the split is one predicate:
**a comment whose glued run reaches the next printed statement's line LEADS it**
(`Printer::comment_leads_next_item`, prettier's remaining-comment placement — code on
both sides of the run binds it forward), and everything before that comment trails.
The reach is a CHAIN, not one `is_same_line`: prettier's `isEndOfLineComment` extends
the comment's end through every comment glued after it before testing for the newline,
so only a newline **outside comment bytes** breaks the chain — a glued pair whose tail
is a multi-line block still leads whole (`a(); /* c */ /* x⏎y */ b();`), while a run
whose closing comment ends its line trails whole (`a(); /* c1 */ /* c2 */⏎b();`). The
scan is the **in-source** axis (an owned comment's bytes glue the chain like any
other's — the multi-line tail in that example is typically owned by `b` and rides
inside its doc, invisible to the to-emit iteration that must still glue the head).
The claim is a prefix by construction (a later comment's chain is a suffix of an
earlier one's), and `Printer::trailing_claim_end` states it as a POSITION, the
element-comma seam's rule: the trailing emitter takes it as its upper bound, the
cursor clamps to it (`find_end_with_trailing_comments(..).min(claim_end)`), and the
leading filter's `leads_target` escape (`Printer::comment_already_trailed`) admits
exactly the handed-over comments — so the two sides cannot claim past each other, and
a re-spelled half is a drop or a double-print. One rule across the family: the program
body, block and `namespace` bodies, switch consequents and the case-list gap (the
comment then leads the next `case`/`default` label via the between-case run), class
bodies, interface bodies, and both type-literal member walks — where the width-aware
layout emits the handed-over run in the next member's segment, byte-identical when
flat so only the broken layout moves. (Enum members sit on the element-comma seam,
whose own machinery already chains glued runs.) The interface member walk stated the
same rule inline first; both its sides now route through the shared predicate.

Three slot rules bound the scan, because the gap can hold erased structure:

- **A dropped `EmptyStatement` closes its slot** (`statement_gap_floor`): a comment
  before the `;` trails the content before it however the lines fall
  (`a(); /* c */ ; b();`), while one after it leads (`a(); ; /* c */ b();`) — prettier
  binds both the same way, and the orphan arm's scan stops at the split so it neither
  swallows nor re-prints the handed-over run.
- **A type member's source separator is its slot floor** (`type_member_gap_floor`): a
  comment before the `;`/`,` trails its member (`a: A /* c */; b: B`), so the
  leads-next test opens past the separator.
- **A class body's stray `;` closes its slot too** (`class_member_gap_floor`), and it
  has no node to key on — the parser drops it without an `EmptyStatement` — so the
  floor reads the source, past the LAST stray `;` in the gap
  (`a = 1; /* c */ ; b = 2;` trails, `a = 1; ; /* c */ b = 2;` leads, both matching
  prettier).

⚠️ **The BLANK question wants the opposite treatment of that same dropped `;`, so the
list carries two cursors.** The comment cursor advances past a `;` that prints nothing
(the slot rules above); the blank question must not, because prettier's
`printStatementSequence` skips an `EmptyStatement` outright and asks `isNextLineEmpty`
of the previous **printed** statement — the `;` is never asked about and can never move
the anchor. Measuring from the shared cursor was wrong in both directions at once:
`a();⏎⏎;⏎b();` lost the author's blank (it sits *above* the `;`, behind the cursor) and
`a();⏎;⏎⏎b();` gained one prettier drops (it sits *below*). So the list's `StatementBlankScan` tracks the
last thing actually PRINTED in its `anchor` — a `;` whose orphan comment run emits nothing leaves it
alone — and its `bound` caps the scan at that same `;`, the two halves of one
sentence: *the author's blank is whatever sits between the last printed statement and
the next thing in the gap*. Two rules bound the bound itself, each found by an existing
fixture: only a `;` that **starts a line** counts (one the author left on the previous
statement's own line, `a();; // c`, is trivia prettier walks straight over —
`skipToLineEnd` is `skip(",; \t")`), and it must lie **ahead** of the anchor (a `;` the
previous statement's trailing run already consumed sits behind it, and bounding there
inverts the range so every later blank reads as absent). Both copies of the walk carry
it — the block/program list and the switch consequent's own. ⚠️ Prettier's
`isNextLineEmpty` is **not** a drop-in for the count here: it byte-scans for `\n`/`\r`
and is blind to U+2028 / U+2029, which the line-break table sees (`syntax/whitespace/
line_terminators`). Capping the table-based count keeps the wider terminator class,
which is the mirror of the trailing-run separator above, where matching prettier's
byte-scanning helper is the whole point.

The split decides only the one-line authoring, where the forced statement-per-line
break must put the comment somewhere; both two-line authorings are dual-stable and
untouched — a comment that ends its line trails (`a(); /* c */⏎let b = 1;`), one on
the next statement's line leads. A `//` can never satisfy the leads test (its line
ends the chain before anything follows it), so the deferred-terminator machinery is
orthogonal to this seam. Pinned by the `*_gap_no_newline_comment` fixtures
(statement list, class body, switch consequent and case gap, type literal, and
interface body — the chain and modifier-start cases folded in alongside) plus the
slot-rule fixtures (`statement_gap_empty_statement_comment`,
`member_gap_stray_semi_comment`).

## The delimiter-line question: one rule, read at three points

"Does a comment sharing the opening delimiter's line stay on it, or lead the first element?" is asked by two families and one shell, and the answer is the same rule every time: **pull onto the delimiter's line only when the container is breaking anyway; otherwise leave the block to hug the first element**, so a container that would have fit still fits.

What differs is where each family can learn "is it breaking?", and that is why the predicates are not textually identical:

- The **list family** (`Printer::delimiter_line_comment_prefix` + `comment_on_delimiter_line` + `first_member_leading_comments`, `printer/comments/lists.rs`) has to derive it from the gap: `pc.has_trailing_comments() && should_force_expansion_for_comments(…)`. It returns `(prefix, Option<pull_pos>)`, and every consumer must drop the pulled comments from the first member's leading set — that is what `pull_pos` is for. The object-literal variant adds one arm with no call-family analogue (`pull_expanding_block`): an object preserves its authored multi-line-ness, so a source newline before the first property already means it will break.
- The **call family** knows it from the builder it is in. Its force-expanded builders ask one named predicate, `PartitionedComments::pulls_to_delimiter_line` — the chain and `new` call it directly; the plain call spells the conjunction inline because it independently needs the `force_expansion` flag beside it (`call_formatting`). (Asking `has_trailing_comments` alone once made the chain the one builder in the family that pulled a lone block.) Its collapse-capable path, `emit_first_arg_leading_comments`, asks the narrower `has_trailing_line` — there the only thing that *can* force the break is a `//` in the run itself, so a block-only run must not be pulled. Exclusion is structural rather than a `pull_pos`: the run is already partitioned into buckets.
- The **`import(…)` shell** is a call shape that borrows the list family's helper outright (`Printer::build_paren_leading_value_doc`, shared by the dynamic-import expression and the TS import type): its own layout decides the break, so the conjunction is the right reading, and taking the helper rather than a third spelling of it is what ended the period when both import spellings answered this gap differently from every other call. Its one addition is where the share STARTS — the `(`, not the gap's start, because that gap deliberately spans the paren and a comment written ahead of it is the head's (`Printer::paren_line_share_anchor`).

⚠️ So `has_trailing_line` vs. the conjunction is **load-bearing**, not drift — swapping either way is a real output change (a block-only run pulled onto a `(` breaks a call that fit; a conjunction on the collapsing path never pulls at all). The emission differs only in mechanism. When you touch one, read the other.

**Once a comment DOES stay on the delimiter's line, the gap ahead of it is one space, and it is the printer's — never the author's.** `fn( // c`, `new Foo( /* paren */`, `obj.fn( // c`, `require( // c`, `import( // c`, `super( // c`, `fn?.( // c`, `@dec( // c`, `[ // c`, `{ // c`, a function type's `( // c`, a parameter list's `( // c`, a required operand pair's `( // c` (an assignment target, an instantiation head, a non-null / sealed-chain shell), and every statement header's `( // c` (`if` / `while` / do-while / `switch` / `catch`, and all three `for` spellings) all write it, whatever spacing the author left (`fn(// c` and `fn(   // c` both normalize to `fn( // c`). Reading the author's spacing there is a fixed point every gate is blind to — F1, the ledger, the census and the injection audits all pass, and the width ratchet grades a column, not a run — so only a prettier `compare` or a cross-construct probe finds a site that drifts. ⚠️ **The rule holds only where the comment stays; where the printer instead pulls the run onto a line of its own the question does not arise**, and the do-while's `(` bucket is where the two meet: its run keeps the `(` line and takes the space, while the *same* run with the condition following on that line is glued to the `(` (`while (/* c1 */ /* c2 */ x)`) because prettier keeps that shape in the parens and is a live oracle for it. One question — does the run hold the delimiter's line? — decides both.

**WHICH comments stay is one rule, and the statement headers were the last construct answering it separately.** The rule: a **line** comment the author glued to the delimiter claims its line, at most one can (a `//` runs to end of line), and a **block** claims nothing — it renders inline inside the construct wherever the run is emitted, so nothing forces the construct open around it. `if` / `while` / do-while / `switch` / `catch` and all three `for` spellings now ask it, where they used to hand the whole gap to the leading run and let prettier's placement decide. Prettier is no oracle for the position — it un-glues at `if`-like heads and the C-style `for`, **glues** at for-in / for-of (emitting the rest of the head unindented at column zero), and relocates the comment out of the parens at do-while — so the one position that happened to agree was what froze the rule, the shape [conformance_prettier.md §Comment Position Philosophy](./conformance_prettier.md#comment-position-philosophy) warns about. What survives on the condition group's own axis (`OpenParenLineBlockComment`) is only the **block** half, which is genuinely do-while's alone. Pinned by `syntax/comments/condition_paren_glued_line_comment_prettier_divergence`, `statements/for/header_paren_glued_line_comment_prettier_divergence` and `expressions/unary/paren_glued_line_comment_prettier_divergence`.

⚠️ **One rule, TWO emitters, split by construct shape** — `Printer::split_open_delimiter_glued_run` (the type paren shells, the unary comment-holder, the restricted-production hang and ASI shell via `Printer::split_located_paren_glued_run`, every statement header, and the required operand pairs — the assignment target / instantiation head, the non-null's needs-parens shell and the sealed chain's, all via `Printer::build_leading_run_expanded_shell_doc`) and `Printer::delimiter_line_comment_prefix` (the container / call / member-list families, and the aligned union-member object's `{`). The first answers "does the run's FIRST comment claim the delimiter's line?"; the second pulls the whole same-line prefix and returns a position the container's own member walk excludes. Both write the printer's one space, and neither reads the author's. **There were three** — the restricted-production and ASI shells carried a third copy that differed from every other delimiter on the space (theirs was the caller's `"( "` text), the blank (no arm at all) and the line-break table (the *layout* one, which `Printer::set_canonical` empties, so a canonical reprint called every own-line comment glued). Folding it in is what leaves two. A new delimiter site asks one of these, never a third.

⚠️ **The author blank BELOW the pulled comment is a second fact, and the answer is KEEP — one value, every caller.** `Printer::push_delimiter_glued_blank` is the one emitter: the type paren shells, the statement headers, the unary comment-holder, the restricted-production hang (`return (` / `throw (` / `yield (`), the ASI operand shell, and the list / call families all push the same `hardline` on top of their own break. The pull moves the comment's LINE, not its membership, and a blank between a comment and what follows it is authorship — which is what every other leading-run emitter in the printer already says (`push_leading_comment_run`, `push_paren_shell_leading_run`). A blank between the delimiter and the comment is not this question: it sits against the delimiter, where both formatters drop it at every bracket.

⚠️ **The blank scan measures a DISTANCE, so it stops at the delimiter glyph.** At almost every site the delimiter precedes the comment (`fn( // c`), leaving nothing but whitespace between the comment and the content — but the **unary comment-holder**'s gap opens at the OPERATOR, so the author may put the `(` on a line of its own (`!! // c⏎(⏎x`). Scanning the whole gap read that `(`'s own line break as a second newline and **fabricated** a blank; ending the scan at the glyph also gives the right answer for a blank *below* it, which is the delimiter-adjacent one every bracket erases. Nothing is dropped or rewritten by a fabricated blank and the result is its own fixed point, so no gate in `deno task check` sees it — only a prettier `compare` or `fabrication:audit` over real code does (§The five hazards, hazard 5). `Printer::push_delimiter_glued_blank` takes `blank_scan_end` first for the same reason, so the scan spans no comment bytes either. Pinned by `expressions/unary/paren_glued_line_comment_prettier_divergence` cases c13–c15.

Prettier keeps this blank at **every** construct — `fn(`, `new Foo(`, `[`, `{`, `if (`, `while (`, `switch (`, `for (`, `!(`, `return (`, `yield` — from its own un-glued placement, so the KEEP side is a plain match rather than a divergence of its own. Pinned at each family by a blank case in the `open_brace_comment` / `open_paren_comment` / `open_bracket_comment` fixtures, each carrying the delimiter-adjacent blank as its control.

⚠️ **It was a two-valued axis (`DelimiterGluedBlank`) and the DROP side did not survive its own argument** — worth keeping in view, because the shape recurs. The argument was: a blank directly under a container's opening line is that container's **leading-gap** blank, which both formatters discard, and pulling the comment onto that line is what leaves the blank there. Two things sink it:

- **The null control measures a different gap.** `fn(⏎⏎a)` / `if (⏎⏎a)` / `!(⏎⏎x)` — the controls the argument cited — hold no comment, so what they clear is the delimiter→content blank, which tsv clears here too and which the paragraph above already excludes. The blank in question is comment→content, and tsv keeps *that* one from the un-glued authoring of the very same comment (`fn(⏎// c⏎⏎a)`).
- **The premise was true only after tsv's own pull.** "Directly under the opening line" is a fact about the OUTPUT, produced by the pull being asked about. So the blank's fate turned on whether the author had glued the comment to the delimiter — `fn(⏎// c⏎⏎a)` kept it, `fn( // c⏎⏎a)` did not — one authored blank with two fates, decided by something that is not about the blank at all. A rule conditioned on what its own output destroys reads as principled and is circular.

## A stripped-paren interior is a partition too, and an ANCHOR SHIFT is not one

The element-comma seam's rule — *two emitters, one gap, claimed exactly once* — has a second shape: a node whose own doc prints **part** of a region and leaves the rest to its parent. A spread's stripped grouping parens are the live case (`...(x⏎/* c */)` leaves comments in `[spread.argument.end, spread.span.end)`), and the split is the source's **own-line question** — the same question every other trailing seam asks:

- `Printer::append_spread_trailing_paren_comments` — the spread's doc — prints what shares the argument's line: the same-line blocks inline, and the same-line `//` (deferred through `line_suffix`). At most one comment can defer — a `//` ends its line, so everything after it in the interior is own-line by construction.
- the **parent** (array element loop, call/`new`/member-chain last-argument emitter, object property loop) prints the **own-line comments** — block or line — which need a line of their own that only the parent can give, each on its own line in source order. `Printer::spread_own_line_comments` is that share, and `push_spread_own_line_comments` emits it. Handing the parent the own-line *blocks only* (an earlier partition) left the own-line `//` deferred up onto the argument's line — a position-losing relocation prettier doesn't perform — and, in the array's end scan, printed **twice**.

⚠️ **Expressing the parent's share as an anchor SHIFT is the recurring bug.** Scanning the parent's trailing gap from `spread.argument.end` instead of from the argument's own end reads as the same thing and is not: it hands the parent the spread's share as well, so every same-line block and same-line `//` prints **twice**. Shifting it *back* is the mirror failure — the own-line comments then have no emitter and are DROPPED. The call family had both at once (three of its five last-argument paths dropped, two double-printed), because the question was answered per path instead of by one named predicate.

⚠️ **A stripped shell's LEADING run is the enclosing gap's, and the pair that says so is one span.** `Printer::leading_edge_shell_claim` finds the redundant shell at a value's leading printed **edge** — under an array suffix, an indexed access, a conditional's check type, an intersection's first member, or an author's extra paren layer, composing — and returns `[shell.(, inner.start)`. Its `end` is the gap emitter's widened window *and* the suppression key `Printer::with_claimed_shell_leading_run` reads, so a site cannot come to measure one window while the emitter claims another. Every enclosing gap that can hold one asks it: the keyword→value seam (through `Printer::keyword_value_stripped_paren_hang`), a union member's `|` gap, a tuple element's and a type argument's list gap, a conditional's `?` / `:` branch gap, and a function type's `=>` gap. Left to itself the shell emits a bare `hardline` at whatever indent it was built at plus a `flush_break` that opens the group it lands in — neither the gap's answer, and the reparse (which finds the comment in that gap) reproduces neither, so the two passes disagreed.

Four rules the claim carries, each of which has bitten:

- **A router asks it too.** A list that picks an all-hardline layout from "is there a line comment in here?" must ask through the same claim (`Printer::leading_edge_shell_line_comment`); routing to the width path leaves the shell printing its own run, which is the defect one step earlier. The union asks both shapes in order — its member may be a shell whose own gap is empty and still carry one inside it (`A | ((⏎// c⏎B)[])`) — never one *or* the other.
- **The claim must cover the whole doc, not the thunk.** A conditional branch's union and intersection arms rebuild the branch from parts and never call the branch thunk, so wrapping only the thunk left those two printing the shell's copy beside the gap's.
- **A second relocator must yield.** An intersection hoists its own first member's run (`intersection_first_member_hoist_comments`); at a gap that claimed, that hoist is a second emitter for one comment and declines. A **union's** first member is the mirror case and is why a union is NOT a descent link: the union reads its own leading region from four emitters across three layout paths, so an outer claim over any part of it double-printed whatever the author wrote between the leading `|` and the shell's `(`. The union claims that member itself instead. A **required paren pair** is the third relocator: where no enclosing gap can widen (an optional tuple element, a later intersection member) the pair itself opens over the run and prints it (`Printer::required_paren_open_run`'s `Edge` arm) — and where one *has* claimed, it declines, on the same rule.

- **A freeze outranks the widening.** A frozen item is a verbatim source slice over its OWN span, so the shell and its run are already on the page and the suppression has no emitter to reach: widening the window prints the run a second time. So the gap's freeze verdict is resolved FIRST, on the unwidened span, and handed to `Printer::leading_edge_claim_and_start` — never read back off the window it decides, which would let the shell's own run change the alone-on-line reading the directive is graded by. One freeze no gap can see is a composite's own Rule A leading-run freeze over the member the shell sits in; the intersection descent link declines on that itself.

Three consequences the parent also owns, the first two instances of "a deferred run must not leave the construct it was written in":

- A comment in that interior must force the argument list **open** (`Printer::spread_paren_comment_forces_expansion`). On a list that stays collapsed the spread's `line_suffix` drains past the call's `)` *and* its `;`, re-binding the comment to the statement (`fn(a, ...(b // c⏎))` → `fn(a, ...b); // c`). The array family needs no such gate — its brackets already break.
- The gap *after* the node may not defer its own `//` once the node's doc has deferred one (`Printer::defers_trailing_line_comment`, `PartitionedComments::demote_trailing_line_after_deferred`). Two deferred `//`s land on one line and weld into a **single** comment, the second `//` becoming text inside the first — the information-losing merge prettier performs here and tsv refuses.
- A share whose **last comment is a `//`** can have nothing glued after it, so at the END of a list the ordinary `[spread.end, closer)` gap emits **first**, its inline blocks landing on the argument's line ahead of any deferred suffix; a block-ending share keeps source order, the gap's inline block gluing onto the share's own line (`...b⏎/* i */ /* t */`, the order-divergence pin). `Printer::spread_share_ends_in_line_comment` is the one spelling of that ordering question, asked by both last-argument emitters.

## A clause gap partitions THREE ways, and two of them mean "takes its own line"

A control-flow clause gap — the condition parens' `test`→`)`, the `}`→`else`/`catch`/`while` gap, a header→body gap — classifies its comments by **line**, against *both* neighbours: sharing the anchor's line (trailing it), sharing the following token's line, or neither (own-line). That is three buckets, and `Printer::partition_comments_by_line` returns three.

⚠️ **Only the header→body gaps need all three; everywhere else the last two are one bucket, and destructuring them apart is a DROP.** A comment sharing the *following* token's line is the one a two-way reading forgets, because at every other gap in the printer that position doesn't exist as a separate case. Binding it to `_` silently deleted every comment written there — `if (a⏎/* c */) {`, `while`, `do…while`, `switch`, `catch`, and their multi-comment runs — from ordinary authored code, with prettier preserving all of it. Use `Printer::partition_comments_trailing_vs_own_line`, which folds the third bucket into the second and states the rule once; reach for the three-way form only where a **glued block comment leads the body inline** (`Printer::split_glued_comments`), which is the sole thing that bucket is separately good for.

The tell in the ratchet is a whole `(Node, clause→clause)` cluster that is **100% DROPPED** across every payload kind — a gate that skips a gap wholesale fails for every comment in it, not just the kind that triggered the skip (§The five hazards, hazard 4). Five clusters shared this one seam.

## Array family vs params family: whether the soft `line` collapses

Whether that soft `line` collapses is decided by one fact, and it predicts every list site. The **array family** — array literals, array patterns, and tuple types — wraps each element's run *plus* the element in a per-element `group` (`Printer::build_list_element_group`), so the `line` is measured against that element alone and collapses (`/* c1 */ /* c2 */ a`) even while the list itself is broken. The **params family** — function / type-parameter / type-argument / call-argument lists — gives an element **no group of its own** (the width path is a bare `join([",", line])`; the comment-forced-multiline path is a hardline-joined list), so the identical `line` has nothing to be measured against but the enclosing broken group, and breaks (`/* c1 */ /* c2 */⏎a`). This mirrors prettier exactly: `printArrayElements` pushes `group(print())` per element and `print()` carries the leading comments (`print/array.js`), while `printFunctionParameters` / `printTypeParameters` / `print/call-arguments.js` do not. Don't re-derive it per site — and don't "fix" a params-family break by adding a group, or an array-family collapse by removing one.
