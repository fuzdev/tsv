**Escaped whitespace ending a prelude**: an at-rule prelude can end in an escaped whitespace (`@layer a\ ;` — the layer is named `a `, since `\ ` is a valid escape whose escaped code point IS that space, css-syntax-3 §4.3.4/§4.3.7). tsv preserves it. Prettier trims it as padding, stranding the backslash onto the `;`, which it then escapes: alone, prettier's output no longer parses (tsv rejects `@layer a\;` with `Expected '{' or ';' after 'at-rule prelude'`); in context it parses but the prelude swallows everything up to the next `{`, silently **merging two at-rules into one**. Prettier gets the block form right (`@layer b\ {`), where the payload space already separates the prelude from the brace — and tsv likewise adds no second separator there. Same rule, same reason as [CSS: Values §Escaped whitespace in a value](#css-values). See [layer_escaped_whitespace](../tests/fixtures/css/at_rules/layer_escaped_whitespace_prettier_divergence/).

**Escaped control char in an at-rule name**: an escape *inside the at-rule name token* (`@m\A x`) is part of the name — Svelte's `parseCss` (and tsv, matching it) decode the whole run to the name (`"m\nx"`, a control char mid-name), with an empty prelude. Postcss/prettier instead **split** the name at the escape into a name plus a prelude (`@m \A x {`), and reject outright when the name *starts* with an escape (`@\6D edia` → "At-rule without name"). tsv can't adopt prettier's split without contradicting its own parse, so it emits the name from **source**, preserving the escape verbatim (`@m\A x {`) — the decoded control char never lands raw in the output. Emitting the *decoded* form would inject a raw newline, corrupting the file, and drop the escape on reparse (name `m\nx` → `m`) — content loss and a broken fixed point. Same escape-preservation rule as escaped property names, which both formatters keep verbatim (`escaped_property_name`, no divergence). The end-of-name subcase (`@n\A {`, the escape needs a terminator space) adds no second separator before `{`, the same absorption as [Escaped whitespace ending a prelude](#css-at-rules) above. See [name_escaped_control_char](../tests/fixtures/css/at_rules/name_escaped_control_char_prettier_divergence/).

**`selector()` argument**: `<supports-selector-fn> = selector( <complex-selector> )` (css-conditional-4 §"Extensions to the @supports rule"), so tsv parses the argument as a selector and prints it with the same printer a rule's own selector uses — `selector(div>span)` normalizes to `selector(div > span)`, `selector(div[data-attr=value])` to `[data-attr='value']`, exactly as those selectors format in rule position, and matching prettier ([supports_selector_interior](../tests/fixtures/css/at_rules/supports_selector_interior/)). The position therefore inherits tsv's cataloged selector-printing choices (the column combinator, the An+B leading `+`, …) rather than a second set of rules. The grammar's argument is a *single* complex selector, but a comma-separated list is read as the list it lexically is — the singular production decides whether the condition is true, which is not a formatting question. Three divergences follow from the grammar rather than from taste:

- A selector **list** stays on the prelude's line, where prettier breaks it one selector per line. A selector's break points belong to a rule's selector list; a condition's own wrapping is the `and`/`or` fill.
- An argument that does **not** parse as a selector — an attribute value that is neither identifier nor string (selectors-4 §"Attribute selectors") — makes the whole thing a `<general-enclosed>`, the third arm of `<supports-in-parens>` (css-conditional-3), whose production is `[ <function-token> <any-value>? ) ]` (mediaqueries-4 §"Syntax"): grammatically valid, contents undefined, "the result is false". tsv keeps those tokens as authored (whitespace runs collapsed); prettier re-prints them as a selector regardless, quoting `[data-attr=1.50]` to `[data-attr='1.50']` — a repair, not a normalization, and one that can flip a false condition true. Both cases: [supports_selector_argument](../tests/fixtures/css/at_rules/supports_selector_argument_prettier_divergence/). *As authored* is also what bounds a **comment** here: no whitespace is inserted on either side of one, so `selector([data-attr=1.50]/* c */.class)` keeps its glue — a space would turn the compound into a descendant `[data-attr=1.50] .class`, and this arm has no parse to tell a compound boundary from a combinator one. That is the same answer the parsed half gives a glued compound-internal comment ([§CSS: Comments](#css-comments), Combinator boundaries), so one `selector()` argument does not get two rules. A comment also switches prettier's own treatment of the argument — it freezes the tokens verbatim and drops the quoting repair above — so both formatters agree on every comment-bearing argument, in `@supports` and in `@import`'s `supports()` alike ([supports_selector_comment](../tests/fixtures/css/at_rules/supports_selector_comment/), [import_supports_condition](../tests/fixtures/css/at_rules/import_supports_condition/)). Two comments **glued to each other** are the exception, and about layout rather than tokens: both print the run glued, but prettier then breaks the prelude across lines — the same stable relocation its printer makes on a glued comment run in rule position ([§CSS: Comments](#css-comments), `compound_comment_run`).
- A CSS function name is ASCII case-insensitive (css-values-4 §"Functional Notations"), so `SELECTOR(…)` is the same function. tsv recognizes it either way; prettier's check is case-sensitive and falls through to its declaration path, emitting `SELECTOR(div: hover)` — no longer a selector. See [supports_selector_name_case](../tests/fixtures/css/at_rules/supports_selector_name_case_prettier_divergence/).

The declaration rules that apply to a `<supports-decl>` — the space after the value `:`, the spacing around a boolean operator — never reach inside a function's argument, in either at-rule. A boolean keyword is an operator only where the grammar can start one (after `(`, after `)`, or at the beginning of a condition), so a value spelled `and` (`(font-family: and)`) and a class named `.and` are ordinary identifiers; the space after `:` is likewise decided by the property name, looking past any comment between them ([supports_condition_spacing](../tests/fixtures/css/at_rules/supports_condition_spacing/)).

**Spec violations**: CSS Syntax 3 §4.3.4 specifies that an identifier immediately followed by `(` tokenizes as a `<function-token>`, not as an `<ident-token>` plus `(`. Media Queries 4 §3 explicitly notes: "Whitespace is required between a 'not', 'and', or 'or' keyword and the following '(' character, because without it that would instead parse as a `<function-token>`." Container Queries (CSS Conditional 5) use the same grammar pattern. Prettier normalizes this for `@supports` but not `@media`, `@container`, or the `supports()` argument of an `@import` prelude; tsv normalizes all four.

**`@import`'s `supports()` argument is a condition, read by the condition reader.** `supports( <supports-condition> | <declaration> )` (css-cascade-5 §"Conditional import rules") is the same grammar `@supports` takes, so tsv parses that argument with the same reader and prints it with the same printer — the position inherits the `@supports` treatment whole, rather than a second set of rules. The value colon spaces (`supports(display:grid)` → `supports(display: grid)`), the value normalizations apply (`(width:.5px)` → `(width: 0.5px)`, `#FFF` → `#fff`, `"s"` → `'s'`), and a `selector()` argument routes to the selector printer (`selector(div>span)` → `selector(div > span)`) — all matching prettier, which value-parses the prelude and arrives at the same place ([import_supports_condition](../tests/fixtures/css/at_rules/import_supports_condition/)). The function's own parentheses **are** the condition's opening and closing parens, which is what lets the bare-`<declaration>` alternative reuse the parenthesized-part grammar unchanged. Function names are matched ASCII case-insensitively here (css-values-4), so `SUPPORTS(a:b)` and `LAYER( a )` normalize like their lowercase spellings rather than falling through to the opaque unknown-function path — matching prettier ([import_function_name_case](../tests/fixtures/css/at_rules/import_function_name_case/)).

Two things diverge. **A boolean keyword glued to `(`**, where prettier's value parser reads `and(` as a function node and keeps the glue — un-gluing it in `@supports` position, on the identical text ([import_supports_boolean_spacing](../tests/fixtures/css/at_rules/import_supports_boolean_spacing_prettier_divergence/)). And **where the line breaks** when the prelude exceeds print width: tsv breaks the condition onto its own indented line (the break point every other function value takes), where prettier tolerates 101 chars and then breaks the *prelude* instead ([import_supports_long](../tests/fixtures/css/at_rules/import_supports_long_prettier_divergence/)). The 100/101 boundary there comes from reserving the rule's `;` against the prelude's last value, which is a property of the `@import` prelude rather than of `supports()` — a breakable `layer(<long-name>)` in that position takes the same boundary and the same shape. Beyond those, the position inherits the `selector()` argument's three cataloged choices whole (a selector list stays inline, a non-selector argument keeps its tokens, and `SELECTOR(` is recognized case-insensitively) — it is the same reader, so it cannot do otherwise.

**SCSS directive preludes**: SCSS/Sass directives (`@include`, `@mixin`, `@if`, `@for`, `@each`, `@while`, `@function`, `@return`, `@debug`, plus `@at-root`, `@extend`, `@nest`, `@use`, `@forward`) are not standard CSS. Per CSS Syntax 3 §5.4.2 an unknown at-rule's prelude is consumed as an opaque list of component values with no defined grammar, so tsv preserves it **verbatim** — not just its numbers, but its whitespace runs, quote spelling and combinator spacing too. Prettier keeps a hardcoded directive table (`parser-postcss.js`) whose params it re-parses, and *which* re-parse depends on the name: most go to `parseValue` and get number-normalized (`@include foo(.5s)`→`0.5s`, `@include baz(1.50)`→`1.5`), while `@at-root`, `@extend` and `@nest` go to `parseSelector`, so their preludes additionally collapse whitespace, re-quote and space combinators (`@at-root input[type="radio"]   >   .class1` → `@at-root input[type='radio'] > .class1`; an authored newline in the prelude collapses to a space). tsv applies each normalization only to contexts whose grammar it parses — declaration values and `@media`/`@supports` preludes (see [CSS: Values](#css-values) "Number dot-ident") — leaving unrecognized directive preludes raw.

The divergence is keyed on prettier's **table**, not on unknown-ness: an at-rule that is on no list (`@unknown foo   bar`) falls through to prettier's own raw-string path and both formatters keep it verbatim, which is the null control in [scss_directive_prelude_verbatim](../tests/fixtures/css/at_rules/scss_directive_prelude_verbatim_prettier_divergence/). Matching prettier would therefore mean encoding SCSS grammar (an `@at-root` prelude *is a selector*) for constructs with no meaning in the languages tsv formats. The grammar-free alternative — collapsing whitespace runs in any raw prelude, which §4.3.1 makes token-preserving since consecutive whitespace is one `<whitespace-token>` — is declined too: it would break the `@unknown` agreement, and a run-collapse over text tsv has not tokenized corrupts string interiors and escaped whitespace, the opacity class cataloged under [§CSS: Values](#css-values). Every output here is valid CSS and a fixed point in both formatters (`.5` and `0.5` are the same `<number>` token; `foo⏎bar` and `foo bar` are the same token stream); the divergence is one of scope, not correctness.

**Empty media query**: Media Queries 4 §Syntax parses a `<media-query-list>` by parsing "a comma-separated list of component values, then parsing each entry as a `<media-query>`", so every top-level comma is a separator and the (possibly empty) text between two of them is an entry; §Error Handling replaces an entry that matches no `<media-query>` with `not all` and notes that a grammar mismatch "does **not** wipe out an entire media query list, just the problematic media query". tsv keeps an empty entry and renders it as the nothing it is (`@media , screen`, `@media screen, , print`); prettier deletes the entry, shortening the list. The rule is one rule in both positions, which is what makes the interior `@import` cases a *match* — prettier's `@media` printer drops an empty query while its value-parsed `@import` prelude keeps one, so `@import url('a.css') screen, , print` agrees ([import_media_query_empty](../tests/fixtures/css/at_rules/import_media_query_empty/)) while `@media screen, , print` does not. As long as the list keeps one other entry the deletion is cosmetic — `not all` matches nothing, so `screen, not all, print` and `screen, print` select the same media — which is what distinguishes those cases from the same shape in a *declaration value*, where an empty element invalidates the whole declaration and deleting it would turn a dead declaration live ([§CSS: Values](#css-values), "Trailing empty comma-list element"). It stops being cosmetic when the empty entry is the **only** entry, which is the ◆prettier_bug half of the tag: `@import url('a.css'),;` is the one-entry list `not all`, so the import never applies, while prettier's `@import url('a.css');` carries no `<media-query-list>` at all — and mediaqueries-4 §"Media Queries" makes an empty list evaluate **true**, so the import now always applies. See [media_query_empty](../tests/fixtures/css/at_rules/media_query_empty_prettier_divergence/). A leading comma followed by a real query is accepted and formatted identically by both ([import_media_query_leading_comma](../tests/fixtures/css/at_rules/import_media_query_leading_comma/)) — the structured `@import` reader is no stricter than the raw `@media` one on the identical list.

**Media query closing comma**: a comma *closing* the list (`@media screen,`) is the opposite case, and tsv **deletes** it. The same algorithm consumes up to each separator, discards it, and stops once the input is empty, so a final comma produces no further entry — `screen,` and `screen` are the same one-entry list, and deleting it leaves the parse untouched. Prettier keeps it in `@media` and drops it in `@import`, where tsv matches; tsv applies one rule in both.

The deletion is conditioned on the parse being unchanged, not unconditional: a list whose last entry is **empty** cannot be spelled without the extra comma, and there the deletion would change what the list means — `@import url('a.css'),;` is the one-entry list `not all` (false), while the empty list mediaqueries-4 evaluates to **true**. See [media_query_closing_comma](../tests/fixtures/css/at_rules/media_query_closing_comma_prettier_divergence/).

The `<media-query-list>` is the **only** construct whose closing comma tsv deletes, and tsv's standing rule runs the other way: a comma the author wrote is a token, and tsv re-spells the tokens it was given. In a **declaration value** the same comma is therefore kept ([§CSS: Values](#css-values), "Closing comma in a value") — a declaration is matched against a grammar rather than split, so the token carries meaning there (css-values-4 §"Component value combinators" makes `transition: a,` and `transition: a` two different declarations, one of which the UA drops; a custom property's verbatim token sequence simply substitutes different tokens). What earns the deletion *here* is that mediaqueries-4 defines the production **as** the split, so the token has no meaning to lose. That is a spec difference, not a preference for tidier output, and nothing weaker would justify it.

**Media comma-list wrapping (not a divergence)**: a comma-separated `@media` query list (Media Queries 4 §"media query list") that exceeds print width is broken at every top-level comma — one query per line, one indent level — matching Prettier exactly. The `@media line wrap` divergence below applies only to a _single_ `and`-joined query (no comma), which Prettier never wraps but tsv does.

**CSS keyword case — the canonicalize/preserve line.** CSS keywords are ASCII case-insensitive (CSS Syntax 3 §"tokenizing"). tsv adopts prettier's canonicalization set wholesale — it **lowercases** property names, at-rule names, units, pseudo-class/element names, media-feature names, keyframe `from`/`to`, hex, and `!important`, and **preserves** values (`color: RED`), custom properties (`--MyVar`), type/element selectors (`DIV`, SVG `linearGradient`), function names (`URL(`/`RGB(`), media types (`SCREEN`), and the `not`/`only` media qualifiers — matching prettier on both sides. tsv parses every case-insensitive keyword (so `@supports (a: b) AND (c: d)`, `@media screen AND (…)`, `:NTH-CHILD(2n+1)` all parse — Class-1 correctness) but only rewrites the spelling where prettier does. The lone exception is unit case: tsv lowercases **all** units to their spec-canonical serialized form, including `Hz`/`kHz`/`Q`, where prettier upcases instead — see "Unit serialization case" under [CSS: Values](#css-values).

The boolean **connectors** `and`/`or`/`not` are **preserved** (`@supports (a: b) AND (c: d)` keeps `AND`), matching prettier: uppercase boolean operators are a recognized "logical-skeleton" readability signal (the SQL convention), so their case carries authorial intent — the same principle that keeps comment position. This is verified by the regular [supports_connector_case](../tests/fixtures/css/at_rules/supports_connector_case/), [container_connector_case](../tests/fixtures/css/at_rules/container_connector_case/), and [media_connector_case](../tests/fixtures/css/at_rules/media_connector_case/) fixtures (no `_prettier_divergence` suffix — tsv matches prettier).

**@scope `to` keyword case** is the lone deliberate keyword-case *canonicalization* divergence (the `Media grouped feature case` below also differs on a feature name's case, but that's a parser-compat consequence of leaving grouped conditions opaque, not a canonicalization choice). `to` is a **delimiter** keyword (it marks the scope limit — a position marker, not a boolean operator, like keyframe `from`/`to`), so tsv canonicalizes it to lowercase for consistency with how it lowercases keyframe `from`/`to`. Prettier inconsistently lowercases keyframe `from`/`to` but **preserves** `@scope`'s `TO`; tsv lowercases both delimiter keywords uniformly. So `@scope (.card) TO (.footer)` → tsv `to`, prettier `TO`. See [scope_to_case](../tests/fixtures/css/at_rules/scope_to_case_prettier_divergence/).

**Media feature-name case**: a media-feature *name* is ASCII case-insensitive (Media Queries 4 §"Syntax"), and prettier lowercases it (`@media (MIN-WIDTH: 100px)` → `(min-width: 100px)`, including the range/boolean forms `(WIDTH >= 600px)` and `(HOVER)`) while preserving media types (`SCREEN`), the `and`/`or`/`not`/`only` keywords, and feature *values* (`(orientation: LANDSCAPE)` keeps `LANDSCAPE`). tsv **matches** prettier here for **simple** feature expressions — covered by the regular [media_feature_case](../tests/fixtures/css/at_rules/media_feature_case/) (no `_prettier_divergence` suffix). A feature whose *value* is a function (`(min-width: calc(…))`, `(width: min(…))`) is still simple: the function's parentheses don't make the feature opaque, so its name lowercases like any other — covered by [media_feature_function_value](../tests/fixtures/css/at_rules/media_feature_function_value/). Custom media names (`--*`) are case-sensitive (CSS Variables 1) and preserved. The one divergence is **grouped** conditions (`((a) and (b))`, `(not (x))`): prettier's media-query parser only partially descends — lowercasing the first nested feature and leaving the rest — whereas tsv treats the whole grouped condition as opaque and leaves it verbatim, so its nested features are handled consistently. See [media_grouped_feature_case](../tests/fixtures/css/at_rules/media_grouped_feature_case_prettier_divergence/). Note `@import`'s media-query feature names are preserved by both formatters (prettier doesn't run them through media-feature parsing), so tsv leaves them too.

## CSS: Selectors

- Column combinator `||` — ◆parser_compat — [column](../tests/fixtures/css/selectors/combinators/column_prettier_divergence/)
- Consecutive combinators (`> > .a`, `+ ~ .d`, glued `>>.a`) — ◆design_choice — [consecutive_combinator](../tests/fixtures/css/selectors/consecutive_combinator_svelte_prettier_divergence/): a run of combinators with no compound between them. tsv **preserves** every authored combinator (normalizing only the whitespace to single spaces, so glued `>>.a` → `> > .a`); prettier **collapses** a whitespace-separated run to its last (`> > .a` → `> .a`, in `output_prettier`) and *freezes* a glued run verbatim (`>>.a`, pinned by `prettier_variant_glued`). tsv declines the collapse because it is lossy — the dropped combinator is authorship the diagnostics layer needs (parseCss collapses too, an AST divergence — see [conformance_svelte.md §CSS Corrections](./conformance_svelte.md#css-corrections)). A *trailing* combinator (`.a > > {}`) rejects in both
- :nth-child() An+B — ◆stable_quirk — [nth_child](../tests/fixtures/css/selectors/pseudo_class/nth_child_prettier_divergence/)
- An+B leading `+` in pseudo-args — ◆stable_quirk — [nth_leading_plus](../tests/fixtures/css/selectors/pseudo_class/nth_leading_plus_prettier_divergence/): a bare An+B term inside functional pseudo-class args (`:foo(+2n + 1)`, `:is(+3)`, `:not(+n)`) is a single `Nth` (Svelte's `parseCss`, which tsv matches), so tsv keeps the leading `+` glued to its coefficient; prettier reads the leading `+` as a combinator and spaces it (`:foo(+ 2n + 1)`). A leading `-` doesn't diverge (both keep `-n + 3` glued)
- :nth-child(… of S) `of` spacing — ◆stable_quirk — [nth_child_of](../tests/fixtures/css/selectors/pseudo_class/nth_child_of_svelte_prettier_divergence/): tsv always emits single spaces around `of`; prettier collapses whitespace runs there but never inserts an absent space, so a glued `of.class` stays glued
- Pseudo-args indent (single compound) — ◆design_choice — [compound_args_indent](../tests/fixtures/css/selectors/pseudo_class/compound_args_indent_long_prettier_divergence/)
- Nested pseudo-args indent — ◆design_choice — [nested_where_is](../tests/fixtures/css/selectors/pseudo_class/nested_where_is_long_prettier_divergence/)
- Escaped `|` in an attribute selector's namespace prefix (`[a\|b|attr]`) — ◆prettier_bug — [namespace_escaped_prefix](../tests/fixtures/css/selectors/attribute/namespace_escaped_prefix_svelte_prettier_divergence/): an escape's payload is content (css-syntax-3 §4.3.7), so the `|` in the prefix `a\|b` is part of its name and the `<wq-name>`'s separator is the next one. Prettier reads the escaped `|` as the separator and **drops the remainder of the selector** — `[a\|b|attr]` comes back as `[a\|b]`, matching a different element — and that truncation is a prettier **fixed point**, so a second pass raises nothing and the loss is silent (the sibling `[svg|a\|b]` degrades further, to the unclosed `[svg|a\]`, which prettier's own next pass then rejects: `Unclosed bracket`). tsv steps forward from the prefix token's span instead of scanning for a `|`, and re-emits the prefix verbatim — a decoded `a|b` would re-parse as a namespace *plus* a `|=` matcher. The hex (`[a\7c b|attr]`) and ordinary (`[a\41 b|attr]`) spellings prettier prints verbatim, agreeing with tsv, which isolates the cause to a raw `|` byte ahead of the real separator. parseCss rejects attribute namespaces outright, so this is also a `_svelte_divergence` — see [conformance_svelte.md](./conformance_svelte.md#css-corrections)
- Control-char combinator whitespace (VT `U+000B` / FF `U+000C`) — ◆stable_quirk — [combinator_control_whitespace](../tests/fixtures/css/selectors/combinator_control_whitespace_prettier_divergence/): a descendant combinator authored with VT or FF — both in JS `\s`, so Svelte's `parseCss` (and tsv, matching it) tokenize them as the descendant combinator — normalizes to a single space, uniform with tab/newline gaps; prettier freezes the raw byte. FF is spec-whitespace via input preprocessing (→LF); VT is a non-printable the spec excludes, where tsv follows Svelte over css-syntax.
- Non-ASCII boundary whitespace (`<NBSP>`, `<LS>`, `<PS>`, `<ZWNBSP>`, every `Zs`) — ◆content_preservation — no fixture; pinned by [css_boundary_whitespace.rs](../tests/css_boundary_whitespace.rs): the same gap authored with a JS-`\s` code point at or above U+00A0. `parseCss` skips it through `allow_whitespace()`, so it is a descendant combinator to both parsers and belongs in neither name — but the two formatters then disagree about the *bytes*: tsv re-emits the run beside the regenerated separator (`*<NBSP>c` → `* <NBSP>c`), where prettier **drops it outright** (`* c`). Dropping a character the author wrote is content loss the corpus SAFETY check reads as `content_lost`, and tsv does not copy it — the same call it makes inside a `[`, where prettier turns `[<NBSP>a]` into `[a]`. The combinator gap is one position of many: the same call is made at every juncture the parser steps such a run at — a selector-list start, each `,`, the compound break, a pseudo-argument list's parens, an attribute selector's interior, a block child's rebuilt head, a block's tail, a condition prelude — so wherever prettier drops the character, tsv keeps it. Glued to an identifier the run is part of the NAME on both sides (`.a<NBSP>b`) and both formatters keep it. Two positions tsv drops it too, ratcheted rather than sanctioned: the stylesheet's trailing whitespace and a comment-bearing property→colon gap. There is no fixture because the class has no fixturable authoring — see that file's module doc — so the printer test there is the gate.

**Pseudo-args indent**: When a pseudo-class/element's argument list breaks, prettier indents it an extra level if the enclosing compound's flat `selector-selector` node count exceeds 2 (`shouldIndent = node.nodes.length > 2` in `printer-postcss.js`). That extra `indent` exists to align the continuation lines of a complex selector broken at its combinators; for a *single* compound (no combinator) there is no continuation to align, so it only nests the pseudo args one level deeper than the rule body. tsv keys the indent on combinator presence instead — a complex selector that spans more than one compound indents its continuation (matching prettier), and a pseudo's broken args always indent exactly one level relative to their pseudo. So a combinator-bearing selector matches prettier, while a single compound's pseudo args sit one level in with the `)` aligned to the selector it closes. Uniform, and no node counting. Combinator-bearing case (which matches prettier): [combinators/pseudo_args_long](../tests/fixtures/css/selectors/combinators/pseudo_args_long/).

**Space-separated value wrap**: Prettier doesn't wrap CSS space-separated values (e.g., `box-shadow`) when they exceed print width. A 101-char `box-shadow: var(--a) color-mix(...)` stays on one line. tsv wraps at the print width boundary, breaking between space-separated values. This respects the configured print width rather than allowing arbitrary overflows.

**Comma+space value boundary**: When comma-separated values contain space-separated parts (like multiple `box-shadow` values), Prettier tolerates lines exceeding printWidth. tsv breaks to stay within 100 chars. See `comma_space_separated_long/` for the matching behavior at 100 and 102 chars.

**Number dot-ident**: tsv matches Prettier's number normalization for all valid CSS — scientific-notation exponents (`1E+2`→`1e2`, `5e0`→`5`), trailing/leading zeros (`1.50`→`1.5`, `.5`→`0.5`), and a trailing dot before a terminator (`1.`→`1`, `1.e1`→`1e1`). This applies to declaration values and to `@media`/`@supports` preludes; `@container` preludes are left raw, matching Prettier. The lone divergence is the _invalid_ sequence `<number>.<ident>` (e.g. `1.px`, `1.foo`): Prettier merges it into a dimension (`1px`), but per CSS Syntax 3 §4.3.3 that is three tokens (`<number>` `<delim .>` `<ident>`), not a dimension — so tsv preserves the source verbatim. This only arises in invalid CSS; Prettier itself keeps `url(1.png)` unmerged.

**Trailing double-dot**: A malformed number with a *consecutive* double dot (`1..`, `1..e-10`, `1..5`) — `parseCss` accepts it (stored raw). The number tokenizer strips a *single* trailing dot (`1.` → `1`), but stripping one from `1..` and re-gluing the leftover onto the next token (`1..e-10` → `1.e-10`) re-parses as a number and normalizes again on the next pass (an F1 non-idempotency). tsv therefore leaves the whole malformed run **verbatim** — uniform with the other malformed-dot forms it already preserves (`..5`, `1.5.5`, `1.px`; see "Number dot-ident" above). Prettier normalizes it (`1..` → `1`, `1..e-10` → `1e-10`, some over two passes — its own transient non-idempotency). Only arises on malformed input.

**Block-valued custom property**: A custom property whose entire value is a top-level `{...}` block is valid per CSS Variables Level 1 §2.1 (`<declaration-value>`, any token sequence with balanced brackets) and appears in Prettier's own corpus. Prettier formats the block contents on their own indented lines like a nested rule body (closing `}` on its own line, then `;`); tsv preserves the value as a single opaque single-line expression. Both forms are stable/idempotent under their respective formatters. (Svelte's CSS parser rejects this form outright with `css_expected_identifier`, so this is also a `_svelte_divergence` — see [conformance_svelte.md](./conformance_svelte.md).)

**Empty custom-property value**: An empty custom-property value is valid — `<declaration-value>?` is optional (CSS Variables 1 §"Custom Property Value Syntax"). CSS Syntax 3 §"Consume a declaration" trims leading **and** trailing whitespace from a declaration's value, so `--a:;`, `--a: ;`, and `--a:     ;` all parse to the same empty value; the spacing is not significant. Prettier preserves whatever spacing the source has (multiple stable forms — `prettier_variant_compact`/`prettier_variant_spaces`); tsv normalizes to a single space (`--a: ;`), the form CSS Variables 1 §"Serializing Custom Properties" mandates ("an empty custom property … must serialize with a single space as its value"). Non-custom empty declarations (`color:;`) remain a parse error — a value is required there. A variant — an empty custom-property value carrying `!important` (`--a: !important;`) — exposes a prettier **non-convergence** bug: prettier adds a space before `!important` on every pass (`--a:!important` → `--a: !important` → `--a:  !important` → …) and never reaches a fixed point, so it can't serve as a formatter oracle. tsv normalizes to the single-space form and is idempotent; guarded by [empty_value_important](../tests/fixtures/css/values/variables/empty_value_important_prettier_divergence/), whose `prettier_nonconvergent.txt` marker makes the validator live-verify the non-convergence (rule F5) instead of running the prettier-anchored rules.

**Trailing empty comma-list element**: an **empty element** in a comma-separated value (`transition: a,,b`, `linear-gradient(red,,blue)`, a leading `,a`) is a real list entry — CSS Syntax 3 §"parse a comma-separated list of component values" produces a group for the stretch between two commas — so tsv preserves it, breaking a declaration's list one-per-line the way prettier does ([comma_empty_element](../tests/fixtures/css/values/lists/comma_empty_element/), where the two agree; `var()`'s fallback is likewise a comma token both keep, [var_comma_fallback](../tests/fixtures/css/values/variables/var_comma_fallback/)). The divergence is the **last** element being the empty one. Spelling that list back needs one more comma than it has separators — joining `["a", ""]` with `,` gives `a,`, which re-splits to `["a"]`, because the same algorithm stops once the input is empty and so produces no group after a *final* comma. tsv writes the extra comma (`transition:⏎\ta,⏎\t,;`, `linear-gradient(red, ,)`, `--x: a, ,`); prettier does not, and its output is not a fixed point — the **second** pass deletes the element (`transition: a;`, `linear-gradient(red)`, `--x: a;`), pinned in the fixture's `audit_signature.txt`. That is a render change: `linear-gradient(red,,)` is an invalid gradient the UA discards, `linear-gradient(red)` paints. The **custom property** is the case with no invalidity to hide behind — `--x`'s value is a verbatim token sequence (css-variables-1 §"Custom Property Value Syntax"), so dropping the element changes what every `var(--x)` substitutes, whatever the referencing property's grammar says. See [comma_trailing_empty_element](../tests/fixtures/css/values/lists/comma_trailing_empty_element_prettier_divergence/). The same construct in a `<media-query-list>` is [§CSS: At-Rules](#css-at-rules) "Empty media query".

**Closing comma in a value**: a comma **closing** a declaration's value with no element after it (`transition: a,`, `linear-gradient(red, blue,)`, `--x: a,`). tsv keeps it; prettier deletes it — and unlike the empty-element case above, prettier's output is a fixed point, so nothing in prettier's own behavior flags the deletion.

The rule is **token preservation**, not a judgment about which authorings deserve to survive: a declaration value is text tsv re-spells, and a comma the author wrote is one of its tokens. That is what tsv already did everywhere else in a value — `var(--a,)` keeps its empty fallback, an opaque `url(a,)` keeps its comma, and the comment-bearing path (which re-emits the value from source) already kept `--x: a /* c */,`. Only the comment-free, non-`var`, non-`url` path deleted it, on the grounds that the comma-split parse is unchanged — which is true, and is the answer to a question a declaration never asks.

What that token *does* is what makes the deletion a rewrite rather than a tidy, and it differs by declaration kind:

- A **custom property** settles it with no grammar involved at all. Its value is a verbatim token sequence (css-variables-1 §"Custom Property Value Syntax") that `var()` substitutes textually, so the comma is not punctuation *around* the value — it is *part of* it. `f(var(--x) b)` is `f(a, b)` when `--x` is `a,` and `f(a b)` when it is `a`; there is no reading on which the two declarations say the same thing. WPT's `css-variables/variable-declaration-21` is built on exactly that shape (`--b: 0,; --c: 128,;` feeding `rgb(var(--b)var(--c)var(--d))`).
- A **grammar-bearing** declaration is matched against its own production, and css-values-4 §"Component value combinators" requires a comma to be omitted when "all items following the comma have been omitted" — so `transition: a,` does not match and `transition: a` does. Note precisely what that establishes: the two forms **mean different things** (the UA drops one and applies the other), so deleting the comma changes the page. It does not, by itself, oblige a formatter to keep it — a formatter is free to repair invalid CSS. That obligation is tsv's own stance, and it is the same one the empty-element case above already takes, one comma later in the same list: re-spell the declaration faithfully rather than silently turning a dead one live.

The deletion is nevertheless **correct** in exactly one construct, and by a real spec difference rather than a carve-out: mediaqueries-4 §Syntax defines a `<media-query-list>` *as* "a comma-separated list of component values", so there the split **is** the grammar — `screen,` and `screen` are the same one-entry list and no token's meaning is lost ([§CSS: At-Rules](#css-at-rules), "Media query closing comma"). A declaration value is never split that way.

An **escaped** comma is content rather than a separator, so it closes nothing and nothing is appended after it (`gap: a, b\,`, [escaped_whitespace](../tests/fixtures/css/values/escaped_whitespace_prettier_divergence/); `var(--b, x\,)`, [var_comma_fallback](../tests/fixtures/css/values/variables/var_comma_fallback/), where prettier agrees). See [comma_closing](../tests/fixtures/css/values/lists/comma_closing_prettier_divergence/).

Deliberately **not** tagged ◆prettier_bug, though the sibling above is: prettier is idempotent here and its output is valid CSS. A meaning change on its own is ◆content_preservation; ◆prettier_bug is earned by output that is non-idempotent, invalid, or unparseable — which the empty-element case is, since prettier's own *next* pass deletes the element again.

A value carrying a **comment** isn't printed from the AST at all — CSS value comments aren't stored there — so it takes a source-extracting path with two width-chosen branches, and the closing comma has to survive both: the inline branch re-emits the normalized value, while the wrapped branch splits the arguments from source, where the comma in final position produces no part (the same §"parse a comma-separated list" rule) and so is written back after them. The comma also costs a column, which the printer must reserve: a **broken** list's last element ends its line `,;`, so an element that would land at exactly 101 wraps at its own space rather than overrunning (tsv's print width is a hard limit). Both axes are pinned at their 100/101 boundaries by [comma_closing_long](../tests/fixtures/css/values/lists/comma_closing_long_prettier_divergence/), whose `unformatted_ours_flat` variant also covers the authored space after the comma (`…, )`). That fixture is the same ◆content_preservation divergence seen at the boundary, **not** a ◆print_width one: prettier deletes the comma everywhere and, a column shorter, never reaches the width at all — neither formatter overruns.

**Unit serialization case**: CSS dimension units are ASCII case-insensitive (CSS Syntax 3) and their canonical **serialized** form is lowercase — including the frequency units `Hz`/`kHz` and the quarter-millimeter `Q`. CSS Values 4 §7.3 states "all `<frequency>` units are compatible, and `hz` is their canonical unit" and that "1Hz serializes as 1hz"; §6.2 likewise gives "1Q serializes as 1q". tsv canonicalizes **every** unit to this lowercase serialized form (`440Hz`→`440hz`, `1kHz`→`1khz`, `10Q`→`10q`), the same rule it applies to `PX`→`px`. Prettier instead **upcases** these three to their prose spelling (`Hz`/`kHz`/`Q`) while lowercasing all other units; tsv follows the spec's canonical form (spec precedence), so they stay lowercase. The all-agree units are the regular [units_case](../tests/fixtures/css/values/units_case/); the `Hz`/`kHz`/`Q` trio is the divergence, [units_serialize_case](../tests/fixtures/css/values/units_serialize_case_prettier_divergence/).

**Unquoted url() content opaque**: Per CSS Syntax 3 §4.3.6 an unquoted `url(...)` is consumed as one opaque `<url-token>` — its content is *not* re-parsed as component values — so tsv preserves it **verbatim** (`url(a(b,c))` and `url(a( b ))` each format to themselves). When the content contains a nested `(...)` group, prettier instead treats it as a value and reformats inside it: `url(a(b,c))` → `url(a(b, c))` (a space is added after the comma) and `url(a( b ))` → `url(a(b))` (the interior whitespace is dropped). tsv is the more defensible side — reformatting inside an opaque token is a divergence, not a normalization — and both formatters keep their own output idempotent. Only a nested `(...)` exposes it; flat url content has nothing to reformat, and a quoted `url("…")` is a string both leave alone. On Prettier's own corpus this surfaces in `tests/format/css/inline-url/inline_url.css` (`url(--var(foo-bar,#dadce0))` → `url(--var(foo-bar, #dadce0))`) and `tests/format/css/loose/loose.css` (`url(var( x ))` → `url(var(x))`). See [url_nested_reformat](../tests/fixtures/css/values/functions/url_nested_reformat_prettier_divergence/).

**Escaped whitespace in a value**: an **escape is opaque** — nothing inside it is structure. `\` followed by a space is a valid CSS escape whose escaped code point **is that space** (CSS Syntax 3 §4.3.4 "Check if two code points are a valid escape" — only a newline after `\` invalidates it — and §4.3.7 "Consume an escaped code point", whose final branch returns the code point itself). So the trailing space in `width: 50px\ ;` is value *content*, not padding: the value is the ident `50px `, and the `;` terminates the declaration. tsv preserves every escape whole; prettier scans through them and corrupts each kind differently:

- **Trailing payload dropped, delimiter stranded** — `width: 50px\ ;` → `width: 50px\;`, `var(--a, 50px\ )` → `var(--a, 50px\)`, `calc(1px\ )` → `calc(1px\)`. The `;` / `)` becomes an *escaped* character, so the declaration, the function, and the block never close: **prettier's own output no longer re-parses** (tsv's CSS parser rejects it with `Expected '}'`).
- **Payload dropped mid-value** — `color: a\ b` → `color: a\b`, silently changing the value from `a b` to `ab`.
- **Escaped delimiter read as structure** — `var(--b, x\,y)` → `var(--b, x\, y)` (the escaped comma splits one ident, which the comma path rejoins with `", "`) and `inset: a\+b` → `inset: a\+ b` (the escaped `+` takes operator spacing). Both split a single ident into two values.
- **Wrapping inside an ident** — a long value may break *on* an escaped space, putting a `\` at end-of-line; `\` before a newline is not a valid escape at all. See [escaped_whitespace_long](../tests/fixtures/css/values/escaped_whitespace_long_prettier_divergence/), which pins the 100/101 boundary.

A **hex** escape is opaque for one byte more than it looks: it takes up to six hex digits and then, optionally, **one whitespace terminator**, which belongs to the escape (§4.3.7). `\41 2px` is therefore the single ident `A2px`, not `\41` followed by `2px` — here prettier agrees, pinned by the regular fixture [escaped_hex_terminator](../tests/fixtures/css/values/escaped_hex_terminator/).

An unquoted `url()` has the same failure at its closing paren — `url(x\ )` → `url(x\)`, and the url token then never terminates — pinned separately by [url_escaped_whitespace](../tests/fixtures/css/values/functions/url_escaped_whitespace_prettier_divergence/), since url content is opaque and takes its own code path.

tsv declines to reproduce any of it — its format→re-parse invariant outranks matching prettier, and emitting output that does not parse is never the defensible side. Svelte's error-recovering `parseCss` still consumes prettier's output, so this is a *formatter* divergence only; tsv's parse AST matches `parseCss` on the input exactly. The selector axis (an escaped space before a combinator, `,`, or `{`, on a class/id/type leaf **or a pseudo**) is a plain bug rather than a divergence — prettier gets it right — and is pinned by [css/selectors/escaped_names](../tests/fixtures/css/selectors/escaped_names/); so is the whitespace-collapse inside a dropped forgiving-selector item ([forgiving_is_where](../tests/fixtures/css/selectors/forgiving_is_where_svelte_divergence/)). See [escaped_whitespace](../tests/fixtures/css/values/escaped_whitespace_prettier_divergence/).

**String glued to a non-ASCII space**: A comma- or space-separated value whose element is a quoted string glued to a **non-ASCII whitespace** character — a non-breaking space (U+00A0) or an em space (U+2003) — on either side, as in `grid-template-areas: 'x', <NBSP>'y'` (leading) or `grid-template-columns: 'a'<NBSP>, 'b'` (trailing). CSS whitespace is ASCII-only (CSS Syntax 3 §4.2), so a non-ASCII space is not a separator but value content — tsv treats every code point ≥ U+00A0 as an identifier code point, following Svelte's `parseCss` (broader than the CSS Syntax ident set, which excludes these look-alike whitespace chars). tsv keeps the element as **one opaque token, inline**, preserving the character. Prettier's value tokenizer splits it into a word (`<NBSP>`) plus a string (`'y'`), which makes the group multi-token — so prettier inserts a space between them and, for a comma list, breaks it one item per line (`<NBSP> 'y'`). tsv does not split adjacent glued value tokens, so the run stays one token and its bytes survive verbatim — the same lossless form it emits for the pure-ASCII analog `font-family: 'x', a'y'` (tsv keeps `a'y'`; prettier splits to `a 'y'`). The trims are load-bearing for **content**: a Unicode-aware `str::trim` at the value parser's element boundaries or in the printer's value-text whitespace normalizer drops a boundary non-ASCII space — for a string element outright (the narrowed text no longer begins with a quote, so the string printer emits nothing and the whole element vanishes, `'x',;` then `'x';` on a second pass — non-idempotent). Both trim only CSS whitespace (`trim_start_css` / `trim_end_preserving_escape`, the same escape-aware trims that keep an escaped `50px\ ` whole), matching CSS's ASCII-only definition. See [comma_string_nonascii_space](../tests/fixtures/css/values/lists/comma_string_nonascii_space_prettier_divergence/).

**Single value glued to a non-ASCII space**: The single-value (non-list) sibling of the above. A **single** declaration value glued to a non-ASCII whitespace character — a non-breaking space (U+00A0) or an em space (U+2003) — at either boundary, as in `content: <NBSP>'z'` (leading) or `quotes: 'a'<NBSP>` (trailing). Same rule and same design choice: the non-ASCII space is value content — tsv treats it as an identifier code point (≥ U+00A0), following Svelte's `parseCss` — so tsv keeps the value as **one opaque token, inline** (`content: <NBSP>'z'`), while prettier splits a **string** value into a word (`<NBSP>`) plus the string and inserts a space (`content: <NBSP> 'z'`). For an **identifier** value (`font-family: <NBSP>q`) prettier keeps it glued, so tsv matches prettier there — only the string cases diverge. Two readers must agree for the **content** to survive (`content: <NBSP>'z'` → `content: 'z'` otherwise): a **trailing** space reaches `locate_value`'s value-boundary trim, which is CSS-whitespace-only (the escape-aware `trim_start_css` / `trim_end_preserving_escape`), and a **leading** space reaches the lexer's whitespace scan in the colon→value gap, which treats only ASCII whitespace as CSS whitespace (CSS Syntax 3 §4.2), so a code point ≥ U+00A0 — which `parseCss` treats as an identifier code point — opens the value's first token rather than being skipped. See [boundary_nonascii_space](../tests/fixtures/css/values/boundary_nonascii_space_prettier_divergence/).

**Glued run of quoted strings**: The pure-ASCII sibling of the two glued cases above, with no separator at all. A single declaration value that is a **run of glued value tokens** whose first and last token are quoted strings, written adjacent: `content: 'a''b'` (two strings), `content: 'a'x'b'` (string, ident, string), `content: "a"x"b"` (double-quoted). tsv does not split adjacent glued value tokens, so it keeps the run as **one opaque token, inline**, verbatim (`content: 'a'x'b'`); prettier's tokenizer splits it into its component tokens and inserts a space, also normalizing the quote (`content: 'a' x 'b'`). Same lossless choice as `font-family: 'x', a'y'` (tsv keeps `a'y'`; prettier splits to `a 'y'`). The classification is what protects the **content**: a `parse_string_literal` that called the run a single string on "first char is a quote and last char is the matching quote" — true for `'a'x'b'` even though its opening `'` closes at index 2 — would strip the outer quotes and re-quote the interior, turning the **delimiter** quotes into literal content (`content: 'a'x'b'` → `content: "a'x'b"`, a value whose CSS meaning changes and which round-trips to a different AST). So the run is a single string only when the opening quote's first **unescaped** matching close falls at the end of the run (`quoted_string_spans_all`); otherwise it is kept verbatim as an opaque identifier. An escaped interior quote (`'a\'b'`) still closes at the end, so a genuine single string is unaffected. See [glued_string_run](../tests/fixtures/css/values/glued_string_run_prettier_divergence/).

**Escaped-paren url() whitespace**: An unquoted `url(...)` whose content carries an escaped paren (`\(` / `\)`) and outer whitespace inside the parens. Per CSS Syntax 3 §4.3.6 the `<url-token>` tokenizer consumes the leading/trailing whitespace, so its canonical value is trimmed; tsv emits that form (`url(  a\(b  )` → `url(a\(b)`). Prettier trims plain url whitespace the same way, but its postcss escaped-paren handling — the same bug that makes it *throw* on [url_escaped_paren](../tests/fixtures/css/values/functions/url_escaped_paren_prettier_divergence/) (`url(a\)b)` → `Unbalanced parenthesis`) — here stops normalizing and keeps the whitespace verbatim (`url(  a\(b  )` stays as-is). Prettier's output is valid, but tsv follows the spec's canonical serialization, so the divergence is escaped-paren-only (plain content agrees). Because tsv's trimmed form is dual-stable, this is pinned by a `prettier_variant_*` rather than an `output_prettier`. On Prettier's own corpus it surfaces in `tests/format/css/url/url.css`. See [url_escaped_paren_ws](../tests/fixtures/css/values/functions/url_escaped_paren_ws_prettier_divergence/).

## CSS: HTML comments (CDO/CDC)

**◆prettier_bug.** Legacy `<!-- … -->` HTML-comment markers in CSS — the CDO/CDC tokens from the old `<style><!-- … --></style>` browser-hiding idiom. Prettier can't format them: rather than throwing, it mangles the markers into invalid CSS (`<!-- -->` → `<!-- -- >`, splitting the `-->` and gluing the next line), so there is no prettier oracle. tsv follows Svelte's `parseCss`, which reads `<!--` … `-->` as a comment span and **discards** it — including any wrapped CSS — so the markers (and their contents) drop on format. Svelte's swallow itself departs from the CSS Syntax spec, where `<!--` (CDO) and `-->` (CDC) are independent no-op tokens and the content between them survives (so the spec — and, mangling aside, prettier — keep a wrapped rule; `parseCss`, and thus tsv, drop it). tsv inherits `parseCss` behavior by design, not the spec's token rules. The parse side (which positions swallow, which keep the markers raw, unterminated errors) is pinned in [conformance_svelte.md §CSS Compat Behaviors](./conformance_svelte.md#css-compat-behaviors) and [tests/css_cdo_cdc.rs](../tests/css_cdo_cdc.rs).
