**Escaped whitespace ending a prelude**: an at-rule prelude can end in an escaped whitespace (`@layer a\ ;` — the layer is named `a `, since `\ ` is a valid escape whose escaped code point IS that space, css-syntax-3 §4.3.4/§4.3.7). tsv preserves it. Prettier trims it as padding, stranding the backslash onto the `;`, which it then escapes: alone, prettier's output no longer parses (tsv rejects `@layer a\;` with `Expected '{' or ';' after 'at-rule prelude'`); in context it parses but the prelude swallows everything up to the next `{`, silently **merging two at-rules into one**. Prettier gets the block form right (`@layer b\ {`), where the payload space already separates the prelude from the brace — and tsv likewise adds no second separator there. Same rule, same reason as [CSS: Values §Escaped whitespace in a value](#css-values). See [layer_escaped_whitespace](../tests/fixtures/css/at_rules/layer_escaped_whitespace_prettier_divergence/).

**Escaped control char in an at-rule name**: an escape *inside the at-rule name token* (`@m\A x`) is part of the name — Svelte's `parseCss` (and tsv, matching it) decode the whole run to the name (`"m\nx"`, a control char mid-name), with an empty prelude. Postcss/prettier instead **split** the name at the escape into a name plus a prelude (`@m \A x {`), and reject outright when the name *starts* with an escape (`@\6D edia` → "At-rule without name"). tsv can't adopt prettier's split without contradicting its own parse, so it emits the name from **source**, preserving the escape verbatim (`@m\A x {`) — the decoded control char never lands raw in the output. Emitting the *decoded* form would inject a raw newline, corrupting the file, and drop the escape on reparse (name `m\nx` → `m`) — content loss and a broken fixed point. Same escape-preservation rule as escaped property names, which both formatters keep verbatim (`escaped_property_name`, no divergence). The end-of-name subcase (`@n\A {`, the escape needs a terminator space) adds no second separator before `{`, the same absorption as [Escaped whitespace ending a prelude](#css-at-rules) above. See [name_escaped_control_char](../tests/fixtures/css/at_rules/name_escaped_control_char_prettier_divergence/).

**Escaped delimiters in a prelude value**: an at-rule prelude that tsv value-normalizes (`@media` / `@supports` / `@import`) is walked byte by byte for the tokens the normalization acts on — strings, `#`-tokens, comments, numbers, `url()` — and **an escape is stepped whole ahead of every one of those arms** (`escapes::escape_len`), because its payload is content and never structure (§4.3.7, §"Consume an ident sequence"). Prettier's prelude pass reads the payload byte instead, and each delimiter fails differently:

- **A quote** opens a string that runs to the next real one, swallowing the region between: `@supports (a: x\"y "z")` keeps its `"z"` where tsv normalizes it to `'z'`, and under `@media` prettier re-quotes the swallowed region and emits `@media (a: x\'y 'z")` — the escape's payload rewritten, the string delimiters moved, and the output no longer parses. See [supports_escaped_quote](../tests/fixtures/css/at_rules/supports_escaped_quote_prettier_divergence/).
- **A `#`** becomes a hash-token, which swallows what follows it into one node, and prettier then re-emits that node **without the separator**: `@supports (a: x\#FFF 5px)` → `x\#FFF5px` — one ident where there were two tokens — and `x\#FFF y` → `x\#FFFy`. The space is content, so that is a token-stream change, and prettier's form is its own fixed point. See [supports_escaped_hash_separator](../tests/fixtures/css/at_rules/supports_escaped_hash_separator_prettier_divergence/).

Where prettier gets the escape right and tsv used to lowercase the escaped run as a hex colour, there is no divergence — the plain [supports_escaped_hash_token](../tests/fixtures/css/at_rules/supports_escaped_hash_token/) pins the agreement, with `@media` (which preserves every hash) as its control. Same rule and same reason as [CSS: Values §Escaped whitespace in a value](#css-values).

**Escaped separator in a media-feature name**: a media-feature name is one **ident sequence**, and an escape's payload is ident content (§"Consume an ident sequence"), so `@media (a\:b: 1px)` is the single name `a:b` and the *second* `:` is the name→value separator. tsv reads the whole run as the name: a plain name is a pre-defined keyword and so ASCII case-insensitive (css-values-4 §"Pre-defined Keywords"), so it lowercases entire, while a custom-media name is an `<extension-name>` (css-extensions-1) with no canonical casing to fold to, so `--A\:B` survives whole. Prettier reads the escape's payload as the separator, ending the name at `a\:` and re-emitting the rest as the start of the value — `(a\: B: 1px)`, inserting a space that is not in the author's ident and leaving `B` uppercase because it now sits in value position. The space is content (`a\: b` is the ident `a:` followed by the ident `b`), and prettier's form is its own fixed point. It is also unrecoverable: nothing in the emitted text says the space was never there, so tsv reads that form as the two idents it literally is and the second, now in name position, lowercases — a third form, pinned as the fixture's `divergent_variant_uppercase`. Case-sensitivity is likewise a property of the **whole** name (prettier's `maybeToLowerCase`, which tsv mirrors), never of one run inside it: asked per run, `(--A B: 1px)` preserved `--A` and folded `B`. See [media_feature_escaped_colon](../tests/fixtures/css/at_rules/media_feature_escaped_colon_prettier_divergence/), with [media_custom_feature_escaped_name](../tests/fixtures/css/at_rules/media_custom_feature_escaped_name/) as the plain sibling where both formatters agree.

**`selector()` argument**: `<supports-selector-fn> = selector( <complex-selector> )` (css-conditional-4 §"Extensions to the @supports rule"), so tsv parses the argument as a selector and prints it with the same printer a rule's own selector uses — `selector(div>span)` normalizes to `selector(div > span)`, `selector(div[data-attr=value])` to `[data-attr='value']`, exactly as those selectors format in rule position, and matching prettier ([supports_selector_interior](../tests/fixtures/css/at_rules/supports_selector_interior/)). The position therefore inherits tsv's cataloged selector-printing choices (the column combinator, the An+B leading `+`, …) rather than a second set of rules. The grammar's argument is a *single* complex selector, but a comma-separated list is read as the list it lexically is — the singular production decides whether the condition is true, which is not a formatting question. Three divergences follow from the grammar rather than from taste:

- A selector **list** stays on the prelude's line, where prettier breaks it one selector per line. A selector's break points belong to a rule's selector list; a condition's own wrapping is the `and`/`or` fill.
- An argument that does **not** parse as a selector — an attribute value that is neither identifier nor string (selectors-4 §"Attribute selectors") — makes the whole thing a `<general-enclosed>`, the third arm of `<supports-in-parens>` (css-conditional-3), whose production is `[ <function-token> <any-value>? ) ]` (mediaqueries-4 §"Syntax"): grammatically valid, contents undefined, "the result is false". tsv keeps those tokens as authored (whitespace runs collapsed); prettier re-prints them as a selector regardless, quoting `[data-attr=1.50]` to `[data-attr='1.50']` — a repair, not a normalization, and one that can flip a false condition true. Both cases: [supports_selector_argument](../tests/fixtures/css/at_rules/supports_selector_argument_prettier_divergence/). *As authored* is also what bounds a **comment** here: no whitespace is inserted on either side of one, so `selector([data-attr=1.50]/* c */.class)` keeps its glue — a space would turn the compound into a descendant `[data-attr=1.50] .class`, and this arm has no parse to tell a compound boundary from a combinator one. That is the same answer the parsed half gives a glued compound-internal comment ([§CSS: Comments](#css-comments), Combinator boundaries), so one `selector()` argument does not get two rules. A comment also switches prettier's own treatment of the argument — it freezes the tokens verbatim and drops the quoting repair above — so both formatters agree on every single-spaced comment-bearing argument, in `@supports` and in `@import`'s `supports()` alike ([supports_selector_comment](../tests/fixtures/css/at_rules/supports_selector_comment/), [import_supports_condition](../tests/fixtures/css/at_rules/import_supports_condition/)); a comment beside a list **comma** is the one position tsv respaces, the rule's own comma-seam quirk ([§CSS: Comments](#css-comments), `supports_selector_list_comment`). Two comments **glued to each other** are the exception, and about layout rather than tokens: both print the run glued, but prettier then breaks the prelude across lines — the same stable relocation its printer makes on a glued comment run in rule position ([§CSS: Comments](#css-comments), `compound_comment_run`).
- A CSS function name is ASCII case-insensitive (css-values-4 §"Functional Notations"), so `SELECTOR(…)` is the same function. tsv recognizes it either way; prettier's check is case-sensitive and falls through to its declaration path, emitting `SELECTOR(div: hover)` — no longer a selector. See [supports_selector_name_case](../tests/fixtures/css/at_rules/supports_selector_name_case_prettier_divergence/). The same miss has a second spelling: a name is an **ident sequence**, so an escape is ident content (§"Consume an ident sequence") and `s\65 lector(…)` is that function too. tsv resolves the escape when it recognizes the name (`printer::values::function_name_is`); prettier reads the name's bytes verbatim and falls through the same way, so `s\65 lector(#ABC)` comes back as `s\65 lector(#abc)` — an ID selector is case-sensitive (selectors-4 §"ID selectors"), so that selects a different element. See [supports_escaped_selector_name](../tests/fixtures/css/at_rules/supports_escaped_selector_name_prettier_divergence/).

The declaration rules that apply to a `<supports-decl>` — the space after the value `:`, the spacing around a boolean operator — never reach inside a function's argument, in either at-rule. A boolean keyword is an operator only where the grammar can start one (after `(`, after `)`, or at the beginning of a condition), so a value spelled `and` (`(font-family: and)`) and a class named `.and` are ordinary identifiers; the space after `:` is likewise decided by the property name, looking past any comment between them ([supports_condition_spacing](../tests/fixtures/css/at_rules/supports_condition_spacing/)).

**Spec violations**: CSS Syntax 3 §4.3.4 specifies that an identifier immediately followed by `(` tokenizes as a `<function-token>`, not as an `<ident-token>` plus `(`. Media Queries 4 §3 explicitly notes: "Whitespace is required between a 'not', 'and', or 'or' keyword and the following '(' character, because without it that would instead parse as a `<function-token>`." Container Queries (CSS Conditional 5) use the same grammar pattern. Prettier normalizes this for `@supports` but not `@media`, `@container`, or the `supports()` argument of an `@import` prelude; tsv normalizes all four.

**`@import`'s `supports()` argument is a condition, read by the condition reader.** `supports( <supports-condition> | <declaration> )` (css-cascade-5 §"Conditional import rules") is the same grammar `@supports` takes, so tsv parses that argument with the same reader and prints it with the same printer — the position inherits the `@supports` treatment whole, rather than a second set of rules. The value colon spaces (`supports(display:grid)` → `supports(display: grid)`), the value normalizations apply (`(width:.5px)` → `(width: 0.5px)`, `#FFF` → `#fff`, `"s"` → `'s'`), and a `selector()` argument routes to the selector printer (`selector(div>span)` → `selector(div > span)`) — all matching prettier, which value-parses the prelude and arrives at the same place ([import_supports_condition](../tests/fixtures/css/at_rules/import_supports_condition/)). The function's own parentheses **are** the condition's opening and closing parens, which is what lets the bare-`<declaration>` alternative reuse the parenthesized-part grammar unchanged. Function names are matched ASCII case-insensitively here (css-values-4), so `SUPPORTS(a:b)` and `LAYER( a )` normalize like their lowercase spellings rather than falling through to the opaque unknown-function path — matching prettier ([import_function_name_case](../tests/fixtures/css/at_rules/import_function_name_case/)).

Two things diverge. **A boolean keyword glued to `(`**, where prettier's value parser reads `and(` as a function node and keeps the glue — un-gluing it in `@supports` position, on the identical text ([import_supports_boolean_spacing](../tests/fixtures/css/at_rules/import_supports_boolean_spacing_prettier_divergence/)). And **where the line breaks** when the prelude exceeds print width: tsv breaks the condition onto its own indented line (the break point every other function value takes), where prettier tolerates 101 chars and then breaks the *prelude* instead ([import_supports_long](../tests/fixtures/css/at_rules/import_supports_long_prettier_divergence/)). The 100/101 boundary there comes from reserving the rule's `;` against the prelude's last value, which is a property of the `@import` prelude rather than of `supports()` — a breakable `layer(<long-name>)` in that position takes the same boundary and the same shape. Beyond those, the position inherits the `selector()` argument's three cataloged choices whole (a selector list stays inline, a non-selector argument keeps its tokens, and `SELECTOR(` is recognized case-insensitively) — it is the same reader, so it cannot do otherwise.

**SCSS directive preludes**: SCSS/Sass directives (`@include`, `@mixin`, `@if`, `@for`, `@each`, `@while`, `@function`, `@return`, `@debug`, plus `@at-root`, `@extend`, `@nest`, `@use`, `@forward`) are not standard CSS. Per CSS Syntax 3 §5.4.2 an unknown at-rule's prelude is consumed as an opaque list of component values with no defined grammar, so tsv preserves it **verbatim** — not just its numbers, but its whitespace runs, quote spelling and combinator spacing too. Prettier keeps a hardcoded directive table (`parser-postcss.js`) whose params it re-parses, and *which* re-parse depends on the name: most go to `parseValue` and get number-normalized (`@include foo(.5s)`→`0.5s`, `@include baz(1.50)`→`1.5`), while `@at-root`, `@extend` and `@nest` go to `parseSelector` (the one standard-CSS name on that side, `@custom-selector`, tsv routes too — **A third reader** below), so their preludes additionally collapse whitespace, re-quote and space combinators (`@at-root input[type="radio"]   >   .class1` → `@at-root input[type='radio'] > .class1`; an authored newline in the prelude collapses to a space). tsv applies each normalization only to contexts whose grammar it parses — declaration values and `@media`/`@supports` preludes (see [CSS: Values](#css-values) "Number dot-ident") — leaving unrecognized directive preludes raw.

The divergence is keyed on prettier's **table**, not on unknown-ness: an at-rule that is on no list (`@unknown foo   bar`) falls through to prettier's own raw-string path and both formatters keep it verbatim, which is the null control in [scss_directive_prelude_verbatim](../tests/fixtures/css/at_rules/scss_directive_prelude_verbatim_prettier_divergence/). Matching prettier would therefore mean encoding SCSS grammar (an `@at-root` prelude *is a selector*) for constructs with no meaning in the languages tsv formats. The grammar-free alternative — collapsing whitespace runs in any raw prelude, which §4.3.1 makes token-preserving since consecutive whitespace is one `<whitespace-token>` — is declined too: it would break the `@unknown` agreement, and a run-collapse over text tsv has not tokenized corrupts string interiors and escaped whitespace, the opacity class cataloged under [§CSS: Values](#css-values). Every output here is valid CSS and a fixed point in both formatters (`.5` and `0.5` are the same `<number>` token; `foo⏎bar` and `foo bar` are the same token stream); the divergence is one of scope, not correctness.

**Empty media query**: Media Queries 4 §Syntax parses a `<media-query-list>` by parsing "a comma-separated list of component values, then parsing each entry as a `<media-query>`", so every top-level comma is a separator and the (possibly empty) text between two of them is an entry; §Error Handling replaces an entry that matches no `<media-query>` with `not all` and notes that a grammar mismatch "does **not** wipe out an entire media query list, just the problematic media query". tsv keeps an empty entry and renders it as the nothing it is (`@media , screen`, `@media screen, , print`); prettier deletes the entry, shortening the list. The rule is one rule in both positions, which is what makes the interior `@import` cases a *match* — prettier's `@media` printer drops an empty query while its value-parsed `@import` prelude keeps one, so `@import url('a.css') screen, , print` agrees ([import_media_query_empty](../tests/fixtures/css/at_rules/import_media_query_empty/)) while `@media screen, , print` does not. As long as the list keeps one other entry the deletion is cosmetic — `not all` matches nothing, so `screen, not all, print` and `screen, print` select the same media — which is what distinguishes those cases from the same shape in a *declaration value*, where an empty element invalidates the whole declaration and deleting it would turn a dead declaration live ([§CSS: Values](#css-values), "Trailing empty comma-list element"). It stops being cosmetic when the empty entry is the **only** entry, which is the ◆prettier_bug half of the tag: `@import url('a.css'),;` is the one-entry list `not all`, so the import never applies, while prettier's `@import url('a.css');` carries no `<media-query-list>` at all — and mediaqueries-4 §"Media Queries" makes an empty list evaluate **true**, so the import now always applies. See [media_query_empty](../tests/fixtures/css/at_rules/media_query_empty_prettier_divergence/). A leading comma followed by a real query is accepted and formatted identically by both ([import_media_query_leading_comma](../tests/fixtures/css/at_rules/import_media_query_leading_comma/)) — the structured `@import` reader is no stricter than the raw `@media` one on the identical list.

**@supports comment-only prelude**: a condition prelude can hold nothing but comments — `@supports /* c */;`, `@container b /* c */ {` — and the query then has no part to carry them, so the prelude *region* is their only carrier. tsv emits them there, and writes no name→prelude separator when there is nothing at all to emit, so a truly empty prelude closes flush (`@media;`, `@supports;`, `@container;`, `@custom-media;` — a match, pinned by [prelude_empty](../tests/fixtures/css/at_rules/prelude_empty/)). `@container` agrees with prettier throughout ([container_prelude_comment_only](../tests/fixtures/css/at_rules/container_prelude_comment_only/)). `@supports` does not: prettier drops the last byte of the comment's closing delimiter, emitting `@supports  /* c *;` — an unterminated comment that swallows the rest of the file and that prettier's own parser then rejects (`CssSyntaxError: Unclosed comment`), so the input has no prettier fixed point at all. Output that does not re-parse is never the defensible side. See [supports_prelude_comment_only](../tests/fixtures/css/at_rules/supports_prelude_comment_only_prettier_divergence/).

**@media value newline**: a `media-value` is a node prettier emits verbatim, so a whitespace run inside a feature expression's value is the author's and both formatters keep it. tsv makes one exception: a run carrying a **newline** collapses to a single space. tsv never emits a raw newline inside an at-rule prelude — the prelude's own line breaks are re-decided by the `and`/`or` fill against print width, and a newline carried through from the source would be counted as prelude text by that fill, so the width accounting and the bytes on the page would disagree. The run is separator whitespace inside the value's text rather than content, so collapsing it loses nothing, and the collapsed form is a fixed point on both formatters. Every other neighbour a verbatim run can have — a comment, an opaque `url()`, a later colon inside the value — leaves it intact, a match pinned by [media_value_verbatim_run](../tests/fixtures/css/at_rules/media_value_verbatim_run/). See [media_value_newline](../tests/fixtures/css/at_rules/media_value_newline_prettier_divergence/).

**Media query closing comma**: a comma *closing* the list (`@media screen,`) is the opposite case, and tsv **deletes** it. The same algorithm consumes up to each separator, discards it, and stops once the input is empty, so a final comma produces no further entry — `screen,` and `screen` are the same one-entry list, and deleting it leaves the parse untouched. Prettier keeps it in `@media` and drops it in `@import`, where tsv matches; tsv applies one rule in both.

The deletion is conditioned on the parse being unchanged, not unconditional: a list whose last entry is **empty** cannot be spelled without the extra comma, and there the deletion would change what the list means — `@import url('a.css'),;` is the one-entry list `not all` (false), while the empty list mediaqueries-4 evaluates to **true**. See [media_query_closing_comma](../tests/fixtures/css/at_rules/media_query_closing_comma_prettier_divergence/).

The `<media-query-list>` is the **only** construct whose closing comma tsv deletes, and tsv's standing rule runs the other way: a comma the author wrote is a token, and tsv re-spells the tokens it was given. In a **declaration value** the same comma is therefore kept ([§CSS: Values](#css-values), "Closing comma in a value") — a declaration is matched against a grammar rather than split, so the token carries meaning there (css-values-4 §"Component value combinators" makes `transition: a,` and `transition: a` two different declarations, one of which the UA drops; a custom property's verbatim token sequence simply substitutes different tokens). What earns the deletion *here* is that mediaqueries-4 defines the production **as** the split, so the token has no meaning to lose. That is a spec difference, not a preference for tidier output, and nothing weaker would justify it.

**Media comma-list wrapping (not a divergence)**: a comma-separated `@media` query list (Media Queries 4 §"media query list") that exceeds print width is broken at every top-level comma — one query per line, one indent level — matching Prettier exactly. The `@media line wrap` divergence below applies only to a _single_ `and`-joined query (no comma), which Prettier never wraps but tsv does.

**CSS keyword case — the canonicalize/preserve line.** CSS keywords are ASCII case-insensitive (CSS Syntax 3 §"tokenizing"). tsv adopts prettier's canonicalization set wholesale — it **lowercases** property names, at-rule names, units, pseudo-class/element names, media-feature names, keyframe `from`/`to`, hex, and `!important`, and **preserves** values (`color: RED`), custom properties (`--MyVar`), type/element selectors (`DIV`, SVG `linearGradient`), function names (`URL(`/`RGB(`), media types (`SCREEN`), and the `not`/`only` media qualifiers — matching prettier on both sides. tsv parses every case-insensitive keyword (so `@supports (a: b) AND (c: d)`, `@media screen AND (…)`, `:NTH-CHILD(2n+1)` all parse — Class-1 correctness) but only rewrites the spelling where prettier does. The lone exception is unit case: tsv lowercases **all** units to their spec-canonical serialized form, including `Hz`/`kHz`/`Q`, where prettier upcases instead — see "Unit serialization case" under [CSS: Values](#css-values).

The boolean **connectors** `and`/`or`/`not` are **preserved** (`@supports (a: b) AND (c: d)` keeps `AND`), matching prettier: uppercase boolean operators are a recognized "logical-skeleton" readability signal (the SQL convention), so their case carries authorial intent — the same principle that keeps comment position. This is verified by the regular [supports_connector_case](../tests/fixtures/css/at_rules/supports_connector_case/), [container_connector_case](../tests/fixtures/css/at_rules/container_connector_case/), and [media_connector_case](../tests/fixtures/css/at_rules/media_connector_case/) fixtures (no `_prettier_divergence` suffix — tsv matches prettier).

**@scope `to` keyword case** is the lone deliberate keyword-case *canonicalization* divergence (the `Media grouped feature case` below also differs on a feature name's case, but that's a parser-compat consequence of leaving grouped conditions opaque, not a canonicalization choice). `to` is a **delimiter** keyword (it marks the scope limit — a position marker, not a boolean operator, like keyframe `from`/`to`), so tsv canonicalizes it to lowercase for consistency with how it lowercases keyframe `from`/`to`. Prettier inconsistently lowercases keyframe `from`/`to` but **preserves** `@scope`'s `TO`; tsv lowercases both delimiter keywords uniformly. So `@scope (.card) TO (.footer)` → tsv `to`, prettier `TO`. See [scope_to_case](../tests/fixtures/css/at_rules/scope_to_case_prettier_divergence/).

**Media feature-name case**: a media-feature *name* is ASCII case-insensitive (Media Queries 4 §"Syntax"), and prettier lowercases it (`@media (MIN-WIDTH: 100px)` → `(min-width: 100px)`, including the range/boolean forms `(WIDTH >= 600px)` and `(HOVER)`) while preserving media types (`SCREEN`), the `and`/`or`/`not`/`only` keywords, and feature *values* (`(orientation: LANDSCAPE)` keeps `LANDSCAPE`). tsv **matches** prettier here for **simple** feature expressions — covered by the regular [media_feature_case](../tests/fixtures/css/at_rules/media_feature_case/) (no `_prettier_divergence` suffix). A feature whose *value* is a function (`(min-width: calc(…))`, `(width: min(…))`) is still simple: the function's parentheses don't make the feature opaque, so its name lowercases like any other — covered by [media_feature_function_value](../tests/fixtures/css/at_rules/media_feature_function_value/). Custom media names (`--*`) are case-sensitive (CSS Variables 1) and preserved. The one divergence is **grouped** conditions (`((a) and (b))`, `(not (x))`): prettier's media-query parser only partially descends — lowercasing the first nested feature and leaving the rest — whereas tsv treats the whole grouped condition as opaque and leaves it verbatim, so its nested features are handled consistently. See [media_grouped_feature_case](../tests/fixtures/css/at_rules/media_grouped_feature_case_prettier_divergence/). Note `@import`'s media-query feature names are preserved by both formatters, and the reason generalizes — see **The two prelude readers** below.

**Media feature split trivia**: `parseMediaFeature` finds the colon that splits a feature expression into its name and value with a **raw scan** — its mode stack tracks nothing tsv would call trivia, so a colon inside a comment, a string, or an escape splits the node just as a real one does. `@media (/* : */ 1.50: a)` becomes the name `/*` and the value `*/ 1.50: a`, printed `(/*: */ 1.5: a)`; `@media ('x:y': 1.50)` splits the string in half, leaving neither side a complete string for `adjustStrings` to normalize; `@media (A\:B: 1.50)` splits at the escaped colon. tsv's `feature_name_end` steps all three whole, so the colon it finds is one that really separates a name from a value — the same reading the parser's node split and the case fold take, and the only one under which a name is the single ident *sequence* css-syntax-3 says it is (§"Consume an ident sequence" makes `A\:B` one name carrying a `:`). Following prettier here would cut a name, a comment or a string in half and hand the pieces to two different printers, and its own output shows the cost: the split comment comes back re-spelled (`/*: */`) and the split string loses the quote normalization it would otherwise get. The cells this covers already diverge on case and spacing for the same reason — the escaped-colon spelling has its own entry above ([media_feature_escaped_colon](../tests/fixtures/css/at_rules/media_feature_escaped_colon_prettier_divergence/)) — and the number pass now joins them. See [media_feature_split_trivia](../tests/fixtures/css/at_rules/media_feature_split_trivia_prettier_divergence/).

**The two prelude readers.** A prelude is a media query by *grammar* in both `@media` and `@import`, but prettier does not read the two with the same parser. `parser-postcss.js` routes by at-rule name: `@media` (and `@custom-media`) to `parseMediaQuery`, and `@supports` — plus every `isModuleRuleName` at-rule, of which `@import` is the one tsv formats — to `parseValue`. The readers tokenize the same text differently and print through different arms, so one authoring has two canonical forms, and tsv keys its prelude normalization on the reader rather than on the at-rule (`value_normalization::ValueReader`, named for the reader because a **declaration value** takes `parseValue` too — a comment-bearing one goes through the same pass). tsv routes the same four names — `@media` and `@custom-media` to the media reader, `@supports` and `@import` to the value reader — and `@container`, which is on **neither** of prettier's lists, keeps its params verbatim. Four of prettier's rules follow the split:

- **The unit gate.** The value reader prints a `value-number` node as `printCssNumber(value) + printUnit(unit)` with no gate — whatever trails the number is the unit and rides through — so `@supports (a: 1.50abc)` is `1.5abc`. The media reader's `adjustNumbers` returns the whole `(WORD_PART)?(NUMBER)(UNIT)?` match verbatim unless the unit is empty, the `<an+b>` `n`, or one CSS defines, so `@media (a: 1.50abc)` stays.
- **The hex fold.** A hex colour lowercases on the value reader (`value-word`'s `isColor && isHex`) and not on the media reader, whose regex has no hash arm at all — `#FFF` is `#fff` under `@supports` and `@import`, `#FFF` under `@media`. The fold reads the **whole** `#` word, not a hex-shaped prefix of it: `#FFF.5` is one `value-word` to postcss-values-parser and no colour at all, so both formatters preserve it (a prefix-width read recased it to `#fff.5`). How far that word reaches is postcss's question, and the answer is its tokenizer plus `splitWord`'s gluing of consecutive `word` tokens, not a character class: the word ends only where a **non-`word` token** intervenes — whitespace, `,`, `:`, `{`, `}`, an operator (`+` / `-` / `*` / `/`), an atword, a string, a comment — or where a `(` makes the run a function. Punctuation that is none of those glues straight through, so `#FFF!5`, `#FFF;5`, `#FFF|5`, `#FFF~5`, `#FFF>5`, `#FFF[5`, `#FFF]5`, `#FFF&5`, `#FFF^5`, `#FFF?5`, `#FFF=5`, `#FFF\5` and `#FFF<5` are each one word and none a colour. ⚠️ tsv's `is_hash_word_char` holds only the ident code points plus `.` and `/`, so it ends the word at each of those and folds where prettier preserves — an open gap, not a sanctioned divergence. Whether a `<hash-token>` starts at all is a second question with a *third* answer: tsv follows §4.3.1's ident code points, while postcss starts a `#` word only when `[a-z0-9]` follows. Both leave `#.50` a bare `<delim-token>` normalizing to `#0.5`. They part at `-`: tsv reads `#-.50` as a hash token whose value is `-` and keeps it, where prettier has **no hash token there at all** — a bare `#`, an operator `-`, and `.50` as its own number, printed `#-0.5`. tsv does not follow that form because it re-tokenizes under §4.3.1 as a hash whose value is `-0`, a token change. `_` and non-ASCII fail postcss's start test too, but the word after them absorbs the number anyway (`#_.50`, `#é.50` agree), so `-` is the only spelling where the narrower start test shows.
- **What a number merges with.** A number abutting the run before it is that run's tail — the canonical form of a `.`-leading number carries a leading `0` that would join the run (`x1` + `.50` → `x10` + `.5`, two different tokens). The value reader takes the word through to its end, so an ident, a `<hash-token>` and a number's own unit all absorb (`1a.50`, `#1.50`, `#1.50px`, `1.5.50` kept whole). "Its end" is the tokenizer's, not a class's, and it has an axis no class can hold: the word-end set depends on the word's **first** character (`wordEndRe` for a non-digit start, `numEndRe` — which adds `-` and a bare `/` — for a digit start), so `x-1.50` is one word where `9-1.50` is two, and `x/1.50` is one where `9/1.50` is two. `splitWord` then glues consecutive `word` tokens, which is why `x!1.50` and `x;1.50` absorb as well. The media reader absorbs only behind a `WORD_PART`, and its `#` is no token head, so the number re-splits: `1a0.5`, `#1.5`, `#1.5px`, `1.50.5`. `$` heads no word part either — `[$@]?` in that regex must be followed by a letter or `_` — so `@media (a: $1.50)` is `$1.5` where `@supports` keeps `$1.50`. A `#` followed by no ident code point heads no `<hash-token>` on either reader (§4.3.1 leaves a bare `<delim-token>`), so `#.50` is `#0.5` in both.
- **Where the media reader runs at all.** `parseMediaQuery` is a node split, not one text — `media-type`, `media-feature`, `media-colon`, `media-value`, `media-keyword`, `media-url`, `media-unknown` — and `adjustNumbers` prints only `media-type` and `media-value`. A **`media-feature`** takes `maybeToLowerCase(adjustStrings(value.replaceAll(/ +/g, " ")))` and **no number pass**, and name position is everything before the expression's splitting `:` — the *whole* interior when there is none, so the boolean `(0.50)` and the range `(WIDTH >= 1.50)` / `(1.50 < width < 2.50)` are all name. Prettier therefore lowercases a feature name and keeps its numbers in the same node (`@media (1.50: 2.50)` → `(1.50: 2.5)`). tsv takes that split in **three** places, all keyed on one boundary. For **whitespace**, at parse time: `parse_raw_prelude_content` tracks the expression's own parens and its first colon, so only the expression's own parens trim, a name's runs collapse to one space, and a value's text is emitted verbatim — `(a: x  ,  9px)` and `(not ( screen and ( color ) ))` are fixed points on both formatters, and a comma, a boolean operator or a comment inside an expression is node text rather than something tsv re-spaces (`(/* c */a: b)`, `(a: b/* c */)` — [media_feature_comment_glued](../tests/fixtures/css/at_rules/media_feature_comment_glued/)). The verbatim run survives every neighbour it can have — a comment, an opaque `url()`, a later colon inside the value — and only the SPLITTING colon holds a run open against the expression's `)`, which is the empty value's mandated space ([media_value_verbatim_run](../tests/fixtures/css/at_rules/media_value_verbatim_run/)); the one spelling tsv does not keep is a run carrying a **newline**, a design choice cataloged as `@media value newline` above. For the **number** pass and the **case fold**, at print time: `value_normalization::feature_name_end` draws the line once and both read it, so `@media (1.50: 2.50)` keeps the name's number and normalizes the value's ([media_feature_name_position](../tests/fixtures/css/at_rules/media_feature_name_position/)). Two smaller rules ride the same axis, each the *other* reader's answer applied where it belongs: `<url-token>` opacity is the **value** reader's (`parse-value.js` special-cases the func, `adjustNumbers` has no url concept), so the media path drops it in `media-value` position only — `@media (a: url(1.50))` is `url(1.5)` while `@media (url(1.50): a)` and a depth-0 `media-url` keep their content ([prelude_url_opacity](../tests/fixtures/css/at_rules/prelude_url_opacity/)); and `adjustNumbers` lowercases its captured unit *before* the `<an+b>` gate and prints `printUnit` of *that*, so `@media (a: 2N)` is `2n` where `@supports` keeps `2N` ([prelude_unit_case](../tests/fixtures/css/at_rules/prelude_unit_case/)).

  Three boundary facts hold that split together, all measured against the oracle rather than assumed. **The splitting colon is the first one at any depth**, not the first at depth 1: `parseMediaFeature` splits in `normal` mode and a call's parens do not protect it, so `@media (calc(1:1.50): a)` splits *inside* the call and prettier prints `(calc(1: 1.5): a)`. **A grouped condition splits the same way** — the whole `(…)` is one expression whose first colon lands wherever it lands, which is what keeps `@media (not (a: .50px))` normalizing to `0.5px` while `@media ((1.50: a) and (b: 1.50))` normalizes only the second. **A `(` glued to an identifier opens no expression at all** but a `<function-token>`, so a media *type* carrying a call is type text and `adjustNumbers` walks it whole: `@media calc(1.50)` is `calc(1.5)`, `@media calc(url(1.50))` is `calc(url(1.5))`, and `@media CALC(A)` folds nothing. ⚠️ tsv's boundary steps trivia and escapes where prettier's is a raw scan, a deliberate narrowing sanctioned below (**Media feature split trivia**).

  ⚠️ **What tsv does not model is the split at query level**, where prettier joins its nodes with one space and returns a `media-unknown` verbatim. Two faces of that one gap: tsv pads a comment there where prettier freezes whatever the author glued (`@media a/* c */b`, `screen/* c */and` — cataloged as [media_list](../tests/fixtures/css/tokens/comments/media_list_prettier_divergence/), and the reason the interior rule above stops at depth 0), and tsv runs the number pass over text prettier hands back untouched because it parsed as one `media-unknown` (`@media calc(1.50) url(1.50)`, `@media (a: b) calc(1.50)`). Both are corpus-absent.

A fifth rides the same axis: **separators**. `parseValue` regroups the value into its own nodes and prints its own, so a comma in a `@supports` / `@import` prelude is a separator and takes `, ` (`(a: x,9px)` and `(a: x , 9px)` both → `(a: x, 9px)`); the media reader's value node is raw text, so the identical authoring comes back verbatim under `@media`. `@container` is on neither list and is verbatim throughout, comma included. tsv keys each on the reader — [prelude_separator_spacing](../tests/fixtures/css/at_rules/prelude_separator_spacing/) carries one authoring under both. ⚠️ The value reader's *operator* spacing is **not** taken: prettier's `printCommaSeparatedValueGroup` spaces a `+` beside a hex colour (`(a: #FFF+5)` → `#fff + 5`), where tsv keeps the authoring — an open gap shared with the **declaration** path, which diverges on the same cell (`a { b: #FFF+5 }`), so it belongs to that rule rather than to the prelude reader.

Those five rules are where the readers part, and tsv keys on the reader for each. The pinned cells are matches: [prelude_number_adjacent_number](../tests/fixtures/css/at_rules/prelude_number_adjacent_number/) and [prelude_hash_adjacent_number](../tests/fixtures/css/at_rules/prelude_hash_adjacent_number/) each carry one authoring under both at-rules and pin the two canonical forms it has, and [import_prelude_value_path](../tests/fixtures/css/at_rules/import_prelude_value_path/) pins `@import` on the value side. That side owns the **whole** `@import` prelude, wherever a value sits in it: tsv structures the `url()`/string head and the `layer` / `supports()` calls and reads everything after them — or the entire prelude when no url/string leads it — as one verbatim tail the value reader normalizes, so `@import 1E3;`, `@import 'a.css' 1E3;` and `@import 'a.css' screen 1E3;` all come back `1e3`, a `#FFF` folds and a `"b"` requotes at each position, and a tail ends at a block as it does at a `;` (`@import 'a.css' screen {}`). None of those is `@import` grammar, but an at-rule prelude is consumed as component values whatever they are (CSS Syntax 3 — an `@import` matching no grammar is dropped at cascade, not a parse error), `parseCss` stores every one raw and prettier value-prints it; [import_prelude_first_value](../tests/fixtures/css/at_rules/import_prelude_first_value/) and [import_prelude_tail_start](../tests/fixtures/css/at_rules/import_prelude_tail_start/) pin the two positions the media-query-shaped fixtures cannot reach. `@container` is on neither of prettier's lists — its params stay raw — which is why its prelude is emitted verbatim (see the SCSS directive entry above).

**A third reader: the selector list.** `@custom-selector` (css-extensions-1: `@custom-selector :--name <selector-list>;`) is the one standard-CSS at-rule prettier routes to `parseSelector` — its `custom-selector` arm splits the `:--name` off the front (`params.match(/:--\S+\s+/)`), parses the rest as a selector list, and prints it through `selector-root` as the name, a `line`, then the selectors joined `,` + `line`, the whole group indented once, so a list that fits stays inline (`:--heading h1, h2, h3`) and one that does not puts every selector on its own indented line under the name, a selector that still overflows breaking at its combinator one level deeper — the same breaks a rule head takes ([custom_selector](../tests/fixtures/css/at_rules/custom_selector/), [custom_selector_long](../tests/fixtures/css/at_rules/custom_selector_long/)). tsv reads the same shape — a `:` glued to a `--`-led ident, a whitespace or comment gap, then the strict complex-selector list — and prints it with the selector printer's own comma seam, so the list normalizes exactly as a rule's would (`h1,h2` → `h1, h2`, `.a>.b` → `.a > .b`, `[attr="v"]` → `[attr='v']`, `2N+1` → `2n + 1`), and the `:--name` keeps its case (an author-defined `<extension-name>` has no canonical casing, the same rule `@custom-media`'s `--name` takes). A prelude that is not that shape — a name with nothing after it, a list with no name, a list the selector parser rejects — is kept verbatim like every other unstructurable prelude, where prettier's arm indexes its regex match unconditionally and **throws** (as it does on the spec's shortest name, a bare `:--`, which tsv structures) ([custom_selector_unroutable](../tests/fixtures/css/at_rules/custom_selector_unroutable_prettier_divergence/), cataloged under [conformance_prettier_ts.md §Prettier rejects valid input](./conformance_prettier_ts.md#prettier-rejects-valid-input)). The gap after the name is what tells it from a list that opens with a pseudo-class, and the two formatters read a name with tokens glued to it differently: prettier's `\S+` takes the whole run as the name and formats the list after it (`:--a:hover h1,h2` → `:--a:hover h1, h2`), while the spec's `<custom-selector>` has nothing glued to the `<extension-name>` but an optional `(args)` and puts no required whitespace ahead of the `<selector-list>`, so `:--a:hover, .b` could as well be the name `:--a` and the list `:hover, .b` — tsv declines to restructure the ambiguous spelling and keeps it as authored ([custom_selector_name_glued](../tests/fixtures/css/at_rules/custom_selector_name_glued_prettier_divergence/), ◆design_choice). Two of prettier's choices tsv does not follow. Its routing test is **case-sensitive** (`node.name === "custom-selector"`, where the media arm compares `lowercasedName`), so `@CUSTOM-SELECTOR :--a h1,h2;` is not routed on the first pass — the name lowercases and the list stays verbatim — and only the second pass, now seeing the lowercase name, formats it: non-idempotent, and the at-rule name is ASCII case-insensitive (CSS Syntax 3), so tsv dispatches every spelling alike ([custom_selector_name_case](../tests/fixtures/css/at_rules/custom_selector_name_case_prettier_divergence/)). And it reads the prelude from `node.params`, postcss's comment-stripped copy (the media and value arms take `raws.params.raw`), so every comment in the prelude is silently dropped — cataloged under [§CSS: Comments](#css-comments). Routing is printer-only: the wire `prelude` is `strip_css_comments(span.extract(source))` for this arm and for `Raw` alike, and the span is the raw reader's.

- Non-ASCII boundary whitespace (`<NBSP>`, `<LS>`, `<PS>`, `<ZWNBSP>`, every `Zs`) — ◆content_preservation — [tail_nonascii_space](../tests/fixtures/css/selectors/attribute/tail_nonascii_space_prettier_divergence/) for the attribute selector's tail, [property_nonascii_space](../tests/fixtures/css/declarations/property_nonascii_space_prettier_divergence/) for a declaration's property→colon gap (under §CSS: Comments); every other juncture is pinned by [css_boundary_whitespace.rs](../tests/css_boundary_whitespace.rs) alone. Dropping a character the author wrote is content loss the corpus SAFETY check reads as `content_lost`, and tsv does not copy it — the same call it makes inside a `[`, where prettier turns `[<NBSP>a]` into `[a]`. The combinator gap is one position of many: the same call is made at every juncture the parser steps such a run at — a selector-list start, each `,`, the compound break, a pseudo-argument list's parens, an attribute selector's interior and tail, a block child's rebuilt head, a declaration's property→colon gap, a block's tail, a condition prelude — so wherever prettier drops the character, tsv keeps it. Glued to an identifier the run is part of the NAME on both sides (`.a<NBSP>b`) and both formatters keep it. Two positions are where the bytes are the whole claim: an attribute selector's tail (`[attr=value<NBSP>]`, `[attr=value<NBSP>i]`, `[attr='value' s<NBSP>]`) and the property→colon gap, where css-syntax-3 — whose whitespace is ASCII only — reads the run as identifier content and the ASCII space beside it as the token separator, while `parseCss` reads the run as the separator. Only the author's bytes tokenize the same way under both, so tsv keeps a bare value glued to a run bare and unquoted, a flag glued to a run glued, and the presence of ASCII whitespace beside a run as one space; prettier normalizes the value to a quoted string and drops the run (`[attr='value']`, `[attr='value' i]`), a selector that no longer matches what the author's did. One position tsv drops it too, ratcheted rather than sanctioned: the stylesheet's trailing whitespace. Model: [conformance_svelte.md §Boundary whitespace](./conformance_svelte.md).

**Pseudo-args indent**: When a pseudo-class/element's argument list breaks, prettier indents it an extra level if the enclosing compound's flat `selector-selector` node count exceeds 2 (`shouldIndent = node.nodes.length > 2` in `printer-postcss.js`). That extra `indent` exists to align the continuation lines of a complex selector broken at its combinators; for a *single* compound (no combinator) there is no continuation to align, so it only nests the pseudo args one level deeper than the rule body. tsv keys the indent on combinator presence instead — a complex selector that spans more than one compound indents its continuation (matching prettier), and a pseudo's broken args always indent exactly one level relative to their pseudo. So a combinator-bearing selector matches prettier, while a single compound's pseudo args sit one level in with the `)` aligned to the selector it closes. Uniform, and no node counting. **Space-separated value wrap**: Prettier doesn't wrap CSS space-separated values (e.g., `box-shadow`) when they exceed print width. A 101-char `box-shadow: var(--a) color-mix(...)` stays on one line. tsv wraps at the print width boundary, breaking between space-separated values. This respects the configured print width rather than allowing arbitrary overflows. A value holding a `/* c */` takes the same fill and the same boundary ([space_separated_comment_long_wrap](../tests/fixtures/css/values/lists/space_separated_comment_long_wrap_prettier_divergence/)): every comment after the first word is a fill item like a word, so the item that wraps for the `;` may be a trailing comment itself. 

**Leading comment run before an over-long first word**: a space-separated value opening with a comment run, `prop: /* c */ word`, where that head does not fit the print width. Prettier keeps the run in postcss `raws.between`, prints it with the colon and glues the first word to it, so the first line is unbreakable and overruns by as much as the word is long. tsv treats the run as a fill item like every other part of the value and breaks after it onto a continuation line — the shape a broken comma list already gives a leading run (on the colon's line, the value beneath). Where the head fits, the two agree ([space_separated_comment_long](../tests/fixtures/css/values/lists/space_separated_comment_long/)). See [space_separated_leading_comment_long](../tests/fixtures/css/values/lists/space_separated_leading_comment_long_prettier_divergence/).

**Wide first item**: a space-separated value whose first item does not fit on the colon's line (`prop: '<item>'` past 100 columns). tsv drops the item to a fresh continuation line and fills the rest of the value on from it — the fresh line is a line start, so the tail packs beside the item when it fits after one space and wraps beneath it otherwise — the wide-element drop every tsv fill makes (the Svelte text fill's [fill_spaced_tag_travel_long](../tests/fixtures/svelte/elements/fill_spaced_tag_travel_long_prettier_divergence/)); the fresh line reclaims the property's width, so a value that fits nowhere overruns by less. Prettier's `fill` never breaks ahead of its first content, so the item stays on the colon's line and the head overruns by as much as the item is wide. At exactly 100 columns the item fits and the two agree. A comment in the value takes the same fill and the same boundary — the `: ` is part of the doc on both paths, so the colon's line ends at the `:` when the head drops. See [space_separated_wide_first_item_long](../tests/fixtures/css/values/lists/space_separated_wide_first_item_long_prettier_divergence/).

**Grid value wrap**: a `grid` / `grid-template*` value authored on one line past the print width. Prettier never wraps one — its grid rule (`comma-separated-value-group.js` §"Formatting `grid` property") joins nodes that share a source line with a literal space, so the line overruns by as much as the value is wide. tsv breaks after the colon and packs the value greedily into rows beneath it (`prop:⏎\t[a] … 1fr [b] 2fr;`), a leading comment run kept on the colon's line. The shape is dictated by prettier's own rule: a grid value is laid out by the author's source lines, tsv takes that rule (`grid_multirow_plan`), and both formatters read a wrapped line as a row on the next pass — so the ordinary fill shape, with the first row left on the colon's line, was never a fixed point (both re-row it beneath the colon), while the head-broken form is. At exactly 100 columns the value fits and the two agree. See [grid_template_wrap_long](../tests/fixtures/css/declarations/grid_template_wrap_long_prettier_divergence/); [escaped_whitespace_long](../tests/fixtures/css/values/escaped_whitespace_long_prettier_divergence/) rides the same wrap.

**Multi-line comment width**: a space-separated value holding a multi-line block comment, where the word after the comment's last line fills that line to exactly 100 columns. tsv keeps the word there: a newline-bearing text ends its line in the fit walk and the column restarts at the comment's real end. **Comma+space value boundary**: When comma-separated values contain space-separated parts (like multiple `box-shadow` values), Prettier tolerates lines exceeding printWidth. tsv breaks to stay within 100 chars. See `comma_space_separated_long/` for the matching behavior at 100 and 102 chars.

**Number dot-ident**: tsv matches Prettier's number normalization for all valid CSS — scientific-notation exponents (`1E+2`→`1e2`, `5e0`→`5`), trailing/leading zeros (`1.50`→`1.5`, `.5`→`0.5`), and a trailing dot before a terminator (`1.`→`1`, `1.e1`→`1e1`). This applies to declaration values and to `@media`/`@supports` preludes; `@container` preludes are left raw, matching Prettier. The lone divergence is the _invalid_ sequence `<number>.<ident>` (e.g. `1.px`, `1.foo`): Prettier merges it into a dimension (`1px`), but per CSS Syntax 3 §4.3.3 that is three tokens (`<number>` `<delim .>` `<ident>`), not a dimension — so tsv preserves the source verbatim. This only arises in invalid CSS; Prettier itself keeps `url(1.png)` unmerged.

**Trailing double-dot**: A malformed number with a *consecutive* double dot (`1..`, `1..e-10`, `1..5`) — `parseCss` accepts it (stored raw). The number tokenizer strips a *single* trailing dot (`1.` → `1`), but stripping one from `1..` and re-gluing the leftover onto the next token (`1..e-10` → `1.e-10`) re-parses as a number and normalizes again on the next pass (an F1 non-idempotency). tsv therefore leaves the whole malformed run **verbatim** — uniform with the other malformed-dot forms it already preserves (`..5`, `1.5.5`, `1.px`; see "Number dot-ident" above). Prettier normalizes it (`1..` → `1`, `1..e-10` → `1e-10`, some over two passes — its own transient non-idempotency). Only arises on malformed input.

**Block-valued custom property**: A custom property whose entire value is a top-level `{...}` block is valid per CSS Variables Level 1 §2.1 (`<declaration-value>`, any token sequence with balanced brackets) and appears in Prettier's own corpus. Prettier formats the block contents on their own indented lines like a nested rule body (closing `}` on its own line, then `;`); tsv preserves the value as a single opaque single-line expression. Both forms are stable/idempotent under their respective formatters. (Svelte's CSS parser rejects this form outright with `css_expected_identifier`, so this is also a `_svelte_divergence` — see [conformance_svelte.md](./conformance_svelte.md).)

**Empty custom-property value**: An empty custom-property value is valid — `<declaration-value>?` is optional (CSS Variables 1 §"Custom Property Value Syntax"). CSS Syntax 3 §"Consume a declaration" trims leading **and** trailing whitespace from a declaration's value, so `--a:;`, `--a: ;`, and `--a:     ;` all parse to the same empty value; the spacing is not significant. Prettier preserves whatever spacing the source has (multiple stable forms — `prettier_variant_compact`/`prettier_variant_spaces`); tsv normalizes to a single space (`--a: ;`), the form CSS Variables 1 §"Serializing Custom Properties" mandates ("an empty custom property … must serialize with a single space as its value"). Non-custom empty declarations (`color:;`) remain a parse error — a value is required there. A variant — an empty custom-property value carrying `!important` (`--a: !important;`) — exposes a prettier **non-convergence** bug: prettier adds a space before `!important` on every pass (`--a:!important` → `--a: !important` → `--a:  !important` → …) and never reaches a fixed point, so it can't serve as a formatter oracle. tsv normalizes to the single-space form and is idempotent; guarded by [empty_value_important](../tests/fixtures/css/values/variables/empty_value_important_prettier_divergence/), whose `prettier_nonconvergent.txt` marker makes the validator live-verify the non-convergence (rule F5) instead of running the prettier-anchored rules.

**`!important` trailing whitespace**: whitespace between `!important` and the declaration's `;` (`color: red !important   ;`, with or without a comment after the keyword). tsv normalizes it away, as it does the gap before every other `;`. Prettier keeps it verbatim as a stable form: its declaration printer emits postcss's `raws.important` — the raw tail from the whitespace ahead of `!` to the `;` — rewriting only the `\s*!\s*important` core to ` !important`, so whatever follows the keyword is copied. Prettier itself normalizes the same gap on a declaration without the keyword. See [important_trailing_whitespace](../tests/fixtures/css/declarations/important_trailing_whitespace_prettier_divergence/).

**`progid:` opaque value**: a declaration value whose content begins with `progid:` — the legacy IE filter syntax (`filter: progid:DXImageTransform.Microsoft.gradient(startColorstr='#FF0000', …)`), which no value grammar describes. Both formatters freeze it: no number, quote, hex or unit normalization, interior whitespace and newlines kept, never wrapped however wide, a leading comment run kept on the colon's line as `raws.between` material, `!important` normalized as usual (the agreeing cells, [progid_opaque](../tests/fixtures/css/values/progid_opaque/)). Prettier's trigger is `value.startsWith("progid:")` in `parser-postcss.js`; the `value-unknown` node it returns is discarded by the AST walk, so the declaration keeps postcss's own `value` string and prints it verbatim — and postcss's `raw()` strips a comment with whitespace on either side out of that string (it survives only in `raws.value.raw`), so prettier **drops** a comment inside or trailing the value, and one ahead of `!important`, leaving the spaces around it (`progid:X.Y(a=1.50)  progid:Z.W(b=2)`, `progid:X.Y(a=1.50) ;` — a second pass then trims the stranded space). tsv keeps every comment where it was written; a comment glued on both sides (`)/* c */progid`) stays in postcss's string too, so that cell agrees. A `progid:` that is not the value's first bytes is not the opaque arm on either side: prettier's value printer then reads its `:` as a separator and inserts a space (`alpha(opacity=50) progid: X.Y(…)`), where tsv keeps the glued token whole. tsv reads the trigger ASCII-case-insensitively: postcss's parser exempts only the lowercase word `progid` ahead of a top-level `:` and throws "Missed semicolon" on `PROGID:` / `Progid:` (Svelte's `parseCss` accepts them, and so does tsv), so prettier has no output there and tsv freezes by the same reasoning rather than normalizing a value it does not understand — a cliff keyed on letter case otherwise. See [progid_opaque](../tests/fixtures/css/values/progid_opaque_prettier_divergence/) and [progid_opaque_case](../tests/fixtures/css/values/progid_opaque_case_prettier_divergence/) (`prettier_rejects.txt`).

**Trailing empty comma-list element**: an **empty element** in a comma-separated value (`transition: a,,b`, `linear-gradient(red,,blue)`, a leading `,a`) is a real list entry — CSS Syntax 3 §"parse a comma-separated list of component values" produces a group for the stretch between two commas — so tsv preserves it, breaking a declaration's list one-per-line the way prettier does ([comma_empty_element](../tests/fixtures/css/values/lists/comma_empty_element/), where the two agree; `var()`'s fallback is likewise a comma token both keep, [var_comma_fallback](../tests/fixtures/css/values/variables/var_comma_fallback/)). The divergence is the **last** element being the empty one. Spelling that list back needs one more comma than it has separators — joining `["a", ""]` with `,` gives `a,`, which re-splits to `["a"]`, because the same algorithm stops once the input is empty and so produces no group after a *final* comma. tsv writes the extra comma (`transition:⏎\ta,⏎\t,;`, `linear-gradient(red, ,)`, `--x: a, ,`); prettier does not, and its output is not a fixed point — the **second** pass deletes the element (`transition: a;`, `linear-gradient(red)`, `--x: a;`), pinned in the fixture's `audit_signature.txt`. That is a render change: `linear-gradient(red,,)` is an invalid gradient the UA discards, `linear-gradient(red)` paints. The **custom property** is the case with no invalidity to hide behind — `--x`'s value is a verbatim token sequence (css-variables-1 §"Custom Property Value Syntax"), so dropping the element changes what every `var(--x)` substitutes, whatever the referencing property's grammar says. See [comma_trailing_empty_element](../tests/fixtures/css/values/lists/comma_trailing_empty_element_prettier_divergence/). The same construct in a `<media-query-list>` is [§CSS: At-Rules](#css-at-rules) "Empty media query".

**Closing comma in a value**: a comma **closing** a declaration's value with no element after it (`transition: a,`, `linear-gradient(red, blue,)`, `(red, blue,)`, `--x: a,`) — a nameless parenthesized group is an argument list like any other, so it takes the rule without a clause of its own. tsv keeps it; prettier deletes it — and unlike the empty-element case above, prettier's output is a fixed point, so nothing in prettier's own behavior flags the deletion.

The rule is **token preservation**, not a judgment about which authorings deserve to survive: a declaration value is text tsv re-spells, and a comma the author wrote is one of its tokens. That is what tsv already did everywhere else in a value — `var(--a,)` keeps its empty fallback, an opaque `url(a,)` keeps its comma, and the comment-bearing path (which re-emits the value from source) already kept `--x: a /* c */,`. Only the comment-free, non-`var`, non-`url` path deleted it, on the grounds that the comma-split parse is unchanged — which is true, and is the answer to a question a declaration never asks.

What that token *does* is what makes the deletion a rewrite rather than a tidy, and it differs by declaration kind:

- A **custom property** settles it with no grammar involved at all. Its value is a verbatim token sequence (css-variables-1 §"Custom Property Value Syntax") that `var()` substitutes textually, so the comma is not punctuation *around* the value — it is *part of* it. `f(var(--x) b)` is `f(a, b)` when `--x` is `a,` and `f(a b)` when it is `a`; there is no reading on which the two declarations say the same thing. WPT's `css-variables/variable-declaration-21` is built on exactly that shape (`--b: 0,; --c: 128,;` feeding `rgb(var(--b)var(--c)var(--d))`).
- A **grammar-bearing** declaration is matched against its own production, and css-values-4 §"Component value combinators" requires a comma to be omitted when "all items following the comma have been omitted" — so `transition: a,` does not match and `transition: a` does. Note precisely what that establishes: the two forms **mean different things** (the UA drops one and applies the other), so deleting the comma changes the page. It does not, by itself, oblige a formatter to keep it — a formatter is free to repair invalid CSS. That obligation is tsv's own stance, and it is the same one the empty-element case above already takes, one comma later in the same list: re-spell the declaration faithfully rather than silently turning a dead one live.

The deletion is nevertheless **correct** in exactly one construct, and by a real spec difference rather than a carve-out: mediaqueries-4 §Syntax defines a `<media-query-list>` *as* "a comma-separated list of component values", so there the split **is** the grammar — `screen,` and `screen` are the same one-entry list and no token's meaning is lost ([§CSS: At-Rules](#css-at-rules), "Media query closing comma"). A declaration value is never split that way.

An **escaped** comma is content rather than a separator, so it closes nothing and nothing is appended after it (`gap: a, b\,`, [escaped_whitespace](../tests/fixtures/css/values/escaped_whitespace_prettier_divergence/); `var(--b, x\,)`, [var_comma_fallback](../tests/fixtures/css/values/variables/var_comma_fallback/), where prettier agrees). See [comma_closing](../tests/fixtures/css/values/lists/comma_closing_prettier_divergence/).

Deliberately **not** tagged ◆prettier_bug, though the sibling above is: prettier is idempotent here and its output is valid CSS. A meaning change on its own is ◆content_preservation; ◆prettier_bug is earned by output that is non-idempotent, invalid, or unparseable — which the empty-element case is, since prettier's own *next* pass deletes the element again.

A value carrying a **comment** isn't printed from the AST at all — CSS value comments aren't stored there — so it takes a source-extracting path with two width-chosen branches, and the closing comma has to survive both: the inline branch re-emits the normalized value, while the wrapped branch splits the arguments from source, where the comma in final position produces no part (the same §"parse a comma-separated list" rule) and so is written back after them. The comma also costs a column, which the printer must reserve: a **broken** list's last element ends its line `,;`, so an element that would land at exactly 101 wraps at its own space rather than overrunning (tsv's print width is a hard limit). Both axes are pinned at their 100/101 boundaries by [comma_closing_long](../tests/fixtures/css/values/lists/comma_closing_long_prettier_divergence/), whose `unformatted_ours_flat` variant also covers the authored space after the comma (`…, )`). That fixture is the same ◆content_preservation divergence seen at the boundary, **not** a ◆print_width one: prettier deletes the comma everywhere and, a column shorter, never reaches the width at all — neither formatter overruns.

**Unit serialization case**: CSS dimension units are ASCII case-insensitive (CSS Syntax 3) and their canonical **serialized** form is lowercase — including the frequency units `Hz`/`kHz` and the quarter-millimeter `Q`. CSS Values 4 §7.3 states "all `<frequency>` units are compatible, and `hz` is their canonical unit" and that "1Hz serializes as 1hz"; §6.2 likewise gives "1Q serializes as 1q". tsv canonicalizes **every** unit to this lowercase serialized form (`440Hz`→`440hz`, `1kHz`→`1khz`, `10Q`→`10q`), the same rule it applies to `PX`→`px`. Prettier instead **upcases** these three to their prose spelling (`Hz`/`kHz`/`Q`) while lowercasing all other units; tsv follows the spec's canonical form (spec precedence), so they stay lowercase. The all-agree units are the regular [units_case](../tests/fixtures/css/values/units_case/); the `Hz`/`kHz`/`Q` trio is the divergence, [units_serialize_case](../tests/fixtures/css/values/units_serialize_case_prettier_divergence/).

**Unquoted url() content opaque**: Per CSS Syntax 3 §4.3.6 an unquoted `url(...)` is consumed as one opaque `<url-token>` — its content is *not* re-parsed as component values — so tsv preserves it **verbatim** (`url(a(b,c))` and `url(a( b ))` each format to themselves). When the content contains a nested `(...)` group, prettier instead treats it as a value and reformats inside it: `url(a(b,c))` → `url(a(b, c))` (a space is added after the comma) and `url(a( b ))` → `url(a(b))` (the interior whitespace is dropped). tsv is the more defensible side — reformatting inside an opaque token is a divergence, not a normalization — and both formatters keep their own output idempotent. Only a nested `(...)` exposes it; flat url content has nothing to reformat, and a quoted `url("…")` is a string both leave alone. On Prettier's own corpus this surfaces in `tests/format/css/inline-url/inline_url.css` (`url(--var(foo-bar,#dadce0))` → `url(--var(foo-bar, #dadce0))`) and `tests/format/css/loose/loose.css` (`url(var( x ))` → `url(var(x))`). See [url_nested_reformat](../tests/fixtures/css/values/functions/url_nested_reformat_prettier_divergence/).

**Escaped whitespace in a value**: an **escape is opaque** — nothing inside it is structure. `\` followed by a space is a valid CSS escape whose escaped code point **is that space** (CSS Syntax 3 §4.3.4 "Check if two code points are a valid escape" — only a newline after `\` invalidates it — and §4.3.7 "Consume an escaped code point", whose final branch returns the code point itself). So the trailing space in `width: 50px\ ;` is value *content*, not padding: the value is the ident `50px `, and the `;` terminates the declaration. tsv preserves every escape whole; prettier scans through them and corrupts each kind differently:

- **Trailing payload dropped, delimiter stranded** — `width: 50px\ ;` → `width: 50px\;`, `var(--a, 50px\ )` → `var(--a, 50px\)`, `calc(1px\ )` → `calc(1px\)`. The `;` / `)` becomes an *escaped* character, so the declaration, the function, and the block never close: **prettier's own output no longer re-parses** (tsv's CSS parser rejects it with `Expected '}'`).
- **Payload dropped mid-value** — `color: a\ b` → `color: a\b`, silently changing the value from `a b` to `ab`.
- **Escaped delimiter read as structure** — `var(--b, x\,y)` → `var(--b, x\, y)` (the escaped comma splits one ident, which the comma path rejoins with `", "`) and `inset: a\+b` → `inset: a\+ b` (the escaped `+` takes operator spacing). Both split a single ident into two values.
- **Wrapping inside an ident** — a long value may break *on* an escaped space, putting a `\` at end-of-line; `\` before a newline is not a valid escape at all. See [escaped_whitespace_long](../tests/fixtures/css/values/escaped_whitespace_long_prettier_divergence/), which pins the 100/101 boundary.

A **hex** escape is opaque for one byte more than it looks: it takes up to six hex digits and then, optionally, **one whitespace terminator**, which belongs to the escape (§4.3.7). `\41 2px` is therefore the single ident `A2px`, not `\41` followed by `2px` — here prettier agrees, pinned by the regular fixture [escaped_hex_terminator](../tests/fixtures/css/values/escaped_hex_terminator/).

An unquoted `url()` has the same failure at its closing paren — `url(x\ )` → `url(x\)`, and the url token then never terminates — pinned separately by [url_escaped_whitespace](../tests/fixtures/css/values/functions/url_escaped_whitespace_prettier_divergence/), since url content is opaque and takes its own code path.

tsv declines to reproduce any of it — its format→re-parse invariant outranks matching prettier, and emitting output that does not parse is never the defensible side. Svelte's error-recovering `parseCss` still consumes prettier's output, so this is a *formatter* divergence only; tsv's parse AST matches `parseCss` on the input exactly. The selector axis (an escaped space before a combinator, `,`, or `{`, on a class/id/type leaf **or a pseudo**) is a plain bug rather than a divergence — prettier gets it right — and is pinned by [css/selectors/escaped_names](../tests/fixtures/css/selectors/escaped_names/); so is the whitespace-collapse inside a dropped forgiving-selector item ([forgiving_is_where](../tests/fixtures/css/selectors/forgiving_is_where_svelte_divergence/)). See [escaped_whitespace](../tests/fixtures/css/values/escaped_whitespace_prettier_divergence/).

**String glued to a non-ASCII space**: A comma- or space-separated value whose element is a quoted string glued to a **non-ASCII whitespace** character — a non-breaking space (U+00A0) or an em space (U+2003) — on either side, as in `grid-template-areas: 'x', <NBSP>'y'` (leading) or `grid-template-columns: 'a'<NBSP>, 'b'` (trailing). CSS whitespace is ASCII-only (CSS Syntax 3 §4.2), so a non-ASCII space is not a separator but value content — tsv treats every code point ≥ U+00A0 as an identifier code point, following Svelte's `parseCss` (broader than the CSS Syntax ident set, which excludes these look-alike whitespace chars). tsv keeps the element as **one opaque token, inline**, preserving the character. Prettier's value tokenizer splits it into a word (`<NBSP>`) plus a string (`'y'`), which makes the group multi-token — so prettier inserts a space between them and, for a comma list, breaks it one item per line (`<NBSP> 'y'`). tsv does not split adjacent glued value tokens, so the run stays one token and its bytes survive verbatim — the same lossless form it emits for the pure-ASCII analog `font-family: 'x', a'y'` (tsv keeps `a'y'`; prettier splits to `a 'y'`). The trims are load-bearing for **content**: a Unicode-aware `str::trim` at the value parser's element boundaries or in the printer's value-text whitespace normalizer drops a boundary non-ASCII space — for a string element outright (the narrowed text no longer begins with a quote, so the string printer emits nothing and the whole element vanishes, `'x',;` then `'x';` on a second pass — non-idempotent). Both trim only CSS whitespace (`trim_start_css` / `trim_end_preserving_escape`, the same escape-aware trims that keep an escaped `50px\ ` whole), matching CSS's ASCII-only definition. See [comma_string_nonascii_space](../tests/fixtures/css/values/lists/comma_string_nonascii_space_prettier_divergence/).

**Single value glued to a non-ASCII space**: The single-value (non-list) sibling of the above. A **single** declaration value glued to a non-ASCII whitespace character — a non-breaking space (U+00A0) or an em space (U+2003) — at either boundary, as in `content: <NBSP>'z'` (leading) or `quotes: 'a'<NBSP>` (trailing). Same rule and same design choice: the non-ASCII space is value content — tsv treats it as an identifier code point (≥ U+00A0), following Svelte's `parseCss` — so tsv keeps the value as **one opaque token, inline** (`content: <NBSP>'z'`), while prettier splits a **string** value into a word (`<NBSP>`) plus the string and inserts a space (`content: <NBSP> 'z'`). For an **identifier** value (`font-family: <NBSP>q`) prettier keeps it glued, so tsv matches prettier there; a **function** value it keeps glued when led by the space (`<NBSP>calc(1px)`) but splits when trailed by one (`calc(1px)<NBSP>` → `calc(1px) <NBSP>`), where tsv keeps it glued — so the string cases and the function-trailing case diverge. (A leading space before a function's *name*, or one between the name and its `(`, is a plain conformance case the two agree on — the value is one opaque identifier to both — pinned by `css/values/boundary_nonascii_space_function`; the same character inside a color function's arguments, in an otherwise-empty custom property carrying `!important`, and glued to a keyframe selector are the sibling agreements: `css/values/colors/boundary_nonascii_space`, `css/values/variables/nonascii_space_important`, `css/at_rules/keyframes_selector_nonascii_space`.) Two readers must agree for the **content** to survive (`content: <NBSP>'z'` → `content: 'z'` otherwise): a **trailing** space reaches `locate_value`'s value-boundary trim, which is CSS-whitespace-only (the escape-aware `trim_start_css` / `trim_end_preserving_escape`), and a **leading** space reaches the lexer's whitespace scan in the colon→value gap, which treats only ASCII whitespace as CSS whitespace (CSS Syntax 3 §4.2), so a code point ≥ U+00A0 — which `parseCss` treats as an identifier code point — opens the value's first token rather than being skipped. See [boundary_nonascii_space](../tests/fixtures/css/values/boundary_nonascii_space_prettier_divergence/).

**url() argument glued to a non-ASCII space**: An **unquoted** `url()` argument glued to a non-ASCII whitespace character — a non-breaking space (U+00A0) — at either end (`url(<NBSP>a)`, `url(a<NBSP>)`). The `<url-token>` tokenizer (CSS Syntax 3 §4.3.6) consumes only CSS whitespace (§4.2, ASCII-only) around the argument, so the character is url content and the token's value is `<NBSP>a`; tsv keeps it, trimming ASCII padding only (`url( <NBSP>a )` → `url(<NBSP>a)`). Prettier's url trim is Unicode-wide and **drops the character** (`url(a)`) — content loss, the same call tsv declines at every other boundary non-ASCII space. The **quoted** form `url(<NBSP>"a")` is the glued-string design choice above seen inside `url()`: both keep the character, prettier splits the run into a word plus a quote-normalized string (`url(<NBSP>'a')`), tsv keeps the glued run as one opaque token verbatim. See [url_nonascii_space](../tests/fixtures/css/values/functions/url_nonascii_space_prettier_divergence/).

**Glued run of quoted strings**: The pure-ASCII sibling of the two glued cases above, with no separator at all. A single declaration value that is a **run of glued value tokens** whose first and last token are quoted strings, written adjacent: `content: 'a''b'` (two strings), `content: 'a'x'b'` (string, ident, string), `content: "a"x"b"` (double-quoted). tsv does not split adjacent glued value tokens, so it keeps the run as **one opaque token, inline**, verbatim (`content: 'a'x'b'`); prettier's tokenizer splits it into its component tokens and inserts a space, also normalizing the quote (`content: 'a' x 'b'`). Same lossless choice as `font-family: 'x', a'y'` (tsv keeps `a'y'`; prettier splits to `a 'y'`). The classification is what protects the **content**: a `parse_string_literal` that called the run a single string on "first char is a quote and last char is the matching quote" — true for `'a'x'b'` even though its opening `'` closes at index 2 — would strip the outer quotes and re-quote the interior, turning the **delimiter** quotes into literal content (`content: 'a'x'b'` → `content: "a'x'b"`, a value whose CSS meaning changes and which round-trips to a different AST). So the run is a single string only when the opening quote's first **unescaped** matching close falls at the end of the run (`quoted_string_spans_all`); otherwise it is kept verbatim as an opaque identifier. An escaped interior quote (`'a\'b'`) still closes at the end, so a genuine single string is unaffected. See [glued_string_run](../tests/fixtures/css/values/glued_string_run_prettier_divergence/).

**Escaped paren in a function argument**: A function whose argument list contains an **escaped** paren (`fn(a\(b, 0.1)`). Per CSS Syntax 3 a `\` followed by anything but a newline is a valid escape whose escaped code point is the character itself, and §"Consume an ident sequence" takes it as ident content — so `a\(b` is the single ident `a(b`, not a nesting paren, and the function's own parens balance at the final *unescaped* `)`. tsv steps every escape whole while locating that closing paren, so the value parses as a function and its arguments normalize like any other (`fn(a\(b,.10)` → `fn(a\(b, 0.1)`). Prettier's postcss miscounts the escaped paren — the same bug as [url_escaped_paren_ws](../tests/fixtures/css/values/functions/url_escaped_paren_ws_prettier_divergence/) above, one construct over — and **stops normalizing the whole declaration**, emitting it verbatim (`fn(a\(b,.10)` keeps its `.10`). tsv's canonical form is a prettier fixed point, so this is pinned by a `prettier_variant_*` rather than an `output_prettier`. The escaped **close** paren is the harder half — there prettier throws rather than degrading, pinned by [escaped_close_paren_arg](../tests/fixtures/css/values/functions/escaped_close_paren_arg_prettier_divergence/) and cataloged in [conformance_prettier_ts.md §Prettier rejects valid input](./conformance_prettier_ts.md#prettier-rejects-valid-input). See [escaped_paren_arg](../tests/fixtures/css/values/functions/escaped_paren_arg_prettier_divergence/).

**Line-comment spelling in a function argument**: A function whose argument list contains a `//` (`fn(//x, 0.1)`). CSS has no line comments — per CSS Syntax 3 §4.3.1 a `/` not followed by `*` is a `<delim-token>`, so `//` is two delimiters and ordinary content — and tsv normalizes the list around it as any other (`fn(//x,.10)` → `fn(//x, 0.1)`), in a declaration value, a `@supports` condition and an `@import` prelude alike; only an unquoted `url()` differs, and there both formatters keep the opaque `<url-token>` whole (`url(//a.fuz.dev/x)`, pinned as a match by [url_comment_chars](../tests/fixtures/css/values/functions/url_comment_chars/)). Prettier's value parser runs postcss-values-parser in `loose` mode, where a `//` outside a `url(` opens a **line comment** to the end of the line (an SCSS/LESS spelling applied to CSS); the comment swallows the closing `)`, the parse throws on the unbalanced paren, and prettier emits the whole value verbatim — the freeze of the entry above, one construct over. Every authoring is therefore a prettier fixed point, the author's line break in a prelude included, which is how prettier's own `tests/format/css/no-semicolon/url.css` (`@import ur⏎  l(//fonts…:400,400italic)`, a `url(` split in two) holds its form. Detected by `css_line_comment_freeze`. See [line_comment_arg](../tests/fixtures/css/values/functions/line_comment_arg_prettier_divergence/).

**Stray close paren in a value**: the other spelling that unbalances prettier's value parser — a `)` with no `(` open (`x ) y`, `@import 'a.css' screen ) print;`). Per CSS Syntax 3 §5.4.7 it is a bare `<)-token>` between two component values, and tsv treats the whitespace around it as any separator: collapsed to one space, never removed, with the rest of the value normalizing as usual (`x  )  .50PX` → `x ) 0.5px`, a list after it takes its `, `) — in a declaration value, with or without a comment, and in an `@import` prelude alike, wherever the value reader runs; only the padding *inside* a group strips (`( x )` → `(x)`), and a stray `)` opens none. (An `@supports` prelude is the condition reader's, which keeps a prelude it cannot structure verbatim — [supports_unbalanced_paren](../tests/fixtures/css/at_rules/supports_unbalanced_paren_prettier_divergence/).) Prettier throws on the unbalanced paren and freezes the whole value verbatim, spaces and `.50PX` included — and with nothing after the `)` it errors outright, so `x );` and `@import 'a.css' screen );` have no prettier form at all (`parseCss` accepts them; tsv prints `x )` and `screen )`), pinned by [trailing_close_paren](../tests/fixtures/css/values/trailing_close_paren_prettier_divergence/) and cataloged in [conformance_prettier_ts.md §Prettier rejects valid input](./conformance_prettier_ts.md#prettier-rejects-valid-input). See [stray_close_paren](../tests/fixtures/css/values/stray_close_paren_prettier_divergence/).

**Unquoted `url()` name case**: an unquoted `url()` spelled in any case but lowercase (`URL(x ,y)`, `Url(a,.50)`). Per CSS Syntax 3 §4.3.4 an ident that is an **ASCII case-insensitive** match for `url` followed by `(` opens a `<url-token>`, whose content is opaque (§4.3.6): `URL(x ,y)` is the url `x ,y`, exactly as `url(x ,y)` is. tsv's lexer reads it that way, and so does the text normalizer that re-reads a value from source (a declaration carrying a comment, an `@import` prelude's tail) — the token is kept verbatim and only the padding inside its parens trims (`URL( x ,y )` → `URL(x ,y)`), the treatment [url_comma_content](../tests/fixtures/css/values/functions/url_comma_content/) pins for the lowercase spelling. Prettier's value parser exempts a url-token from function parsing only when the name is the exact lowercase word `url`, so `URL(` and `Url(` are ordinary **functions** to it and their argument lists normalize — `URL(x, y)`, `Url(a, 0.5)` — which changes the URL itself (`x ,y` and `x, y` are two different resources). The same case-sensitive compare is what makes `URL(//x)` freeze where `url(//x)` is opaque (the entry above). See [url_name_case](../tests/fixtures/css/values/functions/url_name_case_prettier_divergence/).

**Escaped delimiter in a function name**: The name-side of the entry above. A function whose *name* carries an escape spelling a delimiter — `a\)b(0.1)`, `a\"b(0.1)`, `a\'b(0.1)`. §"Consume an ident sequence" takes an escape as ident content, and an ident sequence immediately followed by `(` is a `<function-token>` (§"Consume an ident-like token"), so each of these is the function `a)b` / `a"b` / `a'b` and its arguments normalize. Prettier's postcss reads the escape's payload **byte** as structure — the `\)` unbalances its paren count, the `\"` / `\'` open a string it never closes — so it stops normalizing and emits the declaration verbatim, keeping the `.10`. Which *spelling* of the character the author used is the whole of the difference: the hex forms `a\28 b(.10)` / `a\29 b(.10)` carry no raw delimiter byte and prettier normalizes those, agreeing with tsv. tsv's canonical form is a prettier fixed point, so this is pinned by a `prettier_variant_*` rather than an `output_prettier`. The escaped **open** paren is the one payload where the two agree — `a\(b(...)` leaves the name region ending in a dangling `\`, not a valid escape and so not an ident sequence, so tsv refuses the function and prints verbatim, the same output prettier reaches by unbalancing; that agreement is what keeps the value parser's escape-blind search for the opening `(` sound, and the agreeing cases are pinned by the plain [escaped_name](../tests/fixtures/css/values/functions/escaped_name/). See [escaped_delimiter_name](../tests/fixtures/css/values/functions/escaped_delimiter_name_prettier_divergence/).

**Escaped-name terminator before `(`**: A hex escape takes up to six hex digits and then **optionally one whitespace character** — the *terminator*, which belongs to the escape (CSS Syntax 3 §4.3.7: "This optional whitespace allow hexadecimal escape sequences to be followed by 'real' hex digits"). `(` is not a hex digit, so a function name ending in one needs no terminator, and `c\41(0.1)` and `c\41 (0.1)` are the **same** `<function-token>` named `cA` — the first ends the escape at its digits, the second inside the escape. tsv emits whichever the author wrote, the same rule it applies to every other escape boundary: the name's span keeps a live terminator (which had been trimmed off, silently re-spelling the token as `c\41(0.1)` — the same restore a property name already made against its colon, `\41 : red`), and a name the author glued stays glued. Prettier writes the terminator in regardless. On that pair the rewrite is lossless, but it is not on a name whose escape is ended by a literal and so needs no terminator at all: `c\41x(0.1)` is the function `cAx(`, and prettier's `c\41x (0.1)` is an `<ident-token>` followed by a `<(-token>` — a token-stream change, and a value no UA reads as a call. Measured, the insertion fires on every name carrying a hex escape that is not whitespace-terminated (`c\41`, `c\4`, `c\419`, `c\41abc`, `c\41_x`, `c-\41x`), and not when the escape carries its terminator (`c\41 x`) or is a literal escape (`c\g`, `c\gx`); a name holding a `-` before its last character (`c\41-x`, `c\41x-y`) also keeps its glue, an exception the fixture pins as measured. The agreeing spellings are the plain sibling [escaped_name_terminator](../tests/fixtures/css/values/functions/escaped_name_terminator/). See [escaped_name_terminator](../tests/fixtures/css/values/functions/escaped_name_terminator_prettier_divergence/).

**Escaped-paren url() whitespace**: An unquoted `url(...)` whose content carries an escaped paren (`\(` / `\)`) and outer whitespace inside the parens. Per CSS Syntax 3 §4.3.6 the `<url-token>` tokenizer consumes the leading/trailing whitespace, so its canonical value is trimmed; tsv emits that form (`url(  a\(b  )` → `url(a\(b)`). Prettier trims plain url whitespace the same way, but its postcss escaped-paren handling — the same bug that makes it *throw* on [url_escaped_paren](../tests/fixtures/css/values/functions/url_escaped_paren_prettier_divergence/) (`url(a\)b)` → `Unbalanced parenthesis`) — here stops normalizing and keeps the whitespace verbatim (`url(  a\(b  )` stays as-is). Prettier's output is valid, but tsv follows the spec's canonical serialization, so the divergence is escaped-paren-only (plain content agrees). Because tsv's trimmed form is dual-stable, this is pinned by a `prettier_variant_*` rather than an `output_prettier`. On Prettier's own corpus it surfaces in `tests/format/css/url/url.css`. See [url_escaped_paren_ws](../tests/fixtures/css/values/functions/url_escaped_paren_ws_prettier_divergence/).

## CSS: HTML comments (CDO/CDC)

**◆prettier_bug.** Legacy `<!-- … -->` HTML-comment markers in CSS — the CDO/CDC tokens from the old `<style><!-- … --></style>` browser-hiding idiom. Prettier can't format them: rather than throwing, it mangles the markers into invalid CSS (`<!-- -->` → `<!-- -- >`, splitting the `-->` and gluing the next line), so there is no prettier oracle. tsv follows Svelte's `parseCss`, which reads `<!--` … `-->` as a comment span and **discards** it — including any wrapped CSS — so the markers (and their contents) drop on format. Svelte's swallow itself departs from the CSS Syntax spec, where `<!--` (CDO) and `-->` (CDC) are independent no-op tokens and the content between them survives (so the spec — and, mangling aside, prettier — keep a wrapped rule; `parseCss`, and thus tsv, drop it). tsv inherits `parseCss` behavior by design, not the spec's token rules. The parse side (which positions swallow, which keep the markers raw, unterminated errors) is pinned in [conformance_svelte.md §CSS Compat Behaviors](./conformance_svelte.md#css-compat-behaviors) and [tests/css_cdo_cdc.rs](../tests/css_cdo_cdc.rs).
