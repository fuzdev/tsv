# Prettier Conformance: Svelte

The Svelte catalog of tsv's deliberate Prettier divergences — template layout, inline
content, attributes, and blocks. The terminology, the `◆reason` tags, the prettier-bug
index, and the decision framework that governs every entry here live in
[conformance_prettier.md](./conformance_prettier.md).

## Whitespace: Form feed

**◆content_preservation ◆spec_precedence.** A form feed (U+000C) is rendered content, not
collapsible whitespace, so tsv preserves it verbatim wherever it appears in template text.
Prettier respells every one of them as a plain space.

- Svelte — [text_form_feed](../tests/fixtures/svelte/elements/text_form_feed_prettier_divergence/)

CSS Text 3 §White Space Processing: processing "affects only the document white space characters:
spaces (U+0020), tabs (U+0009), and segment breaks" — and in HTML the segment break is U+000A,
the DOM having normalized CR/CRLF away. U+000C is in none of those, so it reaches the rendered
text. Svelte's compiler implements exactly that (`clean_nodes` classifies with
`regex_not_whitespace` = `/[^ \t\r\n]/`, and its trim/collapse replacements use the same set), so
`<span>␌<code>a</code>␌</span>` compiles with both form feeds intact. prettier-plugin-svelte
splits on `[\t\n\f\r ]` instead, so it treats a form feed as collapsible — a content change: the
compiled component's text differs.

Two things follow that make this worth stating as a rule rather than as one fixture. The oracle
here is **the compiler, not prettier**: because both formatters shared the wider class, no corpus
diff against prettier could surface it, and tsv's own class was Rust's `is_ascii_whitespace`,
which includes `\f` for the same historical reason. And the divergence is **uniform across
positions** — content boundary, inter-sibling separator, sole content, inside prose, and the ASCII
half of a boundary run that trims up to it — because it is one character-class question asked in
six places, now answered once by `internal::is_collapsible_ws`. ⚠️ That class is *not* the HTML
**tokenizer's** whitespace, which does include the form feed (a form feed separates attributes);
the parser keeps the wider set deliberately. See
[conformance_svelte.md §Template Whitespace](./conformance_svelte.md#template-whitespace-clean_nodes).

**Fill after inline**: Prettier's fill algorithm allows lines to exceed print width when text follows an inline element closing tag. Prettier produces 111 char lines, tsv breaks at exactly 100 chars.

**Fill boundary**: When fill content exceeds print width, Prettier tolerates the overage while tsv breaks earlier. This is an emergent behavior from prettier-plugin-svelte's doc structure (separate fills per text node with `group([line, element])` wrappers). See also `inline_element_fill_100/` which shows both formatters match at exactly 100 chars.

**Fill after breaking attr**: When an inline element has breaking attributes (e.g., multiline values) and long trailing text follows, Prettier's `handleTextChild` early return for last-child text skips wrapping the previous element, so there's no break point between the closing tag and trailing text. Prettier allows the line to exceed print width (102 chars). tsv's fill correctly breaks trailing words at the print width boundary (100 chars). See also `multiline_value_inline/` which shows both formatters match when trailing text is short.

**Component fill boundary**: Same fill boundary behavior as above but with component elements (`<Comp>text</Comp>`) instead of HTML inline elements. At 101 chars, Prettier keeps everything on one line while tsv breaks the closing `>` of the closing tag to stay within print width. At 100 chars both formatters match.

**Wide inline child own-line**: When an inline child (component or HTML element) is too wide to share a line with the preceding text, Prettier hugs it onto the text line (101+) and breaks it internally — attributes wrap and the closing `>` dangles (the inline content hug). tsv keeps printWidth a hard limit, so the whole child drops to its own line and the preceding word stays hugged on the text line. The break sits at the collapsible space before the child, so it holds regardless of tag-name length (`inline_component_wide_longname_long`), for repeated children in one run (`inline_component_wide_multi_long`), for a multi-attribute component whose own attributes could break (`inline_component_wide_multiattr_long` — it still drops whole, attributes intact), and for special elements (`inline_svelte_element_wide_long`); HTML inline elements produce the identical shape (`inline_element_wide_long`, and `inline_element_wide_multiattr_long` for the multi-attribute counterpart). When a *short* dropped child (its content fits, so the whole tag stays intact on its own line) is followed by trailing text, that text **hugs the intact tag on either authored boundary**, exactly like the wide-content case below — the boundary is render-free, so a newline converges to the form a space produces — because the short child packs its tail like any other fill word (`inline_component_wide_multiattr_long` / `inline_element_wide_multiattr_long`). These fixtures also pin idempotence — the compact authored form and Prettier's hugged form both normalize to the flow form in one pass.

**Wide inline content + trailing text**: The mirror of the above for an element whose own _content_ (not its attributes) overflows, followed by trailing text — `<strong>…90 chars…</strong> tail`. Prettier keeps the content on a single over-width line and lets `>…content…</tag` exceed printWidth (the inline content hug again); tsv wraps the content _inside_ the element, so every line stays ≤100. Terminal trailing text **hugs the intact `</tag>`** (`</tag> tail` — `inline_wide_content_trailing_long`, covering both `<strong>` with no attributes and `<a>` with a short one) on **either** authored boundary: the whitespace between a closing tag and a terminal text sibling is render-free under Svelte 5, so it carries no authoring signal to preserve and tsv converges both spellings onto one fixed point. This mirrors how a _short_ inline element already keeps `<el>x</el> tail` inline. Prettier does distinguish the two (it hugs a space and breaks a newline), so on a space authoring the **content wrap is the sole divergence**, while the newline authoring is additionally a **normalization** divergence — `prettier_variant_newline_tail` is the same block-style content with the tail on its own line, which prettier keeps and tsv folds back to the hug, isolating the boundary from every other difference. The `unformatted_ours_*` variants pin tsv's idempotence: differently-authored forms all normalize to the hugged form in one pass. The convergence stops at a **blank line** — an authored blank line is a Tier-2 signal independent of render, so it survives under both formatters (`variant_blank_line_tail`, dual-stable). A **non-terminal** text run (followed by another inline element) takes the same per-width answer: the tail boundary after an inline element is a fill decision measured from the closing tag's own column — the tail hugs when it fits and breaks when it does not, whatever the authoring and however the element came to be multiline (`inline_wide_content_text_sibling_long` for prose content, `inline_wide_element_content_tail_long` for element-child content at the exact 100/101 boundary; prettier groups the boundary with the element, so its tail always drops once the element is multiline, and it re-breaks the hugged form where tsv holds it). For the **regenerating kinds** — a component, or an element whose content is not a reflowable fill — the per-width answer is forced by idempotence, not taste: their width-broken form emits the very boundary newlines the next parse reads as the Tier-2 expansion signal, so the width-broken and statically-broken renderings must answer the tail boundary identically or the document converges only on pass 2. The one scope where the joint element+boundary measurement survives is an element inside a leading inline-sibling wrap whose **other side does not flow** — a spaced comment or a control-flow block, whose own-line spelling is a fixed point and therefore the only convergeable target: two boundaries then meet on one element and resolve outside-in (see the two-boundaries entry below and `inline_sibling_drop_tail_flow_long`). A wrap coming from an element or tag sibling flows, so it takes the per-width answer like every unwrapped shape (`inline_wide_content_text_sibling_long`'s element-sibling case). The terminal-hug is scoped to *terminal* trailing text, **not** to a first-child element: a wide element **sandwiched** by a preceding text sibling (pushed to its own line by a preceding break) still lets its space-authored terminal tail hug the intact `</tag>` (`inline_wide_content_trailing_sandwiched_long`) — nothing follows the tail, so the hug stays convergent. The rule also covers the **dropped short child**: a short element pushed to its own line by the preceding text (`inline_component_wide_multiattr_long` / `inline_element_wide_multiattr_long`) packs its tail after the intact tag on either authoring, just like the wide-content case. It reaches the **nested wide child** too (`inline_nested_child_trailing_space_long`) — the tail hugs `</tag>` whichever way the boundary is written; prettier keeps the newline form stable where tsv converges it, which is why that form is a `prettier_variant_ownline` rather than a dual-stable `variant_*`.

Separately, a **short** inline element sandwiched in a wrapping fill packs *pairwise* into the surrounding fill after the preceding word rather than being isolated onto its own line (`inline_short_content_fill_long`, HTML `<code>`; `inline_short_component_fill_long`, the component sibling): the flow boundary measures whether the *element* fits after the preceding word — mirroring prettier's greedy fill — not the whole element-plus-trailing-text unit. When the packed run exceeds printWidth tsv wraps it at a word boundary where prettier keeps the over-width inline-content hug — and the divergence is **normalization**, not end state: prettier holds the wrapped `input` stable too, so its hug is a *second* fixed point, reached only from a compact or extra-spaced authoring (`prettier_variant_over_width`, which both `unformatted_ours_*` variants land on and tsv reflows back to `input`). ◆print_width is what picks between the two, so neither fixture carries an `output_prettier`. Components and HTML inline elements pack identically because the fold (`build_after_element_fold`) takes a plain `DocId` and never inspects the element's type.

**Fill expr travel boundary**: The continuation line after a traveled expression tag (see the spaced-tag travel rule in [§Print Width Philosophy](./conformance_prettier.md#print-width-philosophy)): the tag starts the continuation line and the following text packs greedily after it. At the width boundary tsv breaks before the word that would cross 100, while prettier packs it onto the continuation line and overflows. See also `fill_expr_travel_continuation_long/` for matching behavior when the continuation stays under 100.

**Fill multi-expression run travels**: a run holding multiple breakable expression tags reflows like any other fill — every welded word+tag unit shares one fit check, a unit that fits at its position stays flat, and the first unit that does not fit travels whole to the whitespace boundary in front of it, so no expression is torn open while a boundary could still absorb the overflow ([fill_multi_expr_travel_long](../tests/fixtures/svelte/elements/fill_multi_expr_travel_long_prettier_divergence/)). Prettier's boundary measurement stops at an expression's first internal break, so it packs the whole run onto one line (101+) and opens the last ternary mid-line at the widest column (breaking inside the comparison, `!==`); at a deep enough indent it dangles the parent's opening bracket instead ([fill_multiple_expr_long](../tests/fixtures/svelte/elements/fill_multiple_expr_long_prettier_divergence/)). The traveled form is a fixed point of both formatters, so the divergence is one of normalization. The convergence is also authoring-stable ([fill_competing_expr](../tests/fixtures/svelte/elements/fill_competing_expr_prettier_divergence/)): the boundary's fit is a pairwise whole-flat measurement, position-independent across authorings — where the historical hard-width layout (plain-space boundaries keeping every expression group's full fits() obligation, with no boundary break points at all) left a *different* expression flat each pass on some authorings, so two layouts alternated forever.

**Inline content (expression)**: When inline element content with _breakable_ expressions (ternaries, `&&`/`||`, `+`/`-`) exceeds print width, tsv lays it out **block-style** — both tags intact, the content on its own indented line, where the expression usually fits unbroken (and wraps within printWidth only if still too wide). Prettier instead dangles the tag delimiters and breaks the expression operator-by-operator at the tighter dangled indent. This is uniform with text and element content; see §Svelte: Inline content block-style.

**Menu block element**: prettier-plugin-svelte's `blockElements` list includes `ol` and `ul` but omits `menu`. The HTML spec treats `<menu>` identically to `<ul>` — same `display: block`, same CSS rules (`padding-inline-start: 40px`, `counter-reset: list-item`). The spec explicitly says: _"The `menu` element is simply a semantic alternative to `ul`."_ tsv includes `<menu>` in the block element list (spec-compliant), causing block formatting (expanded content) where Prettier hugs content. This only manifests when compact input is formatted — both formatters preserve the block form if given it directly.

**Summary block element**: The same spec gap one element over. prettier-plugin-svelte's `blockElements` list carries `details` and `li` but omits `summary`, while the HTML spec's rendering section defines `details, summary { display: block; }` and then gives the disclosure triangle its own rule on top — `details > summary:first-of-type { display: list-item; counter-increment: list-item 0; list-style: disclosure-closed inside; }`. `list-item` is `li`'s display too, so prettier-plugin-svelte classifies two elements with identical UA display in opposite ways. tsv includes `<summary>` in the block element list (spec-compliant).

The divergence is narrower than "tsv vs prettier": **prettier's own HTML printer agrees with tsv.** `blockElements` is a hand-maintained list transcribed from an MDN doc page (the URL is the comment above it in `../prettier-plugin-svelte/src/lib/elements.ts`), whereas prettier core derives `CSS_DISPLAY_TAGS` programmatically from the UA stylesheet via the `html-ua-styles` package (`../prettier/src/language-html/constants.evaluate.js`, `CSS_DISPLAY_DEFAULT = "inline"` plus a short override block naming neither element). Run through `--parser html`, prettier breaks `<div>text1<summary>text2</summary>text3</div>` onto separate lines exactly as tsv does, and keeps the `<span>` control inline. **The same holds for `menu`** — so both of tsv's block-set additions are agreements with prettier core and disagreements only with the Svelte plugin, whose list has drifted from the source its own project uses.

The visible effect is on the following sibling: as an inline element the space boundary collapses into the surrounding fill and the sibling hugs the closing tag (`</summary> text2 text3`), where as a block element `<summary>` takes its own line and the sibling keeps its own. Like `menu`, this only manifests when compact input is formatted — both formatters preserve the block form if given it directly.

**Block multiline attrs hug**: When whitespace-sensitive elements (`<pre>`, `<textarea>`) have multiline attributes and hugged content that would exceed print width, Prettier keeps `>{content}</tag>` on the attribute line (101+ chars). tsv breaks `>` to its own line (`\n>{content}`) to respect print width while preserving whitespace semantics (no text node added since `>` immediately precedes content).

**svelte:element `this`**: prettier-plugin-svelte ignores `singleQuote` for a brace-wrapped string literal in `<svelte:element this={…}>`, always emitting double quotes (`this={'hello'}` → `this={"hello"}`), and skips escaping entirely — so `this={'a"b'}` becomes the invalid `this={"a"b"}` and `this={'a\b'}` corrupts to a backspace. tsv delegates the literal to the normal string printer, honoring `singleQuote` and escaping like any other string. The bug is narrow — only a *directly* brace-wrapped string literal triggers it; concatenations, template literals, and other expressions delegate to the JS printer and agree (boundary fixture [svelte_element_this](../tests/fixtures/svelte/special_elements/svelte_element_this/)). One adjacent facet diverges further: a *parenthesized* literal `this={('hello')}` collapses to the plain attribute `this="hello"` under prettier (structural rewrite), while tsv keeps `this={'hello'}` — encoded by the fixture's `unformatted_ours_paren` + `variant_paren_collapse` pair.

**svelte:element class ws**: prettier-plugin-svelte does not collapse repeated whitespace in a `class` attribute on `<svelte:element>` (`class="a   b    c"` stays verbatim), while it still collapses on a plain element (`<div class="a   b    c">` → `class="a b c"`) — and so does tsv, everywhere. The `<svelte:element>` attribute path runs off a separate code path from the normal attribute printer, like the `this` bug. tsv collapses uniformly across all elements. Both formatters keep the single-spaced form stable; the divergence shows only when collapsing multi-space input.

**Space after block element**: When a block element (`<div>`, `<p>`, …) is directly followed by content text with a same-line (space, no linebreak) boundary, prettier-plugin-svelte trims the text's leading whitespace (`trimTextNodeLeft`) but still emits the block-child break, stranding a **leading space** on the text line (`<div>block</div> text` → `>⏎ text`). It is **non-idempotent** — a second pass trims the space, converging to the same form tsv produces. tsv takes the same trim but emits no fold/group after the block (the block's own break already supplies the separating line), so no stray space survives and the result is identical in one pass from either authoring. The `unformatted_ours_compact` variant pins tsv's one-pass normalization; `prettier_intermediate_compact` captures prettier's stray-space first pass (which converges to `input` on the next pass).

## Svelte: Inline content block-style

Design choice. tsv lays out an inline element's **wrapping content** block-style — both tags stay intact and the content moves to its own indented line(s), collapsing to `<tag>content</tag>` when it fits, exactly like a block element. Prettier instead **dangles** the tag delimiters (`<tag⏎\t>content</tag⏎>`, pre-breaking the opening tag and dangling the closing `>`). This is uniform across text, expression, and element/component children, with and without attributes (the `>` is **attr-keyed** — it hugs the last attribute when attributes fit and dedents to its own line when they wrap), and including table cells (which are inline-classified). Content that fits stays inline; only overflow breaks to block-style.

### The compiler's whitespace model, and what follows from it

**The compiler's whole whitespace model is three rules, and every claim in this section derives from them.** Svelte 5 deliberately replaced Svelte 4's much more complicated algorithm with: (1) whitespace *between* nodes collapses to one whitespace; (2) whitespace at the *start and end* of a tag's content is removed entirely; (3) `<pre>` / `<textarea>` (and `white-space: pre`) are exempt. The result is deliberately not quite HTML — `<p>foo<span> - bar</span></p>` renders `foo - bar` in HTML but `foo- bar` in Svelte 5, and an author who wants the space writes it outside the tag or as `{' '}`.

Rule 2 is why content-boundary whitespace is **render-free**, so the injected block-style boundaries are render-equivalent (confirmed at corpus scale by `ast_diff --render`) and the boundary may not select a layout. Rule 1 is why a separator's *presence* carries signal — a glued boundary is never split, since breaking it would inject a rendered space — while its *spelling* carries none, so space, tab and single newline are one document. Rule 3 is why `<pre>`/`<textarea>` are dispatched out of this path entirely. Where tsv still lets a *spelling* decide a layout, that is a bug against rule 1, not a divergence from prettier: prettier converges neither axis, so it is no oracle here and the question is tsv-vs-tsv consistency.

Because it is render-free, that whitespace does **not select the layout**. Wherever the content goes multiline, the rule holds without exception: it holds whether the content breaks **structurally** (a block child, a control-flow block) or by **width**, and it holds for a boundary the author *hugged* (zero whitespace) exactly as for one they spaced or broke. So the authorings of one document — `<span>text<div>…`, `<span> text<div>…`, and the newline form — converge on one form. Prettier lets the boundary decide, so it keeps a *different* stable form for each ([content_boundary_convergence](../tests/fixtures/svelte/components/content_boundary_convergence_prettier_divergence/) is one document with three prettier forms and one tsv form), and its space form is additionally **non-idempotent** (the space is emitted at line-start, where the next parse reads it as indentation and drops it). This is the authoring-independence property `authoring_audit` checks — it mutates each content boundary across hug ↔ space ↔ newline and requires every authoring to converge.

The corollary is that whitespace *inside* the content — a **separator between two siblings** — is render-significant and therefore does still decide layout. Whitespace between two adjacent expression tags (`{a} {b}`) is a collapsible break: a space while the element fits, a newline once it goes block-style, so each tag takes its own line ([inline_content_spaced_tags_long](../tests/fixtures/svelte/elements/inline_content_spaced_tags_long_prettier_divergence/)); a text run between them flows as one fill and keeps them on the content line. The boundary carries no signal and must not select the layout; the separator carries one and must.

**But it is the separator's *presence* that carries the signal, not its *spelling*.** A separator's **existence** decides layout — a *glued* boundary is never split, since breaking there would inject a rendered space. Its **form** does not: Svelte 5 collapses an inter-sibling run to one whitespace, so a space and a newline there render identically, and `text1⏎<span>inline1</span>⏎text2` is the same document as `text1 <span>inline1</span> text2`. tsv therefore flows an inline sibling isolated by authored newlines back onto the content line, converging those authorings; prettier lets each boundary decide and holds a stable form for each. This is what turns the large majority of `authoring_audit`'s `content-leading` / `content-trailing` sites from `diverge (dual-stable)` to `converge`; the remainder are shapes the exclusions below deliberately keep.

Note this is **orthogonal to whether the element lays out multiline at all**, which an authored newline *does* decide and which is preserved: a newline anywhere in the content keeps the element multiline (want air, author multiline), and the fully hugged authoring stays hugged — both are shared fixed points with prettier. So the convergence target is the **multiline** form, not a collapsed one-liner; flowing the siblings must not also destroy the air the author asked for.

### What the rule does not reshape, and where convergence stops

Four things are **not** reshaped, because none is a mere spelling difference. A **comment** keeps its authored line (its position is authorship — folding one into a fill would relocate it across a semantic boundary, see [§Comment Position Philosophy](./conformance_prettier.md#comment-position-philosophy)); a **blank line** still breaks (a Tier-2 authoring signal independent of render); a **block sibling** still takes its own line (blocks merely partition a fragment into inline runs, each of which flows on its own); and a **control-flow block** (`{#if}` / `{#each}` / `{#key}` / `{#await}` / `{#snippet}`) keeps its own line too — for `{#snippet}` that is now unconditional (it is a declaration and takes its own line, [see below](#svelte-inline-content-block-style)), so only the four rendering heads remain in question here. The reason for that last one is neither "a block's width is not fixed" (a breaking `{expr}` tag expands mid-run too — `{f(⏎…⏎)}text4` — so width separates nothing) nor a bare appeal to a regressed fixture. It is that **a flowed block has no way to pay an overflow except by tearing itself open.** An inline element that cannot fit drops to its own line *whole*, tags intact — that is what `break_before_wide_flow` buys, and it is what makes flowing safe for elements. No such escape reaches a control-flow block, whose head and tail wrap a *fragment*: the only break available is at its own head↔body seam, so the body node lands on its own line and the flowed sibling text welds to the tail (`{#key key}⏎text6⏎{/key}text7`). The visible cost is that identical constructs then render differently by horizontal accident — in a run of five blocks, the two that happen to straddle the width boundary expand while their siblings stay inline. So the exclusion is a **consequence of a missing mechanism, not a property of blocks**: admitting them is gated on giving a block the same whole-unit drop an element has (widening the `next_is_flow` / `break_before_wide_flow` coupling past `is_inline_el_or_comp`), not on re-litigating this predicate. Measured against the fixture suite, admitting blocks as-is converges ~39 more `authoring_audit` sites — the yield is real, which is exactly why the bar is the layout, not the count. A breaking `{expr}` tag, by contrast, expands *inside its own expression* (the call's argument list) and leaves both of its outer adjacencies untouched, so it flows without this hazard — a settled choice rather than a rough edge.

**The comment exclusion is held on each SIDE independently, and it is where this section's convergence deliberately stops rather than a divergence from prettier.** "Keeps its authored line" is the symmetric reading, and it is the weaker one: the newline *after* a comment holds the following run off the comment's line exactly as the newline *before* it holds the comment off the preceding run's, so a one-sided authoring is a fixed point on that side alone — `text1 <!-- c -->⏎text2` and `text1⏎<!-- c --> text2` both stay, at any width, beside the both-sided form — and beside the form with a newline on neither side, which stays hugged, because the rule HOLDS an authored line rather than FORCING one around a comment (that fourth authoring is the pair's null control: it varies the same dimension, so without it an implementation that always broke both sides would satisfy the other three). Prettier holds all four too, so there is nothing to catalog against it here; the exclusion's whole cost is that these authorings do not converge with each other, which is the price [§Comment Position Philosophy](./conformance_prettier.md#comment-position-philosophy) is already paid for. ⚠️ **It is comment-specific, and the discriminating control has to hold the SITE fixed** — an element or a tag in the identical position flows (`text1 <span>a</span>⏎text2` collapses). Two *other* gates in this rule suppress flow for every sibling kind at once (the prose gate below, and the reflowable-fill suppression the paragraph after it, which closes this rule by making the element multiline for a reason it does not read), so an element control run in a shape either one already catches keeps its lines regardless of what sits there, and reads back as "the newline rule is not about comments" when it is. — [inline_separator_comment_newline](../tests/fixtures/svelte/elements/inline_separator_comment_newline/) pins all four comment authorings, and is deliberately **not** a divergence fixture: prettier holds each one too, so there is nothing for an `output_prettier` to claim. The element twins of the one-sided pair are [inline_sibling_newline_flow](../tests/fixtures/svelte/elements/inline_sibling_newline_flow_prettier_divergence/)'s `prettier_variant_newline_after` / `prettier_variant_newline_before`, which converge on its input — that pair beside these four is the whole control. ⚠️ **The exclusion is scoped to the comment's OWN two boundaries: it BOUNDS the run, it does not STERILIZE one.** The runs a comment separates keep flowing on their own — `text1 <span>a</span> text2⏎<!-- c -->⏎text3 <span>b</span> text4` converges from every isolated authoring of those spans, with only the comment's two newlines held. Nothing distinguishes that from the wider reading ("a run holding a comment keeps every line") unless a control puts a flowing run *beside* the comment and re-authors it: a control whose run is already hugged in every file is a fixed point under either rule and cannot separate them, which is why [inline_sibling_newline_flow](../tests/fixtures/svelte/elements/inline_sibling_newline_flow_prettier_divergence/)'s comment-boundary control is re-authored in all three `prettier_variant_*` files rather than held. The same is true of every other run-bounding sibling (that fixture's block-sibling control carries the parallel pin), so the property belongs to run boundaries in general and not to comments — what is comment-specific is only the *holding*. The practical consequence is that a comment tsv has broken onto its own line for **width** ([fill_break_before_comment_spaced_long](../tests/fixtures/svelte/elements/fill_break_before_comment_spaced_long_prettier_divergence/)) reaches a second fixed point when the run after it was authored on the next line — the same document, differing only in whether that run shares the comment's line.

**The rule's boundary is the presence of a `fill` to reflow into, not the shape of the separator node.** Flowing means reflowing a run per width, and a run reflows only where there is prose for a `fill` to pack. So the rule reaches a whitespace-only separator standing *between two non-text siblings* — `text1⏎<span>a</span>` and `<span>a</span>⏎<span>b</span>` converge alike — **when that separator's inline run holds a content text**, and not otherwise. A run of pure elements or tags (`<Comp {a} />⏎<Comp {b} />`) keeps its authored lines: with no prose its newlines are the only structure the author has, collapsing them packs independent siblings onto one line, and on a short run the collapse cascades into the parent element's own hug decision — an outright idempotency break (`<mrow>` re-hugs on the second pass once its children fold). A run is bounded by whatever owns its own line — a block element, a control-flow block, a comment — and by an authored blank line, so a fragment's prose does not license flow in a neighbouring run that has none. Bounding is not sterilizing, though: a run that *does* hold prose still flows right up against the bounding sibling, and the two spellings of that ("its own boundaries are held" vs "every line near it is held") are only separated by a control that re-authors the neighbouring run — see the comment-boundary note above. Two mechanics keep this sound and are load-bearing. First, a flowing single newline takes the **space arm verbatim** rather than a parallel one: emitting a different collapsible form for the newline than for the space it claims to equal makes the formatter write a newline that its next pass re-reads as flowable and collapses. Second, the boundary must defer to the next sibling for a **tag** as well as an element — a bare `line` in the child list resolves all-or-nothing with the parent group, and a multiline fragment's parent group is always broken, so without that the one boundary owned by a content text's `fill` would flow while the rest of the same run hard-broke. That deferral is gated on the flow predicate and not on "next is a tag", because a plain authored space before a tag may have a **comment** on its other side, whose line is authorship. Note `authoring_audit` is blind to the tag half: both spellings agree there whichever form the rule picks — on the flowed form now, on the hard-broken one under a narrower gate — so it scores them as converging either way. — [inline_sibling_newline_flow](../tests/fixtures/svelte/elements/inline_sibling_newline_flow_prettier_divergence/) (an inline element, a component, an expression tag and a render tag, plus all five controls) and [expressions/angle_escaped](../tests/fixtures/svelte/expressions/angle_escaped_prettier_divergence/) (the tag-separator case, where prettier's plain `line` holds each tag on its authored line), and the shapes the rule reaches across the suite: [fill_text_inline_collapse](../tests/fixtures/svelte/elements/fill_text_inline_collapse_prettier_divergence/), [root_text_newline_inline](../tests/fixtures/svelte/elements/root_text_newline_inline_prettier_divergence/), [block_text_multiline_collapse](../tests/fixtures/svelte/elements/block_text_multiline_collapse_prettier_divergence/), [inline_attrs_multiline_content](../tests/fixtures/svelte/elements/inline_attrs_multiline_content_prettier_divergence/), [components/root_with_text](../tests/fixtures/svelte/components/root_with_text_prettier_divergence/). Where this rule and the render-free content boundary meet on one element, the two compose to a single form — the flowed content with the boundaries hugged — and must settle in **one pass**, since the flow and the collapse it enables are one decision ([inline_content_flow_collapse](../tests/fixtures/svelte/elements/inline_content_flow_collapse_prettier_divergence/), which pins prettier's two stable forms alongside it). An element-separator run where both formatters agree once tsv flows it is pinned by `tests/fixtures/svelte/script/escapes` and `tests/fixtures/svelte/style/escapes`.

**That same "is there a `fill`?" question decides whether the content boundary may select the layout at all**, and it is asked of the RUN, never of the separator's shape or the sibling count. A fill needs two things: **prose to pack** (the predicate above, shared verbatim) and **a whitespace seam to reflow at**. With both, the render-free boundary is inert and the element converges on the inline form — so `<span>⏎<Comp /> text1 <Comp />⏎</span>`, `<span>⏎text1 <code>a</code>⏎</span>` and `<span>⏎{a} text1 {b}⏎</span>` all reach the same one form as the space-separated `<span>⏎<code>a</code> <code>b</code>⏎</span>` that already did. The pure-sibling case is a *third* path to that answer rather than an instance of those two: a run like `<span>⏎{a}\t{b}⏎</span>` holds no prose at all, but the author left the siblings on **one line**, so the boundary newline is not air there either and the element converges inline exactly as its space-separated twin does. That disjunct reads the *line structure*, never the spelling — a space and a tab render the same, so both reach it, and only a **newline** (the spelling that put the siblings on separate lines to begin with, and so the frontier the paragraph above keeps) does not. Testing a literal space there instead let the spelling pick the layout, so one document reached two forms across all three sibling kinds — [inline_separator_tab](../tests/fixtures/svelte/elements/inline_separator_tab_prettier_divergence/), whose hugged-boundary control isolates it: the tab alone was never the trigger, only the tab *with* a newline-authored boundary that had a layout left to select. **A spelling reaches that disjunct through what it DECODES to, not through its bytes**, so an entity-encoded space or tab does too: `&#9;` decodes to whitespace the compiler collapses, which makes it interchangeable with the plain space beside it — and only the *layout* converges, since the entity's own bytes print verbatim (respelling one is a content edit) — [inline_separator_entity_collapse](../tests/fixtures/svelte/elements/inline_separator_entity_collapse_prettier_divergence/). An `&nbsp;` decodes to a non-breaking space, which renders as itself and never collapses, so it does not reach the rule at all ([inline_separator_nbsp_newline](../tests/fixtures/svelte/elements/inline_separator_nbsp_newline/)), and neither does an entity in a run the author *did* break, which holds no prose to reflow ([inline_separator_entity_newline](../tests/fixtures/svelte/elements/inline_separator_entity_newline/)). So the two questions read different texts on purpose and neither may borrow the other's axis: the whitespace scalars that decide what PRINTS read `raw` (matching prettier's `node.raw || node.data`), while the separator questions that decide LAYOUT — is this node the run's prose, is this separator interchangeable with a space — read the decoded data. ⚠️ The authority for "same render" is rule 1 for an element or component pair and the **browser's** own collapse for a tag pair, because `clean_nodes` skips the collapse whenever a neighbor is an `ExpressionTag` — `{a}⇥{b}` reaches compiled output with its tab, where `<code>a</code>⇥<code>b</code>` compiles to a space. Both are render-identical under `white-space: normal`, which is the model tsv's render oracle implements and the one this whole section already assumes ([conformance_svelte.md §Template Whitespace](./conformance_svelte.md#template-whitespace-clean_nodes)); do not restate the tag case as a rule-1 consequence, it is not one. Without a seam the content is one unbreakable unit with nothing to reflow, so the boundary is the only signal the author has and it keeps its authored lines — glued `<a>⏎{expr}text⏎</a>` stays multiline, and prettier agrees ([elements/inline_multiline_nontext](../tests/fixtures/svelte/elements/inline_multiline_nontext/)). Two consequences are load-bearing. First, the run boundary is the *same* one the flow rule uses: a comment, a control-flow block, a block element or an authored blank line ends the run, and content holding one is structured rather than flowed — without that, a `<!-- … -->` and the text beneath it flatten onto one line and an authored blank line is deleted, content-preservation breaks rather than layout choices. Second, **every** reader of "did the author break this content?" must consult this one answer. The predicate suppresses a multiline signal, and a suppressed element lays its content out as one `fill` — which, once the content is wide, wraps a prose text ACROSS LINES and so writes the very newline the other readers key on. A reader left out reports the break on the next pass, the multiline arm then freezes the authored newlines as hardlines, and the two arrangements alternate forever: a real F1 break on real prose tables, and the reason a narrower predicate that gated only the boundary arm had to be reverted. — [inline_content_flow_collapse](../tests/fixtures/svelte/elements/inline_content_flow_collapse_prettier_divergence/) carries the whole class (element pair, table cell, component pair, expression-tag pair, a lone element with prose leading and trailing, and an element pair followed by prose). That last case is what pins the reader count at **four**: its newline lands in a whitespace-ONLY separator node rather than inside a content text, so the run's prose and its break live in *different* nodes — the one shape the other three readers cannot reach, and the last arm to be left out.

**The rule has one boundary — the prose gate above — and the enclosing element's own multiline cause is not a second one.** The rule reaches this separator wherever the element is multiline at all, however it came to be, which is what keeps one run from reaching two answers: the flow rule is consulted at three sites, and the other two — a content text's leading and trailing runs — ask nothing about the cause, so a narrower gate here half-applies it. Inside an element made multiline by its own newlines the boundaries touching a text node then flow while the one between two adjacent siblings does not, and `text1 <span>a</span>⏎<span>b</span> text2` comes out broken in a line that fits — a form neither formatter produces, and a rule keyed on the container cannot be right at one of its boundaries and wrong at the next. The narrow gate was written against a period-2 cycle — collapsing the separator was held to delete the break that chose the multiline arm, so the next pass would take the inline arm, whose separator before a tag is a bare `line`, all-or-nothing with the already-broken parent group, and split the run apart again. That cycle does not occur, for a structural reason rather than a lucky one: this separator is *interior* to the content, so collapsing it cannot touch the element's own boundary newlines, which are what the multiline decision reads. Both spellings converge, for element and tag siblings alike. ⚠️ `authoring_audit` guards only the **element** half of that: on the tag half it scores the two spellings as converging whichever form they land on (the note above), so it cannot see a regression back to the split form, and the fixture below is the only pin. A run laid out by **width** rather than by its own newlines reaches the same interior: the separator before a tag defers to the next sibling's per-width group exactly as it does in the multiline arm, so one prose run has one layout however its element became multiline. Keying it on the cause instead gave a width-broken element one tag per line while its newline-authored twin packed — two interior policies for one document, held apart only by the reflowable-fill suppression that used to keep the authored form out of the multiline arm entirely, and a two-pass cycle the moment authored air is honored there ([inline_boundary_air](../tests/fixtures/svelte/elements/inline_boundary_air/), where the kinds agree with each other and with prettier on the both-boundaries case; the ONE-boundary arity differs per kind and is pinned by [boundary_air_one_sided](../tests/fixtures/svelte/elements/boundary_air_one_sided_prettier_divergence/) — inline is both-or-neither, a block expands on its leading boundary alone, and a component is both-or-neither except that a newline landing inside a content TEXT counts for it, so the same leading boundary expands it in front of text and not in front of an element). — [inline_content_spaced_tags_tail_long](../tests/fixtures/svelte/elements/inline_content_spaced_tags_tail_long_prettier_divergence/), whose overflowing `<small>` holds a spaced tag pair with a trailing text run (the shape that makes the run prose) — one case each for a tag lead and an element lead, plus the 100-char control that stays inline and an `unformatted_ours_one_per_line` variant carrying prettier's form, which tsv packs back in one pass. ⚠️ The widening costs a **tag** divergence prettier does not share: tsv converges an adjacent tag pair onto one line where prettier splits it even though the line fits. That is the same convergence this whole section spends everywhere else, and an element pair in the identical shape prettier already agrees on — the pair beside each other is the assertion. — [inline_adjacent_sibling_newline_flow](../tests/fixtures/svelte/elements/inline_adjacent_sibling_newline_flow_prettier_divergence/) (element pair, tag pair, the structural-cause control that isolates the axis, and a prose-free run that keeps its authored lines).

**Two boundaries meeting on one element break outside-in.** A text run after an inline element meets a *second* boundary whenever that element also carries a leading one (the inline-sibling wrap — the collapsible boundary to the sibling before it). The two are independent decisions and tsv resolves the **leading** one first: once it breaks, the element starts a fresh line, and every later pass measures the trailing boundary from that fresh line. Measuring both inside one group instead answers the trailing question against the column *before* the leading break — a column the output no longer contains — so the document formats to one form and reformats to another, forever. Prettier keeps the leading boundary hugged and breaks only the trailing one; that holds a stable form per authoring but cannot converge them, because the other side of this shape is pinned — a comment's authored line is authorship ([§Comment Position Philosophy](./conformance_prettier.md#comment-position-philosophy)), so the own-line authoring is a fixed point the hugged form can never reach. The price is one more line in the shapes where the hugged form would have fit, and the purchase is the single fixed point. The trailing boundary still measures *together with* the element, because an element too wide to sit flat has to push its tail down and only the joint measurement sees that: detaching it to decide on its own column packs a tail after an element that wrapped its own attributes, which the next pass unpacks. — [inline_sibling_drop_tail_flow_long](../tests/fixtures/svelte/elements/inline_sibling_drop_tail_flow_long_prettier_divergence/), whose 100-char control keeps the element hugged on the sibling's line and whose 101-char case breaks the leading boundary and flows the tail onto the closing tag. At fitting widths the convergence deliberately stops at the comment boundary — both spellings are comment authorship, so the control holds **two** fixed points, hug and own-line (the fixture's dual-stable `variant_control_own_line`), while a tail split mid-run repacks identically under both formatters (`unformatted_tail_split`): the divergence is confined to the boundary. The same shape meets a plain **text** sibling one step in — a word standing between two elements in a mid-run pack, where the leading boundary is ordinary inter-sibling whitespace and so carries no authorship: tsv converges the spaced and own-line authorings and lets the word, the element after it and that element's terminal tail reflow as one fill, while prettier holds the own-line authoring stable and isolates the word on a line of its own. — [inline_multi_element_pack_boundary_long](../tests/fixtures/svelte/elements/inline_multi_element_pack_boundary_long_prettier_divergence/), whose 100-column control packs the run to exactly print width and **agrees** with prettier, and whose 101-column case moves the word and folds element plus tail after it (`prettier_variant_own_line` pins prettier's second fixed point).

### Scope: every fragment in the language

**Scope: every fragment in the language, not just an element's content.** Svelte has two families of fragments — an element's/component's content, and **block bodies** (`{#if}` / `{:else}` / `{#each}` and its `{:else}` fallback / `{#key}` / each `{#await}` phase / `{#snippet}`) — and their boundaries are **equally render-free** (verified against `svelte/compiler`: every fragment boundary in the language is trimmed at compile; only inter-sibling whitespace and `<pre>`/`<textarea>` are significant). The stance applies to both: a block whose body renders multiline lays out block-style — head and tail intact, body on its own indented lines — however the author wrote that boundary, collapsing inline when the body fits. Prettier instead lets the boundary decide, keeping a hugged body hugged (`{#if c}<div>b1</div>⏎<div>b2</div>{/if}`) even as it breaks across lines, so it holds a different stable form for each authoring of one document.

Two corollaries specific to blocks, both following from "the boundary carries no signal":

- **Hug is all-or-nothing, across the whole construct.** A body welded to only the head, or only the tail, is not a half-expansion signal — it converges like any other authoring ([if/hugged_boundary_convergence](../tests/fixtures/svelte/blocks/if/hugged_boundary_convergence_prettier_divergence/)). And a branch that would render inline still drops to its own line once any *sibling* branch went multiline, so `{:else}` never welds its body while `{#if}` holds its own.
- **The body-expand decision is made by width alone, never by whether the head may wrap.** Those are orthogonal — head-wrap is a property of the head, body layout a property of the body. Keying the body on the head's wrap-ability welded the body of any block following a *breakable* sibling ([expression_tag/adjacent_if_block_long](../tests/fixtures/svelte/expression_tag/adjacent_if_block_long_prettier_divergence/) and its `{@html}` / `{@render}` siblings), where prettier's welded line only fits by breaking the body's inner call arguments. Welding is not merely the worse layout, it is **unstable**: the body then renders at the column where the over-width head ended, so its fill breaks at *every* separator, and re-formatting that output reads the newline it just injected as authored leading whitespace and settles on a different form — an **F1 (idempotency) break**. Expanding is what makes the emitted form its own fixed point.

**And the rule reaches below layout: when the content fits, the boundary run is simply removed.** An inline element's authored boundary space is deleted, not preserved — `<span> text </span>` → `<span>text</span>`, uniformly with block elements and components — because those authorings are the same document (the compiler trims every fragment edge at compile), and whenever tsv keeps content inline, every whitespace character in the output is one the compiler keeps. The run is trimmed whole (spaces, tabs, collapsing newlines), a whitespace-only element collapses (`<b> </b>` → `<b></b>` — and with wrapped attributes the close hugs, [inline_empty_long](../tests/fixtures/svelte/elements/inline_empty_long_prettier_divergence/)), and the trim stops at content: an NBSP is content, a comment is a node (the space before a boundary comment is a fragment edge and trims; the space after it is inter-sibling and stays — render-safe under `preserveComments` too), and a both-side newline-authored boundary around an element child keeps its layout meaning (want air → author multiline). Prettier instead preserves an authored boundary space whenever the content fits — the HTML/CSS inline whitespace model, which Svelte 5 deliberately broke from — so the spaced authorings are prettier-stable forms tsv normalizes: [inline_boundary_whitespace](../tests/fixtures/svelte/elements/inline_boundary_whitespace_prettier_divergence/), including a `<title>` outside `<svelte:head>` — a RegularElement, pinned separately because prettier's `<title>` handling could move independently: [title_boundary_whitespace](../tests/fixtures/svelte/elements/title_boundary_whitespace_prettier_divergence/) (the TitleElement form inside `<svelte:head>` prettier trims too, so only the regular form diverges) — and the rest of prettier's whitespace-sensitive set (`<td>`, `<option>`, a foreign svg `<text>`): [inline_boundary_whitespace_misc](../tests/fixtures/svelte/elements/inline_boundary_whitespace_misc_prettier_divergence/). Block elements, components, and `svelte:element` boundaries prettier trims too, so those agree. With this, no render-free boundary character survives anywhere in tsv's inline output, and `authoring_audit` asserts full authoring-independence at content boundaries (hug ↔ space ↔ newline reach one fixed point) everywhere outside `<pre>`/`<textarea>`.

**A HOISTED node does not stand between the content and the fragment edge.** `clean_nodes` lifts `{@const}` / `{const …}` / `{let …}` / `{@debug}` / `<title>` (and, for the compiler, `{#snippet}` plus the `<svelte:head>` family — see below) out of the fragment **before** it trims, so rule 2 measures the edges against what is left: the text beside such a node *is* the first/last node, and the run between them is a render-free edge run rather than an inter-sibling one — `{#if c}text {@debug cond}{/if}` compiles to `text`, exactly like the glued authoring, where `{#if c}text <b>y</b>{/if}` keeps its space. ⚠️ **The hoist licenses two different things, and only one of them is a trim.** The *break* beside such a node is render-free for the same reason its edge run is, so trimming the run and breaking it are both render-correct and only one can happen; tsv splits the set on exactly that question. A **declaration tag** and a **`{#snippet}`** spend the licence on the break (next paragraph); `{@debug}` and `<title>` take the trim, and tsv converges their authorings on the glued form where prettier holds one stable form per authoring — [blocks/hoisted_boundary_convergence](../tests/fixtures/svelte/blocks/hoisted_boundary_convergence_prettier_divergence/). ⚠️ The trim reaches the fragment's **edges only**: with content on both sides the two runs merge into a single rendered space (`a {@debug cond} b` → `a b`), so a space survives there and gluing would be a different document — the fixture's interior control. ⚠️ tsv's participating set is deliberately **narrower** than the oracle's, and every exclusion is one judgement: **a node that owns its own line keeps it.** `<svelte:head>` / `<svelte:window>` / `<svelte:body>` / `<svelte:document>` are block-classified here, so each already gets a line — and a fragment-edge line break is itself render-free, so trimming it and breaking it are both render-correct yet cannot both happen (`<svelte:body … />b` trims to the glued form, whose next pass re-breaks it — an F1 2-cycle the fuzz gate caught). A **`{#snippet}`** declares a binding and renders nothing — the same two facts as a declaration tag — so it spends the licence the same way: it takes its own line (next paragraph) and reaches the trim only through that break. Trimming its edge run instead welded a snippet *declaration* onto the content beside it (`<Details>⏎{#snippet summary()}…{/snippet}⏎text⏎</Details>`), the worse layout for the same render. ⚠️ This hoist is **not** one of Svelte 5's three published whitespace rules, which say nothing about which nodes the edge is measured against; it lives only in `clean_nodes`, so it is verified against the compiler rather than the summary. ⚠️ **`ast_diff --render` is blind to it** for exactly that reason — its normalizer implements the three published rules, so it reports a whitespace change beside a hoisted node as a semantic one. Both gating oracles drive the compiler instead (`render_audit`, and the fixture validator's render-equivalence check), so this costs nothing at the gates; it is a triage trap, not a coverage hole. Reach for `canonical_compile` on the two forms when triaging anything in this class.

**A DECLARATION TAG takes its own line** — `{@const}`, `{const …}`, `{let …}`: the tags that declare a binding and render nothing. The hoist above is what makes the whitespace beside such a tag render-free (at a fragment edge the run is deleted; in the interior the two runs it splits merge back into the single whitespace rule 1 would have produced anyway — `{#if c}a {@const x = 1} b{/if}` compiles to `a b`, exactly like the own-line form), so the layout question is free, and tsv answers it with the tag's own line: that is where authors already write these tags (41 of 41 declaration tags across the corpus sit on their own line) and what makes a run of them read as the declarations they are. Every authoring — glued, spaced, newline — is therefore one document reaching one form, in **every** fragment: block bodies, component and element content, and the root (`{@const}` must be a block/component child, but `{const}`/`{let}` carry no placement restriction and are legal anywhere). Prettier welds the tag to whatever the author wrote beside it, keeping a stable form per authoring — [tags/declaration_own_line](../tests/fixtures/svelte/tags/declaration_own_line_prettier_divergence/). ⚠️ **The exception is a tag glued to CONTENT on both sides**, the one shape where the break is not render-free: `{#if c}a{@const x = 1}b{/if}` compiles to `ab` while the own-line form compiles to `a b` — a different document. That is the standing "a glued boundary is never split" rule, and it is what bounds this one; gluing is asked of the nearest *content* on each side, so a hoisted neighbour does not count and a run of consecutive tags is not glued to itself. A **lone** tag touches only its fragment's boundaries, which are not content either, so it is not glued and takes its line all the same — the host goes multiline (`{#if cond}⏎\t{@const x = 1}⏎{/if}`). **`{#snippet}` is in the set**: it declares a binding (the snippet name), renders nothing, and hoists alike, so it takes its own line under the same rule with the same glued-both-sides exception — [blocks/snippet/own_line](../tests/fixtures/svelte/blocks/snippet/own_line_prettier_divergence/). ⚠️ **`{@debug}` is excluded** — it is not a declaration but a transient debugging aid, so welding it to its neighbour keeps it out of the way of the code it inspects, and it keeps the trim instead.

**"The trim stops at content" is one rule, so it holds at the ROOT fragment too** — the root is a fragment like any other, and it was the one place that used a *wider* whitespace class (Rust's `str::trim`, the Unicode `White_Space` property) and so deleted a boundary NBSP the compiler keeps: [root_leading_nbsp](../tests/fixtures/svelte/elements/root_leading_nbsp_prettier_divergence/) (◆content_preservation — prettier deletes it too, so only the compiler oracle sees it). The line break tsv leaves after such a node is render-free on its own terms: whitespace at a block-level boundary is not rendered, so `&nbsp;<div>` and `&nbsp;⏎<div>` reduce to the same render key. This is the same class as [§Whitespace: Form feed](#whitespace-form-feed) — a character that looks like whitespace to a wide predicate and is content to the compiler — which is why the printer now asks one predicate (`internal::is_collapsible_ws`) everywhere instead of a per-site spelling.

**And it reaches inter-sibling whitespace in the one place that is *also* render-free: a whitespace-collapsing container.** Inside `<table>` / `<tbody>` / `<thead>` / `<tfoot>` / `<tr>` / `<colgroup>` / `<select>` / `<datalist>` (Svelte's `clean_nodes` `can_remove_entirely`) the compiler removes an inter-sibling whitespace-only run **entirely** rather than collapsing it to a rendered space, so it never renders. tsv lays such a container out **block-style** — each child on its own indented line, the inter-sibling whitespace trimmed — matching the compiled render, the same stance every other render-free boundary takes; prettier keeps a container authored inline on one line. An **authored blank line** between two children survives (collapsed to a single blank), because blank-line preservation is a Tier-2 authoring signal independent of render — uniform with every other block-style boundary tsv produces. This is the **exact** Svelte set: a deliberate *subset* of what HTML collapses (Svelte's source carries a `// TODO others?`), so `optgroup` / `ul` / `ol` / `menu` / `dl` / `fieldset` are **not** members — tsv keeps their inter-sibling space, matching Svelte (tsv is a drop-in for Svelte's compiler, not for raw HTML). The SVG arm of `can_remove_entirely` (any SVG element outside a `<text>` element) is namespace-based rather than name-based and is a follow-up; everywhere else an inter-sibling space is render-significant and stays. — [ws_collapsing_containers](../tests/fixtures/svelte/elements/ws_collapsing_containers_prettier_divergence/) (`<select>` / `<table>` block-style, with an ordinary `<div>` control that keeps its space), [implicit_close_table](../tests/fixtures/svelte/elements/implicit_close_table_prettier_divergence/) (the same block-style over a table built with implicit end tags), the `<td>` / `<option>` cases of [inline_boundary_whitespace_misc](../tests/fixtures/svelte/elements/inline_boundary_whitespace_misc_prettier_divergence/) (where the container block-style overlaps the boundary-space trim), and [ws_collapsing_container_blank](../tests/fixtures/svelte/elements/ws_collapsing_container_blank_prettier_divergence/) (an authored blank line between two `<option>`s is preserved block-style; prettier dangles the compact authoring).

**That container licence stops at a TEXT child, and the stop is part of the rule.**
`can_remove_entirely` removes a node only when its data is exactly `' '` — a whitespace-only run
between two *non-text* children, which is what an injected line break becomes there. A boundary
with a **content text** child lands *inside* that text node, where the run collapses to a single
rendered space instead of vanishing, so block-styling across it would change the compiled output.
tsv therefore reproduces such a boundary as authored: a **glued** boundary gets no break at all,
and an authored **space** is spent on the line break rather than re-emitted beside it. The
container's own edges stay free either way (`clean_nodes` strips the first and last text node's
outer whitespace whatever the parent), so a lone text child still takes its own line. —
[ws_collapsing_container_text_child](../tests/fixtures/svelte/elements/ws_collapsing_container_text_child_prettier_divergence/).

Two consequences of "the boundary carries no signal":

- **A break on one side alone is not an expansion signal.** A component expands when the author broke **both** content boundaries; a lone opening newline collapses back inline rather than half-breaking the tags ([opening_newline_only](../tests/fixtures/svelte/components/opening_newline_only_prettier_divergence/)). Prettier honors the lone break and dangles the closing delimiter to hold the content against it.
- **`svelte:*` elements are not special here.** `<slot>`, `<svelte:element>`, `<svelte:component>`, `<svelte:fragment>` and friends run the **same** layout analysis as regular elements, so they converge on the same block-style form. (They are block-kind for whitespace purposes: their content boundaries are trimmed, not preserved as a space. Prettier draws the same line from the other side — its `isInlineElement` requires a `RegularElement`.)

### Where a content-boundary dangle survives

**A CONTENT-boundary dangle survives in exactly one place: inside `<pre>` / `<textarea>`**, where that boundary whitespace *is* render-significant and the dangle is mandatory rather than cosmetic — see [pre_closing_tag](../tests/fixtures/svelte/elements/pre_closing_tag/), [textarea_content_long](../tests/fixtures/svelte/elements/textarea_content_long/). Those elements never reach the shared layout analysis. An *empty* whitespace-sensitive element has no content to protect, so an inline parent hugging it lays out block-style like any other ([textarea_empty_hugged_long](../tests/fixtures/svelte/elements/textarea_empty_hugged_long_prettier_divergence/)).

**tsv does keep one dangle of its own, and it is not an exception to this rule** — the **sibling `>` dangle** (`<a href={root}>Home</a⏎>{#each …}`), where an inline element byte-glued to a following sibling hands its closing `>` to that sibling's line: a multiline-rendering block head (as here), a following glued element (the G2 chain), or glued following text (the glued-both dangle in the break-before paragraph above). See [§Svelte: Blocks](#svelte-blocks). The distinction is the whole point of this section: that dangle is keyed on **inter-sibling** whitespace — specifically its *absence* — and inter-sibling whitespace is render-**significant** under Svelte 5 (it collapses to one space; it does not vanish). So the character selecting that layout is one the compiler *keeps*, which is exactly the license a content-boundary character lacks. Same reason `authoring_audit` reshapes inter-sibling runs (space↔newline) but *creates and destroys* content-boundary ones (hug↔space↔newline).

Both formatters keep the block-style form once produced (`prettier(input) == input`); the divergence is that tsv *converges every authoring* to block-style while prettier dangles a compact authoring — so these fixtures carry `unformatted_ours_*` compact variants (tsv normalizes them to the block-style input, prettier does not) alongside `prettier_variant_*` files pinning prettier's stable dangle form (which tsv likewise normalizes to the block-style input). See also the "Inline content (text)", "Inline content (expression)", and "Wide inline content + trailing text" rows above.

### Moving a run: break-before, travel, and welded units

**The rule reaches the element's own *position*, not just its content: an opening tag never dangles after a space.** When an inline element is preceded by same-line inline content that must wrap, tsv breaks at the last **whitespace** boundary before the element — carrying any *glued* prefix with it, whether a glued text word or a glued HTML **comment** (`<!--c--><a…>`, a run of them, or a word *and* a comment `word<!--c--><a…>` — each binds to the element it precedes and moves to the fresh line as one unit) — so the element starts a fresh line rather than leaving its opening tag stranded at the end of the text line. On its fresh line the element lays out uniformly with everything above: it collapses back inline when it fits, goes block-style when only its content overflows, and wraps its attributes when the opening tag itself exceeds printWidth. The whitespace boundary before the element is inter-node whitespace that collapses to one space at compile, so turning it into a break is render-equivalent (`ast_diff --render`); the *glued* boundary inside the run is render-significant and is never split (breaking there would inject a rendered space). Prettier keeps the opening tag on the text line — hugging it and dropping only the content, or dangling its attributes/`>` — and lets the line run past printWidth. tsv already preserves the fresh-line form when authored; the change is that it now *converges* the compact and dangled authorings to it. The one place an opening tag may still sit at a line end is after a **glued preceding element** whose own tag must wrap: there tsv dangles that preceding element's closing `>` onto the next element's line (`<span>foo</span⏎><a…`, the **G2** shape), reusing the sibling-`>` dangle so nothing is stranded after a space. A run of 3+ glued elements is one indivisible unit: the whole run breaks before together (a wide element anywhere in it pulls the entire run to a fresh line — no earlier short element can strand it on the text line), and every adjacent Soft pair sheds its `>` (a mid-run element both receives its predecessor's `>` and sheds its own). — [inline_break_before_wrap_long](../tests/fixtures/svelte/elements/inline_break_before_wrap_long_prettier_divergence/) (the HTML inline-element cases: control@100, collapse@101, last child, block-style, attrs-wrap), [inline_break_before_component_long](../tests/fixtures/svelte/elements/inline_break_before_component_long_prettier_divergence/) (component parity), [inline_break_before_void_long](../tests/fixtures/svelte/elements/inline_break_before_void_long_prettier_divergence/) (void / self-closing parity), [inline_break_before_glued_long](../tests/fixtures/svelte/elements/inline_break_before_glued_long_prettier_divergence/) (a glued text prefix travels with the element — never split; the glue may run *through* an expression tag — `glued{x}<a …>`, crossing the width on either side of the tag — into a tag whose expression itself must break, which travels first and breaks internally on the fresh line, and into *another* tag — `glued{x}{y}`, packing at 100 and travelling at 101; a tag glued to a following *block* element does not extend the unit — the block detaches to its own line regardless, so the measured unit stays the word+tag pair, packing at 100 and travelling at 101 like the smallest welded unit it is — see [§Print Width Philosophy](./conformance_prettier.md#print-width-philosophy) and [fill_glued_tag_travel_long](../tests/fixtures/svelte/elements/fill_glued_tag_travel_long_prettier_divergence/)), [inline_break_before_comment_glued_long](../tests/fixtures/svelte/elements/inline_break_before_comment_glued_long_prettier_divergence/) (a glued HTML **comment** prefix travels with the element the same way — `<!--c--><a…>` breaks before the comment, incl. a run of two comments and a block-style tail), [inline_break_before_comment_glued_word_long](../tests/fixtures/svelte/elements/inline_break_before_comment_glued_word_long_prettier_divergence/) (a glued word *and* comment — `word<!--c--><a…>` — form one run that breaks before the word), [inline_break_before_gt_dangle_long](../tests/fixtures/svelte/elements/inline_break_before_gt_dangle_long_prettier_divergence/) (the G2 closing-`>` dangle for a glued element pair), [inline_break_before_chain_long](../tests/fixtures/svelte/elements/inline_break_before_chain_long_prettier_divergence/) (the G2 dangle generalized to a run of 3+ glued elements — whole run breaks before, every pair sheds), [inline_closing_text](../tests/fixtures/svelte/elements/inline_closing_text_prettier_divergence/) (a component with glued trailing text `.` collapses on its fresh line), [multiline_value_inline](../tests/fixtures/svelte/attributes/multiline_value_inline_prettier_divergence/) + [_long](../tests/fixtures/svelte/attributes/multiline_value_inline_long_prettier_divergence/) (the break is triggered by a forced-multiline *attribute* value, not width), [inline_nbsp_boundary_long](../tests/fixtures/svelte/elements/inline_nbsp_boundary_long_prettier_divergence/) (the element collapses on its fresh line; a trailing NBSP stays glued to the close tag), [inline_break_before_nonterminal_long](../tests/fixtures/svelte/elements/inline_break_before_nonterminal_long_prettier_divergence/) (a following whitespace-separated sibling — the element still breaks before and block-styles; the terminal ` tail` hugs the intact close tag).

**The mirror on the other side of the run — a TEXT run that must move.** Once a text run's first word no longer fits after its preceding sibling, the whole run starts a fresh line and flows there as one fill, and the boundary space is **spent on the break** rather than re-emitted beside it: a re-emitted space strands a leading space at the head of the continuation line, which the next pass reads as indentation and drops, leaving the format with no fixed point. When that boundary is **glued**, no break may land *inside* it — the run stays welded to the preceding node even where the glued head overruns printWidth, since breaking there would inject a rendered space (and the mangled form is itself a fixed point, so idempotency alone can never see it). tsv holds that structurally rather than by a layout rule: a glued comment prefix is built *into* the run's first fill item, and a fill breaks only between items.

**But "unbreakable inside" is not "immovable".** The glued unit still has whatever boundary sits in front of *it*, and when the unit begins its line there is none — it simply stands, however far it overruns. When the unit sits **mid-line** that boundary is ordinary inter-node whitespace, which the compiler collapses to one rendered space, so tsv spends it: the comment and the word it is glued to move to a fresh line **together**. Prettier welds the unit to the preceding word in both positions and lets the line run over, so the mid-line position is a divergence and the line-start position is not. ⚠️ Note the mid-line claim is *"spend the break you have"*, not the stronger [§Print Width Philosophy](./conformance_prettier.md#print-width-philosophy) hard limit: a comment wider than print width cannot be made to fit by any break, and tsv moves the unit anyway rather than leave an available break unused.

**Take the glue away on both sides and the boundary in front is an ordinary fill break.** A comment spaced on *both* sides is its own fill item, so the word before it is measured **without** it and keeps its column, and the comment starts a fresh line as soon as it no longer fits — the same render-free boundary as above, now with nothing welded to either side of it. ⚠️ Here the claim *is* the [§Print Width Philosophy](./conformance_prettier.md#print-width-philosophy) hard limit and not the weaker mid-line one: a word and a comment that each fit on a line but not together have a layout that meets the limit, so the break must be taken. Prettier packs the comment onto the text line and lets the line run over, keeping that form stable alongside tsv's, which makes it a normalization divergence. Nothing but a width measurement separates the two — both forms are idempotent, comment-complete and reparse-clean, and on the widest case prettier's packed form is the over-width line itself, so the oracle cannot grade it.

— [fill_after_comment_spaced_long](../tests/fixtures/svelte/elements/fill_after_comment_spaced_long_prettier_divergence/) (the spaced boundary: whole line @100, first word @100, 101 → the run moves, a long run rewrapping on its fresh line, and the container-class control — an inline `<span>`, whose collapsible content leaves it with no multiline cause), [fill_after_comment_glued_long](../tests/fixtures/svelte/elements/fill_after_comment_glued_long/) (the glued boundary at line start — never split, incl. a run of two glued comments; both formatters agree, so it is not a divergence), [fill_after_comment_glued_midline_long](../tests/fixtures/svelte/elements/fill_after_comment_glued_midline_long_prettier_divergence/) (the glued boundary mid-line: fits @98 → stays, 104 → the unit moves and lands @100, the case where it moves and is still over @101, and the case where the boundary in front of the unit is *also* glued → the unit cannot move and the break travels further left), [fill_break_before_comment_spaced_long](../tests/fixtures/svelte/elements/fill_break_before_comment_spaced_long_prettier_divergence/) (spaced on *both* sides — the break in front of the comment: @100 it stays, @101 it moves and the preceding word holds its column, a word+comment pair that fits on no shared line, the same boundary with nothing after the comment at all, and the container-class control (an inline `<span>` and a table cell, whose collapsible content leaves the container with no multiline cause) — pinned from the one-line authoring, since prettier's packed form carries a newline after the comment that tsv preserves by a separate rule).

**The complement: an element *glued* to its predecessor breaks *after* itself.** With no whitespace boundary before it the break-before rule can't fire, so tsv breaks after the element instead — the sibling-`>` dangle generalizes from a glued following *element* to glued following **text**. ⚠️ **A welded RUN is one movable unit, and "unbreakable inside" must not be mistaken for "immovable".** A run of glued nodes — element, glued text, element (`<code>.x</code>.w<b>y</b>`) — admits no break in either of its glued boundaries, since each would inject a rendered space (`.x.wyyyyyyyy` → `.x.w yyyyyyyy`). The two shapes are pinned separately — a welded pair with a *spaced* tail, where both formatters agree once tsv travels ([fill_inline_pairwise_welded_long](../tests/fixtures/svelte/elements/fill_inline_pairwise_welded_long/)), and the divergent tail forms above. ⚠️ **The rule does not depend on what precedes the run either**, and that axis is the one that has to be pinned from the *render* side rather than the build side: every case above has text in front of the run, so the boundary belongs to that text's own fill, whereas an inline **element** or **tag** sibling leaves the boundary to the run's own leading whitespace — where a head of a single glued word (`(<a …>`) is a bare text node rather than a fill, and the flag selecting the whole-flat measurement is only ever read off a fill. — [inline_welded_run_after_sibling_long](../tests/fixtures/svelte/elements/inline_welded_run_after_sibling_long_prettier_divergence/) (lone-word head at the exact 100/101 boundary, the same before a tag sibling, a two-word head at the same width — how many words head the run cannot change the answer — and the two overflow regimes: a run far too wide to pack that still fits on its own line, and one whose element is wider than a whole line and travels anyway before laying out block-style). ## Svelte: Attributes

**Trailing comments in `{...}`** (◆content_preservation) — [expr_trailing](../tests/fixtures/svelte/syntax/comments/expr_trailing_prettier_divergence/) (block comments, inline); [expr_trailing_line](../tests/fixtures/svelte/syntax/comments/expr_trailing_line_prettier_divergence/) (line comments — `}` kept on its own line so the `//` doesn't swallow it). Each fixture's README lists the contexts; they include `<svelte:element this={…}>` / `<svelte:component this={…}>`, whose expression Svelte's AST holds bare (no `ExpressionTag` around it) but which is the same `{…}` attribute value as any other. The *leading* and *interior* positions there are preserved by both formatters — [expr_special_this](../tests/fixtures/svelte/syntax/comments/expr_special_this/). A **run** of trailing comments is not the one-comment rule twice: prettier deletes them all, so tsv alone answers where the second one goes, and it answers with the run's own shape — a `//` ends the line, so what follows starts a fresh one and drops the separator space that would otherwise be leading whitespace; and the run's LAST comment decides the closer (a run ending in a block comment leaves no break for `}` to reuse, so a directive value takes the block form rather than hugging) — [expr_trailing_run](../tests/fixtures/svelte/syntax/comments/expr_trailing_run_prettier_divergence/). Reusing that break also fixes the closer's **column**, since the renderer indents a line from the line command that produced it: wherever the head's own content is indented, the run-final `//`'s break is emitted one level out so the `}` still lands at the tag's column and not the content's. Two things indent it — a **leading** line comment hanging a block head's continuation ([§Svelte: Blocks](#svelte-blocks)) and a `{@const}` init taking the break-after-operator layout — with a leading-comment-free control pinning that the column is the same either way; prettier's `{@const}` output there is additionally corrupt (an unmatched paren it then throws on) — [expr_trailing_indented_content](../tests/fixtures/svelte/syntax/comments/expr_trailing_indented_content_prettier_divergence/). A **frozen** value is the third indent and answers identically — [braced_value_trailing_line](../tests/fixtures/svelte/syntax/prettier_ignore/braced_value_trailing_line_prettier_divergence/). The `bind:` **function-binding sequence** is the same position one host in: prettier keeps the sequence's leading and inter-operand comments (so [function_comment](../tests/fixtures/svelte/directives/bind/function_comment/) matches) and deletes only the one past the last operand — [value_sequence_trailing_comment](../tests/fixtures/svelte/directives/bind/value_sequence_trailing_comment_prettier_divergence/). An `{#each}` **key paren** is the same position without the `{`: prettier deletes a comment trailing the key expression (`(item.id /* c */)`, carried by `expr_trailing` above) and keeps the leading one. That verdict does not depend on the head having an `as` binding, and the **no-`as`** shape is where it is load-bearing — with no binding pattern after the iterable, the key parens are the only comment-bearing gap the `, index (key)` tail has, and every other position in it is a parse error in canonical Svelte (and in tsv) — [no_as_key_comment](../tests/fixtures/svelte/blocks/each/no_as_key_comment_svelte_prettier_divergence/), which pairs each position with its `as`-bound counterpart so the two head shapes are pinned to one form.

**Leading/interior comments in a `bind:` function-binding sequence** (◆content_preservation) — `bind:value={getter, setter}` carries getter/setter expressions as a bare (parens-stripped) sequence; tsv preserves a comment at the author's position where prettier keeps it. **Multi-line block comment leading a parenthesized `{…}` value** (◆content_preservation) — a `{…}` expression value wrapped in redundant grouping parens whose *leading multi-line block comment* prettier drops as it strips the parens (`{a > b}`), across every `{…}` context: directive values (`bind:value={/* c⏎*/ (a > b)}`, `class:active={…}`, and the other directive kinds) — [value_paren_multiline_comment](../tests/fixtures/svelte/directives/value_paren_multiline_comment_prettier_divergence/) — and expression tags (a plain `{expr}` template tag and the `style:` value Svelte models as one) — [paren_multiline_comment](../tests/fixtures/svelte/expression_tag/paren_multiline_comment_prettier_divergence/). tsv strips the redundant parens too, but keeps the comment and reaches the same expanded fixed point the **bare** (no-paren) authoring produces — there the comment is glued to its operand, both formatters already preserve it (a multi-line block forces the value to break), and that shared expanded form is each fixture's `input.svelte`, so the bare form is *not* a divergence. **Same-line `//` comment placement in the attribute list** (◆comment_preservation) — [comment_same_line](../tests/fixtures/svelte/attributes/comment_same_line_prettier_divergence/): a line comment the author put on the same line as the tag name (`<div // foo`) or trailing an attribute that has more attributes after it (`a="1" // mid`) stays trailing that token; prettier relocates it to its own line. A `//` trailing the *last* attribute (before `>`/`/>`) already stays inline in both formatters, so it is not a divergence — [comment_trailing_same_line](../tests/fixtures/svelte/attributes/comment_trailing_same_line/). The rule is about the **gap**, not the comment's spelling: a same-line *block* comment in those same two gaps trails its token too, and prettier relocates it the same way — [comment_same_line_long](../tests/fixtures/svelte/attributes/comment_same_line_long_prettier_divergence/). It needs a `long` fixture of its own because a block comment is self-delimiting and so forces no wrap: while the list fits on one line both formatters agree, and only a width-forced wrap makes the binding visible. Own-line comments are preserved as-written by both. The rule is the attribute list's, not the tag's, so it holds at every head that has one; the foreign `<template lang="…">` head, whose layout comes from its own builder, pins it separately at [template_foreign_lang_comment](../tests/fixtures/svelte/elements/template_foreign_lang_comment_prettier_divergence/) — its other comment positions match prettier and are the plain [template_foreign_lang_comment](../tests/fixtures/svelte/elements/template_foreign_lang_comment/). The whitespace-sensitive `<pre>` / `<textarea>` head (also its own builder) pins the between-attribute position at [ws_sensitive_attr_comment_mid_list](../tests/fixtures/svelte/elements/ws_sensitive_attr_comment_mid_list_prettier_divergence/) — there the `//` also wraps the list, and the `>` still hugs the last attribute; the layout both formatters share on the own-line authoring is the plain [ws_sensitive_attr_comment_own_line](../tests/fixtures/svelte/elements/ws_sensitive_attr_comment_own_line/). See [Comment Position Philosophy](./conformance_prettier.md#comment-position-philosophy).

**Attribute-list comment with no attribute to anchor it** (◆content_preservation) — a comment in the region between a tag name and its `>` / `/>` is **deleted** by prettier whenever the list holds no attribute the comment can attach to; tsv keeps it where the author wrote it. The loss is total (the comment does not move, it disappears) and both comment kinds are affected, each keeping its authored placement — a `//` on the tag-name line stays there and forces the `>` / `/>` to the next line, an own-line comment keeps its own line, an inline `/* */` stays inline, and consecutive comments keep their order. Three positions, one rule:

- **An empty attribute list**, across every tag kind — HTML elements with or without content, components, void elements, `<slot>`, the special elements that take no `this` (`<svelte:head>`, `<svelte:window>`), and the whitespace-sensitive `<pre>` / `<textarea>`, whose head is printed by a builder of its own — [comment_no_attributes](../tests/fixtures/svelte/attributes/comment_no_attributes_prettier_divergence/). One real attribute is enough for both formatters to keep the comment at any position in the list, which is exactly why the shape hides — the discriminator is pinned by the plain [comment_with_attribute](../tests/fixtures/svelte/attributes/comment_with_attribute/), whose kinds include the whitespace-sensitive pair (there the `>` hugs straight through an inline `/* */`).
- **Around a synthesized `this`** — `<svelte:element>` / `<svelte:component>` hold their binding in the AST's element kind rather than in `attributes`, so `this={…}` is synthesized at the head of the list. With no other attribute prettier deletes the comment; with one it moves it after `this` onto its own line, collapsing the two authorings (before-`this` and after-`this`) into one form. tsv keeps the **side of `this`** the author wrote it on — two authorings, two fixed points, the same model as the tag-name and between-attribute positions below — [special_this_comment](../tests/fixtures/svelte/special_elements/special_this_comment_prettier_divergence/). When the binding is written **after** other attributes it is hoisted to the head (both formatters do), and each comment stays with the token it binds: a comment bound to another attribute keeps its authored location while `this` moves past, where tsv matches prettier — pinned by the plain [special_this_mid_list_comment](../tests/fixtures/svelte/special_elements/special_this_mid_list_comment/); only a same-line comment trailing the tag name and an own-line comment leading `this` itself travel with the binding, where prettier instead re-glues the former to the next attribute and moves the latter to the end of the list — [special_this_mid_list_comment_prettier_divergence](../tests/fixtures/svelte/special_elements/special_this_mid_list_comment_prettier_divergence/).
- **`<svelte:options>`**, which is hoisted out of the fragment and printed from its own builder — there the deletion does not depend on the list being empty: it happens with attributes present too, at the leading, between-attribute, and trailing positions alike. Only one `<svelte:options>` may appear per component, so the shapes split across fixtures: block comments at all three positions — [svelte_options_attr_comment](../tests/fixtures/svelte/special_elements/svelte_options_attr_comment_prettier_divergence/); the `//` forms, which force the head to break into the same shape width already produces — [svelte_options_attr_comment_line](../tests/fixtures/svelte/special_elements/svelte_options_attr_comment_line_prettier_divergence/); and the no-attribute arm — [svelte_options_bare_comment](../tests/fixtures/svelte/special_elements/svelte_options_bare_comment_prettier_divergence/) for the inline `/* */`, [svelte_options_bare_comment_line](../tests/fixtures/svelte/special_elements/svelte_options_bare_comment_line_prettier_divergence/) for the breaking `//` and own-line forms.

See [Comment Position Philosophy](./conformance_prettier.md#comment-position-philosophy).

**`//` comment in a whitespace-sensitive element's attribute list** (◆prettier_bug / content_corruption) — in `<pre>` / `<textarea>` the `>` **hugs** the last attribute, so that no character is added to the literal content. A `//` runs to end of line and so cannot share that line: tsv breaks before the `>` — with content it takes the next line one level in and the closing tag dangles, the layout an over-width `<textarea>` already takes ([textarea_attrs_long](../tests/fixtures/svelte/elements/textarea_attrs_long/)); with no content it sits at base indent, the shape every other element takes. The break lands inside the tag, where no character is content, so the render is unchanged. Prettier instead **ejects the comment out of the element** — `<pre data-attr="value">text</pre> // c`, where `// c` is now a text node that renders on the page, and its own next pass moves it again (`</pre>`⏎`// c`), so the first output is not a fixed point; `<textarea>` takes the same corruption one place further in, into the closing tag (`</textarea // c`⏎`>`), which the next pass reads as junk and drops. An **own-line** `//` before the `>` is ejected the same way, and it carries a second difference: the line break the author gave the comment wraps the attribute list around it in tsv (the [ws_sensitive_attr_comment_own_line](../tests/fixtures/svelte/elements/ws_sensitive_attr_comment_own_line/) rule), with the `>` keeping the next line one level in. With no attribute in the list prettier deletes the comment outright at once, the empty-list rule above — [ws_sensitive_attr_comment_line](../tests/fixtures/svelte/elements/ws_sensitive_attr_comment_line_prettier_divergence/). A `//` *between* attributes is the one position where prettier's output stays well-formed — relocation only, cataloged with the same-line rule above — [ws_sensitive_attr_comment_mid_list](../tests/fixtures/svelte/elements/ws_sensitive_attr_comment_mid_list_prettier_divergence/). See [Comment Position Philosophy](./conformance_prettier.md#comment-position-philosophy).

**Unofficial directive modifiers** (◆content_preservation) — a directive type *without* official modifier support — `use:` / `bind:` / `class:` / `animate:` / `let:` — carrying a `|modifier` (`use:action|mod`). Svelte's permissive parser records the trailing text in `modifiers`, and tsv's parser AST matches it exactly (so this is **not** a `_svelte_divergence`); but prettier-plugin-svelte silently *drops* the text on format, while tsv preserves it verbatim — [modifier_preservation](../tests/fixtures/svelte/directives/modifier_preservation_prettier_divergence/). A `|modifier` is semantics-bearing source, not whitespace, so deleting it is content loss. The three officially-supporting types (`on:` / `transition:` / `style:`) keep their modifiers in both formatters; tsv emits and prints modifiers uniformly across all eight directive types. See [conformance_svelte.md §Directive Modifiers](./conformance_svelte.md#directive-modifiers).

**Attribute value containing a literal `"`** (◆prettier_bug / content_corruption) — a quoted attribute or `style:` value whose (single-quote-authored) raw text contains a literal `"` — `attr='a"b'`, `class='c"d'`, `style:content='"x"'`. tsv defaults attribute delimiters to double quotes (`'value'` → `"value"`, matching prettier-plugin-svelte) but switches to **single** quotes for the one value shape double quotes cannot hold — HTML §13.1.2.3 requires a double-quoted value to contain no literal `"`, and single-quoted attribute values are an equal first-class syntax. prettier-plugin-svelte instead re-wraps the value in `"` unconditionally, so the interior `"` closes the value early and the output is corrupted markup that **does not re-parse** (`prettier(output)` throws) — a semantic change, and prettier's own `html` / `vue` / `angular` formatters keep single quotes here, so only the svelte plugin regresses it. The rule is total and lossless: wherever the **element** attribute reader parsed the value its raw text carries at most one literal quote kind (its unquoted value stops at either quote, and a quoted value cannot contain its own delimiter — that quote must appear as an entity inside, `&apos;`/`&quot;`, which tsv preserves verbatim), so a `"`-bearing value never also has a literal `'` and no escaping is ever needed; single quotes surface *only* for values that literally cannot be double-quoted. Plain attributes / `class` / component props / multi-part values — [attributes/value_double_quote](../tests/fixtures/svelte/attributes/value_double_quote_prettier_divergence/); `style:` directive values — [directives/style/value_double_quote](../tests/fixtures/svelte/directives/style/value_double_quote_prettier_divergence/); `<svelte:element>` plain-string `this=` values — [special_elements/svelte_element_this_double_quote](../tests/fixtures/svelte/special_elements/svelte_element_this_double_quote_prettier_divergence/).

**Static attribute value containing both quote kinds** (◆prettier_bug / content_corruption) — the position where the rule above runs out of delimiters. A top-level `<script>`/`<style>` head reads its attributes with Svelte's `read_static_attribute`, whose value alternative is `[^>\s]+` — the one reader that admits a raw value holding a literal `"` *and* a literal `'` (`<script a=x'y"z>`). Neither quote can delimit it, so tsv emits it **unquoted**, which is both the authored form and the only lossless one: having come from that alternative the value holds no whitespace and no `>`, so the unquoted form always round-trips. Prettier wraps it in `"` like any other value, and the interior `"` closes it early — broken markup that does not re-parse. The one-kind cases at the same position keep the single/double rule unchanged. See [script/static_attribute_value_both_quotes](../tests/fixtures/svelte/script/static_attribute_value_both_quotes_prettier_divergence/), and [conformance_svelte.md §Static Attribute Reader Corrections](./conformance_svelte.md#static-attribute-reader-corrections) for the reader itself.

## Svelte: Own-line JSDoc cast at a braced head

**◆content_preservation ◆design_choice.** A JSDoc cast whose comment the author gave a
line of its own (`{#if⏎\t/** @type {A} */⏎\t(aa)}`), at a braced head whose value **hugs
its delimiters**: the block heads (`{#if}` / `{:else if}` / `{#each}` + its key /
`{#await}` bare and `then` shorthand / `{#key}`), the prefixed tags (`{@html}` /
`{@render}`), the braced attribute heads (`{...spread}` / `{@attach}`), the `{expr}` tag,
attribute values (event handlers included), the `style:` directive value (Svelte models
it as an expression tag), and `<svelte:element this={…}>`. No such head can hang the
value — it starts right after the head's prefix, so there is no operator line to end,
unlike every TS value gap — so tsv **reflows** the authored break: the comment joins the
head's line and the cast glues to it (`{#if /** @type {A} */ (aa)}`), the fixed point the
glued authoring already reaches. This is
[§Comment Position Philosophy](./conformance_prettier.md#comment-position-philosophy)'s
corollary applied to a flattening container — own-line-ness is authoring signal only
where the container keeps lines at all, and a braced head's group flattens when it fits.
The mid-line authoring with the `(` on the next line (`{#if /** @type {A} */⏎(aa)}`)
reflows to the same fixed point, per
[§Authored breaks in value position](./conformance_prettier.md#authored-breaks-in-value-position).

Prettier is no oracle for the shape: at every one of these heads it **drops the cast
comment and its parens outright** (`{#if aa}` — comment loss plus a semantic change,
since the type assertion stops existing; the same template strip
[§JSDoc / paren semantics](./conformance_prettier_ts_comments.md#jsdoc--paren-semantics)
catalogs for the glued authoring). Where that strip misses the cast because its paren is
not the expression's root, prettier keeps the comment and largely agrees with tsv: at a
**left-spine** cast (`{#if /** @type {A} */ (aa) && bb}`, a member base alike) it reflows
the authored break to tsv's same glued form — a plain match, pinned by
[blocks/if/head_jsdoc_cast_left_spine](../tests/fixtures/svelte/blocks/if/head_jsdoc_cast_left_spine/)
— and at the `{@render}` callee (`{@render /** @type {A} */ (fn)()}`) it shares tsv's
glued fixed point while also holding the mid-line broken form stable, a second fixed
point tsv normalizes (pinned as that fixture's `prettier_variant_break`).

The two heads that **can** give the comment a properly indented line of its own are
deliberately excluded and keep the authoring: `{@const}` hangs the value off its `=`
exactly like a TS declarator — both formatters agree, pinned by
[tags/const_jsdoc_cast_own_line](../tests/fixtures/svelte/tags/const_jsdoc_cast_own_line_svelte_divergence/)
(a `_svelte_divergence` only for the cast comment's attachment) — and an expression-value
directive (`on:` / `bind:` / `class:` / `use:` / `transition:` / `animate:`) takes its
block form with the comment on its own indented line, pinned by
[directives/on/jsdoc_cast_own_line](../tests/fixtures/svelte/directives/on/jsdoc_cast_own_line_svelte_prettier_divergence/)
(still a ◆content_preservation divergence — prettier drops the comment there too).

- blocks — [head_jsdoc_cast_own_line](../tests/fixtures/svelte/blocks/head_jsdoc_cast_own_line_svelte_prettier_divergence/), [head_jsdoc_cast_multiline_comment](../tests/fixtures/svelte/blocks/head_jsdoc_cast_multiline_comment_svelte_prettier_divergence/) (the multiline-comment arm — the reflowed comment's own verbatim newlines keep the head open in the comment-broken block shape of [§Svelte: Blocks](#svelte-blocks))

## Svelte: Blocks

Standalone head wrap + dangle + body-expand:

- `{#each}` — [each_long](../tests/fixtures/svelte/blocks/each/long_prettier_divergence/)
- `{#await}` — [await_long](../tests/fixtures/svelte/blocks/await/long_prettier_divergence/)
- `{#key}` — [key_long](../tests/fixtures/svelte/blocks/key/long_prettier_divergence/)
- `{#if}` (binary / member chain / call / `{:else if}`) — [if_long](../tests/fixtures/svelte/blocks/if/long_prettier_divergence/)
- `{#if}` last block quirk — [last_block](../tests/fixtures/svelte/blocks/if/last_block_prettier_divergence/)

The shape is keyed on **that the head broke, not on why**: tsv's block head hugs its first
fragment to `{#if`, indents what follows, and drops `}` to base — whether the break came from
printWidth or from a comment. A head far under printWidth still takes that shape when a *line*
comment forces the break. (A **multi-line block** comment's newlines live inside its verbatim
source span, which renders with no context indent by design, so its continuation is the
comment's own line and only the `}` dangle shows; a **single-line block** comment breaks
nothing and the head stays inline, both formatters agreeing.) Prettier never dangles a block
head's `}` whatever broke it, so this is the one divergence on a second trigger — not a
print-width tolerance:

- `{#if}` (comment-forced head break) — [if/condition_breaking_comment](../tests/fixtures/svelte/blocks/if/condition_breaking_comment_prettier_divergence/)

Same layout inside an inline element (head wraps + body expands, element hugs the outer boundary):

- `{#if}` — [if/inline_element_long](../tests/fixtures/svelte/blocks/if/inline_element_long_prettier_divergence/)
- `{#each}` — [each/inline_element_long](../tests/fixtures/svelte/blocks/each/inline_element_long_prettier_divergence/)
- `{#key}` — [key/inline_element_long](../tests/fixtures/svelte/blocks/key/inline_element_long_prettier_divergence/)
- `{#await}` — [await/inline_element_long](../tests/fixtures/svelte/blocks/await/inline_element_long_prettier_divergence/)
- `{#snippet}` (params inline + body expand vs prettier's param-wrap) — [snippet/inline_element_long](../tests/fixtures/svelte/blocks/snippet/inline_element_long_prettier_divergence/)
- `{#snippet}` standalone, **flush body** (tsv keeps params inline + body on its own line; prettier wraps the params just to keep the body hugging `)}`) — [snippet/flush_body_param_wrap_prettier_divergence](../tests/fixtures/svelte/blocks/snippet/flush_body_param_wrap_prettier_divergence/)

**◆print_width.** Prettier doesn't apply width-based wrapping to block expressions at all:

- **Method chains** in `{#each}`, `{#await}`, `{#if}`, `{#key}`, etc. don't account for the tag prefix width, resulting in 140+ char lines. tsv passes context offset for proper wrapping.
- **Logical expressions** (`&&`, `||`) in block conditions are never wrapped internally by Prettier, even when exceeding 100 chars. (In `<script>`, assignments provide a break point so this isn't an issue.) tsv wraps them with proper indentation.
- **Function calls** in block expressions don't wrap their arguments. tsv wraps function arguments when they exceed print width.

**Head `}` dangle + clause hug.** When a block head wraps, tsv drops the closing `}` (and any `as item` / `then value` clause) to its own line at the tag's base indent — `{#if a &&⏎\t…⏎}`, `{#each …⏎as item}` — consistent with tsv's JS `if (⏎…⏎) {` and its broken-element `>` (`bracketSameLine: false`). The one shape that hugs is a single call/`new` whose arguments wrapped: its `)` already dedents to base, so the clause + `}` continue on it (`) as item}`, `)}`, `) then r}`). Prettier never wraps a block head, so it never faces this.

**Body-expand (whole construct goes multiline).** When the head wraps — or the inline construct simply exceeds printWidth, or the body breaks for any other reason — tsv expands the **entire** block: the body, every `{:then}` / `{:catch}` / `{:else}` / `{:else if}` section/branch, and the `{/tag}` close each drop to their own indented lines, uniformly across `{#if}` / `{#each}` / `{#await}` / `{#key}` / `{#snippet}`. The decision is **all-or-nothing and width-driven**: the body boundary is render-free (see [§Svelte: Inline content block-style](#svelte-inline-content-block-style)), so neither the whitespace the author wrote there nor the head's wrap-ability may select it — a block following a breakable sibling expands exactly as it would standalone. This holds **inside inline elements/components too** (`<span>{#if …}…{/if}</span>`) — block-body boundary whitespace is render-non-significant there (verified against the Svelte compiler), so it is safe; the only gate is `<pre>` / `white-space:pre`, where the drop is suppressed and the body stays on the line (both formatters agree — [elements/pre_block_body_long](../tests/fixtures/svelte/elements/pre_block_body_long/)). Inside `<pre>` a nested element's wrapped attributes and close token indent off its nesting depth — one level per enclosing container, the same model as prettier ([elements/pre_nested_attr_indent](../tests/fixtures/svelte/elements/pre_nested_attr_indent/)) — and the source close form is preserved (self-closing `/>` vs explicit `></tag>`), for components and HTML inline elements alike. One residual divergence remains there: an empty self-closing element whose attributes fit within printWidth (counting the preserved-text prefix on the line) keeps them on one line with only `/>` dropping, where prettier full-breaks them regardless — [elements/pre_block_empty_element](../tests/fixtures/svelte/elements/pre_block_empty_element_prettier_divergence/). Prettier keeps the construct inline past printWidth (only the enclosing element wraps).

**Middle zone (head fits alone, head + body doesn't).** tsv decouples the head-wrap decision (head-alone width) from the body-expand decision (head + body width): when the head fits on its own line but the whole construct overflows, the head stays flat and only the body expands. This is chosen in one pass (no wrap-then-unwrap across two formats), so every layout is an idempotent fixed point.

**Uniform body drop (no breakable-element hug).** When an inline-authored block body overflows, tsv drops it to its own indented line **uniformly — for every body shape**: text, expression tags (`{x}`), void/empty elements (`<Spinner />`, `<Comp></Comp>`), and elements/components **with attributes or children** alike. Prettier instead leaves the body hugging the `}` and breaks it *internally* (an element wraps its attributes / closing `>`; text just overflows) — prettier's block-body layout is driven by authored boundary whitespace, never by width. tsv's uniform drop keeps the layout idempotent (a one-pass `conditional_group`, no special case keyed on whether the body can break internally) and consistent across all body shapes and contexts (block level, inside inline elements/components, in any section/branch). tsv does not hug a breakable body element: as a non-first body node (behind leading text, a comment, a void sibling, or an atomic `{:else}` branch) hugging over-wraps the head and is non-idempotent across two passes. Cataloged at [if/element_body_long](../tests/fixtures/svelte/blocks/if/element_body_long_prettier_divergence/) and [each/element_body_long](../tests/fixtures/svelte/blocks/each/element_body_long_prettier_divergence/) (block level, at the 100/101 boundary), [await/element_body_long](../tests/fixtures/svelte/blocks/await/element_body_long_prettier_divergence/) and [snippet/element_body_long](../tests/fixtures/svelte/blocks/snippet/element_body_long_prettier_divergence/) (inside `<Container>`), [await/full_form_element_body_long](../tests/fixtures/svelte/blocks/await/full_form_element_body_long_prettier_divergence/) (the full `{:then}`/`{:catch}` form, each section body drops), [key/void_element_body_long](../tests/fixtures/svelte/blocks/key/void_element_body_long_prettier_divergence/) (void body + an attributed body that drops the same way), [elements/inline_if_sibling_fill_long](../tests/fixtures/svelte/elements/inline_if_sibling_fill_long_prettier_divergence/) (body drop next to an inline sibling), [elements/inline_component_else_body_long](../tests/fixtures/svelte/elements/inline_component_else_body_long_prettier_divergence/) (breakable element in `{:else}`, behind an atomic consequent), [if/element_body_leading_node_long](../tests/fixtures/svelte/blocks/if/element_body_leading_node_long_prettier_divergence/) (non-first body node — leading text, a comment, or a void element before the breakable element), and [if/element_body_deep_nested](../tests/fixtures/svelte/blocks/if/element_body_deep_nested_prettier_divergence/) (deep nesting — the dropped element re-wraps at the body indent). Paramless `{#snippet}` bodies drop the same way once the whole construct still overflows — the paramless shape is pinned by [snippet/element_body_long](../tests/fixtures/svelte/blocks/snippet/element_body_long_prettier_divergence/) above; [snippet/inline_element_long](../tests/fixtures/svelte/blocks/snippet/inline_element_long_prettier_divergence/) now pins only prettier's width-keyed forms, since the snippet's own line ([the declaration rule](#svelte-inline-content-block-style)) gives tsv one form at every width there. The drop reads correctly embedded in realistic nested context with inline siblings (incl. the breadcrumb shape) — [elements/block_body_drop_nested_siblings](../tests/fixtures/svelte/elements/block_body_drop_nested_siblings_prettier_divergence/).

**Sibling `>` dangle (axis 3).** When an inline element is immediately followed — no whitespace — by a block that **renders multiline**, tsv dangles that element's **closing `>`** onto the block-head line (`<a href={root}>Home</a⏎>{#each …}`). This applies to the **four rendering block heads** — `{#if}` / `{#each}` / `{#key}` / `{#await}`. (`{#snippet}` mostly left this regime: it is a declaration and takes its own line — [the declaration rule above](#svelte-inline-content-block-style) — so a glued boundary beside it splits rather than dangling the `>`. The exception is a snippet glued to content on BOTH sides, which keeps the author's line and *stays* in this regime: when it renders multiline, the preceding sibling's `>` dangles exactly as for the four heads.) It generalizes the rule tsv already applies from the enclosing-element side: the `>` token immediately preceding a block's `{#…}` dangles, whether it's the *opening* `>` of a parent inline element holding a sole-content block (`<span⏎>{#if …}`) or the *closing* `>` of a preceding inline sibling. The `>` moves only *inside* the closing tag (`</a⏎>`), so the boundary whitespace is tag-internal and the output parses to a byte-identical AST — render-safe (verified against the Svelte compiler), the same property as the element boundary-`>` wrap. It is **strict / multiline-only**: a short block that stays inline keeps the `>` hugged (`<span>text</span>{#if c}text{/if}`), and the decision keys on whether the block actually renders multiline — not on whether its body is authored inline or on its own line — so the layout is a fixed point on its own output. It is **leading-side only**: the closing side (`{/if}<span>`) keeps flowing. Text/expression siblings (`wide text {#if…}`, `{x}{#if…}`) keep hugging — there is no `>` to dangle and the boundary whitespace is render-fixed, an asymmetry that is forced, not a tsv inconsistency. Prettier never expands the block at all, so it always keeps the boundary hugged. **`{#await}`:** unlike `{#if}` / `{#each}` / `{#key}`, an await doesn't force its block parent multiline on its own (a lone `<div>{#await p}x{/await}</div>` stays inline, matching prettier) — it goes multiline only once it follows a **breakable** sibling: an inline element / component / expression-or-`{@html}`-or-`{@render}` tag (the `has_preceding_breakable` set). There the parent breaks so the dangle, the block-on-own-line separation for a block sibling, and the body-drop all resolve in one pass. `has_preceding_breakable` reaches only the **head** (it holds the head flat, so the sibling breaks first); the **body**-drop is width's decision alone and never keys on it — see [§Body-expand](#svelte-blocks) above. After a **non-breakable** sibling — plain text or a comment — it stays **inline**, matching prettier; the force is additionally gated on `kind.is_block()`, so an inline element or component parent never breaks for *any* sibling. This is a distinct axis from the `>` dangle above: a breakable sibling breaks the *parent* even when the short block keeps its own `>` hugged, and that break is itself a divergence (prettier keeps the short inline-authored construct inline). Cataloged at [elements/inline_sibling_gt_dangle](../tests/fixtures/svelte/elements/inline_sibling_gt_dangle_prettier_divergence/) (the dangle for the four heads + both `{#snippet}` shapes — one-side glued splits, both-sides glued dangles — + a no-dangle control), [elements/await_snippet_breakable_sibling](../tests/fixtures/svelte/elements/await_snippet_breakable_sibling_prettier_divergence/) (the short-case parent break after a breakable sibling; its snippet case additionally splits under the declaration rule), [elements/await_nonbreakable_sibling_inline](../tests/fixtures/svelte/elements/await_nonbreakable_sibling_inline/) (the non-breakable text/comment counterpart that stays inline, matching prettier), [components/await_sibling_inline](../tests/fixtures/svelte/components/await_sibling_inline/) (a component parent stays inline for any await sibling, incl. after `{@debug}`), [blocks/await/preceding_sibling_body_long](../tests/fixtures/svelte/blocks/await/preceding_sibling_body_long_prettier_divergence/) (await body-drop after a non-danglable expression-tag sibling), [elements/block_body_drop_nested_siblings](../tests/fixtures/svelte/elements/block_body_drop_nested_siblings_prettier_divergence/) (the breadcrumb `</a>` dangle in realistic context), and [elements/inline_if_sibling_fill_long](../tests/fixtures/svelte/elements/inline_if_sibling_fill_long_prettier_divergence/) (the `</span>` dangle in a fill). The **inline counterpart** of the dangle — a preceding sibling before an inline-rendering `{#await}` — **hugs** the `>` (`</a>{#await …}`) rather than dangling it. The `>` must always be **placed, never dropped** — a dropped `>` (`</a{#await …}`) is unreparseable. `{#await}` reaches this on two paths, both handled: the empty-await path (a short empty block hugs; a long head that width-wraps dangles — a *render-time* decision `will_break` can't see, so it's an `if_break`-in-`group`) and the space-only path (a `group` that hugs when it fits). Cataloged at [blocks/await/empty_sibling_gt](../tests/fixtures/svelte/blocks/await/empty_sibling_gt/) (a bare empty `{#await promise}{/await}` after a sibling — the `>` hugged in parity with prettier; its space-only-authoring variants exercise the space-only path).

**Empty `{#await}` sections (◆correctness on `:catch`).** An **empty-body `:then`** — `{#await p} {:then v}{/await}`, or the shorthand `{#await p then v}{/await}` — is **dropped**, marker and binding, collapsing to `{#await p}{/await}` in parity with prettier (the `value` binding is unused when nothing renders; a *space-only* pending folds to the same fixed point via `await_shorthand`, while a *newline*-authored one keeps its full multiline form). But an **empty `:catch` is kept** (`{#await p}…{:catch e}{/await}`) — a deliberate divergence from prettier, which deletes it too. An empty `{:catch}` still **handles** a rejection (renders nothing); deleting it lets the rejection **propagate** instead — a semantic change, so tsv preserves the section (correctness over conformance). Kept the same way whether the construct is inline or **block-style**: the section's boundary separators are soft, so inline the empty section collapses and its markers glue (`{#await p}x{:catch e}{/await}`), while in block form it keeps its own line like any other section — `{:catch e}` and `{/await}` each on a line, the empty body's blank line between. Cataloged at [blocks/await/empty_catch](../tests/fixtures/svelte/blocks/await/empty_catch_prettier_divergence/) (inline) and [blocks/await/empty_catch_multiline](../tests/fixtures/svelte/blocks/await/empty_catch_multiline_prettier_divergence/) (block form).

**Empty branch, block form (◆design_choice).** An empty branch of `{#if}` / `{:else if}` / `{:else}`, and an empty `{#each}` body or `{:else}` fallback, keeps its own line inside a **block-form** construct: the marker and the close each sit on a line, with the empty body's blank line between (`{:else}⏎⏎{/if}`). tsv normalizes to that shape **whatever the author wrote at the branch boundary**, so a glued and a newline-authored empty branch reach one fixed point. Prettier instead **preserves** the authored boundary — it leaves a newline-authored branch in exactly that shape (tsv agrees) but keeps a **glued** one glued. tsv declines that preservation because an empty branch renders nothing, so the whitespace inside it is **render-free** and must not select the layout — the same principle as the all-or-nothing body-expand above. **Inline** the separators vanish and the branch collapses instead ([blocks/if/empty](../tests/fixtures/svelte/blocks/if/empty/) pins `{#if a}<div>text</div>{:else}{/if}`, which both formatters produce) — one soft-separator rule, two renderings. A branch carrying content is untouched. Cataloged at [blocks/empty_branch_collapse](../tests/fixtures/svelte/blocks/empty_branch_collapse_prettier_divergence/).

**Space-only section boundaries glue inline (◆design_choice — Svelte-mirror trim).** A space-only content boundary in a block section is **render-free** — the compiler trims every fragment edge at compile (`clean_nodes`) — so tsv removes it in inline layout: `{#if a} x {/if}` → `{#if a}x{/if}`, uniformly across `{#if}` / `{:else if}` / `{:else}` / `{#each}` (+ fallback) / `{#key}` / every `{#await}` phase / `{#snippet}`. A render-free character neither survives in the output nor selects the layout; a **newline**-authored boundary keeps its meaning (the construct stays multiline) — a space is not intent. Prettier's own treatment splits by family: it **expands** a symmetric-spaced `{#if}` / `{#each}` / `{#key}` / `{#snippet}` body to multiline — a render-free space selecting the whole construct's form — with a quirk (the last block in a file stays inline as authored), yet it **preserves** a spaced `{#await}` inline, keeping a space the compiler deletes. (The split is a plugin artifact, not a stance: every block fragment maps a spaced boundary to the same `line` doc, but the plugin's `AwaitBlock` printer is the one block case built without the `breakParent` the `IfBlock`/`EachBlock`/`KeyBlock` cases carry, so only await's `line`s can collapse.) tsv glues consistently regardless of family or position. Same render-free principle as the empty-branch normalization above, and the same trim an inline element's content boundary gets (see [§Svelte: Inline content block-style](#svelte-inline-content-block-style)). Cataloged at [blocks/boundary_space_trim](../tests/fixtures/svelte/blocks/boundary_space_trim_prettier_divergence/) (the expanding if-family) and [blocks/await/boundary_space_trim](../tests/fixtures/svelte/blocks/await/boundary_space_trim_prettier_divergence/) (the preserving await, incl. the `then` shorthand); [blocks/if/spaces](../tests/fixtures/svelte/blocks/if/spaces_prettier_divergence/) is the if-family maximal injection — a space at every collapsible position at once (tag-internal + block-element content boundary + section boundary), across div/text/`{:else if}`/space-only-empty shapes.

## Svelte: destructuring literal normalization

**◆design_choice.** tsv routes the binding patterns of `{#each … as}`, `{#await … then}`, `{:then}`, and `{:catch}` through its TypeScript printer, so **literal default values** normalize to tsv's canonical form — string literals to single quotes (`{ a = "x" }` → `{ a = 'x' }`, with escape-minimizing keeping double quotes when single would need escaping, so `"a'b"` stays double) and numeric literals to canonical shape (lowercase hex/exponent, leading/trailing-zero rules: `0xFF` → `0xff`, `1.50` → `1.5`, `.5` → `0.5`, `1E10` → `1e10`, `0xFFn` → `0xffn`). This is the same normalization `{@const}` (and every other literal tsv emits) already applies. prettier-plugin-svelte instead prints these patterns from raw source, preserving the author's quote style and numeric token verbatim — in these binding positions it ignores `singleQuote` and numeric normalization. tsv normalizes uniformly so a destructuring default reads the same wherever it appears. Booleans, `null`, and regex literals are already canonical in both formatters and are unaffected.

## Svelte: destructuring rename-with-default key drop

**◆prettier_bug.** A renamed (non-shorthand) destructuring property that carries a **default value** loses its source key in prettier-plugin-svelte's binding-pattern printer for `{#each … as}`, `{#await … then}`, `{:then}`, and `{:catch}`. `{ a: b = 1 }` (read property `a`, bind to `b`) prints as `{ b = 1 }` (read property `b`) — a **semantic change**, since the output reads a different source property.
