# Tasks

tsv's tasks live in two files under the same names. `deno.json` holds every task that runs
Deno (`deno task <name> <flags>`); `package.json` holds the rest as npm scripts
(`npm run <name> -- <flags>`), and `deno task <name>` falls through to the `package.json`
script when `deno.json` has no task of that name, so `deno task <name>` runs either. `npm ci`
installs the JS dependencies `package-lock.json` pins into `node_modules`; `.npmrc` turns
install scripts off.

With a `package.json` beside it, Deno resolves a bare specifier through `node_modules`, any
package installed there whether the `package.json` lists it or not, and looks for `npm:`
specifiers there instead of in its own cache; with no `node_modules`, a type check that needs
`@types/node` or a listed package fails outright. The root-config checks that hold code free
of npm imports (`typecheck:scripts`' Deno half, `typecheck:bench-core`, `test:deno`) therefore
run with `DENO_NO_PACKAGE_JSON=1`, which keeps the root `package.json` out of Deno's view, so a
bare import still fails them and a checkout with no `node_modules` still passes them.
`typecheck:scripts`' other half is `tsc` from `node_modules` over the Node scripts and
tsv_debug's sidecar, whose packages resolve from its own install, so `typecheck:scripts` as a
whole needs `npm ci` and `npm ci --prefix crates/tsv_debug/sidecar`.

`package.json` takes no comments, so the rationale for a script whose body can't carry its
own lives here, one section per script. A `deno.json` task's rationale sits beside it as its
`//<name>` key.

## `build:stamped`

`cargo build <args>`, then every final artifact it reports (a bin's executable, a cdylib's library) dated at now — what each build task whose output an mtime guard reads goes through (`build:ffi*`, `build:napi*`, `build:check`). Cargo keys `Cargo.lock` and a manifest by content, so one rewritten to something already built (a version bump restored and re-applied, a `git reset`, a branch switched away and back) makes the build a no-op that re-links the cached artifact under its ORIGINAL date; the guard, which compares dates, then refuses a current artifact and names a rebuild that cannot clear it. Stamping makes the date mean when cargo last confirmed the artifact current. Rationale + why only leaf artifacts: scripts/cargo_build.ts.

It runs under Node on Node's own `node:*` modules (`scripts/roots/cargo_build.ts`), a named exception to the host-module rule the other Node scripts follow: CI runs it on Windows and macOS (the `platforms` job's `test:napi` and `test:napi:npm`) and in the `artifacts` job, none of which installs `node_modules`, and gro's host modules don't run programs on Windows. So nothing it imports is a package, which `typecheck:scripts`' Deno walk and `scripts/no_package_closure_test.ts` enforce. Cargo is the bare name `cargo` on `PATH` and inherits the whole environment; the stamp reaches beneath the checkout's `target/` only, so an artifact a `CARGO_TARGET_DIR` puts elsewhere fails the run rather than being dated. A cargo ended by signal `N` exits `128 + N`.

## `build:napi:packages`

`build:napi`, then `cargo build -p tsv_cli --release`, then the staging (`scripts/roots/build_napi_packages.ts`, its library `scripts/build_napi_packages.ts`): the `@fuzdev/tsv` loader and the host's platform package written into `crates/tsv_napi/pkg/`. The task chains `deno task` legs, so it stays in `deno.json`.

The staging runs under Node on Node's own `node:*` modules, a named exception to the host-module rule: CI runs it on Windows and macOS (the `platforms` job's `test:napi:npm`) and in the `artifacts` job, none of which installs `node_modules`; the release workflow's build rows run it on every platform through `scripts/pgo/pgo.ts stage`; and the release `publish` job runs it (`--loader-only`) holding the npm credentials, where nothing is installed by decision; gro's host modules are a package none of those jobs has. So nothing it imports is a package, which `typecheck:scripts`' Deno walk and `scripts/no_package_closure_test.ts` enforce. Every path it stages is beneath the checkout the entry sits in, never the working directory; an `--artifact` or `--cli-artifact` path is read as given. Each staged copy keeps its source's mode and is dated at the staging (`scripts/stage_file.ts`); the CLI binary is `chmod`ed `0o755` everywhere but Windows. With no `--triple` the host's triple is Node's platform and CPU, `gnu` or `musl` by whether the runtime reports a glibc. The triple names the platform package's directory beneath `crates/tsv_napi/pkg/`, so one outside `SUPPORTED_TRIPLES` (the platforms the loader pins) is refused before anything is written; `--loader-only` stages no platform package and takes any host.

## `build:npm:format`

`build:npm:format`, `build:npm:parse`, and `build:npm:all`: wasm-pack's `web` target into `crates/tsv_wasm/pkg/<variant>/npm/`, then the patcher (`scripts/roots/patch_npm_package.ts`, its library `scripts/patch_npm_package.ts`), which turns that build into the published package: the entries, their declarations, the patched glue and manifest, and the copied README, LICENSE, NOTICE, facade and (for `all`) CLI. `build:packages` chains all three with the deno bundles, and CI's `artifacts` job and `scripts/publish.ts` run that.

The patcher runs under Node on gro's host modules. Its reach: the checkout read-only, found from the entry's location, never the working directory; writes beneath the variant's staging alone, the directory wasm-pack built, opened once the argument names a variant (a missing one fails before anything is written); and `gzip`, found on `PATH`, with gro's base environment, for the bundle's gzipped size, the byte length of `gzip -c`'s output (a missing `gzip` fails the summary, after the package is written). Each copied file keeps its source's mode and is dated at the staging (`scripts/stage_file.ts`, bound to the two handles by `scripts/stage_file_handle.ts`). A usage error and each refusal of the generated bundle exit 1. A staging is stale when the entry, or any module it loads, is newer than it (`WASM_STAGING_SOURCES` in `scripts/check_staged_freshness.ts`, held to the entry's import closure by `scripts/staging_sources_test.ts`), or `package.json`, where wasm-pack's feature flags are. wasm-pack itself runs as the npm script's command, with the whole environment.

## `build:wasm:deno`

`build:wasm:deno`, `build:wasm:parse:deno`, `build:wasm:all:deno`, and `build:wasm:all:nodejs`: the wasm-pack builds of the `deno` and `nodejs` targets the bench loads and `validate:artifacts` sizes, each through `scripts/roots/run_if_stale.ts` (its library `scripts/run_if_stale.ts`), which skips wasm-pack when the bundle is newer than every source feeding it: the crates `benches/js/lib/tsv_artifacts.ts` names, the workspace `Cargo.toml` and `Cargo.lock`, and `package.json`, where the tasks are. A source it finds but can't read (a symlink under a crate's `src/` pointing outside the checkout, a directory it can't list) fails the task, naming the path, rather than skipping on what it could see. `TSV_BUILD_FORCE=1` builds whatever the mtimes say; `scripts/publish.ts` sets it.

It runs under Node on gro's host modules. Its reach: the checkout read-only, found from the entry's location, where the `--target` path resolves and the command runs; `wasm-pack` alone, found on `PATH` (a missing one fails only a run that builds); and `TSV_BUILD_FORCE`. Its wasm-pack gets gro's base environment and `WASM_PACK_PASS_ENV` (`scripts/wasm_pack_env.ts`): cargo's list (`scripts/cargo_env.ts`), wasm-pack's cache variables, and what `wasm-bindgen` and `wasm-opt` read, not the whole environment. The `build:npm:*` tasks' wasm-pack shares the same cargo `target/` with the whole environment, so the two find each other's output fresh because the list holds every variable that build reads. A usage error exits 2, a command other than `wasm-pack` exits 1, and a wasm-pack ended by signal `N` exits `128 + N`.

## `build:release`

The workspace optimized build, minus the three binding crates: one cargo invocation unifies features across everything it builds, so a workspace build would hand `tsv_ffi` / `tsv_napi` / `tsv_wasm` the features `tsv_cli` and `tsv_debug` enable (`locations`, `_internal_debug_lex`) and write the fatter library to `target/release/libtsv_ffi.*`, the plain library `build:ffi` builds and the PGO pipeline holds the bench's profile-guided one byte-identical to (`byteid-ffi`) — a fatter reference there grades a build no consumer gets. Each binding builds alone, through its own task (`build:ffi`, `build:napi`, the wasm-pack tasks), which `build:all` chains right after this.

## `typecheck:features`

The per-package feature sets `deno task typecheck` cannot see: all three binding crates under each single feature (`strip` and `imports` for the two that carry them — `tsv_ffi` has neither), then the three language crates alone — without the `locations` feature `tsv_cli` and `tsv_debug` unify in, which no binding enables, so a reference to the loc-bearing wire that is not gated on it (a test included) fails here and nowhere else. `cargo check --workspace` resolves features unified and with defaults ON, so `tsv_ts`'s `json` is always enabled there — while `@fuzdev/tsv-format-wasm` builds `--no-default-features --features format`, where `tsv_ts::ast::convert` does not exist. An unconditional reference to a `json`-gated item therefore compiles clean through the whole gate, and `deno task lint`'s `--all-features` cannot catch it either: that is the feature UNION, never a subset. The three crates share one shape — a `#[cfg(any(feature = "parse", feature = "format"))]` import of `tsv_arena`'s goal macros over a `format`-gated `with_doc_arena` — so one edit can break any of them. Where each subset would otherwise surface, and how late: `tsv_wasm`'s are the PUBLISHED packages, built only at `build:packages` (and for wasm32, a target `check` deliberately never touches), so CI's publish step is the first reader; `tsv_ffi`'s are the size-only `build:ffi:format` / `build:ffi:parse` artifacts, built natively but only by `build:bench`, which `check` never runs; `tsv_napi`'s are built by NOTHING today — the split is declared to mirror its siblings, so this task is the only thing keeping it from rotting unbuilt. All checked NATIVELY here because the failure is feature resolution, not codegen — no wasm32 toolchain needed. ONE INVOCATION PER SUBSET, not per crate, so the shared language stack (`tsv_lang` → `tsv_ts`/`tsv_css`/`tsv_svelte`) compiles once per subset instead of three times — measured head to head with both sets of worlds warm, 27.9 s → 2.6 s after a `tsv_lang` edit, and ~0.4 s warm either way. What makes that safe is checked, not assumed: the three crates forward the SAME `tsv_*` features in each leg, so cross-package unification resolves every shared crate exactly as the per-crate invocation did (`cargo tree -e features` per crate against the combined run is the check). The one thing unification does add is on OPTIONAL DEPS — in the `format` leg `tsv_ffi` alone pulls neither `tsv_ignore` nor `tsv_discover`, and beside its siblings it does — which cannot reach it: a crate's extern prelude holds only what its OWN manifest declares, and `tsv_ffi` declares neither, so they compile as siblings it can never name. ⚠ The equivalence is a fact about today's manifests: a crate whose `format` stopped forwarding the same `tsv_*/format` set as its siblings WOULD be checked against the union, and its own subset would go ungraded. Re-run the feature diff above when one changes, and split that crate back into its own invocation if one ever diverges. `-D warnings` because a subset build's characteristic finding is a WARNING, not an error: a payload only the other feature's arm reads is dead code here and live under `--all-features`, so `dead_code` fired in this task and scrolled past a green gate (it caught `tsv_wasm`'s `OptionValue::Bool` and could not fail on it). Via RUSTFLAGS rather than a trailing `-- -D warnings`, which `cargo check` does not accept; registry deps are `--cap-lints allow`, so only workspace crates are graded, and the flag's own fingerprint COEXISTS with the plain one rather than invalidating it — `deno task typecheck` stays warm across this task, at the cost of one ~30 s dep build the first time. The LAST leg is a consumer's graph rather than a subset: smallvec's `union` feature, which a dependency elsewhere in a consumer's tree can turn on (deno_core's serde_v8 does), shrinks every `SmallVec` — so a layout bound written for the plain one, or code leaning on its shape, breaks that consumer's build and no other (it broke gro's once). `-p tsv_svelte` alone reaches every crate that holds one: features unify across its graph, so `tsv_lang` and `tsv_ts` compile with `union` too (`tsv_css` holds none), and `cargo tree -p tsv_svelte --features smallvec/union -e features -i smallvec` shows it. The lib only, never `--all-targets`: the test build's exact layout pins describe the plain `SmallVec` on purpose.

## `validate:artifacts`

The built WASM artifacts graded as files (`scripts/roots/validate_artifacts.ts`, its library and bands `scripts/validate_artifacts.ts`): each variant's bundle, the npm staging's and the deno target's, against its size band, the distance from each subset build to `all` against its band, and each npm package's third-party `NOTICE`, declared in its `files` and equal to `crates/tsv_html/NOTICE`. It runs nothing it grades: what a package does when loaded is the package suites' (`test:npm*:run` under Node, `test:bun` under Bun), and the npm packages claim Node and Bun, not Deno. The deno bundles it sizes are the bench's Deno row's, built beside the packages by `build:packages`. An unbuilt variant is skipped, and nothing built fails; an npm staging counts as built once any file a staging step writes is there, so one holding some without the rest fails. A stale artifact is refused before anything is graded, a deno bundle dated by its crates, the workspace `Cargo.toml` and `Cargo.lock`, and `package.json`, where its wasm-pack flags are, an npm staging by the checks every reader of a staging shares (`wasm_package_checks` in `scripts/check_staged_freshness.ts`); `BENCH_STALE_OK=1` makes staleness a warning, and a missing staged file is always fatal. Every failure exits 1.

It runs under Node on gro's host modules. Its reach: the checkout read-only, found from the entry's location, never the working directory, and `BENCH_STALE_OK`.

## `validate:napi`

The size bands of a staged N-API platform package's two binaries (`scripts/roots/validate_napi_artifact.ts`, its library and bands `scripts/validate_napi_artifact.ts`): with no `--triple`, the one platform package staged under `crates/tsv_napi/pkg/`; `--pgo` grades the profile-guided bands the release ships. Both binaries report their size before the exit, so a failed addon never hides the CLI's.

It runs under Node on Node's own `node:*` modules, a named exception to the host-module rule: CI runs it in the `artifacts` job, and the release workflow on every build row, `win32-x64` included (directly and through `scripts/pgo/pgo.ts`), none of which installs `node_modules`. So nothing it imports is a package, which `typecheck:scripts`' Deno walk and `scripts/no_package_closure_test.ts` enforce. It reads the checkout the entry sits in and writes nothing.

## `test:bun`

The parse-failure table (scripts/parse_failure_suite.ts) over the STAGED packages under Bun, both engines — the one leg that grades the failure objects the engines build and return under Bun (every other package suite runs under Node). Positional args (format / parse / all / napi) name the packages, each required; none grades all four. Builds nothing and refuses a stale staging (BENCH_STALE_OK=1 the override). Where no `bun` is on the PATH it warns, naming what it skipped, and exits 0 — unless `--require-bun` is passed, which fails instead. It rides every package suite's `:run` task over that suite's own package (warn-skipping), and publish.ts runs it over the three wasm packages, with `--require-bun` whenever its Step 1 preflight found bun (a --wetrun without bun already failed there, unless --no-check). The napi engine under Bun is graded only locally, by `test:napi:npm[:run]` on a machine with bun. CI installs no bun.

The launcher (`scripts/test_bun.ts`, the same file `bun test` then runs as the suite) runs under Node on Node's own `node:*` modules, a named exception to the host-module rule twice over: Bun runs the file too, and CI runs the launcher on Windows and macOS (`test:napi:npm` in the `platforms` job) and in the `artifacts` job, none of which installs `node_modules`. So nothing it imports is a package, which `typecheck:scripts`' Deno walk and `scripts/no_package_closure_test.ts` enforce. `bun` is the bare name on `PATH` and inherits the whole environment.

## `typecheck:packages`

Type-checks the STAGED npm packages' merged declarations as a consumer's compiler sees them — nothing else does: `check:ast-types` grades `tsv_ast.d.ts` alone, and the package suites run the JS. Each package is installed into a temp consumer's node_modules (package.json + exactly its `files`), and lean consumer modules plus every TypeScript and JavaScript (checkJs) block of the README it ships compile against it through the `exports` map, under strict / exactOptionalPropertyTypes / noUncheckedIndexedAccess / skipLibCheck false / types [], with both nodenext and bundler resolution — the wasm packages with the DOM lib their entries name, the napi loader and every `./locations` subpath without it. One program per package and configuration, so one package's lib reference cannot satisfy another's. Positional args (format / parse / all / napi) name exactly the set graded, each required — publish.ts passes all four, after staging the napi loader (a file copy, `scripts/roots/build_napi_packages.ts --loader-only`); no args grades every staged package and fails when none is. A stale staging is refused like the package suites refuse it (BENCH_STALE_OK=1 the same override). TypeScript and @types/node come from benches/js/node_modules (`scripts/typecheck_install.ts`, which publish.ts's preflight reads too); absent, it FAILS, pointing at `deno task bench:install` — which is why it is not in `check` (CI installs no bench node_modules) and runs from publish.ts after artifact validation. The README fence + marker grammar it reads is unit-tested in `test:node` (scripts/typecheck_packages_test.ts).

It runs under Node on gro's host modules (`scripts/roots/typecheck_packages.ts`, its library `scripts/typecheck_packages.ts`). Its reach: the checkout read-only, found from the entry's location, for the staged packages and the install; a temp directory, the consumer project, removed when the run ends; and `BENCH_STALE_OK`. TypeScript is loaded with `createRequire` from the install's computed path, a named exception to the host-module rule: no host module loads a CommonJS module, and TypeScript reads the consumer project and the install through Node's own `fs`. `typecheck:scripts`' `tsc` never follows the computed path, so it resolves nothing from the bench install.

## `engines:audit`

ENGINE PARITY: the WASM engine and the native engine must format every file to the same bytes (`scripts/roots/engine_parity.ts`, its library `scripts/engine_parity.ts`, whose module doc has the legs and their blind spots). Each corpus root is copied into two temp trees, one formatted by the native `tsv` and one by the `all` package's `cli.js` under Node, and the two runs must agree on the exit code, stdout, stderr, a `--list` over spelled, overlapping roots, and every byte left on disk; `tsv strip` is compared per file over the strip fixtures, and `strip_typescript` and the import records in one Node child holding both engines. Roots name directories resolved against the checkout; none means `tests/fixtures`, `tests/fixtures_compile`, and `../corpora/collections` (absent, a warn-skip). `--json` prints the reports. Not in `check`: it needs both engines built (`build:npm:all`, `build:napi:packages`), and CI's `artifacts` job runs it after the steps that build them. A stale engine is refused (BENCH_STALE_OK=1 the same override); a missing one, no `node`, or nothing gradable fails. Every failure exits 1.

It runs under Node on gro's host modules. Its reach: the checkout read-only, found from the entry's location, and each root read-only; temp directories, for the trees and the child's consumer project; `node`, found on `PATH`, and the native binary by its path beneath the checkout (the staged platform package's, the host's first, else `target/release/tsv`), each with gro's base environment, since neither CLI reads a variable of its own; and `BENCH_STALE_OK`. The native binary resolves against the working directory, so the task runs from the checkout's root, as the npm scripts and `deno task` do. The host's platform and CPU, which pick the platform package, come from `node:process`, a named exception to the host-module rule: no host module reports them.

## `publish:crates`

Publishes the crates meant for crates.io (docsrs_crates.ts's set, cargo-ordered from `cargo metadata`) — a DRY RUN unless `--wetrun`, which is the user's to run (by token for the first publish). Each run reads every crate's versions from the crates.io API (a failed lookup is fatal), runs the public-API gate — `cargo semver-checks` per crate at its docs.rs feature set named explicitly, against its published baseline, a crate with none SKIPPED loudly rather than passed (`--bump <level>` grades an already-live version; `--no-semver-checks` skips the gate, as loudly) — then `cargo publish --workspace --locked` (`--dry-run` unless `--wetrun`, which excludes the crates already live, so a re-run resumes; crates.io's new-crate rate limit stops a first publish part-way, and `--wait` sleeps through it). A `--wetrun` refuses unless HEAD is the commit `v<version>` names and `git status` is empty: crates published from any other commit would carry post-release source under the released version, for good. Before packaging it removes the target directory's `package/` (`cargo metadata`'s `target_directory`) and this version's overlay unpacks under `$HOME/.cargo/registry/src/`, plus any overlay dir that leaves empty — at an unchanged version cargo reuses both, verifying an earlier run's sources. Needs the network: NOT in `check`. The release workflow's `crates` job runs the dry run on the tag, by dispatch and weekly. Flags and design: scripts/publish_crates.ts. Through `npm run`, flags follow a `--` (`npm run publish:crates -- --bump minor`); `deno task publish:crates --bump minor` forwards them as written.

It runs under Node on gro's host modules (`scripts/roots/publish_crates.ts`). Its reach: the checkout read-only; `cargo` with cargo's variables (`CARGO_PASS_ENV`, whose `CARGO_*` carries a `CARGO_REGISTRY_TOKEN` on a publish) and `git` with git's local ones, each found on `PATH`, a missing one failing only the call that needs it; the crates.io API and no other host; and writes beneath `target/package` and `$HOME/.cargo/registry/src` alone (`scripts/roots/package_state.ts`). So a `CARGO_TARGET_DIR`, `CARGO_BUILD_TARGET_DIR`, or `build.target-dir` that moves the target directory out of the checkout's `target/` fails every run at the cleanup, and a `CARGO_HOME` other than `$HOME/.cargo` fails one that finds an unpack to remove there, each loudly and naming what moved it, rather than going uncleared; whether a directory is inside its grant is read from the path cargo or the environment gives, lexically, and a symlink beneath a grant is followed. Cargo and git start from gro's base environment (`LC_ALL=C` among it) plus those variables, not the whole environment; the semver-checks and dry-run publish runs keep the terminal, stdin included, and a `--wetrun`'s publish shows cargo's stderr as it arrives while keeping a copy to read a rate limit from.

## `publish:crates:package`

The packaging half of `publish:crates`' dry run alone — every crate packaged and built from its own tarball against its siblings', the build no workspace command reaches (features unify there) — with the public-API gate skipped and so the crates.io API read too (both said so in its output: between releases there is no release to grade, and nothing else reads the API on a dry run) — so an API outage cannot redden it; it still needs the index cargo resolves through. What CI's `artifacts` job runs on every commit.

## `publish:napi`

Publishes the staged N-API packages (`scripts/roots/publish_napi.ts`, its library `scripts/publish_napi.ts`): the `@fuzdev/tsv` loader and every platform package its `optionalDependencies` pin, each platform checked for both binaries and the loader's version, the CLI binaries' executable bit re-armed and verified, then `npm publish` per package, platforms first and the loader last, a version already on the registry skipped (an `npm view` error that is no 404 fails rather than reading as unpublished). `--expect-tag v<version>` refuses a staged version that isn't the tag's; `--provenance` is the release workflow's; `--dry-run` checks nothing against the registry and runs `npm publish --dry-run` over every package, reading npm's refusal to publish over a live version as a pass. What the release workflow's `publish` job runs, after it stages the loader (`build:napi:packages`' `--loader-only`); a local run holds only the host's platform package, so it stops at the partial-set refusal by design. Through `npm run`, flags follow a `--` (`npm run publish:napi -- --dry-run`); `deno task publish:napi --dry-run` forwards them as written.

It runs under Node on Node's own `node:*` modules, a named exception to the host-module rule: the release workflow's `publish` job holds the npm token and `id-token: write`, and its `release` job (`release:notes`, `release:assets`) holds `contents: write` and `id-token: write`, so neither installs `node_modules`, whose code would run beside those credentials. So nothing it imports is a package, which `typecheck:scripts`' Deno walk and `scripts/no_package_closure_test.ts` enforce. The deps the three entries hand their libraries (a captured program run, the file operations, the platform, the pause, the print streams) are built in `scripts/release/node_host.ts`, which `scripts/release/node_host_test.ts` exercises over temp files and harmless programs, leaving each entry its checkout, one call, and the exit code; the libraries' suites drive them over fakes alone, the real publish paths included, and the closure test holds those suites to that. Its reach: reads the staged packages under `crates/tsv_napi/pkg/` in the checkout the entry sits in, never the working directory's, at the directories the loader's `optionalDependencies` names make (`build:napi:packages` writes them from its fixed platform list; nothing but the mode write checks a name against that directory); sets the CLI binaries' mode there and nowhere else (a platform name that would climb out of it is refused before the `chmod`), on every host but Windows; and runs `npm`, found on `PATH` and started with no shell, in the checkout, with stdin on `/dev/null` and its output captured. npm gets the whole environment: its auth (`NODE_AUTH_TOKEN`, and the `.npmrc` setup-node writes) and, under `--provenance`, the runner's OIDC request variables and the `GITHUB_*` and `RUNNER_*` variables it attests are a set no test here can pin, so there is no list. Windows isn't one of its hosts: `npm` there is `npm.cmd`, which a start with no shell doesn't find, so the first `npm` run reads as one that exited 127 and the publish fails. Every refusal exits 1; a bad flag throws.

## `release:notes`

The GitHub Release body for a tag (`scripts/roots/release_notes.ts`, its library `scripts/release_notes.ts`): CHANGELOG.md's stamped `## <version>` section, printed. What release.yml's `release` job feeds to `gh release create`; run locally to preview what a tag would say (`npm run release:notes -- v<version>`). Fails on a missing or empty section — at a release tag it exists by construction (publish.ts refuses to stamp an empty `## Unreleased`).

It runs under Node on Node's own `node:*` modules, the credentialed jobs' named exception (§`publish:napi`). Its reach: the checkout's `CHANGELOG.md`, found from the entry's location, never the working directory; it writes nothing and runs nothing. The job redirects its stdout into the Release body, so stdout carries the notes alone; the usage error and each refusal go to stderr and exit 1, and a flag throws.

## `release:assets`

The GitHub Release assets for a PUBLISHED version (`scripts/roots/release_assets.ts`, its library `scripts/release_assets.ts`) — every platform package's native `tsv` CLI binary + SHA512SUMS — pulled back from the npm registry (not the build artifacts), so the asset is byte-identical to what npm serves, re-run or not — plus the third-party NOTICE, copied from the checkout. `--out <dir>`, through `npm run` after a `--` (`npm run release:assets -- v<version> --out <dir>`). Run locally against any released version to re-derive a release's SHA512SUMS from npm. The registry reads retry for a bounded window (`REGISTRY_ATTEMPTS` and `REGISTRY_RETRY_MS` in the library — the workflow runs this seconds after the publish, and a just-published version can lag the registry's read path), so a typo'd version fails after that window, not before.

It runs under Node on Node's own `node:*` modules, the credentialed jobs' named exception (§`publish:napi`). Its reach: writes `--out`, read against the working directory, and one temp directory (`tsv_release_assets_*` under the system's), removed whether or not the run succeeds; reads the checkout's NOTICE, found from the entry's location; and runs `npm` (`view`, `pack`) and `tar` (`-xzf <tarball> -C <temp dir> package/<binary>`), each found on `PATH` and started with no shell, in the working directory, with the whole environment, stdin on `/dev/null`, and the output captured. Each `npm pack` carries `--min-release-age=0`: npm reads the checkout's `.npmrc`, whose `min-release-age` window the npm of some Node versions (CI's among them) applies to `npm pack` without honoring its `@fuzdev/*` exclusion, and the version packed here was published moments before, so without the flag it reads as no matching version until the window passes; a flag outranks every config file and the environment, so it holds whatever the `.npmrc` later says. `npm view` reads the whole packument, which no window filters, so it takes none. What the registry answers can't steer a write: a platform package whose triple isn't lowercase words joined by `-` is refused, so each asset lands directly in `--out`; the tarball `npm pack` reports must be a file name; and an extracted binary that is no regular file (a symlink) is refused before the copy. A failure midway leaves the assets written so far in `--out` and no `SHA512SUMS`, and exits 1, as does a usage error; a flag throws.

## `strip:fixtures:oracle`

The ORACLE side of the strip fixtures (tests/fixtures_strip): re-derives each fixture's expected output from ts-blank-space (benches/js/package.json) and cross-checks it against Node's module.stripTypeScriptTypes, failing on a stale file or an undeclared oracle disagreement; `strip:fixtures:update` writes the files instead. Runs under NODE (the second oracle is Node's own; the script refuses to run as Deno) and needs `deno task bench:install`, so it is NOT in `check` — CI installs no bench node_modules. tsv's side is `strip:fixtures:validate`, which `cargo test` also runs (tests/strip_fixtures_tests.rs).

## `imports:fixtures:validate`

The import-record fixtures (tests/fixtures_imports): per fixture, the tree's shape, ORACLE FRESHNESS (the canonical parser's tree — acorn-typescript, Svelte's parse — walked by tsv_debug's imports_fixtures oracle, regenerated in memory, must equal the committed expected.json; a fixture marked oracle.txt walks tsv's own parse wire instead) and tsv's records. Needs the sidecar, so it is NOT in `check`; `cargo test` grades tsv against the committed files alone (tests/imports_fixtures_tests.rs). `imports:fixtures:update` writes the files.

## `compile:corpus:compare`

Roots: the WHOLE ../corpora snapshot (every collection it vendors — the author's repos, the framework source, the third-party Svelte libraries — one root, so a new collection is in scope the day it lands), then Svelte's own runtime/snapshot/SSR/css suites, then any per-machine roots in the gitignored `compile_corpus_compare.roots.local` (one path per line, `#` comments; live checkouts the snapshot cannot carry). A missing roots file adds none; a missing positional root fails the run.

## `test:node`

The JS suites beside their modules under `scripts/` and `benches/js/lib/`, under Node: `tsc -p tsconfig.vitest.json` typechecks them, then vitest runs them. The suites are the `_test.ts` files `tsconfig.vitest.json` names, which `vitest.config.ts` reads as its include list, so a suite vitest runs is always one `tsc` checks, and a named file that's missing fails the run. Named rather than a directory, because `benches/js/lib/` also holds `canonical_test.ts`, which needs the bench install (`test:node:canonical`), and the suites still on `deno test` (`test:deno`): the ones whose module under test calls `Deno.*` in the paths they test. A suite moves here once its module runs under Node, and is added by name. The script starts `tsc` and vitest with `node` because `deno task`, and `npm run` inside a `deno task`, runs a package's bin under Deno; `vitest.config.ts` refuses to run under Deno, which is also what a machine with no Node gets, since `deno task` then resolves `node` to its node-compat shim. Some modules the suites import still call `Deno.*` in functions the suites don't reach; `deno_global.d.ts` declares `Deno` as `any` for this program, and `typecheck:scripts` grades those calls against Deno's types (its walk of `scripts/` reaches the bench modules among them). The suites import the repo's own modules by relative path (the npm facade from `crates/tsv_wasm/npm/`), never the `@fuzdev/tsv` that `@fuzdev/gro` brings into the root `node_modules`, and none spawns `tsv`. The suites mutate no environment variable and no process state, so vitest's default pool serves; the ones that do (`perf_ab_test.ts` clears git's variables) are among those on `deno test`.

## `test:node:canonical`

`benches/js/lib/canonical_test.ts` under Node, typechecked by `tsc -p tsconfig.canonical.json` and run by `vitest.canonical.config.ts`: the canonical prettier baseline's `filepath` hint and its `.js` → babel / `.ts` → typescript parser routing. It loads prettier, `prettier-plugin-svelte`, Svelte and acorn, which resolve from `benches/js/node_modules` (the nearest `node_modules` above `benches/js/lib/`), so it needs `npm run bench:install` and is not in `check`.

## `test:depth`

The parsers' depth-limit gate (`tests/depth_limit.rs`) in an OPTIMIZED build, where its stack legs grade the shipped 2 MiB contract, over `check`'s scope of the shapes: every named shape and grammar position, the generated sweep's pairs behind the heads `a` and `a()`, a few hundred seeded triples, the commented links, a sample of the prefix alphabet — every pair of prefix operators, each operator with a comment in its gap, and each over a few links and as a few operators' operand — and a sample of the decorators (`TSV_DEPTH_SWEEP=full`, which `test:depth:napi` sets, takes every head, the full triple sample, the whole prefix alphabet with its authored-pair forms, and every decorator callee and payload). Each shape, generated at its limit, must hold no wire path past either limit (the count charges at least what the walks recurse through), runs parse + both wire writers + format + the type strip on a 2 MiB thread (an overflow aborts the binary, which fails the task), its format's output must parse again and be its own format (F1 — the printer's added pairs are charged as nesting at parse time), one level deeper is refused by the depth error, and each calibrated shape's wire depth is checked to sit at the limit. The plain `cargo test` run (`deno task test`) builds the same file in debug, where it grades the debug contract's 16 MiB thread over the named shapes and a stride of the sweep. `--features tsv_debug/_internal_audits` puts the build in the `corpus` world `build:check` builds, so it compiles nothing twice; that world carries the audit seams, which no shipped artifact does, so the shipped profile's run is its own task, `test:depth:napi` (docs/cli.md §Recursion Depth).

## `test:depth:napi`

The same depth-limit gate built in the shipped binaries' optimization: `--profile napi`, the profile of the published N-API addon — `release`'s fat LTO and single codegen unit with an unwinding panic, which a test binary takes in any profile (the harness cannot abort), so a `release` test build would be this world under another name — but WITHOUT the profile guidance the published pair is built with, which moves inlining and so frames. No test build can carry it: the profile is matched to functions by symbol names that carry each crate's build hash, and the test graph compiles the language crates with other features, so a `-Cprofile-use` test build would find no profile for them. The profile-guided addon itself is graded by `build:pgo` and by the release workflow on every row, through the staged binary (scripts/pgo/addon_depth.ts; on Windows each pass under a scratch node.exe copy whose PE stack reserve sits just above its request, so a worker's requested stack sizes its thread) — except a `win32-x64` row where that still cannot grade (a copy does not start, the gate's thread would exceed the contract, or the control survives on a thread node.exe's reserve rather than its request sized), which falls back to this run, logged and warned; this run grades what that one cannot: the Rust wire writers' `loc` path and the spine shapes on their small threads. It grades the FULL sweep (`TSV_DEPTH_SWEEP=full`: every pair behind every head, the full triple sample, the whole prefix alphabet), where `test:depth` grades `check`'s smaller scope. `test:depth`'s `corpus` world (no LTO, sixteen codegen units, the audit seams) lays frames out differently enough that one shape can need more than twice the stack in one world as in the other, so passing one proves nothing about the other. Not in `check`, which pays for no fat-LTO build: publish.ts runs it right after `check` (Step 3, skipped by --no-check), and CI's `artifacts` job runs it on every push and PR beside the N-API build it shares the profile with (docs/cli.md §The stack contract).

## `test:depth:wasm`

The depth-limit gate in the WASM engine (scripts/depth_wasm.ts): every shape `tests/depth_limit.rs` generates, at its accepted depth, through the staged `@fuzdev/tsv-wasm` package on a Node MAIN thread — the parse (object, `{locations: true}` and `_json`), the format, the format's output parsed again and formatted to itself (F1), the import records and the type strip must each return a result, never trap or throw a `RangeError`, and one level deeper must be the depth refusal. Every shape runs cold (`--liftoff-only`) and warm (tiered up after a warm-up pass, `--wasm-sync-tier-up`), sharded over a few processes. The shapes and their depths come from the native test's `write_shape_limits`, built under the `napi` profile `test:depth:napi` already built. Needs `deno task build:npm:all` (refuses a stale staging) and Node; not in `check`, which builds no package: CI's `artifacts` job runs it after the engine-parity audit, and publish.ts in Step 6's artifact validation (docs/cli.md §The stack contract).

## `paren:audit`

`--require-relational` is the audit's SEED-SET vacuity floor, and this is the invocation entitled to it: the relational `<`…`>` class lives in tests/fixtures (typescript/expressions/binary/relational_*) and essentially nowhere else, so a run over the fixture tree that enumerates ZERO relational sites means the class stopped enumerating. The real-code leg of `audit:corpus` (benches/js/corpus_audit.ts, publish Step 3c) deliberately does NOT pass it — nobody writes `a < b > c` in real code, both relational rows are legitimately 0 over the ../corpora snapshot, and a floor there fails a clean run. A flag rather than a paths-contains-tests/fixtures sniff, because a sniff answers wrongly on a subtree run; a NARROWED run under the flag fails its floor by design, like a ratchet refusing a narrowed `:update`, and drops the flag instead. The TOTAL floor (any site at all) stays unconditional in the audit.

## `fuzz:audit:debug`

The fuzzer's three legs (`fuzz:audit` = the fixtures as found, then `--embedded css`, then `--embedded ts`) with the same arguments, built under `--profile corpus-debug`: the `corpus` world plus `debug-assertions` and `overflow-checks`, the checks a consumer's dev build compiles in and every `--profile corpus` audit compiles out. A fired `debug_assert!` is a caught `panic` finding (the profile unwinds), reported with its input and location like any other. Same arguments as the release legs, so a finding here and not there is an assert or an overflow. Its own profile, so it builds a second world rather than invalidating the one every `check` audit shares (docs/audits.md §Seeded Mutational Fuzzer).

## `bench:runtimes`

Preflight for the aggregates: the three-runtime tasks NEED node and bun, and without this they discover a missing one only after the legs ahead of it have run — after regenerating two of the three siblings and skipping `bench:compose`, which leaves the committed combined report stale against fresh siblings and reading as a two-runtime run. Deno is the only hard dependency of the repo; a machine without node or bun runs the per-runtime tasks instead, which is what the message says. Each check is PARENTHESIZED: `a || b && c || d` binds left-associatively, so the flat form runs the second `||` arm after the first one failed and reports BOTH runtimes missing when only one is. ⚠ The node arm asks what the binary IS, never whether the NAME resolves: `deno task` prepends its node-compat shim directory (`~/.cache/deno/node_compat_bin`, holding a `node` symlink to the deno binary) to PATH, so `which node` succeeds inside every deno task on a machine with no node at all. That shim also RUNS the harness — `current_runtime()` then reports `deno`, and `bench:node` overwrites `report.deno.*` instead of producing a node sibling, which is the exact silent two-runtime run this preflight exists to stop. `globalThis.Deno` is the tell the shim cannot hide. The same probe asserts the VERSION the message names, so the ≥22.18 requirement is checked rather than merely stated — below it `node benches/js/bench.ts` fails on the first type annotation it reads, naming the syntax instead of the runtime.
